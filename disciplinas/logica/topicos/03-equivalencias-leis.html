Tópico 3 · Equivalências e leis de De Morgan

Duas fórmulas são logicamente equivalentes quando têm o mesmo valor em todas as linhas da tabela-verdade. Equivalências são a ferramenta para simplificar condições: reescrever uma fórmula longa em outra mais curta, sem mudar o que ela significa.

As leis que mais aparecem

  • De Morgan: ¬(p ∧ q) ≡ ¬p ∨ ¬q, e ¬(p ∨ q) ≡ ¬p ∧ ¬q. Negar uma conjunção vira disjunção das negações, e vice-versa.
  • Dupla negação: ¬¬p ≡ p.
  • Implicação: p → q ≡ ¬p ∨ q.
  • Contraposição: p → q ≡ ¬q → ¬p. É a forma usada em provas por contrapositiva.
  • Negação da implicação: ¬(p → q) ≡ p ∧ ¬q. A única forma de quebrar “se p, então q” é ter p verdadeiro e q falso.
  • Distributividade: p ∧ (q ∨ r) ≡ (p ∧ q) ∨ (p ∧ r).

O erro clássico é negar só uma parte: ¬(p ∧ q) não é ¬p ∧ ¬q. Quando a negação de uma conjunção aparece em um if, a forma correta é a De Morgan.

Exemplo: simplificando uma condição

Uma regra de acesso diz: “negar a entrada se NÃO (é_admin OU tem_token)”. Aplicando De Morgan:

¬(admin ∨ token)  ≡  ¬admin ∧ ¬token

# Antes
if not (is_admin or has_token):
    negar()

# Depois, com a mesma semântica e mais legível
if not is_admin and not has_token:
    negar()

O mesmo raciocínio vale para a implicação. Em vez de if not (a and b): x, o equivalente é if not a or not b: x.

Jogo: Memória das Equivalências

Vire duas cartas. Se as fórmulas forem equivalentes, o par fica marcado (+20 pontos). Menos tentativas é melhor.

No mercado de trabalho

Otimizadores de compiladores e de consultas SQL aplicam equivalências para reescrever expressões. O planejador de um banco relacional, por exemplo, reordena predicados (sem mudar o resultado) para usar índices. Em revisão de código, simplificar uma condição com De Morgan reduz bugs de negação, um dos erros mais frequentes em regras de autorização.

Referência: a documentação do PostgreSQL sobre o planejador de consultas (seção “Planner/Optimizer”) descreve essas reescritas de expressão booleanas.
