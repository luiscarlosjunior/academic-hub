Tópico 14 · Performance de frontend

Um design system pode ser perfeito em acessibilidade e ainda assim lento, se cada página carrega um pacote de centenas de kilobytes que o usuário não usa. Performance não é um detalhe de acabamento: ela afeta conversão, retenção e o uso real do sistema. Este tópico ensina a medir o que o usuário sente, a identificar o que atrasa a tela e a manter o pacote dentro de um orçamento combinado com o time.

Objetivos desta página. Ao final, você deve conseguir:

  • explicar LCP, INP e CLS e os limites que o Google classifica como bons;
  • dividir o código por rota e carregar componentes pesados sob demanda;
  • definir um orçamento de tamanho de pacote e fazê-lo falhar o pipeline quando estourar;
  • medir a performance real com dados de usuários, e não só com testes de laboratório.

Teoria: os três indicadores que o usuário sente

Os Core Web Vitals são três métricas que o Google usa para medir a experiência de carregamento e de interação. Cada uma captura um problema diferente, e as três devem ser acompanhadas juntas, porque melhorar uma pode piorar outra.

  • LCP (Largest Contentful Paint): o tempo até o maior elemento visível da tela ser pintado. É a percepção de “a página carregou”. Bom até 2,5 segundos.
  • INP (Interaction to Next Paint): o tempo entre uma interação, como um clique, e a próxima pintura da tela. Mede a responsividade durante o uso. Bom até 200 milissegundos. Substituiu o FID em 2024.
  • CLS (Cumulative Layout Shift): a soma dos deslocamentos inesperados de elementos. É o que faz um botão mudar de lugar enquanto o usuário vai clicar. Bom até 0,1.

A medição tem duas formas. O laboratório roda a página em condições controladas, como o Lighthouse, e serve para comparar mudanças e encontrar causas. O campo mede usuários reais, em aparelhos e redes variadas, e mostra o que as pessoas de fato vivem. Uma página pode passar no laboratório e falhar no campo, por exemplo porque o usuário tem um celular intermediário e uma conexão instável. O campo é a medida que importa para o usuário.

MétricaBomPrecisa melhorarCausa mais comum no design system
LCPaté 2,5 sacima de 4 sPacote único grande, fonte que bloqueia a renderização, imagem sem dimensões
INPaté 200 msacima de 500 msTarefas longas no JavaScript, como renderizar uma tabela inteira de uma vez
CLSaté 0,1acima de 0,25Fonte que troca após o carregamento, imagem ou banner sem reserva de espaço

Operação 1 · Dividir o código por rota

Sem divisão, o navegador baixa o código de todas as telas antes de mostrar a primeira. Com divisão, cada rota carrega o seu código, e os componentes pesados entram só quando são exibidos. A animação compara os dois cenários. Observe que o LCP só é afetado pelo que a primeira tela precisa, não pelo tamanho total da aplicação.

Animação: pacote único e pacote dividido

O cenário lento leva o LCP acima do limite; o dividido mantém a primeira tela leve.

Em TypeScript (React) · carregamento preguiçoso de uma tabela pesada

import { lazy, Suspense } from 'react';

// a tabela só entra no pacote da página quando ela é renderizada
const TabelaComponentes = lazy(() => import('./TabelaComponentes'));

export function PaginaComponentes() {
  return (
    <main>
      <h1>Componentes</h1>
      <Suspense fallback={<p>Carregando tabela…</p>}>
        <TabelaComponentes />
      </Suspense>
    </main>
  );
}

Por que funciona: o bundler separa TabelaComponentes num arquivo próprio, que é baixado somente quando o componente é necessário. O Suspense mostra um texto enquanto isso acontece, o que evita tela em branco. Repare no fallback: ele deve ter a mesma altura do conteúdo final para não gerar CLS.

Operação 2 · Orçamento de tamanho no pipeline

Tamanho de pacote cresce sem alarde. Cada dependência nova parece pequena, e a soma vira um problema meses depois. Um orçamento explícito, verificado no pipeline, transforma essa conversa em número: se o pacote passa do limite, o build falha, e o time decide se vale o custo. A ferramenta size-limit faz essa medição, com o tamanho comprimido, que é o que o navegador de fato baixa.

Em JSON · package.json com orçamento por arquivo de entrada

{
  "scripts": {
    "tamanho": "size-limit"
  },
  "size-limit": [
    {
      "name": "Entrada principal",
      "path": "dist/index.js",
      "limit": "80 kB",
      "gzip": true
    },
    {
      "name": "Página de componentes",
      "path": "dist/componentes.js",
      "limit": "40 kB",
      "gzip": true
    }
  ]
}

Em YAML · etapa no pipeline

- run: npm run build
- run: npm run tamanho   # falha se algum arquivo passar do limite

Por que funciona: o limite é uma decisão registrada no repositório, e não uma impressão. Quando um pull request estoura o orçamento, a discussão acontece sobre um número concreto: “esta dependência adiciona 35 kB; vale?”. Use o tamanho comprimido com gzip, porque é ele que trafega na rede. Revise o orçamento a cada trimestre, para que ele acompanhe as necessidades reais.

Operação 3 · Imagens e fontes sem atrasar a tela

Imagens e fontes são as causas mais frequentes de LCP alto e de CLS. A imagem que é a maior da tela precisa ser carregada logo; as demais podem esperar. Dimensões explícitas reservam o espaço antes do download, e isso zera o deslocamento. A fonte precisa de uma estratégia de exibição: o texto aparece com a fonte de reserva e troca depois, o que pode causar deslocamento se as métricas forem diferentes.

Em HTML · imagem da primeira dobra e imagens abaixo dela

<!-- imagem principal: carregada cedo, com dimensões reservadas -->
<img src="/img/hero.webp" width="1200" height="630"
     fetchpriority="high" alt="Painel de tokens do design system">

<!-- imagens abaixo da dobra: esperam o usuário se aproximar -->
<img src="/img/exemplo-tabela.webp" width="640" height="360"
     loading="lazy" decoding="async" alt="Tabela de componentes por produto">

<!-- fonte: texto visível logo, com troca suave -->
<style>
  @font-face {
    font-family: "Inter";
    src: url("/fonts/inter.woff2") format("woff2");
    font-display: swap;
  }
</style>

Por que funciona: fetchpriority="high" avisa o navegador que a imagem principal é prioridade, enquanto loading="lazy" adia as outras. Os atributos width e height permitem ao navegador calcular o espaço antes do download, o que evita o deslocamento. Não use lazy na imagem principal: isso atrasa justamente o elemento que define o LCP.

Operação 4 · Medir o campo com a biblioteca web-vitals

A biblioteca web-vitals mede as três métricas no navegador do usuário e envia os valores para um endpoint. O envio usa navigator.sendBeacon, que não atrasa a navegação e funciona mesmo quando a página está sendo fechada. Com esses dados, é possível ver a distribuição por página, por país e por tipo de aparelho.

Em TypeScript · medir.ts

import { onCLS, onINP, onLCP } from 'web-vitals';

function enviar(metrica) {
  const corpo = JSON.stringify({
    nome: metrica.name,
    valor: metrica.value,
    rota: location.pathname,
    id: metrica.id,
  });
  navigator.sendBeacon('/api/metricas', corpo);
}

onLCP(enviar);
onINP(enviar);
onCLS(enviar);

Por que funciona: o campo id identifica a medição de forma única, o que permite somar as duas partes quando uma métrica é reportada mais de uma vez, como o INP, que pode mudar ao longo da visita. Não envie dados pessoais nesse payload: o caminho da rota é suficiente para a análise, e isso está de acordo com a LGPD, como visto no tópico 8.

Mais exemplos comentados

Os dois exemplos cobrem o diagnóstico de um LCP alto e a escolha entre cache longo e cache curto, que é o que mais confunde quem começa.

Exemplo 1 · Diagnosticando um LCP alto

Quando o LCP de uma página passa de 4 segundos, a causa costuma ser uma de quatro. O processo de diagnóstico começa pelo próprio elemento: descobrir qual é o maior elemento visível, e em seguida ver o que o atrasa até ser pintado. A tabela organiza as causas e os sinais que as confirmam.

Sinal no relatórioCausa provávelCorreção
O elemento LCP é uma imagem grande, carregada tardeImagem sem fetchpriority, ou com lazy na dobraPriorizar a imagem principal e reservar dimensões
O elemento LCP é texto, e a renderização espera uma fonteFonte com bloqueio de exibiçãoUsar font-display: swap e pré-carregar a fonte principal
Tempo de rede alto antes do primeiro byteOrigem distante ou cache ausenteVerificar a CDN e a política de cache (tópico 4)
Muito JavaScript antes do renderPacote único ou bloqueio por script síncronoDividir por rota e carregar scripts com defer

Por que funciona: a tabela parte do sinal observado, e não de um palpite. Esse método evita o erro mais comum, que é otimizar o JavaScript quando o problema é uma imagem sem dimensões. Sempre confirme a causa antes de mudar o código, e meça de novo depois da correção.

Exemplo 2 · Cache longo ou curto?

A regra do tópico 4 separa dois tipos de arquivo. Arquivos com hash no nome podem ter cache de um ano, porque o nome muda quando o conteúdo muda. O HTML e os arquivos sem hash precisam de revalidação. Um caso que vale estudar é a imagem sem hash, como um logotipo que muda de cor. Ela não deve ter cache longo, porque o usuário veria a versão antiga por meses.

Tipo de arquivoCache-ControlMotivo
JavaScript e CSS com hashpublic, max-age=31536000, immutableO nome muda com o conteúdo
Imagem com hash no nomepublic, max-age=31536000, immutableMesma lógica do código
Logotipo sem hash, que pode mudarpublic, max-age=3600Mudança visível precisa chegar em horas, não meses
HTML principalno-cacheAponta para os arquivos novos a cada deploy

Por que funciona: o cache longo é seguro somente quando o nome do arquivo garante a identidade do conteúdo. Sem essa garantia, o cache longo vira um problema de atualização. Antes de aumentar o tempo de cache de um arquivo, pergunte o que acontece se ele mudar sem o nome mudar.

Práticas do mercado

  • Orçamento de performance como critério de revisão: pull requests que estouram o orçamento são bloqueados até haver decisão registrada.
  • Lighthouse CI: roda a medição de laboratório em cada pull request e compara com a versão anterior.
  • Medição contínua: os Core Web Vitals do campo entram no painel de produto junto com as métricas de negócio.
  • Componentes sem efeitos colaterais de layout: o design system reserva espaço para estados de carregamento, o que protege todos os produtos contra CLS.

Exercícios resolvidos

1. O INP de uma tabela é de 650 ms ao filtrar. O que provavelmente acontece?

Ver resposta

Resposta: o clique dispara uma tarefa longa de JavaScript, provavelmente a renderização de todas as linhas de uma vez. O navegador não pinta até a tarefa terminar. A correção é reduzir o trabalho por interação: filtrar sobre dados já carregados, paginar, ou dividir a renderização em partes menores.

2. Ao carregar a página, o título desce meio centímetro após a fonte carregar. Qual métrica piora e como corrigir?

Ver resposta

Resposta: o CLS piora, porque o deslocamento é inesperado. A correção é usar uma fonte de reserva com métricas parecidas (com ajuste de tamanho e espaçamento), pré-carregar a fonte principal e manter font-display: swap com a reserva equivalente. O deslocamento some quando as duas fontes têm a mesma altura de linha.

Exercícios propostos

  1. Meça o LCP da página de documentação com o Lighthouse antes e depois de dividir o pacote por rota. Registre os dois valores.
  2. Defina um orçamento de 60 kB para a entrada principal e veja se a versão atual passa. Se não passar, identifique a dependência que mais pesa.
  3. Escreva o endpoint que recebe as métricas do medir.ts e grava apenas nome, valor e rota, com um limite de tamanho do corpo.

Ponte para a certificação AWS

Performance de frontend não é tema das provas AWS. O ponto de contato está na entrega: a latência percebida depende da CDN e do cache, que são cobrados no SAA-C03 como parte do domínio de alto desempenho. O CloudWatch RUM, serviço da AWS para medição de usuários reais, aparece como referência para essa medição. O conteúdo técnico deste tópico vale por si, independentemente de exames.

Teste seus conhecimentos

Qual é o limite de “bom” para o LCP segundo os Core Web Vitals?

Correto. Até 2,5 s é bom; acima de 4 s precisa de melhoria.

Por que a imagem principal da tela não deve usar loading="lazy"?

Correto. O carregamento preguiçoso adia o download; na imagem principal, isso atrasa o próprio LCP.

Qual é a diferença entre medição de laboratório e de campo?

Correto. O campo reflete a experiência real, com aparelhos e redes variadas; o laboratório ajuda a comparar e a diagnosticar.

O que levar desta página

  • LCP até 2,5 s, INP até 200 ms e CLS até 0,1 são os limites de bom desempenho.
  • Divida o código por rota e carregue sob demanda o que não aparece na primeira tela.
  • Orçamento de tamanho no pipeline transforma a discussão de peso em número.
  • Priorize a imagem principal; reserve dimensões; nunca use lazy na dobra.
  • Meça o campo com web-vitals; o laboratório serve para diagnosticar, não para julgar.
