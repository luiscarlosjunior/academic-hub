Tópico 18 · Padrões corporativos e problemas resolvidos com AWS

Um padrão é a descrição de uma solução recorrente para um problema recorrente, expressa de forma que possa ser reutilizada em contextos diferentes. A noção foi formulada originalmente no campo da arquitetura urbana por Christopher Alexander (1977) e adotada pela engenharia de software. Em sistemas corporativos, alguns problemas reaparecem em praticamente todos os projetos: integrar sistemas que não se conhecem, migrar uma aplicação antiga sem interromper o serviço, manter a consistência de uma operação que atravessa vários sistemas e impedir que a falha de um componente se propague para os demais. Este tópico apresenta um conjunto desses padrões e mostra como os serviços da AWS os implementam.

Objetivos de aprendizagem. Ao final desta página, o estudante deverá ser capaz de:

  • definir padrão e distinguir o problema, a solução e o contexto de aplicação;
  • identificar, em um cenário, o problema corporativo que um padrão resolve;
  • mapear os padrões aos serviços correspondentes da AWS e justificar a escolha;
  • reconhecer as limitações e as armadilhas de cada padrão;
  • analisar casos documentados e extrair lições de projeto.

Compreensão inicial · problema, padrão e solução

Uma analogia útil é a de uma receita. Uma receita não é um ingrediente, nem um prato pronto: é um procedimento testado para obter um resultado a partir de condições conhecidas. Do mesmo modo, um padrão descreve quando ele se aplica, qual problema resolve, como a solução funciona e quais consequências ela traz. Essa estrutura de quatro partes é a que se encontra nos catálogos clássicos e é a que este tópico segue.

Teoria · origem e catálogo de padrões

O campo de padrões de software se consolidou com o livro de Gamma, Helm, Johnson e Vlissides (1994), que catalogou padrões de projeto orientado a objetos. Para a integração de sistemas corporativos, Hohpe e Woolf (2003) organizaram um vocabulário de padrões de mensagens, canais e roteamento que sustenta a maior parte das arquiteturas orientadas a eventos atuais. Para a nuvem, os padrões passaram a ser documentados também pelos fornecedores, que os associam aos seus serviços.

Alguns padrões deste tópico têm origem em trabalhos específicos. A saga foi proposta por Garcia-Molina e Salem (1987), como alternativa às transações longas em bancos de dados. O estrangulador (strangler fig) foi descrito por Fowler (2004) a partir da analogia com a figueira que envolve gradualmente a árvore hospedeira. O disjuntor (circuit breaker) foi difundido por Nygard (2007), no livro Release It!, a partir de práticas de resiliência em sistemas de produção.

Operação 1 · Migração incremental pelo estrangulador

Reescrever um sistema legado de uma só vez é arriscado: o custo é alto, o prazo é incerto e o resultado só aparece no fim. O padrão estrangulador propõe o contrário. Um roteador é colocado na frente do sistema antigo, e as funcionalidades são migradas uma a uma. Como o roteador decide, para cada requisição, qual sistema a atende, a migração pode ser feita por fatias, com retorno imediato ao legado se algo der errado. A animação mostra a transferência gradual do tráfego.

Animação: do legado ao novo serviço

Os quadros mostram o tráfego deslocando-se gradualmente. Observe que o roteador não muda de posição em nenhum momento.

Em TypeScript (CDK) · roteamento por caminho com CloudFront

import * as cloudfront from 'aws-cdk-lib/aws-cloudfront';
import * as origins from 'aws-cdk-lib/aws-cloudfront-origins';

const distribuicao = new cloudfront.Distribution(this, 'Portal', {
  defaultBehavior: {
    origin: new origins.HttpOrigin('legado.interno.exemplo.com.br'),
  },
  additionalBehaviors: {
    // o caminho migrado é atendido pelo novo serviço; o restante continua no legado
    '/catalogo/*': {
      origin: new origins.HttpOrigin('catalogo.interno.exemplo.com.br'),
    },
  },
});

Interpretação. A regra de comportamento por caminho é a forma mais simples de estrangulamento. Cada nova rota migrada exige apenas uma entrada adicional, e a reversão consiste em removê-la. A armadilha principal é a duplicidade de dados: enquanto as duas versões coexistem, é preciso decidir qual é a fonte da verdade para cada entidade, e registrar essa decisão.

Operação 2 · Publicação e assinatura com filas

Quando um evento de negócio, como a criação de um pedido, interessa a vários sistemas, o produtor não deve conhecer cada um deles. O padrão de publicação e assinatura resolve esse problema: o produtor publica em um tópico, e cada assinante recebe uma cópia. A ligação de cada assinante a uma fila permite que ele processe no próprio ritmo. A combinação de tópico e filas é conhecida como fan-out.

Animação: fan-out e falha de um consumidor

No cenário com falha, a mensagem que não pode ser processada é desviada para a fila de mensagens mortas.

Em TypeScript (CDK) · tópico, filas e fila de mensagens mortas

import * as cdk from 'aws-cdk-lib';
import * as sns from 'aws-cdk-lib/aws-sns';
import * as subs from 'aws-cdk-lib/aws-sns-subscriptions';
import * as sqs from 'aws-cdk-lib/aws-sqs';

const dlq = new sqs.Queue(this, 'DlqEmail', {
  retentionPeriod: cdk.Duration.days(14),
});

const filaEmail = new sqs.Queue(this, 'FilaEmail', {
  visibilityTimeout: cdk.Duration.seconds(60),
  deadLetterQueue: { queue: dlq, maxReceiveCount: 3 },
});

const pedidosCriados = new sns.Topic(this, 'PedidosCriados');
pedidosCriados.addSubscription(new subs.SqsSubscription(filaEmail));

Interpretação. O parâmetro maxReceiveCount define quantas vezes uma mensagem pode ser recebida sem ser confirmada antes de ir para a fila de mensagens mortas. O visibilityTimeout deve ser maior que o tempo de processamento usual; caso contrário, a mesma mensagem é entregue a dois consumidores ao mesmo tempo. Ambos os parâmetros têm efeito direto sobre a confiabilidade e devem ser justificados.

Operação 3 · Saga com compensação

Um pedido envolve reservar estoque, cobrar o cliente, emitir a nota fiscal e enviar a confirmação. Em sistemas distribuídos, não existe uma transação que abranja todos esses passos com garantia de atomicidade a custo razoável. A saga resolve o problema com uma sequência de transações locais. Se um passo falha, executam-se compensações: ações que desfazem os passos anteriores, em ordem inversa. Compensar não é o mesmo que reverter: a cobrança recusada nunca chegou a ser efetivada, mas a reserva de estoque precisa ser liberada explicitamente.

Animação: pedido concluído e cobrança recusada

No cenário de falha, a compensação libera o estoque reservado, e o sistema retorna a um estado consistente.

Interpretação. A retentativa com espera crescente (BackoffRate) evita sobrecarregar um serviço que se recupera. Essa retentativa só é segura se a cobrança for idempotente, isto é, se repetir o pedido não cobrar duas vezes; por isso, a chamada de cobrança deve carregar uma chave de idempotência. Sem ela, a própria política de retentativa causa o dano que deveria evitar.

Operação 4 · Disjuntor e isolamento de falhas

Um serviço lento é, muitas vezes, mais perigoso do que um serviço fora do ar. As chamadas se acumulam, consomem conexões e threads, e a falha se propaga aos chamadores. O disjuntor observa as chamadas a uma dependência e, ao detectar falhas repetidas, deixa de encaminhá-las por um intervalo, respondendo com um fallback. Ele opera em três estados: fechado (chamadas passam), aberto (chamadas são bloqueadas) e meio-aberto (algumas chamadas de teste são permitidas).

Animação: estados do disjuntor

Escolha o cenário. No serviço instável, o disjuntor abre e o fallback responde enquanto a dependência se recupera.

Em TypeScript · implementação didática do disjuntor

type Estado = 'fechado' | 'aberto' | 'meio-aberto';

export class DisjuntorSimples {
  private estado: Estado = 'fechado';
  private falhas = 0;
  private abertoDesde = 0;

  constructor(private limite = 3, private esperaMs = 30_000) {}

  async executar<T>(chamada: () => Promise<T>, fallback: () => T): Promise<T> {
    if (this.estado === 'aberto') {
      if (Date.now() - this.abertoDesde < this.esperaMs) return fallback();
      this.estado = 'meio-aberto';
    }
    try {
      const resultado = await chamada();
      this.falhas = 0;
      this.estado = 'fechado';
      return resultado;
    } catch {
      this.falhas += 1;
      if (this.estado === 'meio-aberto' || this.falhas >= this.limite) {
        this.estado = 'aberto';
        this.abertoDesde = Date.now();
      }
      return fallback();
    }
  }
}

Interpretação. A implementação é deliberadamente simples e não deve ser usada em produção sem testes de concorrência e de tempo. Em ambientes reais, recorre-se a bibliotecas maduras ou a configurações de retentativa e de tempo limite do próprio cliente de serviço. O conceito, porém, é o mesmo: a falha de uma dependência não pode consumir os recursos do chamador.

Mais exemplos comentados

Os exemplos a seguir tratam de dois problemas recorrentes: a leitura repetida de dados caros e a escolha entre serviços de mensageria.

Exemplo 1 · Cache-aside com ElastiCache

No padrão cache-aside, a aplicação consulta primeiro o cache. Se o dado não estiver lá (cache miss), ela o busca no banco, guarda-o no cache com um tempo de vida e o devolve. A escrita invalida a entrada correspondente. O código abaixo ilustra o ciclo completo com o Redis do ElastiCache.

Em TypeScript · componente-cache.ts

import Redis from 'ioredis';

const redis = new Redis({ host: process.env.CACHE_HOST, port: 6379, tls: {} });

export interface Componente { id: string; nome: string; versao: string; }

export async function obterComponente(
  id: string,
  buscarNoBanco: (id: string) => Promise<Componente>,
): Promise<Componente> {
  const chave = 'componente:' + id;

  const emCache = await redis.get(chave);
  if (emCache) return JSON.parse(emCache) as Componente;

  const dado = await buscarNoBanco(id);
  await redis.set(chave, JSON.stringify(dado), 'EX', 300);
  return dado;
}

export async function atualizarComponente(c: Componente, gravar: (c: Componente) => Promise<void>) {
  await gravar(c);
  await redis.del('componente:' + c.id);   // invalida a entrada antiga
}

Interpretação. O tempo de vida de 300 segundos limita o período em que um dado obsoleto pode ser servido, caso a invalidação falhe. A conexão com tls protege os dados em trânsito, o que é exigido em muitas políticas corporativas. O custo do padrão é a possibilidade de leitura de dado desatualizado por algum tempo; em dados financeiros, essa tolerância pode ser nula, e o padrão deve ser reavaliado.

Exemplo 2 · Escolhendo entre SQS, SNS e EventBridge

Os três serviços transportam mensagens, mas resolvem problemas diferentes. A escolha depende do número de destinatários, do tipo de roteamento necessário e da garantia de entrega. A tabela organiza o raciocínio.

NecessidadeServiço mais adequadoMotivo
Um produtor, um consumidor, processamento desacopladoSQSFila que armazena mensagens até o consumo; o consumidor controla o ritmo
Um evento que interessa a vários consumidores independentesSNS com filas SQSCada assinante recebe uma cópia; a fila de cada um isola sua falha
Eventos classificados por conteúdo e roteados por regrasEventBridgePadrões de evento, agendamentos e integração com fontes e destinos diversos
Processamento ordenado de mensagens por grupoSQS FIFOPreserva a ordem dentro de um grupo de mensagens, com menor vazão

Interpretação. A escolha não é excludente: um tópico SNS pode alimentar filas SQS, e um barramento de eventos pode encaminhar eventos para filas. O erro mais frequente é usar uma fila onde um barramento de eventos seria mais adequado, o que obriga a reimplementar o roteamento dentro do produtor.

Casos reais documentados

Os casos a seguir são documentados publicamente. Quando um caso é ilustrativo, isso é indicado de forma explícita. A finalidade é mostrar como os padrões aparecem na prática e quais lições decorrem deles.

Caso 1 · Disjuntor na biblioteca Hystrix (padrão: disjuntor)

A Netflix desenvolveu e publicou, em 2012, a biblioteca Hystrix, que implementa o padrão de disjuntor, isolamento de chamadas e fallback para dependências remotas. A biblioteca foi adotada amplamente e influenciou a forma como equipes de microsserviços tratam falhas de dependências. Em 2018, a Netflix anunciou que o projeto entraria em modo de manutenção e recomendou alternativas mais recentes, como a biblioteca Resilience4j.

Lições. O caso ilustra que o padrão é conceitual e pode ser implementado em bibliotecas que evoluem. Também mostra que uma solução de resiliência precisa ser mantida: o disjuntor depende de parâmetros ajustados à carga real, e sua configuração deve ser revisada à medida que o sistema cresce.

Caso 2 · Migração gradual de sistemas legados (padrão: estrangulador)

O padrão estrangulador foi descrito por Martin Fowler (2004) e é recomendado em orientações de migração publicadas pela AWS. O processo típico começa pela identificação de uma funcionalidade de baixo risco, a implementação do novo serviço, a comparação de resultados em paralelo e a transferência do tráfego por etapas. Trata-se de um caso documentado de forma geral pela literatura e pela documentação de arquitetura, e não de um único caso de empresa.

Lições. A migração gradual reduz o risco, mas aumenta a complexidade operacional durante a transição, pois dois sistemas precisam ser mantidos. A medição da equivalência de resultados é a atividade que decide quando a transferência pode avançar.

Caso 3 · Pedido de varejo com fan-out (ilustrativo)

Caso ilustrativo, inspirado na documentação pública da AWS sobre fan-out de tópicos SNS para filas SQS. Um varejista publica o evento de pedido criado. Os assinantes são o estoque, o faturamento e o envio de e-mails. Durante uma promoção, o serviço de e-mail passa a responder lentamente. Como cada assinante possui sua própria fila, o estoque e o faturamento continuam processando sem atraso. As mensagens de e-mail se acumulam e são processadas quando o serviço se recupera.

Lições. O isolamento entre assinantes evita que uma falha local vire uma falha geral. A acumulação de mensagens, porém, exige monitoramento do tamanho das filas, e o processamento tardio pode ser inaceitável para certos tipos de notificação. O padrão resolve o acoplamento, mas transfere para o projeto a responsabilidade por prazos.

Vantagens e limitações dos padrões

A adoção de padrões corporativos traz benefícios reais, mas nenhum deles é gratuito. A análise a seguir considera o uso dos padrões como um conjunto, e não de forma isolada.

Vantagens

  • Vocabulário comum: equipes discutem soluções com termos precisos, o que reduz ambiguidade em projetos grandes.
  • Reuso de soluções testadas: o padrão reduz a necessidade de reinventar mecanismos de resiliência e de integração.
  • Redução do risco de mudança: a migração incremental e o isolamento de falhas limitam o alcance de erros.
  • Correspondência com serviços gerenciados: boa parte dos padrões já tem implementação operada pela AWS, o que reduz a administração.

Limitações

  • Complexidade distribuída: a solução de um problema cria outros, como duplicidade de mensagens, consistência eventual e depuração de fluxos assíncronos.
  • Aplicação indevida: usar um padrão sem que o problema exista adiciona complexidade sem benefício.
  • Dependência de configuração: tempos limite, limiares e políticas de retentativa precisam de ajuste empírico, e configurações erradas causam falhas.
  • Custo de transição: migrações incrementais mantêm dois sistemas por período prolongado.
  • Lacunas de observabilidade: fluxos distribuídos exigem rastreamento e métricas (tópico 13) que nem sempre são implantados.

Síntese. Um padrão responde a uma força específica e, ao resolvê-la, cria outra. A competência profissional não consiste em conhecer todos os padrões, mas em reconhecer a força presente no sistema e avaliar se a solução proposta compensa o custo que ela introduz.

Exercícios resolvidos

1. Um serviço de faturamento chama, de forma síncrona, um serviço fiscal que frequentemente excede o tempo limite. Qual padrão é mais adequado e por quê?

Ver resposta

Resposta: o disjuntor, combinado com tempo limite e retentativa com espera crescente. O disjuntor impede que as chamadas lentas se acumulem e derrubem o faturamento; o fallback permite registrar a emissão como pendente. Se a emissão puder ser assíncrona, o canal de mensagens é uma alternativa, pois desacopla os dois serviços no tempo.

2. Em um fan-out para e-mail, o cliente recebe duas mensagens idênticas. Qual é a causa provável e a correção?

Ver resposta

Resposta: a entrega com garantia de pelo menos uma vez pode repetir uma mensagem, por exemplo quando o consumidor processa, mas não confirma a mensagem antes de um tempo limite. A correção é tornar o consumo idempotente: registrar o identificador do evento processado e ignorar repetições. Também é preciso revisar o tempo de visibilidade, que deve ser maior que o tempo de processamento.

Ponte para a certificação AWS

Os padrões deste tópico correspondem a temas recorrentes nas certificações da AWS. No SAA-C03, o desacoplamento com SQS, SNS e EventBridge, e a escolha de mecanismos de resiliência, são cobrados nos domínios de arquiteturas resilientes e de alto desempenho. No DVA-C03, Step Functions, Lambda e os destinos de falha aparecem em cenários de desenvolvimento e de tratamento de erros. Recomenda-se conferir os guias vigentes, pois o escopo é revisado periodicamente.

Teste seus conhecimentos

Qual padrão trata da consistência de uma operação que atravessa vários serviços, por meio de compensações?

Correto. A saga executa transações locais e, em caso de falha, aplica compensações que desfazem os passos anteriores.

Um evento deve ser entregue a vários consumidores independentes. Qual combinação de serviços da AWS é mais adequada?

Correto. O tópico entrega uma cópia a cada assinante, e cada fila isola o processamento de um consumidor.

Qual é a finalidade principal do disjuntor?

Correto. Ao bloquear chamadas a uma dependência que falha de forma repetida, o disjuntor preserva os recursos do sistema que chama.

Síntese do tópico

  • Padrão é uma solução recorrente para um problema recorrente, descrita por contexto, problema, solução e consequências.
  • O catálogo parte do problema: a escolha do serviço AWS decorre da força presente no sistema.
  • Migração incremental, saga, publicação e assinatura, disjuntor e cache são os padrões mais recorrentes em sistemas corporativos.
  • Toda solução de mensageria exige idempotência, e toda retentativa exige cuidado com operações não idempotentes.
  • Padrões resolvem forças e criam outras; a competência está em avaliar o custo que cada solução introduz.
