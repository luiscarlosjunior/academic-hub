Tópico 4 · Hospedagem na AWS

A documentação do design system é um site estático: HTML, CSS e JavaScript gerados pelo Storybook. Esse tipo de site dispensa servidor. Na AWS, o padrão é guardar os arquivos num bucket S3 e entregá-los pelo CloudFront, a rede de distribuição de conteúdo da AWS, com o domínio controlado pelo Route 53. O bucket fica privado, e só a distribuição tem acesso a ele.

Objetivos desta página. Ao final, você deve conseguir:

  • explicar o caminho de uma requisição: DNS, borda, origem e cache;
  • configurar um bucket privado acessível apenas pelo CloudFront, com OAC;
  • definir políticas de cache diferentes para arquivos com hash e para o index.html;
  • publicar uma nova versão da documentação com sincronização e invalidação.

Teoria: borda, origem e cache

O CloudFront é formado por locais de borda espalhados pelo mundo. Cada local guarda cópias dos objetos por um tempo definido pelo TTL. Quando a borda já tem o arquivo, a resposta é um cache hit, e a origem nem é consultada. Quando não tem, é um cache miss, e a borda busca o arquivo na origem, que aqui é o bucket S3.

O Origin Access Control (OAC) é o mecanismo atual para o CloudFront acessar um bucket privado. Ele assina as requisições com SigV4, e a política do bucket autoriza apenas a distribuição específica. Antes do OAC existia o Origin Access Identity (OAI), que a AWS recomenda substituir. A documentação oficial lista as diferenças.

Dois detalhes costumam cair na prova e na prática. Primeiro, o certificado ACM usado pelo CloudFront precisa estar na região us-east-1, independentemente da região do bucket. Segundo, o Route 53 aponta o domínio para a distribuição com um registro do tipo alias, que resolve para o endereço da distribuição sem um IP fixo.

Operação 1 · Seguir uma requisição

Acompanhe duas visitas ao mesmo endereço. Na primeira, o arquivo ainda não está na borda, e o CloudFront busca no S3 com OAC. Na segunda, a borda responde sozinha. É exatamente essa diferença que explica a queda de latência e o custo menor de requisições ao S3.

Operação 2 · Bucket privado e política com OAC

O bucket mantém o Block Public Access ligado. Ninguém acessa os arquivos diretamente pelo endereço do S3. A única exceção é a política abaixo, que permite a leitura somente quando a requisição vem da distribuição indicada em AWS:SourceArn. Sem essa condição, qualquer outra distribuição da mesma conta poderia usar o bucket.

Em JSON · política do bucket

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "PermitirSomenteCloudFront",
      "Effect": "Allow",
      "Principal": { "Service": "cloudfront.amazonaws.com" },
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::ds-docs-123456789012/*",
      "Condition": {
        "StringEquals": {
          "AWS:SourceArn": "arn:aws:cloudfront::123456789012:distribution/EDFDVBD6EXAMPLE"
        }
      }
    }
  ]
}

Operação 3 · Publicar sem servir versão antiga

A publicação sobe os arquivos com --cache-control diferente por tipo, e depois invalida só o que precisa de revalidação. Invalidar tudo (/*) funciona, mas custa mais e perde o benefício do cache dos assets com hash. Por isso, a invalidação fica restrita ao index.html.

Em Bash · publicar-docs.sh

#!/usr/bin/env bash
set -euo pipefail

BUCKET="ds-docs-123456789012"
DISTRIBUICAO="EDFDVBD6EXAMPLE"

# 1. assets com hash: longa duração e imutáveis
aws s3 sync ./storybook-static "s3://$BUCKET" \
  --exclude "index.html" --exclude "versions.json" \
  --cache-control "public, max-age=31536000, immutable" \
  --delete

# 2. páginas que mudam a cada deploy: sempre revalidadas
aws s3 cp ./storybook-static/index.html "s3://$BUCKET/index.html" \
  --cache-control "no-cache"

# 3. invalidar somente o que pode estar desatualizado
aws cloudfront create-invalidation \
  --distribution-id "$DISTRIBUICAO" \
  --paths "/index.html"

Em produção, o passo 3 costuma virar uma etapa do pipeline do tópico 6, com as credenciais obtidas por OIDC. O comando --delete remove do bucket o que não existe mais no build; use-o com cuidado e somente em pastas dedicadas.

Práticas do mercado

  • Documentação por versão: cada versão major publica em um prefixo (/v1/, /v2/), para que consumidores antigos consultem o que usam.
  • Domínio próprio: design.empresa.com.br aponta para o CloudFront por alias, com certificado ACM em us-east-1.
  • Alternativas gerenciadas: Chromatic, Netlify e Vercel publicam Storybook sem operar bucket. O AWS Amplify Hosting cobre o mesmo papel dentro da AWS. A escolha depende de quem opera e de onde estão os dados.
  • Logs e métricas: o CloudFront registra acessos e taxa de cache hit, que mostra se a configuração está funcionando (tópico 8).

Exercícios resolvidos

1. Um colega sugere tornar o bucket público para “simplificar”. Qual é o risco e a alternativa?

Ver resposta

Resposta: com o bucket público, os arquivos ficam acessíveis sem passar pela borda, sem WAF e sem o controle de cache. Qualquer pessoa pode listar e baixar o conteúdo, e o custo de transferência sai do controle. A alternativa é manter o bucket privado e liberar a leitura só para a distribuição via OAC.

2. Depois de um deploy, o usuário ainda vê a versão anterior, mas os assets novos carregam. Qual é a causa mais provável?

Ver resposta

Resposta: o index.html ficou com cache longo na borda ou no navegador, então aponta para os nomes antigos dos assets. A correção é ter no-cache no index e invalidá-lo no CloudFront, como na operação 3.

Teste seus conhecimentos

Qual é o mecanismo recomendado para o CloudFront acessar um bucket S3 privado?

Correto. O OAC assina as requisições da distribuição, e a política do bucket autoriza apenas essa distribuição.

Por que o index.html usa no-cache, enquanto os assets com hash usam immutable?

Correto. O nome com hash torna o arquivo imutável; o index.html aponta para os assets e precisa estar sempre atualizado.

Em qual região o certificado ACM deve estar para ser usado por uma distribuição CloudFront?

Correto. O CloudFront exige o certificado em us-east-1, independentemente da região do bucket.

O que levar desta página

  • O site estático vai para S3 privado e é entregue pelo CloudFront via OAC.
  • Assets com hash: cache longo e imutáveis. index.html: no-cache e invalidação.
  • Certificado de CloudFront fica em us-east-1; o domínio é um alias no Route 53.
  • Publicar é sincronizar com cache por tipo e invalidar só o necessário.
