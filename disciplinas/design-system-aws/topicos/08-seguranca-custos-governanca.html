Tópico 8 · Segurança, custos e governança

Um design system publicado na AWS é um serviço em produção, e serviços têm três riscos permanentes: alguém acessar o que não deveria, alguém atacar a aplicação e a conta gerar uma fatura inesperada. Este tópico trata dos três, com as ferramentas que a AWS oferece e com o modelo que organiza quem faz o quê.

Objetivos desta página. Ao final, você deve conseguir:

  • aplicar o princípio do mínimo privilégio em uma política IAM;
  • descrever regras de AWS WAF para a borda do CloudFront, incluindo limite de taxa;
  • criar um orçamento com alerta no AWS Budgets;
  • separar as responsabilidades da AWS e do cliente e avaliar uma arquitetura pelos seis pilares do Well-Architected.

Teoria: modelo de responsabilidade compartilhada

A AWS é responsável pela segurança da nuvem: data centers, rede física, hardware e o software que sustenta os serviços. O cliente é responsável pela segurança na nuvem: quem tem acesso, como a configuração é feita, se o bucket está público, se os dados estão criptografados. Na maior parte dos incidentes em documentação estática, o problema está no lado do cliente.

O mínimo privilégio diz que cada identidade recebe só as ações e os recursos de que precisa, e nada mais. Um papel de deploy que só sincroniza um bucket não deve poder criar usuários nem ler outros buckets. Em geral, começa-se com nenhuma permissão e acrescenta-se o que o teste mostrar necessário, e não o contrário.

Por último, a governança trata da organização das contas. O AWS Organizations agrupa contas em unidades organizacionais, e as service control policies (SCPs) definem o limite máximo de ações permitidas em cada grupo. Assim, mesmo um administrador de conta não consegue, por exemplo, desabilitar o CloudTrail em produção.

Operação 1 · Política do papel de deploy

A política abaixo substitui a versão “administrador” que muita gente usa nos primeiros dias. Ela permite gravar e remover objetos no bucket de produção, listar e ler para a sincronização, e criar invalidações em uma única distribuição. Qualquer outra ação é negada por padrão, sem precisar de regra explícita.

Em JSON · política do papel ds-deploy-producao

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "SincronizarDocumentacao",
      "Effect": "Allow",
      "Action": ["s3:ListBucket", "s3:GetObject", "s3:PutObject", "s3:DeleteObject"],
      "Resource": [
        "arn:aws:s3:::ds-docs-producao",
        "arn:aws:s3:::ds-docs-producao/*"
      ]
    },
    {
      "Sid": "InvalidarCache",
      "Effect": "Allow",
      "Action": "cloudfront:CreateInvalidation",
      "Resource": "arn:aws:cloudfront::123456789012:distribution/EDFDVBD6EXAMPLE"
    }
  ]
}

O erro mais comum é "Resource": "*" junto com "Action": "s3:*". Uma política assim funciona, mas permite apagar todos os buckets da conta. Se o pipeline for comprometido, o estrago é total. Com a política acima, o estrago fica limitado a um bucket.

Operação 2 · Filtrar tráfego com AWS WAF

O AWS WAF é anexado à distribuição do CloudFront e avalia cada requisição antes de ela chegar ao S3. Ele tem dois tipos de regra que interessam aqui: grupos de regras gerenciados, mantidos pela AWS, que cobrem padrões como injeção de SQL e XSS; e regras de taxa, que bloqueiam um IP acima de um limite em uma janela de cinco minutos. Para CloudFront, o WAF precisa ser criado na região us-east-1 com escopo CLOUDFRONT. Escolha um cenário na animação.

Animação: pedidos avaliados pelo WAF

O tráfego normal passa de ponta a ponta. Com ataque, o WAF bloqueia por regra e limita a rajada de login.

Em JSON · regras do Web ACL (WAFv2)

[
  {
    "Name": "RegrasComuns",
    "Priority": 0,
    "Statement": {
      "ManagedRuleGroupStatement": {
        "VendorName": "AWS",
        "Name": "AWSManagedRulesCommonRuleSet"
      }
    },
    "OverrideAction": { "None": {} },
    "VisibilityConfig": {
      "SampledRequestsEnabled": true,
      "CloudWatchMetricsEnabled": true,
      "MetricName": "RegrasComuns"
    }
  },
  {
    "Name": "LimitarTaxaPorIP",
    "Priority": 1,
    "Statement": {
      "RateBasedStatement": { "Limit": 100, "AggregateKeyType": "IP" }
    },
    "Action": { "Block": {} },
    "VisibilityConfig": {
      "SampledRequestsEnabled": true,
      "CloudWatchMetricsEnabled": true,
      "MetricName": "LimitarTaxaPorIP"
    }
  }
]

O limite de 100 requisições por IP em cinco minutos é o mínimo aceito pela regra de taxa. Ele precisa ser calibrado com o tráfego real: um limite baixo demais bloqueia usuários legítimos atrás de uma mesma rede corporativa.

Operação 3 · Orçamento com alerta

Custos de documentação estática costumam ser baixos, mas três itens podem crescer sem aviso: transferência de dados do CloudFront, requisições ao S3 quando o cache não funciona (tópico 4) e armazenamento de pacotes no CodeArtifact. Um orçamento com alerta em percentual avisa antes da fatura chegar. Marque também as tags de alocação de custo, como projeto=design-system, para separar o gasto desta disciplina ou produto dos demais.

Em JSON · orcamento.json

{
  "BudgetName": "design-system-mensal",
  "BudgetLimit": { "Amount": "200", "Unit": "USD" },
  "BudgetType": "COST",
  "TimeUnit": "MONTHLY"
}

Em Bash · criar o orçamento com alerta em 80%

aws budgets create-budget \
  --account-id 123456789012 \
  --budget file://orcamento.json \
  --notifications-with-subscribers '[{
    "Notification": {
      "NotificationType": "ACTUAL",
      "ComparisonOperator": "GREATER_THAN",
      "Threshold": 80,
      "ThresholdType": "PERCENTAGE"
    },
    "Subscribers": [{ "SubscriptionType": "EMAIL", "Address": "time-ds@sua-org.com.br" }]
  }]'

Operação 4 · Avaliar pelo Well-Architected

O AWS Well-Architected Framework organiza as boas práticas em seis pilares. Usá-lo como checklist de revisão de arquitetura é uma prática comum, e a ferramenta Well-Architected da console registra as respostas e os riscos encontrados.

PilarPergunta que faz ao design systemOnde aparece neste curso
Excelência operacionalComo o pipeline é observado e atualizado?Tópico 6 e tópico 8
SegurançaQuem acessa o bucket e a distribuição?Tópicos 4 e 8
ConfiabilidadeO que acontece se uma região cair?Tópico 4 (CloudFront)
Eficiência de desempenhoO cache está servindo a maior parte das requisições?Tópico 4
Otimização de custosQual é o custo por visita à documentação?Operação 3
SustentabilidadeO cache e o tamanho dos assets reduzem o consumo de recursos?Tópico 4 e tópico 2

Práticas do mercado

  • Detecção contínua: GuardDuty analisa eventos e o Security Hub consolida achados de vários serviços numa única tela.
  • Registro de auditoria: CloudTrail ativo em todas as regiões, com logs em um bucket de conta separada.
  • Dados pessoais: a documentação não deve conter dados de pessoas reais. Em projetos no Brasil, a LGPD se aplica quando há coleta de dados de usuários, como em exemplos com cadastros.
  • Tags obrigatórias: políticas de tag no AWS Organizations garantem que todo recurso tenha dono e projeto.

Mais exemplos comentados

Os exemplos aplicam proteções em três níveis: a organização inteira (SCP), o bucket (política com TLS obrigatório) e a operação (alarme de erros no CloudFront). Em cada um, a explicação mostra o que a proteção impede e o que ela não cobre.

Exemplo 1 · Uma SCP que protege a trilha de auditoria

Uma service control policy define o limite máximo de ações de todas as contas de uma unidade organizacional. Ela não concede permissão; apenas remove. Mesmo um administrador local não consegue desligar o CloudTrail se a SCP estiver ativa, o que protege a trilha que investigações de incidente dependem.

Em JSON · SCP aplicada à unidade de produção

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ProtegerTrilhaDeAuditoria",
      "Effect": "Deny",
      "Action": [
        "cloudtrail:StopLogging",
        "cloudtrail:DeleteTrail",
        "cloudtrail:UpdateTrail"
      ],
      "Resource": "*"
    }
  ]
}

Por que funciona: o Deny vence qualquer Allow, então nenhum papel dentro da conta consegue contornar a regra. Dois limites precisam ser lembrados. Primeiro, a SCP não se aplica à conta de gerenciamento da organização, por isso a conta de gerenciamento deve ter pouquíssimos acessos. Segundo, a SCP não substitui a política de leitura: ela restringe o que pode existir, mas não concede nada.

Exemplo 2 · Recusando conexões sem TLS

Mesmo com o bucket privado, uma conexão sem criptografia expõe o conteúdo na rede. A condição aws:SecureTransport é verdadeira quando a requisição usa HTTPS. A política abaixo nega qualquer acesso que chegue sem TLS, inclusive de quem tem permissão.

Em JSON · política do bucket de produção

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "NegarSemTLS",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:*",
      "Resource": [
        "arn:aws:s3:::ds-docs-producao",
        "arn:aws:s3:::ds-docs-producao/*"
      ],
      "Condition": {
        "Bool": { "aws:SecureTransport": "false" }
      }
    }
  ]
}

Por que funciona: a negação é total, porque Principal "*" alcança todos, e a condição só dispara quando a conexão não é TLS. Quem usa a AWS CLI ou o SDK com HTTPS nunca é afetado. O CloudFront também acessa a origem por HTTPS, então a distribuição continua funcionando. Esse é um exemplo de política que reduz risco sem exigir mudança no fluxo normal.

Exemplo 3 · Alarme de erros 5xx no CloudFront

Um pico de erros 5xx indica que a origem está falhando ou que uma configuração quebrou. As métricas do CloudFront são publicadas na região us-east-1, com a dimensão Region=Global, e não na região do bucket. Esse detalhe faz muitos alarmes nunca dispararem: o alarme foi criado na região errada.

Em Bash · criação do alarme

aws cloudwatch put-metric-alarm \
  --region us-east-1 \
  --alarm-name docs-5xx-alto \
  --namespace AWS/CloudFront \
  --metric-name 5xxErrorRate \
  --dimensions Name=DistributionId,Value=EDFDVBD6EXAMPLE Name=Region,Value=Global \
  --statistic Average \
  --period 300 \
  --evaluation-periods 2 \
  --threshold 5 \
  --comparison-operator GreaterThanThreshold \
  --treat-missing-data notBreaching

Por que funciona: a métrica 5xxErrorRate é um percentual. O alarme exige duas janelas de cinco minutos acima de 5%, o que evita disparos por um erro isolado. notBreaching trata a ausência de dados como normal, porque um site sem visitas não deve gerar alerta. Ajuste o limite com o histórico real, e não com um número arbitrário.

Exemplo 4 · Calculando o custo com o cache

O custo de transferência depende do volume servido pela borda, e o custo de requisições depende de quantas chegam à origem. O cálculo abaixo mostra como a taxa de cache hit muda a conta. Os preços exatos variam por região e faixa, então use a calculadora oficial. A lógica é a que importa.

PassoCálculo com 50 mil visitas e 2 MB por visita
Volume total servido50.000 × 2 MB = 100 GB, independentemente do cache
Requisições totaisAssuma 20 arquivos por visita: 1 milhão de requisições
Cache hit de 50%Metade das requisições chega ao S3: 500 mil requisições de origem
Cache hit de 95%Apenas 50 mil requisições chegam ao S3: dez vezes menos

Por que funciona: o volume de transferência não muda com o cache, porque o usuário sempre recebe o arquivo. O que o cache reduz é a carga na origem e o número de requisições ao S3, que é cobrado por requisição. Por isso, a métrica de cache hit (tópico 4) é um indicador de custo, e não apenas de desempenho. Uma queda nessa taxa após uma mudança de configuração deve gerar alerta tanto quanto um aumento de latência.

Exercícios resolvidos

1. Uma política tem "Action": "s3:*" e "Resource": "*". Qual é o problema e como corrigir?

Ver resposta

Resposta: a identidade pode executar qualquer ação de S3 em qualquer bucket da conta, incluindo apagar todos eles. A correção é listar apenas as ações necessárias (s3:PutObject, s3:ListBucket etc.) e restringir o campo Resource aos ARNs do bucket de produção.

2. Um usuário legítimo reclama de bloqueio pelo WAF. Qual é a primeira investigação?

Ver resposta

Resposta: consultar as requisições amostradas no WAF para identificar qual regra bloqueou e qual IP foi afetado. Se foi a regra de taxa, o limite pode estar baixo para o tráfego real, ou o usuário compartilha IP com outros. A correção vem da análise, e não de desligar a regra.

Exercícios propostos

  1. Escreva a política mínima do papel de staging, que publica num bucket diferente do de produção, e mostre que ela não permite acesso ao bucket de produção.
  2. Calcule o gasto mensal de um site que recebe 50 mil visitas com 2 MB de transferência cada, e compare com o orçamento de US$ 200. Use a calculadora de preços da AWS.
  3. Avalie o design system deste curso pelos seis pilares e escreva um risco por pilar com uma ação de correção.

Teste seus conhecimentos

No modelo de responsabilidade compartilhada, de quem é a segurança da configuração de um bucket público?

Correto. A AWS protege a infraestrutura; a configuração de acesso e de dados é responsabilidade do cliente.

Para anexar um Web ACL do WAF a uma distribuição do CloudFront, em que escopo e região ele deve ser criado?

Correto. Para CloudFront, o WAF usa escopo CLOUDFRONT e fica na região us-east-1.

Qual dos itens abaixo não é um dos seis pilares do Well-Architected Framework?

Correto. Os pilares são excelência operacional, segurança, confiabilidade, eficiência de desempenho, otimização de custos e sustentabilidade.

O que levar desta página

  • Responsabilidade compartilhada: AWS protege a nuvem; o cliente protege o que configura nela.
  • Mínimo privilégio: liste as ações e os recursos; nada de s3:* sobre *.
  • WAF filtra na borda; regras gerenciadas e de taxa cobrem a maior parte dos casos comuns.
  • Orçamento com alerta e tags de custo evitam surpresa na fatura.
