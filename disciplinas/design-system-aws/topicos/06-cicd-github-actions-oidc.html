Tópico 6 · CI/CD, OIDC e testes visuais

Um design system só é confiável se cada mudança passa pelas mesmas verificações antes de chegar aos produtos. O pipeline de CI/CD faz isso: roda lint, testes, build, testes visuais, publica em homologação e, depois de uma aprovação humana, publica em produção. Para falar com a AWS, o pipeline usa OIDC: pede credenciais temporárias ao STS em troca de um token do provedor, sem guardar nenhuma chave de acesso no repositório.

Objetivos desta página. Ao final, você deve conseguir:

  • ordenar as etapas de um pipeline e justificar a ordem (falha rápida primeiro);
  • configurar um papel IAM que confia no token OIDC de um repositório e de uma branch;
  • usar environments do GitHub para aprovação antes de produção;
  • tratar falhas de teste visual sem aceitar diferenças por reflexo.

Teoria: ordem das etapas e confiança entre sistemas

A ordem das etapas segue um princípio: o que é barato e rápido falha primeiro. Lint leva segundos; o teste visual leva minutos. Se o lint reprova, nenhum minuto é gasto com o resto. Cada etapa só roda se a anterior passou, e isso é expresso no pipeline com dependências explícitas (needs).

O OIDC resolve um problema antigo: chaves de acesso de longa duração vazam, não expiram e são difíceis de rotacionar. Com OIDC, a AWS confia em um emissor externo (o GitHub) e entrega credenciais que duram uma hora. A trust policy do papel IAM define quem pode assumi-lo, e a condição sub limita o repositório, a branch ou o environment. Se a condição for frouxa, qualquer branch, inclusive de um fork, consegue publicar em produção.

O teste visual compara uma captura atual de cada história com uma referência aprovada. A diferença de um pixel reprova o build. Isso protege contra regressões de estilo que nenhum teste funcional enxerga.

Operação 1 · Montar o pipeline

O workflow abaixo tem quatro jobs encadeados. A publicação em produção só começa depois de staging, e o environment producao exige um revisor humano configurado no GitHub. Note também a permissão id-token: write, sem a qual o job não consegue pedir o token OIDC.

Animação: do commit à produção

Escolha o cenário. Com a falha, o pipeline para na etapa visual, e nada chega à homologação.

Em YAML · .github/workflows/publicar.yml

name: publicar-design-system

on:
  push:
    branches: [main]

permissions:
  contents: read
  id-token: write          # obrigatório para pedir o token OIDC

jobs:
  qualidade:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20, cache: npm }
      - run: npm ci
      - run: npm run lint
      - run: npm test
      - run: npx playwright test --project=visual

  storybook:
    needs: qualidade
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20, cache: npm }
      - run: npm ci
      - run: npm run build-storybook
      - uses: actions/upload-artifact@v4
        with: { name: storybook-static, path: storybook-static }

  staging:
    needs: storybook
    runs-on: ubuntu-latest
    environment: staging
    steps:
      - uses: actions/download-artifact@v4
        with: { name: storybook-static, path: storybook-static }
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/ds-deploy-staging
          aws-region: sa-east-1
      - run: aws s3 sync storybook-static s3://ds-docs-staging --delete

  producao:
    needs: staging
    runs-on: ubuntu-latest
    environment: producao     # revisores obrigatórios configurados no GitHub
    steps:
      - uses: actions/download-artifact@v4
        with: { name: storybook-static, path: storybook-static }
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/ds-deploy-producao
          aws-region: sa-east-1
      - run: aws s3 sync storybook-static s3://ds-docs-producao --delete

Operação 2 · Papel IAM que confia no token

Antes do workflow funcionar, a conta AWS precisa de um provedor OIDC para o GitHub e de um papel cuja trust policy restrinja a origem. A animação mostra o que acontece com uma branch permitida e com uma branch de funcionalidade que não está na condição.

Animação: troca do token por credenciais

Troque entre as duas branches e compare o quadro em que o STS emite credenciais.

Em JSON · trust policy do papel ds-deploy-producao

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "Federated": "arn:aws:iam::123456789012:oidc-provider/token.actions.githubusercontent.com"
      },
      "Action": "sts:AssumeRoleWithWebIdentity",
      "Condition": {
        "StringEquals": {
          "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
          "token.actions.githubusercontent.com:sub": "repo:sua-org/design-system:environment:producao"
        }
      }
    }
  ]
}

Para o papel de staging, o sub seria repo:sua-org/design-system:ref:refs/heads/main. Restringir por environment é mais forte, porque a aprovação do GitHub passa a ser parte da condição de acesso.

Operação 3 · Teste visual com referência aprovada

O Playwright compara capturas com as imagens de referência guardadas no repositório. Quando a mudança é intencional, a referência é atualizada de forma explícita, com um comando, e revisada no pull request. Atualizar a referência sem olhar o diff é o erro mais comum: transforma o teste em um carimbo.

Em TypeScript · botao.visual.spec.ts

import { test, expect } from '@playwright/test';

test('botão primário mantém a aparência de referência', async ({ page }) => {
  await page.goto('http://localhost:6006/iframe.html?id=componentes-button--primaria&viewMode=story');
  await expect(page.locator('#storybook-root')).toHaveScreenshot('botao-primario.png', {
    maxDiffPixelRatio: 0
  });
});

Em Bash · atualizar a referência de forma intencional

# só depois de revisar o diff gerado no relatório
npx playwright test --project=visual --update-snapshots

Práticas do mercado

  • Pipeline como código: o arquivo do workflow fica no repositório, passa por revisão e tem histórico, como qualquer código.
  • Proteção de branch: main só recebe mudança por pull request com a CI verde e revisão obrigatória.
  • Sem chaves de longa duração: OIDC é o padrão recomendado pela AWS e pelo GitHub para pipelines que acessam a conta.
  • Plataforma: o CodeCommit deixou de aceitar novos clientes em 2024. Por isso, o código costuma estar no GitHub ou GitLab, e a AWS entra no deploy, com CodeBuild e CodePipeline como alternativas gerenciadas.
  • Visual testing como serviço: Chromatic e Percy automatizam a revisão de diferenças em pull requests.

Mais exemplos comentados

Os exemplos cobrem três situações de pipeline real: impedir dois deploys simultâneos, levar o relatório visual para o pull request e diagnosticar uma falha de OIDC lendo o token.

Exemplo 1 · Dois deploys não se atropelam

Se dois commits entram em main em sequência, dois jobs de deploy podem rodar ao mesmo tempo e escrever no mesmo bucket. O bloco concurrency coloca os jobs de um mesmo grupo em fila. O ponto importante é cancel-in-progress: false: um deploy já iniciado nunca é cancelado no meio, porque isso deixaria o bucket com arquivos misturados de duas versões.

Em YAML · trecho do job de produção

jobs:
  producao:
    needs: staging
    runs-on: ubuntu-latest
    environment: producao
    concurrency:
      group: deploy-producao
      cancel-in-progress: false
    steps:
      - uses: actions/download-artifact@v4
        with: { name: storybook-static, path: storybook-static }
      - run: aws s3 sync storybook-static s3://ds-docs-producao --delete

Por que funciona: com cancel-in-progress: true, o segundo commit cancelaria o deploy do primeiro no meio do sync, e o bucket ficaria parcialmente atualizado. Com false, o segundo deploy espera o primeiro terminar e depois publica a versão mais nova. Essa é a configuração recomendada para deploys, e o cancelamento fica para testes de pull request.

Exemplo 2 · Relatório visual no pull request

Quando o teste visual falha num pull request, quem revisa precisa ver a diferença sem rodar o projeto localmente. O workflow abaixo roda só quando arquivos de interface mudam e envia o relatório do Playwright como artefato, que pode ser baixado na página da execução.

Em YAML · .github/workflows/pr-visual.yml

name: pr-visual

on:
  pull_request:
    paths: ['src/**', '.storybook/**']

jobs:
  visual:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20, cache: npm }
      - run: npm ci
      - run: npx playwright install --with-deps chromium
      - run: npx playwright test --project=visual
      - uses: actions/upload-artifact@v4
        if: failure()
        with:
          name: relatorio-visual
          path: playwright-report/

Por que funciona: o filtro paths evita rodar o teste visual em mudanças de documentação, o que economiza minutos de execução. if: failure() envia o relatório só quando há falha, para não lotar o armazenamento com execuções verdes. O relatório HTML mostra lado a lado a referência, a captura atual e a diferença destacada.

Exemplo 3 · Lendo o token OIDC para diagnosticar

Quando a AWS recusa a troca de token com Not authorized to perform sts:AssumeRoleWithWebIdentity, a causa quase sempre está no claim sub. O token é um JWT: três partes em base64 separadas por ponto. A parte do meio é o payload, que contém o sub. Decodificá-la mostra exatamente o que a trust policy precisa aceitar. Nunca imprima o token completo em log, pois ele dá acesso enquanto estiver válido.

Em Bash · inspeção segura do claim (sem imprimir o token)

# dentro de um passo de depuração temporário, com o token em variável de ambiente
PAYLOAD=$(echo "$ID_TOKEN" | cut -d. -f2 | tr '_-' '/+')
# acrescenta o padding de base64 que o decodificador exige
while [ $(( ${#PAYLOAD} % 4 )) -ne 0 ]; do PAYLOAD="$PAYLOAD="; done
echo "$PAYLOAD" | base64 --decode 2>/dev/null | jq '{sub, aud, ref}'

Por que funciona: o comando extrai só três claims. O sub diz de qual repositório e branch veio o pedido, o aud deve ser sts.amazonaws.com, e o ref mostra a branch. Comparar esses valores com a trust policy acha a diferença em segundos. Remova o passo de depuração assim que o problema for resolvido.

Exemplo 4 · Tabela de falhas de OIDC

Mensagem ou sintomaCausa provávelCorreção
Not authorized, sub não confereJob rodando em outra branch ou em environment não listado na trust policyAjustar a condição sub para o caso real
Error: Could not load credentials / Token not foundFalta id-token: write no bloco permissionsAdicionar a permissão no workflow ou no job
Not authorized, aud diferenteCondição de audiência ausente ou com valor erradoUsar sts.amazonaws.com em :aud
Provedor não encontradoProvedor OIDC do GitHub não criado na contaCriar o provedor token.actions.githubusercontent.com na conta

Por que funciona: cada linha separa uma camada do problema: o provedor, a permissão do job, a audiência e a condição de identidade. Seguir a tabela de cima para baixo evita o hábito de afrouxar a trust policy “para testar”, que é justamente o erro que o tópico 8 proíbe.

Exercícios resolvidos

1. Por que guardar AWS_ACCESS_KEY_ID como segredo do repositório é pior do que OIDC?

Ver resposta

Resposta: a chave é de longa duração: não expira sozinha, vale para quem a obtiver e precisa de rotação manual. Um segredo vazado em um log, um fork ou uma dependência comprometida dá acesso até alguém perceber. Com OIDC, a credencial dura uma hora, e a trust policy limita quem pode obtê-la.

2. O teste visual falhou num botão, mas a mudança era intencional. O que fazer?

Ver resposta

Resposta: abrir o relatório do Playwright, conferir que a diferença é exatamente a esperada, atualizar a referência com --update-snapshots e registrar a mudança no pull request, para que a revisão aprove a nova aparência. Nunca atualizar sem olhar o diff.

Exercícios propostos

  1. Altere a condição sub para aceitar qualquer branch e explique por que isso é perigoso. Depois, restrinja de novo.
  2. Adicione um job de acessibilidade (axe, do tópico 3) antes da etapa de staging e descreva o que acontece quando ele falha.
  3. Reordene o workflow colocando o teste visual antes dos testes unitários. Compare o tempo médio de falha nos dois casos.

Teste seus conhecimentos

Qual permissão o workflow precisa para pedir um token OIDC ao GitHub?

Correto. Sem id-token: write, o job não consegue solicitar o token que a AWS usa para validar a identidade.

Por que a condição sub da trust policy deve ser restrita?

Correto. Sem restrição, qualquer origem que obtenha um token válido do provedor pode assumir o papel.

Um teste visual reprova uma diferença inesperada. Qual é a ação correta?

Correto. A referência é a aprovação da aparência; atualizá-la sem revisão apaga o valor do teste.

O que levar desta página

  • Ordene as etapas do mais barato para o mais caro; use needs para encadear.
  • OIDC substitui chaves de longa duração por credenciais que expiram em uma hora.
  • Restrinja a trust policy por repositório, branch ou environment.
  • Teste visual exige revisão do diff antes de atualizar a referência.
