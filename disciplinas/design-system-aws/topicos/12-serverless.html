Tópico 12 · Computação serverless

Serverless significa que você escreve código e a AWS cuida de executar, escalar e aplicar correções no ambiente. No caso da Lambda, você paga pelas invocações e pelo tempo de execução, medido em milissegundos e pela memória alocada. Quando uma função não recebe chamadas, nada é cobrado. Isso muda o modo de pensar: o código passa a ser uma coleção de reações a eventos, e não um processo que fica ligado.

Objetivos desta página. Ao final, você deve conseguir:

  • escrever um handler Lambda que reaproveita conexões entre invocações;
  • explicar o cold start e tomar decisões de memória e de inicialização com base nele;
  • garantir idempotência em eventos que podem chegar mais de uma vez;
  • tratar falhas de invocações assíncronas com destino de falha;
  • decidir quando serverless é a escolha certa e quando não é.

Teoria: como a Lambda executa o seu código

Uma função Lambda tem um handler, que é a função exportada chamada a cada evento. Antes dela, a plataforma cria um ambiente de execução: carrega o runtime e o seu código. Esse ambiente é reaproveitado em invocações seguintes, enquanto estiver ativo. Por isso, o trabalho caro, como abrir conexão com banco ou carregar configuração, deve ficar fora do handler. Assim ele é feito uma vez por ambiente, e não a cada chamada.

O cold start é o tempo de criar um ambiente novo. Ele inclui baixar o código, iniciar o runtime e executar o código fora do handler. Ele afeta a primeira chamada de um ambiente, e fica mais visível em runtimes pesados e pacotes grandes. Duas alavancas reduzem o impacto: pacotes menores e mais memória, porque a Lambda aloca CPU proporcionalmente à memória. A concorrência provisionada mantém ambientes prontos, ao custo de pagar por eles mesmo sem uso.

Eventos podem chegar mais de uma vez, porque a maioria das fontes tem entrega pelo menos uma vez. Por isso, a função precisa ser idempotente: processar o mesmo evento duas vezes produz o mesmo resultado que processar uma vez. É a propriedade que evita cobrar duas vezes ou criar dois registros quando uma rede falha no meio do caminho.

Fonte de eventoModo de invocaçãoO que acontece na falha
API GatewaySíncrona: o cliente espera a respostaO erro volta ao cliente, que decide se tenta de novo
EventBridge, S3, SNSAssíncrona: a plataforma enfileira e chama a funçãoA plataforma tenta de novo; depois, envia ao destino de falha, se configurado
SQSEm lote, com sondagem da filaO lote volta à fila; use DLQ da própria fila após N tentativas

Operação 1 · Escrever o handler

O exemplo a seguir expõe uma rota que devolve a versão atual dos tokens publicados. Ele mostra as duas regras de performance: o cliente de banco é criado fora do handler, e a resposta sai com cabeçalhos de cache que a CDN do tópico 4 pode usar. A animação do tópico 12 mostra o caminho de uma chamada com e sem cold start.

Animação: uma chamada com ambiente quente e com cold start

Alterne entre os cenários. A diferença está na etapa da Lambda, que é a única que muda de tempo.

Em TypeScript · src/versao-tokens.ts

import type { APIGatewayProxyEventV2, APIGatewayProxyResultV2 } from 'aws-lambda';
import { DynamoDBClient } from '@aws-sdk/client-dynamodb';
import { DynamoDBDocumentClient, GetCommand } from '@aws-sdk/lib-dynamodb';

// Fora do handler: criado uma vez por ambiente e reaproveitado nas chamadas seguintes
const doc = DynamoDBDocumentClient.from(new DynamoDBClient({ region: 'sa-east-1' }));

export const handler = async (evento: APIGatewayProxyEventV2): Promise<APIGatewayProxyResultV2> => {
  const canal = evento.pathParameters?.canal ?? 'producao';

  const resposta = await doc.send(new GetCommand({
    TableName: 'VersoesTokens',
    Key: { pk: 'CANAL#' + canal },
  }));

  if (!resposta.Item) {
    return { statusCode: 404, body: JSON.stringify({ erro: 'canal não encontrado' }) };
  }

  return {
    statusCode: 200,
    headers: {
      'content-type': 'application/json',
      'cache-control': 'public, max-age=60',
    },
    body: JSON.stringify({ versao: resposta.Item.versao }),
  };
};

Por que funciona: o DynamoDBDocumentClient é caro de criar e barato de usar, e por isso fica fora do handler. O cache-control de 60 segundos permite que a CDN responda sem chamar a função na maioria das vezes, o que reduz custo e latência ao mesmo tempo. Erros esperados, como canal inexistente, devolvem código 404 em vez de lançar exceção, para não gerar tentativas automáticas inúteis.

Operação 2 · Processar o mesmo evento sem duplicar

Suponha uma função que registra a publicação de uma versão de tokens a partir de um evento do EventBridge. Se o evento chegar duas vezes, a função não pode criar dois registros de publicação. A técnica é gravar uma chave de idempotência com uma condição: a escrita só acontece se a chave ainda não existir. Quando a condição falha, o evento já foi processado, e a função simplesmente encerra com sucesso.

Em TypeScript · src/registrar-publicacao.ts

import { PutCommand } from '@aws-sdk/lib-dynamodb';
import { ConditionalCheckFailedException } from '@aws-sdk/client-dynamodb';

export async function registrarPublicacao(doc: DynamoDBDocumentClient, evento: { id: string; versao: string }) {
  try {
    await doc.send(new PutCommand({
      TableName: 'Publicacoes',
      Item: { pk: 'EVENTO#' + evento.id, versao: evento.versao, criadoEm: new Date().toISOString() },
      ConditionExpression: 'attribute_not_exists(pk)',
    }));
  } catch (erro) {
    if (erro instanceof ConditionalCheckFailedException) {
      return { status: 'ja-processado' };
    }
    throw erro;
  }
  return { status: 'registrado' };
}

Por que funciona: a condição attribute_not_exists(pk) torna a verificação e a escrita uma única operação atômica. Não há janela entre “ver se existe” e “gravar”, em que duas execuções paralelas passariam ao mesmo tempo. O identificador do evento precisa ser estável: use o id que a fonte fornece, e não um valor gerado na hora. Outros erros são relançados, para que a plataforma tente de novo.

Operação 3 · Falhas com destino de falha

Em invocações assíncronas, a plataforma tenta de novo algumas vezes e depois descarta o evento. Se o evento tem valor, descartá-lo é perda. Um destino de falha recebe o evento que não foi processado, junto com o motivo do erro. Assim, ele pode ser inspecionado, corrigido e reprocessado. Sem esse destino, o erro só existe nos logs, e os logs expiram.

Em TypeScript (CDK) · função com destino de falha em fila

import * as cdk from 'aws-cdk-lib';
import * as lambda from 'aws-cdk-lib/aws-lambda';
import * as destinations from 'aws-cdk-lib/aws-lambda-destinations';
import * as sqs from 'aws-cdk-lib/aws-sqs';

const falhas = new sqs.Queue(this, 'FalhasPublicacao', {
  retentionPeriod: cdk.Duration.days(14),
});

const publicar = new lambda.Function(this, 'Publicar', {
  runtime: lambda.Runtime.NODEJS_20_X,
  handler: 'index.handler',
  code: lambda.Code.fromAsset('dist/publicar'),
  memorySize: 512,
  timeout: cdk.Duration.seconds(30),
  retryAttempts: 2,
  onFailure: new destinations.SqsDestination(falhas),
});

Por que funciona: retryAttempts: 2 limita as tentativas automáticas, e o destino de falha guarda o que sobrou. A retenção de 14 dias dá tempo para a equipe investigar antes de o evento sumir. Acompanhe o tamanho dessa fila com um alarme, porque um crescimento súbito costuma indicar uma regressão na função.

Mais exemplos comentados

Os exemplos cobrem agendamento de tarefas e uma comparação de custo entre serverless e instância sempre ligada, que é a pergunta que decide a arquitetura.

Exemplo 1 · Tarefa agendada com EventBridge

Uma tarefa diária, como gerar o relatório de adoção do design system, não precisa de servidor. Uma regra do EventBridge com expressão cron dispara a função todo dia de manhã. A expressão do EventBridge tem seis campos, e o formato difere do cron tradicional do Linux porque inclui o ano e exige um dos campos de dia como ?.

Em TypeScript (CDK) · regra diária às 9h, horário UTC

import * as events from 'aws-cdk-lib/aws-events';
import * as targets from 'aws-cdk-lib/aws-events-targets';

new events.Rule(this, 'RelatorioDiario', {
  schedule: events.Schedule.expression('cron(0 12 * * ? *)'),
  targets: [new targets.LambdaFunction(relatorio)],
});

Por que funciona: cron(0 12 * * ? *) roda às 12h UTC, que é 9h no horário de Brasília (UTC menos três), sem horário de verão no Brasil desde 2019. Escrever em UTC evita erros de fuso, e a conversão fica documentada no comentário do código. Como o disparo é assíncrono, a função deve ser idempotente, como na operação 2.

Exemplo 2 · Serverless ou instância sempre ligada?

A escolha depende do padrão de uso. Uma função paga por invocação e por tempo; uma instância paga por hora, esteja ocupada ou não. A conta abaixo compara os dois casos com a mesma carga. Os valores de preço mudam com o tempo e a região, então use a calculadora oficial; a estrutura é a que importa.

CargaServerless tende a ser melhor quandoInstância tende a ser melhor quando
Tráfego esporádicoHá longos períodos sem chamadasNão há períodos ociosos
Tráfego previsível e constanteNunca: a conta cresce linear ao usoA instância ocupada o tempo todo custa menos por requisição
Picos imprevisíveisA escala é automática e sem configuraçãoExige auto scaling ajustado e aquecimento
Processo longo, acima de 15 minutosNão se aplica: o limite da Lambda é de 15 minutosAdequado para processos longos

Por que funciona: a tabela transforma uma discussão de opinião em critérios. A pergunta de corte é a ocupação: se a máquina ficaria ocupada a maior parte do tempo, serverless tende a custar mais. Para o design system, rotas de documentação e relatórios costumam ser esporádicos, o que favorece serverless.

Práticas do mercado

  • Funções pequenas e com um propósito: uma função por evento ou rota facilita permissões mínimas e medição de custo.
  • Frameworks de aplicação serverless: AWS SAM e o CDK com NodejsFunction são usados para empacotar e implantar as funções.
  • Teste local e de integração: o código de negócio é testado sem a Lambda, e a integração com eventos reais roda em ambiente de homologação.
  • Limites de cota vistos cedo: concorrência reservada evita que uma função esgote a concorrência da conta e derrube as outras.

Exercícios resolvidos

1. Uma função cria o cliente do banco dentro do handler. Qual é o efeito e como corrigir?

Ver resposta

Resposta: a conexão é criada a cada invocação, mesmo quando o ambiente é reaproveitado. Isso aumenta a latência de todas as chamadas e pode esgotar o número de conexões do banco sob carga. A correção é mover a criação para fora do handler, no escopo do módulo.

2. Uma função de cobrança falhou no meio e o evento foi reenviado. Qual propriedade precisa existir?

Ver resposta

Resposta: idempotência. A função precisa reconhecer o evento já processado, usando um identificador estável e uma condição de escrita, como na operação 2. Sem isso, o reenvio gera uma cobrança duplicada, que é um dos erros mais caros de corrigir.

Teste seus conhecimentos

Por que o cliente de banco deve ser criado fora do handler?

Correto. O ambiente da Lambda é reaproveitado; o código de inicialização fora do handler roda uma vez por ambiente.

Uma função assíncrona falha todas as tentativas. Qual recurso preserva o evento para investigação?

Correto. O destino de falha recebe o evento e o motivo do erro, para inspeção e reprocessamento.

Qual propriedade garante que reprocessar um evento não produz efeito duplicado?

Correto. Idempotência faz o processamento repetido produzir o mesmo resultado que um único processamento.

O que levar desta página

  • O cliente de banco e as configurações ficam fora do handler, para reaproveitamento entre chamadas.
  • Cold start afeta a primeira chamada; memória maior também aumenta a CPU disponível.
  • Eventos podem repetir; a função deve ser idempotente, com id estável e condição de escrita.
  • Falhas assíncronas precisam de destino de falha, senão o evento se perde.
  • Serverless vence com carga esporádica; instância vence com ocupação alta e constante.
