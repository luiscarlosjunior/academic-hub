Tópico 5 · Distribuição de pacotes

Para os produtos consumirem o design system, ele precisa ser um pacote com versão. O AWS CodeArtifact é um repositório de pacotes gerenciado, com acesso por IAM, que aceita npm, pip, Maven e outros formatos. Assim, o pacote fica privado, mas continua instalável com o gerenciador comum do time. A versão é o contrato: quem depende de ^1.4.2 precisa saber o que muda quando o número sobe.

Objetivos desta página. Ao final, você deve conseguir:

  • explicar a hierarquia domínio → repositório → upstream do CodeArtifact;
  • autenticar o npm no repositório com credenciais temporárias;
  • escolher entre patch, minor e major com base no impacto para os consumidores;
  • automatizar versões e changelog com changesets.

Teoria: hierarquia do CodeArtifact e versionamento

Um domínio do CodeArtifact agrupa repositórios e define a criptografia com AWS KMS. Um repositório guarda os pacotes e pode ter um upstream: se o pacote não existe no repositório privado, a busca segue para outro repositório ou para o registro público do npm. Essa ligação permite que o time instale dependências públicas e privadas pelo mesmo endereço, com uma única configuração.

O Versionamento Semântico (SemVer), definido por Tom Preston-Werner, usa três números: MAJOR.MINOR.PATCH. Uma mudança patch corrige algo sem alterar a interface. Uma minor acrescenta funcionalidade compatível. Uma major quebra a compatibilidade, por exemplo ao remover ou renomear uma propriedade. Em dependências npm, o intervalo ^1.4.2 aceita qualquer versão de 1.4.2 até antes de 2.0.0.

MudançaExemploVersão
Correção de bug visualFoco do botão sumia no SafariPatch: 1.4.2 → 1.4.3
Nova varianteBotão com variante fantasmaMinor: 1.4.3 → 1.5.0
Remoção de proptamanho vira sizeMajor: 1.5.0 → 2.0.0

Operação 1 · Autenticar e publicar no repositório

O comando aws codeartifact login obtém um token temporário, válido por até 12 horas, e grava a configuração do npm para o repositório. Não há senha no projeto. Em um pipeline, quem executa esse passo é um papel IAM assumido por OIDC (tópico 6).

Em Bash · publicação manual para teste

# configura o npm para o repositório privado (token temporário)
aws codeartifact login --tool npm \
  --domain ds-dominio \
  --domain-owner 123456789012 \
  --repository ds-pacotes

# confere o registro ativo e publica a versão do package.json
npm config get registry
npm publish --access restricted

Em JSON · package.json do consumidor

{
  "name": "meu-produto-web",
  "dependencies": {
    "@sua-org/design-system": "^1.4.2"
  }
}

Operação 2 · Escolher o tipo de mudança

A pergunta que define a versão é: um consumidor que já usa a versão atual precisa mudar o código para continuar funcionando? Se não precisa, é patch ou minor. Se precisa, é major. Selecione cada tipo na animação e observe o que acontece com o consumidor que declarou ^1.4.2.

Animação: da alteração ao consumidor

Escolha o tipo de mudança no seletor. No caso de major, observe que o consumidor não é atualizado automaticamente.

Operação 3 · Versionar com changesets

A ferramenta changesets, muito usada em monorepos, separa duas decisões: quem escreve registra a intenção (um arquivo markdown com o tipo da mudança), e o processo de release calcula a versão e gera o changelog. Assim, ninguém edita o número na mão, e o histórico fica legível para os consumidores.

Em Bash · fluxo de release

# 1. quem muda o componente registra a intenção (patch, minor ou major)
npx changeset

# 2. no release: aplica as versões e gera o CHANGELOG.md
npx changeset version

# 3. publica no registro configurado (CodeArtifact)
npx changeset publish

Em Markdown · arquivo gerado em .changeset/

---
"@sua-org/design-system": major
---

O prop `tamanho` do Button foi renomeado para `size`.
Migração: troque `tamanho="sm"` por `size="sm"` em todos os usos.

Programa completo

Em disciplinas/design-system-aws/exemplos/ está o package.json do pacote, com publishConfig apontando para o repositório, e o script de release. Ele reproduz os três passos da operação 3 e pode ser chamado pelo pipeline.

Mais exemplos comentados

Os exemplos mostram quais versões um intervalo aceita, como consultar o histórico de publicações, como depreciar uma versão com problema e como um changeset cobre dois pacotes de uma vez.

Exemplo 1 · Quais versões cada intervalo aceita?

O intervalo de versão decide o que o gerenciador instala quando alguém roda npm install. Considere um conjunto de versões publicadas: 1.4.1, 1.4.2, 1.4.9, 1.5.0 e 2.0.0. A tabela mostra o que cada intervalo escolhe.

IntervaloEscolhePor quê
1.4.2 (exato)1.4.2Só aceita a versão indicada
~1.4.21.4.9Aceita patches: mesmo minor, versão de patch igual ou maior
^1.4.21.5.0Aceita minor e patch: qualquer versão 1.x igual ou acima de 1.4.2
^0.4.20.4.x apenasEm versões 0.x, o minor já é tratado como quebra; o intervalo fica preso ao 0.4
>=1.4.2 <2.0.01.5.0Equivalente a ^1.4.2, escrito de forma explícita

Por que funciona: o intervalo é uma promessa do consumidor. ^1.4.2 diz “aceito qualquer 1.x a partir da 1.4.2”, e isso só é seguro se o time do design system respeitar o SemVer. Por isso o caso ^0.4.2 merece atenção: a convenção é que, antes da 1.0.0, qualquer versão pode quebrar. Se o design system ainda estiver em 0.x, o consumidor precisa ser avisado de que o minor também é potencialmente quebra.

Exemplo 2 · Consultando e depreciando versões

Depois de publicar, duas perguntas são comuns: quais versões existem e como avisar quem usa uma delas com problema. O npm responde às duas com comandos simples. A depreciação não remove a versão; ela exibe um aviso no instalador.

Em Bash · consulta e depreciação

# lista todas as versões publicadas no repositório configurado
npm view @sua-org/design-system versions --json

# marca a 1.4.2 como depreciada, com a versão a usar
npm deprecate "@sua-org/design-system@1.4.2" "Problema de foco no Safari. Use 1.4.3 ou superior."

Por que funciona: a depreciação é reversível e não quebra instalações existentes, porque a versão continua disponível. Quem tem a 1.4.2 no lockfile recebe o aviso no próximo npm install e migra quando puder. Remover a versão seria pior: quebra builds que já dependem dela.

Exemplo 3 · Um changeset para dois pacotes

Num monorepo, uma mudança pode tocar mais de um pacote. O changeset declara o tipo de mudança para cada um. Assim, o pacote de tokens recebe um patch enquanto o de componentes recebe um minor, e o changelog de cada um mostra apenas o que lhe diz respeito.

Em Markdown · .changeset/foco-e-variante.md

---
"@sua-org/design-system": minor
"@sua-org/design-tokens": patch
---

Nova variante `fantasma` no Button. Correção do token de cor de foco,
que estava abaixo de 3:1 contra o fundo claro.

Por que funciona: o changesets calcula a versão de cada pacote separadamente e atualiza as dependências internas. Se o componente depende dos tokens, o pacote de componentes sobe junto quando necessário. Escreva a descrição pensando no consumidor: ela vai para o changelog, e é ela que o time de produto lê.

Exercícios resolvidos

1. O time quer trocar a cor do foco para atender ao WCAG. Patch, minor ou major?

Ver resposta

Resposta: patch. A API (props, nomes, comportamento de uso) não muda, e o consumidor não precisa alterar código para continuar funcionando. Ainda assim, vale registrar no changelog a mudança visual, para que o time de produto saiba que o contraste foi ajustado.

2. A versão publicada tem um bug grave. Podemos republicar 1.4.2 com o conserto?

Ver resposta

Resposta: não. Versões publicadas são imutáveis: consumidores com lockfile já instalaram aquele conteúdo. A correção é publicar 1.4.3 com o conserto, e, se necessário, marcar a 1.4.2 como depreciada com uma mensagem.

Práticas do mercado

  • Changelog como interface: o consumidor decide o que atualizar lendo as notas; por isso, toda major tem guia de migração.
  • Atualização automatizada: Dependabot ou Renovate abrem pull requests quando sai uma minor ou patch; majors geralmente exigem revisão manual.
  • Pacote com escopo: o nome @org/design-system separa o pacote de bibliotecas públicas e facilita a política de acesso.
  • Lockfile versionado: cada produto fixa a versão exata no package-lock.json, e atualiza em ritmo próprio.

Ponte para a certificação AWS

Os guias de estudo da AWS tratam serviços de artefatos e de implantação com foco no DVA-C03, e a prova cobra a ideia de que o artefato é versionado, autenticado e publicado por processo automatizado. Confira a lista de serviços do guia oficial da versão vigente, porque ela muda com as revisões. O conceito de credencial temporária, que aparece aqui, é cobrado em todas as certificações de IAM.

Correto. O comando obtém o token temporário e grava a configuração do registro para o npm.

O que levar desta página

  • CodeArtifact guarda pacotes privados; o login usa token temporário, sem senha no projeto.
  • SemVer: patch corrige, minor acrescenta compatível, major quebra. Decida pelo impacto no consumidor.
  • Versão publicada é imutável: corrige-se com nova versão.
  • Changesets separa a intenção da mudança do cálculo de versão e do changelog.
