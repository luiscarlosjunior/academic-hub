Tópico 7 · Infraestrutura como código

Até aqui, cada peça foi descrita à mão: bucket, distribuição, política, registro DNS. A infraestrutura como código (IaC) transforma essa descrição em um arquivo versionado, revisável e reproduzível. O AWS CDK permite escrever essa descrição em TypeScript, com as ferramentas de uma linguagem de programação, e gera um template do CloudFormation, que é quem de fato cria os recursos.

Objetivos desta página. Ao final, você deve conseguir:

  • descrever uma pilha com bucket privado, distribuição com OAC e registro alias em TypeScript;
  • explicar a diferença entre App, Stack e Construct, e os níveis L1, L2 e L3;
  • gerar e ler o template com cdk synth;
  • revisar mudanças com cdk diff antes de aplicar com cdk deploy.

Teoria: a árvore de construtos

Um programa CDK é uma árvore. A raiz é o App. Dentro dele ficam uma ou mais Stacks, que correspondem a uma pilha do CloudFormation e são a unidade de deploy. Dentro da pilha ficam os Constructs, que são os recursos e os agrupamentos. Essa árvore é percorrida no synth, que a transforma em JSON.

Os constructs têm três níveis. O L1 (Cfn*) é uma tradução direta de um recurso do CloudFormation, sem padrões. O L2 (como s3.Bucket) traz padrões seguros e métodos que criam permissões e ligações, e é o nível usado no dia a dia. O L3 (padrões) combina vários recursos em uma solução pronta. Ao escolher um L2, você ganha o padrão seguro; ao escolher um L1, você assume toda a responsabilidade.

Um detalhe importante: cdk synth não cria nada na AWS. Ele só gera o template. A criação acontece no cdk deploy, quando o CloudFormation recebe o template e cria os recursos na ordem das dependências. Por isso, cdk diff é a etapa mais importante antes de qualquer mudança em produção.

Operação 1 · Descrever bucket, distribuição e registro

A pilha abaixo cria tudo o que o tópico 4 descreveu à mão. Repare que a política do bucket não aparece: a chamada S3BucketOrigin.withOriginAccessControl cria o OAC e a permissão de leitura para a distribuição, com o AWS:SourceArn correto. Esse é o ganho do L2: a parte fácil de errar fica pronta.

Em TypeScript · lib/docs-stack.ts (trecho central)

export class DocsStack extends cdk.Stack {
  constructor(scope: Construct, id: string, props: DocsStackProps) {
    super(scope, id, props);

    const bucket = new s3.Bucket(this, 'DocsBucket', {
      blockPublicAccess: s3.BlockPublicAccess.BLOCK_ALL,
      encryption: s3.BucketEncryption.S3_MANAGED,
      enforceSSL: true,
      removalPolicy: cdk.RemovalPolicy.RETAIN,
    });

    const distribuicao = new cloudfront.Distribution(this, 'DocsDistribution', {
      defaultBehavior: {
        origin: origins.S3BucketOrigin.withOriginAccessControl(bucket),
        viewerProtocolPolicy: cloudfront.ViewerProtocolPolicy.REDIRECT_TO_HTTPS,
        cachePolicy: cloudfront.CachePolicy.CACHING_OPTIMIZED,
      },
      defaultRootObject: 'index.html',
      domainNames: [props.dominio],
      certificate: acm.Certificate.fromCertificateArn(this, 'Certificado', props.certificadoArn),
    });

    new route53.ARecord(this, 'AliasDocs', {
      zone: route53.HostedZone.fromHostedZoneAttributes(this, 'Zona', {
        hostedZoneId: props.zonaId,
        zoneName: props.zonaNome,
      }),
      recordName: props.dominio,
      target: route53.RecordTarget.fromAlias(new targets.CloudFrontTarget(distribuicao)),
    });

    new cdk.CfnOutput(this, 'DistribuicaoId', { value: distribuicao.distributionId });
  }
}

O arquivo completo, com as importações e a interface DocsStackProps, está em disciplinas/design-system-aws/exemplos/docs-stack.ts. Já RemovalPolicy.RETAIN mantém o bucket se a pilha for removida: um comando de destruir a pilha não deve apagar a documentação publicada.

Operação 2 · Do código à criação dos recursos

O ciclo tem quatro passos. O synth gera o template. O diff compara o template com a pilha existente e mostra o que será criado, alterado ou removido. O deploy aplica. A animação acompanha o fluxo; compare com o caminho que você faria à mão no console.

Animação: do código ao recurso

Cada quadro é uma etapa do ciclo. O código é a fonte da verdade; o recurso na AWS é consequência dele.

Em Bash · sequência de comandos

# uma vez por conta e região: prepara o bucket de artefatos do CDK
npx cdk bootstrap aws://123456789012/sa-east-1

# gera o template em cdk.out/ (não cria nada na AWS)
npx cdk synth DocsStaging

# mostra o que mudaria em relação à pilha atual
npx cdk diff DocsStaging

# aplica; "broadening" pede aprovação quando há novas permissões
npx cdk deploy DocsStaging --require-approval broadening

Em JSON · trecho do template gerado em cdk.out/

{

Práticas do mercado

  • Escolha da ferramenta: CDK quando a equipe já escreve TypeScript; Terraform (HashiCorp) quando há múltiplos provedores de nuvem; CloudFormation puro para times que preferem YAML ou JSON sem camada de código.
  • Ambientes por stack: a mesma classe gera DocsStaging e DocsProducao com parâmetros diferentes.
  • Revisão de diff no pull request: o resultado de cdk diff entra no comentário da mudança, para o revisor ver o impacto antes do merge.
  • Proteção contra remoção acidental: RETAIN em dados, terminationProtection em pilhas críticas.

Exercícios resolvidos

1. Um colega troca removalPolicy para DESTROY “para limpar o ambiente de testes”. Há algum risco se esse código for o de produção?

Ver resposta

Resposta: sim. Com DESTROY, remover a pilha apaga o bucket e a documentação publicada, e o cdk diff mostra isso como remoção. A prática segura é separar as pilhas por ambiente e usar DESTROY apenas em staging, com o diff revisado.

2. Ao alterar o nome lógico do bucket ('DocsBucket' para 'DocsBucket2'), o diff mostra substituição. Por quê?

Ver resposta

Resposta: o identificador lógico faz parte do nome do recurso no template. O CloudFormation trata um novo identificador como um recurso diferente: cria o novo e remove o antigo. Com RETAIN, o bucket antigo permanece, mas o ideal é não renomear identificadores de recursos com dados.

Exercícios propostos

  1. Crie duas stacks, DocsStaging e DocsProducao, a partir da mesma classe, com domínios diferentes passados por props.
  2. Rode cdk synth e localize, em cdk.out/, o recurso AWS::CloudFront::Distribution. Identifique onde está a referência ao OAC.
  3. Altere o cachePolicy para um valor de sua escolha e descreva o resultado esperado no cdk diff.

Ponte para a certificação AWS

O CloudFormation é o motor por trás do CDK, e ele aparece nas provas como serviço de implantação e de infraestrutura. Nas provas de SAA-C03 e DVA-C03, o foco é entender templates, pilhas e dependências entre recursos, mais do que escrever código. O CDK em si não tem uma questão dedicada; use-o para consolidar o conceito de template e pilha. Confira os guias oficiais para o escopo vigente.

Teste seus conhecimentos

O que cdk synth faz?

Correto. O synth só gera o template; quem cria os recursos é o deploy, via CloudFormation.

Qual comando mostra as mudanças antes de aplicá-las?

Correto. O diff compara o template gerado com a pilha atual e mostra criações, alterações e remoções.

Por que usar RemovalPolicy.RETAIN em um bucket com a documentação publicada?

Correto. Com RETAIN, o recurso permanece quando a pilha é removida, evitando perda de dados.

O que levar desta página

  • App contém Stacks; Stack é a unidade de deploy; Constructs são os recursos.
  • L2 traz padrões seguros (como o OAC); L1 é a tradução direta do CloudFormation.
  • synth gera; diff revisa; deploy aplica.
  • Proteja dados com RETAIN e separe ambientes em stacks diferentes.
