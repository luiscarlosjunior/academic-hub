Tópico 3 · Componentes, acessibilidade e Storybook

Um componente é o contrato entre o design e o código: ele expõe propriedades para variar, estados previsíveis e um comportamento que funciona com teclado e leitores de tela. Quando o componente é bem feito, o produto herda acessibilidade de graça. Quando é mal feito, cada time precisa reinventar a correção, e o erro se repete em todo o portfólio.

Objetivos desta página. Ao final, você deve conseguir:

  • projetar a API de um componente com variantes, tamanhos e estados;
  • verificar contraste e foco com os critérios do WCAG 2.2 de nível AA;
  • documentar o componente como história no Storybook;
  • automatizar a checagem de acessibilidade no pipeline com axe-core.

Teoria: contrato, princípios WCAG e papéis ARIA

As diretrizes WCAG 2.2 (W3C, 2023) se organizam em quatro princípios, lembrados pela sigla POUR: conteúdo perceptível, operável, compreensível e robusto. A conformidade comum exigida em editais e na indústria é o nível AA. Para componentes, os critérios mais frequentes são:

  • 1.4.3 Contraste mínimo: texto normal com razão de 4,5:1; texto grande com 3:1.
  • 1.4.11 Contraste não textual: bordas e ícones essenciais com 3:1.
  • 2.4.7 Foco visível e 2.4.11 Foco não obscurecido (novo no 2.2): o foco nunca some atrás de um cabeçalho fixo.
  • 2.5.8 Tamanho mínimo do alvo: 24 × 24 px no mínimo para controles.
  • 4.1.2 Nome, função e valor: o componente informa ao leitor de tela o que é e em que estado está.

Para os padrões de interação, o WAI-ARIA Authoring Practices Guide do W3C descreve como montar caixas de diálogo, abas, menus e combobox com teclado. Use a semântica HTML antes de ARIA: um <button> já tem papel, foco e ativação com Enter e Espaço. ARIA só complementa o que o HTML não oferece.

Operação 1 · Projetar a API do componente

A API tem três ideias. Variantes são opções fechadas (primaria, secundaria), para que o time não invente estilos fora do sistema. Tamanhos seguem a mesma lógica. Estados como carregando e desabilitado viram propriedades, não classes improvisadas. Por fim, o componente repassa os atributos HTML e a referência, porque o consumidor sempre vai precisar de algo a mais.

Em TypeScript (React) · Button.tsx

import { forwardRef, type ButtonHTMLAttributes } from 'react';

type Variante = 'primaria' | 'secundaria' | 'perigo';
type Tamanho = 'sm' | 'md';

export interface ButtonProps extends ButtonHTMLAttributes<HTMLButtonElement> {
  variante?: Variante;
  tamanho?: Tamanho;
  carregando?: boolean;
}

export const Button = forwardRef<HTMLButtonElement, ButtonProps>(
  ({ variante = 'primaria', tamanho = 'md', carregando = false, disabled, children, ...rest }, ref) => (
    <button
      ref={ref}
      type="button"
      data-variante={variante}
      data-tamanho={tamanho}
      aria-busy={carregando || undefined}
      disabled={disabled || carregando}
      {...rest}
    >
      {children}
    </button>
  )
);

Observe aria-busy: ele só aparece quando carregando é verdadeiro, e assim o leitor de tela anuncia que a ação está em andamento. O disabled impede o clique, mas um botão com aria-disabled seria a escolha para manter o elemento focável, dependendo do caso.

Operação 2 · Calcular o contraste

A razão de contraste compara a luminância relativa de duas cores: (L maior + 0,05) / (L menor + 0,05). Cada canal RGB é linearizado antes de ser ponderado. Por isso, o cinza claro parece legível e reprova: a percepção humana não é linear. Use o seletor para trocar entre texto normal e texto grande e veja quais pares passam.

Operação 3 · Foco visível com tokens

Um dos erros mais comuns é remover o contorno do foco por estética. O correto é estilizá-lo com :focus-visible, que aparece para teclado e não para clique do mouse, e tratá-lo como um token, para que o tema escuro também tenha foco legível.

Em CSS · button.css

.btn {
  min-height: 24px;                 /* 2.5.8: alvo mínimo */
  padding: var(--space-2) var(--space-4);
  border-radius: var(--radius-md);
}

.btn:focus-visible {
  outline: 3px solid var(--color-focus);   /* token, não cor fixa */
  outline-offset: 2px;
}

.btn[data-variante='primaria'] {
  background: var(--color-action-primary);
  color: var(--color-on-action);           /* par já validado no contraste */
}

Note que a cor de texto do botão é um token (--color-on-action), e não um branco fixo. Isso permite validar o par de contraste uma única vez, no arquivo de tokens, e não em cada componente.

Operação 4 · Documentação viva e teste automatizado

O Storybook renderiza cada componente isolado, com os estados possíveis como histórias. Ele também é o site de documentação que vai para o S3 (tópico 4). O addon de acessibilidade roda o axe-core em cada história, e um teste de ponta a ponta pode falhar o pipeline se aparecer uma violação.

Em TypeScript · Button.stories.tsx

import type { Meta, StoryObj } from '@storybook/react';
import { Button } from './Button';

const meta: Meta<typeof Button> = {
  title: 'Componentes/Button',
  component: Button,
  tags: ['autodocs'],
  parameters: { a11y: { test: 'error' } },
};
export default meta;

type Story = StoryObj<typeof Button>;

export const Primaria: Story = { args: { children: 'Confirmar' } };
export const Carregando: Story = { args: { children: 'Salvando', carregando: true } };

Em TypeScript · button.a11y.spec.ts (Playwright + axe)

import { test, expect } from '@playwright/test';
import AxeBuilder from '@axe-core/playwright';

test('botão primário não tem violações WCAG 2.2 AA', async ({ page }) => {
  await page.goto('http://localhost:6006/iframe.html?id=componentes-button--primaria&viewMode=story');
  const resultado = await new AxeBuilder({ page })
    .withTags(['wcag2a', 'wcag2aa', 'wcag22aa'])
    .analyze();
  expect(resultado.violations).toEqual([]);
});

O axe-core encontra apenas parte dos problemas de acessibilidade. Ordem lógica de foco, textos alternativos com sentido e clareza de linguagem exigem teste manual com teclado e leitor de tela. Por isso, a automação é um piso, não um atestado de conformidade.

Práticas do mercado

  • Acessibilidade como critério de aceite: o componente só entra na biblioteca com história no Storybook, teste axe e checagem de teclado.
  • Declaração de acessibilidade por componente: o Carbon (IBM) e o Primer (GitHub) documentam o comportamento de teclado e ARIA de cada peça.
  • Testes visuais junto dos de acessibilidade: uma captura por história, comparada a cada alteração (tópico 6).
  • Revisão com pessoas usuárias: testes com leitores de tela (NVDA, VoiceOver, TalkBack) completam a automação.

Mais exemplos comentados

Três padrões de acessibilidade aparecem em quase todo formulário e diálogo: campo com erro anunciado, diálogo com foco preso e uma prova automatizada desse comportamento.

Exemplo 1 · Campo com rótulo e erro anunciado

Um campo precisa de três ligações para funcionar com leitor de tela. O label aponta para o campo pelo id. aria-invalid informa que o valor está errado. aria-describedby liga a mensagem de erro ao campo, para que o leitor a leia junto. A mensagem usa role="alert" para ser anunciada quando aparece.

Em TypeScript (React) · Campo.tsx

import type { InputHTMLAttributes } from 'react';

type CampoProps = {
  id: string;
  rotulo: string;
  erro?: string;
} & Omit<InputHTMLAttributes<HTMLInputElement>, 'id'>;

export function Campo({ id, rotulo, erro, ...rest }: CampoProps) {
  const erroId = id + '-erro';
  return (
    <div>
      <label htmlFor={id}>{rotulo}</label>
      <input
        id={id}
        aria-invalid={erro ? true : undefined}
        aria-describedby={erro ? erroId : undefined}
        {...rest}
      />
      {erro && <p id={erroId} role="alert">{erro}</p>}
    </div>
  );
}

Por que funciona: o aria-invalid só aparece quando há erro, porque undefined não gera atributo no HTML. Assim, o leitor de tela não anuncia “inválido” em campos que ainda não foram preenchidos. Note também que o rótulo não é substituído pelo placeholder: o placeholder desaparece ao digitar, e o rótulo precisa continuar visível.

Exemplo 2 · Diálogo com foco preso

Um diálogo modal precisa manter o foco dentro dele enquanto estiver aberto. Sem isso, a tecla Tab leva o usuário para trás do diálogo, para elementos que ele não está vendo. O código abaixo faz o foco circular entre o primeiro e o último elemento focável.

Em JavaScript · prender-foco.js

const FOCAVEIS = 'a[href], button:not([disabled]), input:not([disabled]), [tabindex]:not([tabindex="-1"])';

function prenderFoco(dialogo) {
  dialogo.addEventListener('keydown', (e) => {
    if (e.key !== 'Tab') return;
    const itens = dialogo.querySelectorAll(FOCAVEIS);
    const primeiro = itens[0];
    const ultimo = itens[itens.length - 1];

    if (e.shiftKey && document.activeElement === primeiro) {
      e.preventDefault();
      ultimo.focus();
    } else if (!e.shiftKey && document.activeElement === ultimo) {
      e.preventDefault();
      primeiro.focus();
    }
  });
}

Por que funciona: o código só intercepta a tecla Tab nas pontas da lista. No meio, o navegador move o foco normalmente. Lembre também do que o código não faz: ele não fecha o diálogo com Escape nem devolve o foco ao botão que o abriu. Esses dois comportamentos completam o padrão. Em projetos novos, o elemento nativo <dialog> com showModal() já faz o trabalho de prender o foco e restaurá-lo, e costuma ser a escolha mais simples.

Exemplo 3 · Provando o erro com um teste automático

A melhor forma de garantir que o campo anuncia o erro é um teste que renderiza o estado de erro e roda o axe. O teste abaixo usa uma história do Storybook com a mensagem já preenchida. Ele falha se o rótulo sumir ou se a mensagem não estiver associada ao campo.

Em TypeScript · campo.a11y.spec.ts

import { test, expect } from '@playwright/test';
import AxeBuilder from '@axe-core/playwright';

test('campo com erro mantém rótulo e mensagem associada', async ({ page }) => {
  await page.goto('http://localhost:6006/iframe.html?id=componentes-campo--com-erro&viewMode=story');

  const resultado = await new AxeBuilder({ page }).withTags(['wcag2a', 'wcag2aa']).analyze();
  expect(resultado.violations).toEqual([]);

  const campo = page.getByLabel('E-mail');
  await expect(campo).toHaveAttribute('aria-invalid', 'true');
  await expect(campo).toHaveAccessibleDescription('Informe um e-mail válido.');
});

Por que funciona: o axe verifica as regras gerais, e as duas últimas linhas verificam o que é específico deste componente. getByLabel só encontra o campo se o rótulo estiver associado a ele. Essa separação é útil: a automação cobre o que é verificável, e o teste manual com leitor de tela cobre a qualidade da frase de erro.

Exercícios resolvidos

1. Um texto cinza #94a3b8 sobre fundo branco é usado num rótulo de 14 px normal. Ele passa no critério AA?

Ver resposta

Resposta: não. O texto é normal (14 px sem negrito não chega a 18,66 px), então exige 4,5:1. A razão de #94a3b8 sobre branco fica abaixo de 3:1, e a animação mostra o mesmo resultado. A correção é escurecer o token de texto secundário, não o componente.

2. Por que <button> é preferível a <div role="button">?

Ver resposta

Resposta: o botão nativo já é focável, responde a Enter e Espaço, e expõe papel e estado ao leitor de tela. Com div, cada um desses comportamentos precisa ser reimplementado com tabindex e eventos de teclado, e quase sempre algo fica de fora.

Exercícios propostos

  1. Implemente um componente Badge com três variantes e verifique o contraste de cada par com a animação desta página.
  2. Escreva a história Carregando de um campo de texto e confirme, com o addon de acessibilidade, se o rótulo está associado ao campo.
  3. Navegue por um menu de abas usando somente o teclado, comparando o comportamento com o padrão de abas da APG do W3C.

Ponte para a certificação AWS

Acessibilidade não é tema das provas AWS. O ponto de contato é a entrega: o site de documentação é um serviço em produção, e a prova DVA-C03 cobre implantação, observabilidade e configuração de aplicações. Um componente que quebra o teclado é um incidente de produto, e o pipeline do tópico 6 é o lugar de impedi-lo.

Teste seus conhecimentos

Qual é a razão mínima de contraste para texto normal no critério AA do WCAG 2.2?

Correto. Texto normal exige 4,5:1 no AA; 7:1 é o nível AAA. Texto grande exige 3:1.

Qual seletor CSS deve estilizar o foco para não aparecer no clique do mouse?

Correto. :focus-visible mostra o foco para navegação por teclado e evita o contorno em cliques.

Qual afirmação sobre axe-core é correta?

Correto. A automação encontra uma parte das violações; o restante exige revisão humana.

O que levar desta página

  • Componente é contrato: variantes fechadas, estados como propriedades e repasse de atributos.
  • Contraste: 4,5:1 para texto normal, 3:1 para texto grande, pelo WCAG 2.2 AA.
  • Use HTML semântico antes de ARIA; :focus-visible para o foco.
  • Storybook documenta e o axe-core automatiza; nenhum dos dois substitui o teste com pessoas.
