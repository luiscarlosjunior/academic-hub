Tópico 11 · Armazenamento e bancos de dados

Quase todo sistema guarda alguma coisa: arquivos, registros, métricas, histórico de versões. A escolha do armazenamento define o custo, a velocidade e o que acontece quando algo falha. Um erro comum é usar o banco relacional para tudo, ou guardar arquivos grandes no banco. Este tópico ensina a escolher a ferramenta a partir do padrão de acesso, que é a pergunta que deve vir antes de qualquer decisão.

Objetivos desta página. Ao final, você deve conseguir:

  • escolher a classe de armazenamento do S3 e configurar ciclo de vida com versionamento;
  • modelar uma tabela DynamoDB a partir dos padrões de acesso, e não das entidades;
  • diferenciar Multi-AZ de réplica de leitura no RDS, com o efeito de cada uma sobre disponibilidade e latência;
  • configurar backup e recuperação pontual, e saber o que eles não protegem.

Teoria: a pergunta que decide a escolha

Antes de escolher um serviço, responda quatro perguntas: como o dado é acessado (por chave, por consulta, por arquivo inteiro), com que frequência, qual é o tamanho e quanto tempo de atraso é aceitável. O S3 guarda objetos inteiros e é ótimo para arquivos e documentos. O DynamoDB responde a acessos por chave em latência baixa e previsível. O RDS oferece SQL, junções e transações entre tabelas, ao custo de administração e de escala vertical, mesmo com recursos gerenciados.

Essas diferenças têm consequência direta no desenho. No DynamoDB, a modelagem começa pela lista de padrões de acesso. Cada consulta necessária vira uma combinação de chave de partição e de ordenação, e as consultas que não cabem nessas chaves exigem um índice secundário global (GSI). Num banco relacional, a modelagem começa pelas entidades e pela normalização, e as consultas se adaptam ao modelo, com índices criados depois.

A disponibilidade tem duas dimensões separadas. Durabilidade é a chance de o dado não se perder; o S3 é projetado para 99,999999999% de durabilidade anual de objetos. Disponibilidade é a chance de o serviço responder agora. Replicação protege a disponibilidade, mas não substitui backup: se um comando apaga dados, a réplica apaga também.

ServiçoPadrão de acesso idealCobrança principalLimite a conhecer
S3Objetos inteiros, leitura e escrita por chave de caminhoArmazenamento por GB e requisiçõesNão há consulta com filtros; é preciso indexar em outro lugar
DynamoDBAcesso por chave de partição e ordenaçãoLeituras e escritas, ou capacidade provisionadaConsultas fora das chaves exigem GSI, que tem custo próprio
RDSSQL com junções e transaçõesInstância por hora e armazenamentoEscala vertical na escrita; réplicas de leitura ajudam só na leitura

Animação do conceito

Classes de armazenamento: custo de guardar versus custo de acesso. Avance pelos quadros: cada um destaca a parte do conceito explicada na legenda.

Operação 1 · Classes do S3 e ciclo de vida

As classes do S3 trocam custo de armazenamento por custo de acesso. A classe Standard é para dados acessados com frequência. As classes de acesso infrequente são mais baratas para guardar, mas cobram por recuperação e têm duração mínima de cobrança. As classes de arquivamento custam centavos por GB, mas a recuperação leva minutos a horas. A regra prática: se você não sabe quando um objeto será lido, deixe a regra de ciclo de vida decidir, e não a memória de quem configurou.

O versionamento guarda cada versão de um objeto. Ele protege contra sobrescrita e exclusão acidental, mas cria custo com versões antigas. Por isso, ele anda junto com uma regra que expira versões não atuais depois de um prazo. O conjunto das duas regras é a configuração que se espera em qualquer bucket de documentação.

Em JSON · regras de ciclo de vida

{
  "Rules": [
    {
      "ID": "arquivar-builds-antigos",
      "Status": "Enabled",
      "Filter": { "Prefix": "builds/" },
      "Transitions": [
        { "Days": 30, "StorageClass": "STANDARD_IA" },
        { "Days": 180, "StorageClass": "GLACIER_IR" }
      ],
      "Expiration": { "Days": 730 }
    },
    {
      "ID": "limpar-versoes-antigas",
      "Status": "Enabled",
      "Filter": {},
      "NoncurrentVersionExpiration": { "NoncurrentDays": 90 }
    }
  ]
}

Em Bash · aplicando as regras

aws s3api put-bucket-versioning \
  --bucket ds-docs-producao \
  --versioning-configuration Status=Enabled

aws s3api put-bucket-lifecycle-configuration \
  --bucket ds-docs-producao \
  --lifecycle-configuration file://ciclo-de-vida.json

Por que funciona: a primeira regra move builds antigos para classes mais baratas e os apaga após dois anos. A segunda limpa versões não atuais após 90 dias. Repare que a regra de versões se aplica a todo o bucket (Filter: {}), porque o acúmulo de versões acontece em qualquer prefixo. Antes de aplicar uma expiração, confirme com a equipe que o prazo está de acordo com qualquer exigência de retenção.

Operação 2 · Modelar pelo padrão de acesso

Imagine que o design system precisa guardar o uso de cada componente por produto. Os padrões de acesso são: listar os produtos que usam um componente, e listar os componentes que um produto usa. Com uma tabela e duas chaves, cada padrão vira uma consulta direta. A tabela abaixo usa a chave de partição pk e a de ordenação sk, e grava o mesmo fato em duas direções.

pkskAtributosPadrão atendido
COMP#buttonPROD#lojaversao: 1.4.3Produtos que usam um componente
PROD#lojaCOMP#buttonversao: 1.4.3Componentes usados por um produto
PROD#lojaCOMP#cardversao: 1.5.0Consulta direta de um par

Em TypeScript (CDK) · tabela com recuperação pontual

import * as dynamodb from 'aws-cdk-lib/aws-dynamodb';

const tabela = new dynamodb.Table(this, 'UsoComponentes', {
  partitionKey: { name: 'pk', type: dynamodb.AttributeType.STRING },
  sortKey: { name: 'sk', type: dynamodb.AttributeType.STRING },
  billingMode: dynamodb.BillingMode.PAY_PER_REQUEST,
  pointInTimeRecoverySpecification: { pointInTimeRecoveryEnabled: true },
  deletionProtection: true,
  removalPolicy: cdk.RemovalPolicy.RETAIN,
});

Em TypeScript · consulta com o SDK v3

import { DynamoDBClient } from '@aws-sdk/client-dynamodb';
import { DynamoDBDocumentClient, QueryCommand } from '@aws-sdk/lib-dynamodb';

const doc = DynamoDBDocumentClient.from(new DynamoDBClient({ region: 'sa-east-1' }));

export async function produtosQueUsam(componente: string) {
  const resposta = await doc.send(new QueryCommand({
    TableName: 'UsoComponentes',
    KeyConditionExpression: 'pk = :p AND begins_with(sk, :prefixo)',
    ExpressionAttributeValues: { ':p': 'COMP#' + componente, ':prefixo': 'PROD#' },
  }));
  return resposta.Items ?? [];
}

Por que funciona: a consulta usa a chave de partição (igualdade) e um prefixo na ordenação. O DynamoDB lê só os itens daquela partição, por isso o custo e a latência não crescem com o tamanho total da tabela. O deletionProtection e a removalPolicy: RETAIN protegem contra exclusão acidental, e a recuperação pontual permite voltar a um momento dos últimos 35 dias, desde que ela esteja ativa antes do incidente.

Operação 3 · Multi-AZ, réplica de leitura e backup

São três recursos com nomes parecidos e objetivos diferentes. A implantação Multi-AZ mantém um standby síncrono em outra zona, e o failover é automático: ele serve para disponibilidade, e o standby não atende leituras comuns. A réplica de leitura recebe a replicação de forma assíncrona e serve para escalar leituras; se o primário falha, a réplica não assume automaticamente. O backup guarda o estado no tempo, e serve para recuperar dados apagados ou corrompidos, algo que replicação nenhuma faz.

RecursoProtege contraNão protege contraReplicação
Multi-AZFalha de zona ou da instânciaComando que apaga dadosSíncrona, standby não legível
Réplica de leituraGargalo de leituraFalha do primário (não é promovida sozinha)Assíncrona, pode estar atrás
Backup e recuperação pontualExclusão e corrupção de dadosPerda de disponibilidade da instânciaNão é replicação

Animação: falha do primário e failover Multi-AZ

Escolha o cenário. Na falha, o standby assume o papel de primário e a aplicação volta a escrever pelo mesmo endpoint.

Em TypeScript (CDK) · banco com Multi-AZ e backup

import * as rds from 'aws-cdk-lib/aws-rds';
import * as ec2 from 'aws-cdk-lib/aws-ec2';

const banco = new rds.DatabaseInstance(this, 'Banco', {
  engine: rds.DatabaseInstanceEngine.postgres({ version: rds.PostgresEngineVersion.VER_16 }),
  instanceType: ec2.InstanceType.of(ec2.InstanceClass.T4G, ec2.InstanceSize.MEDIUM),
  vpc,
  vpcSubnets: { subnetType: ec2.SubnetType.PRIVATE_ISOLATED },
  multiAz: true,
  storageEncrypted: true,
  backupRetention: cdk.Duration.days(14),
  deletionProtection: true,
  removalPolicy: cdk.RemovalPolicy.SNAPSHOT,
});

Por que funciona: o banco fica na sub-rede isolada (tópico 10), criptografado, com retenção de backup de 14 dias e proteção contra exclusão. O removalPolicy: SNAPSHOT cria um snapshot final se a pilha for removida, o que evita perda definitiva. Os valores de versão e classe de instância mudam com o tempo; confirme os disponíveis na região antes do deploy.

Mais exemplos comentados

Os dois exemplos mostram decisões que aparecem em projetos reais: quando o DynamoDB não é a escolha certa, e como estimar o custo de uma regra de ciclo de vida.

Exemplo 1 · Quando o DynamoDB não é a escolha certa

Suponha que a equipe queira um relatório com filtros livres: “componentes usados em mais de três produtos, com versão anterior à 1.4, agrupados por time”. Essa consulta cruza atributos que não fazem parte das chaves. No DynamoDB, cada combinação exigiria um GSI ou uma varredura da tabela inteira. No RDS, a mesma consulta é uma junção com filtro e agregação, escrita em SQL. A regra é simples: se as consultas são previsíveis e por chave, use DynamoDB; se são exploratórias e cruzam dados, use banco relacional, ou um armazenamento analítico.

Em SQL · consulta que o DynamoDB faria mal

SELECT c.nome, p.time, COUNT(u.produto_id) AS produtos
FROM componentes c
JOIN uso u ON u.componente_id = c.id
JOIN produtos p ON p.id = u.produto_id
WHERE c.versao < '1.4.0'
GROUP BY c.nome, p.time
HAVING COUNT(u.produto_id) > 3
ORDER BY produtos DESC;

Por que funciona: o SQL expressa a consulta sem que o modelo precise prever todas as combinações. O custo é outro: o banco precisa de capacidade para executar a agregação, e essa carga não deve competir com a aplicação. Por isso, relatórios costumam rodar numa réplica de leitura, que é exatamente o caso de uso dela.

Exemplo 2 · Estimando o efeito de uma regra de ciclo de vida

Uma regra de transição parece barata, mas o custo depende do tamanho dos objetos e do tempo de permanência. A conta abaixo compara manter 500 GB em Standard com movimentar esses objetos para uma classe de acesso infrequente após 30 dias. Use os preços da calculadora oficial da sua região; a estrutura do cálculo é a parte que se aplica em qualquer cenário.

PassoComo calcular
Custo mensal em Standard500 GB × preço Standard por GB-mês
Custo em IA, se nenhum objeto for lido500 GB × preço IA por GB-mês, mais o custo de cada transição
Custo de recuperaçãoGB lidos × preço de recuperação. Se o objeto for lido todo mês, a IA pode custar mais que a Standard
Duração mínimaObjetos apagados antes do prazo mínimo da classe são cobrados como se tivessem ficado o prazo inteiro

Por que funciona: o erro mais comum é transicionar para uma classe barata um dado que é lido com frequência. O custo de recuperação passa a dominar a conta. Antes de criar a regra, consulte as métricas de acesso do bucket, ou use a classe Intelligent-Tiering, que move objetos sozinha conforme o uso.

Práticas do mercado

  • Migrações com expansão e contração: mudanças de esquema em bancos relacionais adicionam colunas antes de usá-las e removem as antigas depois, em versões separadas do software.
  • Backup testado: restaurar um backup em conta separada, uma vez por trimestre, é o único jeito de saber que ele funciona.
  • Criptografia e chaves gerenciadas: KMS com chaves por aplicação, e não uma chave única para tudo.
  • Custo visível por recurso: tags de alocação de custo em cada bucket e tabela permitem ver quem gera a conta.

Exercícios resolvidos

1. Um time propõe usar uma réplica de leitura como plano de alta disponibilidade. Qual é a objeção?

Ver resposta

Resposta: a réplica de leitura não é promovida automaticamente quando o primário falha; a promoção é manual, e a réplica pode estar alguns instantes atrás. Para disponibilidade com failover automático, a escolha é a implantação Multi-AZ. A réplica continua útil para escalar leituras.

2. Alguém apagou, sem querer, todos os itens de uma tabela DynamoDB que tem replicação global e recuperação pontual ativa. Dá para recuperar?

Ver resposta

Resposta: a recuperação pontual permite restaurar a tabela para um momento dos últimos 35 dias, anterior à exclusão, e isso só funciona se ela estava ativa. A replicação global não ajuda aqui, porque ela copia a exclusão para as outras regiões. A lição é a mesma do tópico: replicação protege disponibilidade, e backup protege contra erro humano.

Teste seus conhecimentos

Uma empresa precisa de failover automático de um banco relacional se uma zona cair. Qual recurso atende?

Correto. Multi-AZ mantém um standby síncrono e faz o failover automaticamente. A réplica de leitura não é promovida sozinha.

Uma tabela DynamoDB é consultada sempre pelo identificador do produto. Qual deve ser a chave de partição?

Correto. A chave de partição deve ser a de maior cardinalidade usada em consultas por igualdade. Booleanos concentram itens em duas partições e causam hot partition.

Um objeto no S3 é lido todo dia. Qual classe evita custo desnecessário de recuperação?

Correto. Dados lidos diariamente pagam caro para recuperar em classes de acesso infrequente ou de arquivamento. A Standard é a adequada para acesso frequente.

O que levar desta página

  • Escolha o armazenamento pelo padrão de acesso, e não pelo hábito.
  • S3: escolha a classe pelo acesso e configure versionamento com expiração de versões antigas.
  • DynamoDB: modele pelas consultas; chave de partição por igualdade; GSI tem custo próprio.
  • Multi-AZ dá disponibilidade; réplica dá leitura; backup dá recuperação. Nenhum substitui os outros.
