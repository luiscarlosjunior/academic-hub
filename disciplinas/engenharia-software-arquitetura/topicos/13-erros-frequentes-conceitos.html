Visão geral

Quase todo programador passa mais tempo lendo erros do que escrevendo código novo. A diferença entre quem avança rápido e quem fica preso costuma estar em reconhecer um erro conhecido em segundos. Esta página reúne os erros que aparecem com mais frequência em fóruns, em estudos com iniciantes e em relatos de produção, e para cada um mostra o sintoma (o que você vê), a causa provável e a correção padrão.

Também reunimos os conceitos que mais aparecem no trabalho diário, como ambiente virtual, variável de ambiente, status HTTP e fuso horário, com o que fazer quando eles dão problema. No fim, há um método para investigar qualquer erro que não esteja nesta lista.

Sobre as fontes. Nem todo item tem o mesmo grau de evidência, e a página indica isso. Há dados medidos (projetos com milhões de compilações de alunos, levantamentos de incidentes em nuvem e o OWASP Top 10), análises de guias e tutoriais, e experiência de prática. Não encontramos um ranking oficial de perguntas do Stack Overflow por tipo de erro; por isso, a “frequência” de cada item é uma estimativa qualitativa, não uma contagem.

Objetivos desta página. Ao final, você deve conseguir:

  • reconhecer os erros mais comuns de Python e explicar a causa de cada um;
  • identificar erros de lógica, de precisão numérica, de codificação e de concorrência;
  • corrigir os problemas típicos de banco de dados, de Git e de segurança;
  • usar um método de investigação em quatro passos para qualquer erro novo;
  • pesquisar e pedir ajuda de forma eficiente, com um exemplo mínimo reproduzível.

Teoria · O que os dados dizem sobre iniciantes

O projeto BlueJ Blackbox coletou os erros de compilação de milhões de compilações feitas por estudantes de Java. Uma análise dos dados (Altadmri e Brown, 2015; Pritchard, 2016) encontrou que os três erros mais comuns de iniciantes em Java são:

  1. Parênteses e colchetes desbalanceados, o primeiro da lista.
  2. Chamar um método com argumento de tipo errado.
  3. Método não-void que pode terminar sem retornar valor.

Um dado que surpreende: os erros que mais demoram para ser corrigidos não são necessariamente os mais frequentes. Confundir operadores de curto-circuito (&&, ||) com os bit a bit (&, |) aparece entre os que mais consomem tempo, porque o código compila e roda, mas com resultado diferente do esperado.

Em Python, uma análise de mensagens de erro de programas reais também coloca erros de sintaxe e de nome não definido no topo. Já na prática profissional, os guias e tutoriais convergem em um conjunto menor e bem conhecido: AttributeError causado por None, TypeError, KeyError, IndexError e falhas de importação. Essa convergência é experiência compartilhada, não contagem, e o restante da página parte dela.

Coletânea 1 · Erros de Python, um a um

Para cada erro, a estrutura é a mesma: a mensagem que aparece, a causa, a correção e a prevenção. Leia a mensagem inteira, incluindo o nome do arquivo e a linha indicada no traceback.

1. AttributeError: 'NoneType' object has no attribute ...

Sintoma: o programa para ao chamar um método ou atributo em uma variável. Causa: a variável vale None, geralmente porque uma função “às vezes falha” e devolve None em vez de lançar erro, ou porque o resultado de uma busca não existe. Esse é o erro mais citado em guias de Python. 

def buscar(id_usuario):
    usuarios = {1: "Ana"}
    if id_usuario in usuarios:
        return usuarios[id_usuario]
    # sem return explícito: a função devolve None

nome = buscar(2)
print(nome.upper())   # AttributeError: 'NoneType' object has no attribute 'upper'

# correção: tratar o caso ausente antes de usar
nome = buscar(2)
if nome is None:
    print("usuário não encontrado")
else:
    print(nome.upper())

Prevenção: quando uma função pode não encontrar algo, documente isso e escolha um contrato explícito: devolver None com verificação obrigatória, ou lançar uma exceção específica como UsuarioNaoEncontrado.

2. TypeError

Sintoma: mensagens como unsupported operand type(s), takes 2 positional arguments but 3 were given ou 'NoneType' object is not subscriptable. Causa: uma operação aplicada a tipos incompatíveis, uma função chamada com o número ou o tipo errado de argumentos, ou um valor None sendo indexado. Em estudos com iniciantes em Java, o tipo errado de argumento está entre os erros mais frequentes, e o mesmo padrão aparece em Python. 

idade = input("Idade: ")          # sempre devolve texto (str)
print(idade + 1)                  # TypeError: can only concatenate str (not "int") to str

# correção: converter na borda, uma vez
idade = int(input("Idade: "))
print(idade + 1)

Prevenção: converta os dados de entrada logo na chegada, e use dicas de tipo (type hints) com uma ferramenta como o mypy, que aponta muitos TypeError antes da execução.

3. KeyError

Sintoma: KeyError: 'total'. Causa: acesso com colchetes a uma chave que não existe no dicionário, muitas vezes em dados vindos de uma API ou de um arquivo, em que o campo é opcional. 

pedido = {"id": 7}
print(pedido["total"])            # KeyError: 'total'

# correção: valor padrão quando o campo é opcional
print(pedido.get("total", 0))     # 0

# correção: exigir o campo e falhar com mensagem clara
if "total" not in pedido:
    raise ValueError("pedido sem o campo 'total'")

4. IndexError: list index out of range

Sintoma: o erro aparece ao acessar uma posição de uma lista. Causa: a lista está vazia ou é menor do que o código supõe, ou o índice vai até o tamanho (e não até o tamanho menos um). O off-by-one, tratado na próxima seção, é a causa mais comum. 

notas = []
print(notas[0])                   # IndexError: list index out of range

# correção: verificar antes, ou usar um valor padrão
ultima = notas[-1] if notas else None

5. ModuleNotFoundError: No module named 'requests'

Sintoma: o pacote está “instalado”, mas o Python não o encontra. Causa: quase sempre há dois interpretadores: o pip instalou o pacote em um Python, e o programa roda com outro, geralmente porque o ambiente virtual não está ativado. Também acontece quando o editor usa um interpretador diferente do terminal. 

# descobrir qual Python está rodando e instalar nele
python -m pip install requests
python -c "import sys; print(sys.executable)"   # confira o caminho do interpretador

Prevenção: um ambiente virtual por projeto, com o arquivo de dependências versionado (requirements.txt). Veja o conceito de ambiente virtual mais abaixo.

6. SyntaxError e IndentationError

Sintoma: o programa nem começa. Causa: parênteses, aspas ou dois-pontos esquecidos, ou indentação inconsistente. A linha indicada costuma estar depois do erro real: um parêntese aberto e não fechado faz o analisador reclamar da linha seguinte. 

if (idade > 18
    print("maior")           # SyntaxError: '(' was never closed, na linha anterior

# correção: fechar o parêntese antes de olhar a linha indicada
if (idade > 18):
    print("maior")

7. NameError e a variável errada

Sintoma: NameError: name 'total' is not defined. Causa: erro de digitação no nome, uso de uma variável antes da atribuição, ou uma variável definida dentro de uma função e usada fora dela.

8. Argumento padrão mutável

Sintoma: a lista “vaza” entre chamadas de uma função, sem nenhum erro. Causa: o valor padrão de um parâmetro é avaliado uma única vez, quando a função é definida, e compartilhado entre chamadas. É um dos erros mais surpreendentes de Python. 

def adiciona(item, lista=[]):     # armadilha: uma única lista para todas as chamadas
    lista.append(item)
    return lista

print(adiciona(1))                # [1]
print(adiciona(2))                # [1, 2]  — inesperado

# correção: usar None como sentinela
def adiciona(item, lista=None):
    if lista is None:
        lista = []
    lista.append(item)
    return lista

Coletânea 2 · Erros de lógica: o programa roda, mas está errado

Estes são os erros mais caros, porque nenhuma mensagem aparece. Quem os resolve é quem sabe o que o programa deveria fazer.

  • Off-by-one. O laço vai uma posição além ou fica uma antes. Sintoma: o último elemento é ignorado, ou ocorre IndexError no final. Correção: confira os limites com um caso pequeno, como uma lista de três elementos, e escreva a faixa como range(n), não range(n+1), quando a intenção for percorrer n posições.
  • Confundir atribuição com comparação. Em C, if (x = 5) compila e sempre é verdadeiro (em Java, a condição precisa ser boolean, e o erro é barrado pelo compilador). Em Python, if x = 5: é erro de sintaxe, o que protege, mas o erro lógico continua possível com == invertido ou com operadores errados.
  • Modificar uma lista enquanto percorre. Remover elementos dentro do for pula itens. Correção: percorra uma cópia (for x in lista[:]) ou construa uma nova lista com uma compreensão.
  • Curto-circuito mal entendido. && e || não avaliam o segundo lado quando o resultado já está decidido. Se o segundo lado tem efeito colateral ou pode dar erro, a ordem importa.
  • Comparar texto sem normalizar. "Ana" != "ana", e espaços no fim fazem diferença. Correção: normalize (strip, lower) nos dois lados, na borda do sistema.
  • Fuso horário e data. Comparar uma data local com uma data em UTC, ou assumir que todo dia tem 24 horas, produz erros que aparecem só em certas épocas do ano. Correção: guarde datas em UTC e converta para exibir.
Técnica: para qualquer erro de lógica, escreva um caso de teste com a entrada mais simples possível e o resultado esperado à mão. Se o resultado do programa não bate com a conta feita no papel, o problema está entre os dois. É a mesma ideia do TDD do tópico 11.

Coletânea 3 · Números: ponto flutuante e dinheiro

Sintoma: 0.1 + 0.2 dá 0.30000000000000004, e um saldo de centavos fica com diferenças estranhas. Causa: o tipo float armazena números em binário, e a maioria das frações decimais não tem representação exata nesse formato. O padrão IEEE 754, usado pela quase totalidade das linguagens, é a origem, e não um problema específico do Python. Os erros se acumulam em somas repetidas. 

from decimal import Decimal

print(0.1 + 0.2)                          # 0.30000000000000004
print(Decimal('0.1') + Decimal('0.2'))    # Decimal('0.3')

# armadilha: criar Decimal a partir de float carrega o erro do float
print(Decimal(0.1))                       # uma expansão longa, não 0.1

Como resolver: para valores monetários e contábeis, use Decimal criado a partir de texto (Decimal('19.90')), ou trabalhe em centavos com inteiros. Para comparar floats, use math.isclose, e não ==. A documentação oficial do Python descreve o problema e a solução com detalhes (ver as referências).

Coletânea 4 · Acentos, codificação e UnicodeDecodeError

Sintoma: UnicodeDecodeError: 'utf-8' codec can't decode byte 0xe7 in position 42, ou acentos que viram caracteres estranhos como “Ã§”. Causa: o arquivo foi salvo em uma codificação (com frequência cp1252 ou Latin-1, comum em arquivos do Windows) e lido como UTF-8, ou o contrário. Quando nenhuma codificação é informada, o Python usa a padrão do sistema, que pode mudar de máquina para máquina. 

# lendo: informe sempre a codificação
with open("dados.csv", encoding="utf-8") as f:
    texto = f.read()

# se o arquivo veio de um Excel no Windows, tente:
with open("dados.csv", encoding="cp1252") as f:
    texto = f.read()

# como último recurso, substitui o byte inválido (perde informação!)
with open("dados.csv", encoding="utf-8", errors="replace") as f:
    texto = f.read()

Como resolver: descubra a codificação real do arquivo antes de adivinhar (um editor de texto costuma mostrar isso), e informe-a ao abrir. Use errors="replace" apenas para recuperar dados de forma consciente, porque ele substitui os bytes problemáticos sem avisar. Prevenção: use UTF-8 em tudo e declare a codificação em cada leitura e escrita.

Coletânea 5 · Condições de corrida

Sintoma: o erro some quando o programa roda devagar com um depurador, aparece uma vez em cada várias execuções, e nunca aparece em testes. Dois clientes conseguem reservar o mesmo assento, ou um saldo fica negativo. Causa: uma condição de corrida, em que o resultado depende da ordem em que operações concorrentes se intercalam. O padrão mais comum é o check-then-act: o programa verifica uma condição e age com base nela, mas outra execução muda a condição entre a verificação e a ação. 

import threading

saldo = 100
trava = threading.Lock()

# versão com corrida: duas threads podem ver saldo >= 80 e sacar as duas
def saca_inseguro(valor):
    global saldo
    if saldo >= valor:            # verificação (check)
        saldo -= valor            # ação (act): o saldo pode ter mudado antes daqui

# correção: verificação e ação em um único passo protegido
def saca(valor):
    global saldo
    with trava:
        if saldo >= valor:
            saldo -= valor
            return True
        return False

Como resolver: torne a verificação e a ação uma única operação indivisível, com trava (lock), operação atômica ou transação de banco. Em sistemas com banco, a forma mais segura costuma ser delegar a regra ao banco, com uma atualização condicional (UPDATE ... WHERE saldo >= ?) e verificar quantas linhas foram afetadas.

Corridas são intermitentes por natureza. Não tente “provar” a correção rodando o programa algumas vezes. Raciocine sobre a sequência de operações e teste o caso com threads deliberadamente intercaladas.

Coletânea 6 · Banco de dados: N+1 e injeção de SQL

O problema N+1

Sintoma: a página que lista 10 autores demora um segundo, e a que lista 1.000 demora um minuto, mesmo com consultas simples. O log do banco mostra a mesma consulta repetida com ids diferentes. Causa: uma consulta busca N registros, e depois uma consulta extra é feita para cada um para carregar algo relacionado. Muitos ORMs fazem isso por padrão, de forma silenciosa, ao acessar uma relação dentro de um laço. Com 10 registros, parecem 11 consultas rápidas; com 10.000, são 10.001 consultas. 

# ruim: uma consulta para os autores e uma por autor, ao acessar a relação
autores = session.scalars(select(Autor)).all()
for autor in autores:
    print(autor.nome, len(autor.livros))      # dispara uma consulta por autor

# correção: carregar a relação junto, em uma consulta extra
from sqlalchemy.orm import selectinload
autores = session.scalars(
    select(Autor).options(selectinload(Autor.livros))
).all()

Como resolver: peça a relação de forma explícita, com eager loading (no SQLAlchemy, selectinload; no Django, select_related e prefetch_related; no Rails, includes). Detecção: observe o log de consultas durante o desenvolvimento e conte as consultas de cada página.

Injeção de SQL

Sintoma: uma consulta funciona com nomes comuns e falha, ou devolve dados demais, com entradas como ' OR '1'='1. Causa: a entrada do usuário é montada diretamente no texto da consulta. A injeção aparece na categoria Injection do OWASP Top 10 (ver as referências), que está entre os riscos mais graves da web. 

import sqlite3
conexao = sqlite3.connect("loja.db")
nome = input("Nome do cliente: ")

# vulnerável: o texto digitado vira parte da consulta
conexao.execute(f"SELECT * FROM clientes WHERE nome = '{nome}'")

# correto: consulta parametrizada, o driver trata o valor como dado
conexao.execute("SELECT * FROM clientes WHERE nome = ?", (nome,))

Como resolver: use sempre parâmetros (? ou %s, conforme o driver) e nunca concatene ou formate valores na consulta. Nomes de tabela e de coluna, que não podem ser parâmetros, devem vir de uma lista fixa de valores permitidos.

Coletânea 7 · Erros de Git e como desfazê-los

Os relatos de erros de Git se repetem muito. A boa notícia é que a maioria é recuperável, porque o Git guarda o histórico de referências por um bom tempo. Os casos mais frequentes:

ErroSinalComo desfazer
Commit feito na main por enganoCommit local, ainda não publicadoCrie a branch apontando para o commit atual com git branch feature/x; depois, na main, volte com git reset --hard origin/main (só se o commit ainda não foi publicado)
Commit com arquivos demais ou com um erroCommit local, não publicadogit reset --soft HEAD~1 desfaz o commit e mantém as mudanças
Arquivo apagado sem querergit status mostra “deleted”git restore arquivo
Trabalho perdido após um resetNão aparece no git loggit reflog mostra onde a referência esteve; volte com git reset --hard <id>
Senha ou chave commitadaAparece no históricoTrocar a credencial primeiro; depois remover do histórico com ferramenta própria. Considere o segredo comprometido.
Conflito de mergeMarcadores <<<<<<< no arquivoEscolha o trecho correto, remova os marcadores, git add e git commit

Regras que evitam a maioria dos problemas: crie uma branch antes de começar; faça commits pequenos; nunca use push --force em uma branch compartilhada; e use git stash para guardar trabalho pendente antes de trocar de branch. Os relatos de desenvolvedores também apontam o mesmo padrão: branches com nomes vagos e vividas por semanas, e commits sem vínculo com uma tarefa.

Coletânea 8 · Os riscos mais frequentes na web

O OWASP Top 10, publicado pela Open Worldwide Application Security Project, lista as categorias de risco mais relevantes para aplicações web. A edição de 2021, em ordem, é: controle de acesso quebrado; falhas criptográficas; injeção; design inseguro; configuração insegura; componentes vulneráveis e desatualizados; falhas de identificação e autenticação; falhas de integridade de software e dados; falhas de registro e monitoramento; e falsificação de requisição do lado do servidor (SSRF). O controle de acesso quebrado passou a liderar a lista.

Para um iniciante, quatro erros concentram a maior parte dos problemas:

  • Controle de acesso quebrado. O sistema verifica que o usuário está logado, mas não verifica que ele pode ver aquele registro. Basta trocar o número na URL (/pedidos/42 para /pedidos/43) para ver o pedido de outra pessoa. Correção: verifique a permissão no servidor, para cada recurso, e negue por padrão.
  • Injeção. Descrita na coletânea anterior. Correção: consultas parametrizadas.
  • Segredos no código. Senhas e chaves no repositório ou no código-fonte de um app que vai ao público. Correção: variáveis de ambiente e cofre de segredos, como visto no tópico 10.
  • Dependências desatualizadas. Uma biblioteca com falha conhecida usada sem atualização. Correção: fixar versões, verificar alertas de segurança e atualizar com testes.
Nunca teste vulnerabilidades em sistemas que você não tem autorização para testar. Em aula, use ambientes próprios e de treino.

Coletânea 9 · O que mais causa incidentes em produção

Estudos de incidentes em nuvem mostram um padrão consistente, embora as categorias e as amostras variem. Um estudo sobre incidentes em produção de nuvem (Liu et al., HotOS 2019) e relatos da indústria, como o levantamento da Gremlin, apontam como principais causas mudanças de software (implantações e envios de código ruim) e bugs de software. Em um dos estudos com dados de incidentes do Azure, bugs de software responderam por cerca de 40% dos casos, e erros de configuração apareceram em menor número.

A consequência prática: os erros que mais derrubam sistemas não são exóticos. São uma mudança sem teste, uma configuração errada e uma dependência que mudou de comportamento. É por isso que os tópicos 11 e 12 insistem em testes automatizados, entregas pequenas e reversão ensaiada.

Conceitos do dia a dia e como resolver

Estes são os conceitos que mais aparecem quando um programa sai da sala de aula. Para cada um, o problema típico e a forma de resolver.

Ambiente virtual e dependências

O que é: um espaço isolado com as bibliotecas de um projeto, em versões específicas. Problema típico: “funciona na minha máquina”, porque cada máquina tem versões diferentes. Como resolver: crie um ambiente por projeto (python -m venv .venv), ative-o e registre as dependências com versões em um arquivo versionado (pip freeze > requirements.txt).

Variáveis de ambiente

O que é: valores de configuração definidos fora do código, por exemplo o endereço do banco. Problema típico: KeyError ou None ao ler uma configuração que não foi definida na nova máquina ou no servidor. Como resolver: leia com os.environ.get e um valor padrão seguro, ou falhe cedo com mensagem clara se a configuração for obrigatória.

Status HTTP

O que é: o código de três dígitos que o servidor devolve. Leitura rápida: 2xx significa sucesso (200 OK, 201 Created); 4xx significa que o cliente errou (400 requisição inválida, 401 não autenticado, 403 proibido, 404 não encontrado, 422 dados que não passam na validação); 5xx significa que o servidor falhou (500, erro interno). Como resolver: se o código for 4xx, procure o problema na requisição; se for 5xx, procure nos logs do servidor, porque a causa está do outro lado.

JSON e formatos de dados

O que é: o formato de texto mais usado para trocar dados entre sistemas. Problema típico: a API muda um campo de número para texto, ou um campo opcional some, e o código quebra. Como resolver: valide a estrutura na entrada (o tópico 10 trata disso), trate campos opcionais com get e não assuma tipos sem verificar.

Leitura de um traceback

O que é: a pilha de chamadas exibida quando um erro acontece. Como ler: a última linha diz o tipo e a mensagem do erro. Logo acima, as linhas do seu código mostram onde ele aconteceu. Procure a primeira linha que é código seu, porque as linhas de biblioteca abaixo ou acima costumam ser consequência. Quando a mensagem menciona um valor, pergunte de onde ele veio.

Depuração com ponto de parada

O que é: pausar o programa em uma linha e inspecionar as variáveis. Problema típico: dezenas de print espalhados, esquecidos no código. Como resolver: use um depurador (no Python, breakpoint() ou a depuração do editor) e inspecione o valor real de cada variável no ponto em que o resultado sai do esperado.

Cache

O que é: guardar um resultado para não recalcular. Problema típico: o sistema mostra dado antigo depois de uma alteração. Como resolver: defina um tempo de validade (TTL) e invalide o cache quando o dado mudar. Quando a informação “some” ou “volta”, desconfie do cache antes de desconfiar do código.

Código síncrono e assíncrono

O que é: executar uma tarefa e esperar por ela, ou deixá-la rodando enquanto o programa segue. Problema típico: o resultado ainda não existe quando o código tenta usá-lo, ou o programa fica “travado” esperando uma resposta de rede. Como resolver: confirme quando o resultado está pronto antes de usá-lo, e não bloqueie a interface com operações de rede ou de disco longas.

Método · Como investigar um erro novo

Quando o erro não está na lista, siga quatro passos, nessa ordem:

  1. Leia a mensagem inteira. O tipo do erro, o texto, o arquivo e a linha. A maior parte das respostas está ali.
  2. Reproduza o erro com o caso mínimo. Reduza a entrada e o código até o menor exemplo que ainda falha. Esse passo sozinho resolve muitos problemas, porque o caso pequeno mostra o que importa.
  3. Forme uma hipótese e teste uma coisa de cada vez. “Acho que usuario é None aqui”. Confirme com um print ou um ponto de parada, e só depois mude o código.
  4. Pesquise com a mensagem exata. Copie o texto do erro entre aspas, sem o nome do seu arquivo, e pesquise. Os resultados costumam trazer a causa comum.

Como pedir ajuda com eficiência. Quem vai responder precisa de três coisas: a mensagem de erro completa, o código mínimo que reproduz o problema e o que você já tentou. Pergunte com um exemplo pequeno, e não com o projeto inteiro. Uma pergunta bem feita é respondida mais rápido, e também ensina quem pergunta a pensar no problema.

Antes de pesquisar, confira três coisas que causam a maioria dos erros “impossíveis”: o ambiente virtual está ativo, o arquivo salvo é o que você está executando e o editor está usando o mesmo interpretador do terminal.

Teste seus conhecimentos

O código print(usuario.upper()) falha com 'NoneType' object has no attribute 'upper'. Qual é a causa mais provável?

Correto. A mensagem diz o tipo do objeto: NoneType é o tipo de None. A pergunta seguinte é de onde ele veio.

Um saldo é verificado e depois debitado, em duas threads. Às vezes o saldo fica negativo, mas nunca nos testes. O que fazer?

Correto. É uma condição de corrida do tipo check-then-act. Rodar mais testes não a prova nem a elimina; a correção é tornar o par verificação-ação indivisível.

O que levar desta página

  • A maioria dos erros de iniciante tem um padrão conhecido. Reconhecer o padrão economiza horas.
  • Erros de lógica não têm mensagem. Use um caso mínimo e confira a conta à mão.
  • Dinheiro não se representa com float. Codificação se declara. Condições de corrida se eliminam, não se testam.
  • Consultas se parametrizam, relações se carregam juntas e permissões se verificam no servidor.
  • Diante de um erro novo: leia a mensagem inteira, reproduza no caso mínimo, teste uma hipótese por vez e pesquise o texto exato.
