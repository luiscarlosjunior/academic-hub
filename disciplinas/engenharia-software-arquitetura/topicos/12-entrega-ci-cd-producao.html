Visão geral

Entregar software é o momento em que todo o trabalho anterior encontra o mundo real. Em muitas equipes, esse momento é um evento raro, tenso e manual: alguém copia arquivos para um servidor numa sexta à noite, reza para que nada quebre e volta para casa torcendo. A entrega contínua transforma esse evento em uma rotina pequena, automática e repetível, que pode acontecer várias vezes por dia.

Esta página fecha a trilha de Programação para a Indústria. Ela mostra como uma pipeline de integração e entrega verifica cada mudança, como os containers tornam o ambiente previsível, como estratégias de implantação reduzem o risco e o que a equipe deve entender por “pronto para produção”.

Objetivos desta página. Ao final, você deve conseguir:

  • descrever as etapas de uma pipeline de CI/CD e o papel de cada portão de qualidade;
  • escrever um fluxo de integração contínua simples com testes e análise estática;
  • explicar o que um container garante e o que não garante;
  • comparar estratégias de implantação e escolher uma de acordo com o risco;
  • usar uma lista de “pronto para produção” para decidir quando uma mudança pode ser entregue.

Teoria · Integração contínua, entrega contínua e implantação contínua

Humble e Farley (2010) organizaram esses conceitos em torno de um princípio: cada mudança deve passar por um caminho automatizado até a produção, e qualquer etapa que falhe interrompe o caminho. Os três termos se distinguem pelo último passo:

  • Integração contínua (CI): cada mudança é integrada à linha principal e verificada automaticamente, com build, testes e análise. O objetivo é descobrir problemas de integração em minutos, não em semanas.
  • Entrega contínua (CD): o software está sempre em um estado pronto para ser implantado, mas a implantação em produção pode exigir uma decisão humana, como a aprovação de um responsável.
  • Implantação contínua: toda mudança que passa na pipeline vai para produção automaticamente, sem intervenção humana.

A diferença entre entrega e implantação contínuas é uma decisão de negócio e de maturidade, não só técnica. Muitas equipes sérias escolhem a entrega contínua com aprovação manual para mudanças de alto impacto, e a implantação automática para o resto.

Forsgren, Humble e Kim (2018) reuniram evidências de que equipes com integração frequente, entregas pequenas e pipelines automatizadas tendem a entregar com mais rapidez e com menos falhas. A integração frequente é a causa mais citada desse efeito.

Teoria · A pipeline e os portões de qualidade

Uma pipeline típica tem etapas em sequência, e cada uma é um portão: só deixa a mudança passar se as verificações forem satisfeitas. Um exemplo comum:

  1. Build: o código é compilado ou empacotado. Falhas aqui quase sempre são erros de dependência ou de sintaxe.
  2. Testes: a suíte automatizada roda (unitários, depois integração). É o portão mais importante, e o tópico 3 e o tópico 11 tratam dele.
  3. Análise estática: ferramentas de lint, de segurança e de cobertura verificam o código sem executá-lo.
  4. Imagem: o artefato é empacotado em um container com uma versão identificável.
  5. Homologação: o artefato é implantado em um ambiente parecido com a produção, onde testes de aceitação e exploratórios acontecem.
  6. Produção: a mudança chega aos usuários, por uma das estratégias descritas adiante.

A regra essencial é que o mesmo artefato percorre todas as etapas. Reconstruir o código para cada ambiente é uma fonte clássica de surpresas: a versão testada não é a versão implantada. A animação desta página mostra a pipeline completa e o que acontece quando um portão falha.

Animação · Uma mudança atravessando a pipeline

Escolha o cenário. No primeiro, a mudança chega à produção depois da aprovação manual. No segundo, os testes falham e a pipeline para antes da homologação.

Exemplo prático · Integração contínua e um container

O arquivo abaixo define uma pipeline de integração no GitHub Actions. Ele roda em cada pull request e em cada mudança na main, instala as dependências, roda a análise estática e a suíte de testes. Se qualquer passo falhar, a pipeline para e marca a mudança como reprovada. 

# .github/workflows/ci.yml
name: ci

on:
  pull_request:
  push:
    branches: [main]

jobs:
  verificar:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
      - run: pip install -r requirements.txt
      - run: ruff check .          # análise estática: falha se houver problemas
      - run: pytest -q             # suíte de testes: falha se algum teste falhar

Repare nos comentários. Cada linha de verificação é um portão, e o nome da etapa comunica a intenção. Um detalhe importante: as versões das ações (@v4, @v5) são fixadas. Versões que mudam sem aviso podem quebrar a pipeline sem que nenhum código tenha mudado.

Agora, o container. Um Dockerfile descreve o ambiente em que o sistema roda, de forma reproduzível: 

# Dockerfile
FROM python:3.12-slim

WORKDIR /app

# Dependências primeiro: esta camada só é refeita quando requirements.txt muda
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

# Configuração entra por variáveis de ambiente, nunca por arquivo com segredos
ENV PORT=8000
EXPOSE 8000

# Um usuário sem privilégios de administrador
RUN useradd --create-home app
USER app

CMD ["python", "-m", "app"]

O container garante que o ambiente de execução é o mesmo em qualquer máquina que o rode. Ele não garante que o código está correto, nem que a configuração de produção está certa, nem que o banco de dados tem o esquema esperado. Essas garantias vêm dos testes, da configuração e das migrações, que devem fazer parte do processo de entrega.

Teoria · Como colocar uma mudança em produção

Implantar não é um ato único. Existem formas de expor a mudança aos usuários de modo gradual, o que limita o estrago de um erro:

  • Substituição direta: a versão antiga é trocada pela nova de uma vez. Simples, mas um erro atinge todos os usuários de imediato.
  • Implantação contínua (rolling): as instâncias são substituídas uma a uma. Reduz o impacto, mas por um tempo convivem duas versões, o que exige compatibilidade entre elas.
  • Azul-verde (blue-green): duas cópias do ambiente; a nova é preparada em paralelo e o tráfego é virado de uma vez. A reversão é imediata, bastando voltar o tráfego.
  • Canário: a nova versão recebe uma pequena fração do tráfego, e a equipe observa métricas de erro e de latência antes de aumentar a fração. É a estratégia que melhor combina risco baixo com aprendizado rápido.

Todas essas estratégias dependem de observabilidade: sem métricas e logs que mostrem o efeito da mudança, não há como saber se o canário está bem ou se a versão antiga precisa voltar. Também dependem de uma reversão planejada, testada antes do incidente. Uma reversão que nunca foi ensaiada costuma falhar justamente quando é necessária.

Mudanças no banco de dados merecem cuidado extra. Uma migração que remove uma coluna usada pela versão antiga quebra a reversão. A prática segura é expandir (adicionar o novo), migrar os dados e só então contrair (remover o antigo), em implantações separadas.

Teoria · Configuração, segredos e ambientes

A pipeline precisa de credenciais para publicar, para acessar o banco e para chamar serviços externos. Essas credenciais são o alvo mais valioso de qualquer ataque, e por isso o princípio é simples: nenhum segredo entra no repositório. Eles ficam em um cofre de segredos da plataforma de CI ou de nuvem, são injetados na execução e são rotacionados periodicamente.

Use o menor privilégio possível. A pipeline que só precisa publicar uma imagem não deve ter permissão para apagar o banco. E cada ambiente (homologação e produção) deve ter credenciais separadas, para que um erro em homologação não atinja produção.

Como visto no tópico 10, a configuração que muda por ambiente vem de variáveis de ambiente. A pipeline é quem as preenche, e o código permanece o mesmo do início ao fim. É esse o motivo de a mesma imagem poder ser promovida de homologação a produção sem alterações.

Teoria · O que significa “pronto para produção”

“Funciona na minha máquina” é uma frase que mostra que o trabalho não terminou. Estar pronto para produção significa que o software é capaz de operar sem o autor por perto, de ser diagnosticado quando algo der errado e de ser revertido sem drama. A lista abaixo é um ponto de partida que equipes podem adaptar, e ela deve ser parte da Definição de Pronto (tópico 1): 

Definição de pronto para produção

[ ] Código revisado por outra pessoa, com pull request pequeno e descrito
[ ] Testes automatizados passando na pipeline (unitários e de integração)
[ ] Análise estática e de segurança sem alertas bloqueantes
[ ] Sem segredos no código; configuração via variáveis de ambiente
[ ] Migrações de banco testadas e compatíveis com a versão anterior
[ ] Logs com contexto, sem dados sensíveis, nos caminhos novos
[ ] Métricas ou alertas para o comportamento novo (erro, latência)
[ ] Procedimento de reversão descrito e testado
[ ] Documentação atualizada (README, ADR se houve decisão relevante)
[ ] Validado pelo dono do produto em homologação

A lista não precisa ser longa. Precisa ser verdadeira, ou seja, cada item deve ser verificado de fato, e não assinalado por hábito. Um item que a equipe nunca confere é uma decoração, e decorações não protegem ninguém.

Boas práticas

  • Pipeline rápida. Uma pipeline que leva uma hora desincentiva integrações frequentes. Paralelize etapas independentes e ponha os testes mais rápidos primeiro.
  • Um artefato, muitos ambientes. Construa a imagem uma vez e promova a mesma versão pelos ambientes.
  • Versione tudo que é executável. Pipeline, Dockerfile, scripts de migração e configuração de infraestrutura entram no repositório, revisados como código.
  • Fixe versões. Dependências, imagens base e ações da pipeline com versão definida. Atualize de forma deliberada, com testes.
  • Ensaie a reversão. Uma reversão que nunca foi testada não é um plano; é uma esperança.
  • Trate a pipeline como produto. Quando ela quebra por instabilidade, o problema é prioritário, porque toda a equipe depende dela.

Problemas comuns

SintomaCausa provávelO que fazer
Funciona na pipeline, falha em produçãoArtefato reconstruído em cada ambiente, ou configuração diferenteConstruir uma vez, promover a mesma imagem e externalizar a configuração
Pipeline falha de forma intermitenteTestes instáveis ou dependência de serviço externoTratar como defeito prioritário; isolar testes de rede; fixar versões
Deploy na sexta à noite dá medoEntregas grandes e reversão não ensaiadaEntregas pequenas, canário e reversão testada
Migração de banco derrubou a versão anteriorRemoção de coluna ainda em usoExpandir, migrar, contrair em implantações separadas
Senha de produção vazou em um commit antigoSegredo no repositórioRotacionar imediatamente; usar cofre; checar o repositório com ferramenta de detecção
Ninguém sabe se a versão atual está saudávelAusência de métricas e alertasDefinir indicadores do comportamento novo e alertas com dono
Armadilha frequente: automatizar a implantação sem automatizar a verificação. Um pipeline que implanta cada commit, com testes que não testam nada, só aumenta a velocidade do erro. Automatize primeiro a verificação; a implantação automática vem depois.

Dicas de aplicação

No projeto da disciplina, comece com a pipeline de integração do exemplo, que roda testes e análise em cada pull request. Depois que ela estiver verde de forma estável, adicione a construção da imagem Docker. Só então pense em implantação, que pode ser simplesmente publicar a imagem em um serviço gratuito de hospedagem de containers.

Antes da entrega final, percorra a lista de “pronto para produção” item por item, sem pular nenhum. Para cada item que você não consegue marcar com sinceridade, escreva uma frase explicando o risco assumido. Esse exercício revela, com poucos minutos de trabalho, onde o projeto é frágil.

Teste seus conhecimentos

Por que a mesma imagem de container deve ser promovida de homologação para produção, em vez de ser reconstruída em cada ambiente?

Correto. Reconstruir a imagem cria a chance de a versão implantada diferir da testada, por causa de uma dependência ou de uma configuração que mudou. Promover o mesmo artefato elimina essa classe de surpresas.

Uma migração remove uma coluna que a versão anterior ainda usa. O que torna a reversão do deploy perigosa?

Correto. Esse é o motivo da prática de expandir, migrar e só depois contrair: a versão antiga precisa continuar funcionando com o esquema novo durante a transição.

O que levar desta página

  • Integração contínua verifica cada mudança em minutos; entrega contínua mantém o software sempre implantável.
  • Cada etapa da pipeline é um portão. Se um portão falha, a mudança não avança.
  • Construa o artefato uma vez e promova a mesma versão por todos os ambientes.
  • Segredos nunca entram no repositório. Configuração vem do ambiente, e cada ambiente tem suas credenciais.
  • Pronto para produção significa operável, diagnosticável e reversível, e a lista de verificação precisa ser verdadeira.
