Visão geral

Na faculdade, um projeto costuma ser de uma pessoa ou de um grupo que se reúne no fim do semestre. O código fica em uma pasta, o histórico é “trabalho final v3 nova versão”, e a integração acontece na véspera da entrega. Na indústria, dezenas de pessoas alteram o mesmo sistema todas as semanas, e o que separa um time produtivo de um caótico é, em grande parte, a forma como o código é versionado e revisado.

Esta página é a primeira da trilha de Programação para a Indústria. Ela trata da transição mais imediata: usar o Git como ferramenta de trabalho em equipe, escrever commits e pull requests que outras pessoas entendem e fazer revisões de código que ensinam, em vez de só apontar defeitos.

Objetivos desta página. Ao final, você deve conseguir:

  • explicar o modelo do Git (commits, branches, referências) o suficiente para não ter medo dele;
  • escrever mensagens de commit que explicam o porquê da mudança;
  • escolher um fluxo de branches adequado ao tamanho da equipe;
  • abrir um pull request que facilita a revisão e conduzir uma revisão de código construtiva;
  • evitar os erros que quebram a integração e expõem segredos.

Teoria · O que o Git guarda

O Git é um sistema de controle de versão distribuído. Ele guarda o histórico do projeto como uma sequência de commits. Cada commit é um instantâneo do projeto, ligado ao anterior por uma referência, formando um grafo. Uma branch não é uma cópia do código: é apenas um nome que aponta para um commit, e avança a cada novo commit feito nela.

Essa simplicidade é o que torna as branches baratas. Criar uma branch é criar um ponteiro. Quando a funcionalidade está pronta, a integração (o merge) cria um commit que tem dois pais e junta as duas linhas. Um rebase faz outra coisa: reaplica os commits de uma branch sobre outra base, produzindo um histórico linear. Ambos são válidos; a escolha depende da política da equipe, e não de uma verdade universal.

Entender esse modelo evita a maior parte dos sustos. Quando algo parece perdido, o histórico quase sempre ainda está lá: o git reflog mostra para onde os ponteiros andaram nas últimas semanas.

Teoria · Fluxos de trabalho

Três fluxos aparecem com frequência, do mais complexo ao mais simples:

  • Gitflow (Driessen, 2010): branches permanentes main e develop, além de branches de funcionalidade, de release e de correção. Oferece organização para produtos com versões formais e ciclos longos, mas tem muitas branches e mais chances de integração tardia.
  • GitHub Flow: uma única branch principal, sempre implantável, e branches curtas para cada mudança, integradas por pull request. Simples e eficiente para a maioria das equipes que entregam continuamente.
  • Trunk-based development: todos integram com muita frequência na linha principal, muitas vezes ao dia, usando branches de vida de horas e funcionalidades escondidas atrás de chaves de configuração. Exige testes automatizados fortes e é a base da entrega contínua do tópico 12.

O critério que importa é o tempo entre escrever o código e integrá-lo. Quanto mais tempo uma branch vive separada, mais difícil é integrá-la, e mais tarde os conflitos aparecem. A animação desta página mostra um ciclo típico do GitHub Flow.

Animação · Do commit estável ao merge

Acompanhe uma funcionalidade nascer de um commit estável da main, ganhar commits pequenos, passar pela revisão e ser integrada. Enquanto isso, a main continua recebendo o trabalho de outras pessoas.

Teoria · Commits que explicam o porquê

Um commit deve ser uma unidade lógica de mudança, que pode ser revertida sem afetar o resto. O diff mostra o que mudou; a mensagem deve dizer por que. Quem lê o histórico daqui a um ano consegue ver o código, mas não a intenção, a menos que a mensagem a registre.

Uma convenção muito usada, derivada do formato Conventional Commits, organiza a primeira linha com um tipo e um resumo curto:

feat(catalogo): filtrar produtos por faixa de preço

A busca por preço era feita no cliente, o que exigia baixar o catálogo
inteiro. A filtragem agora acontece na API, com limites inclusivos,
conforme o critério CT-07 do requisito RF-07.

Refs: #34

Os tipos mais comuns são feat (nova funcionalidade), fix (correção), refactor (mudança de forma sem mudança de comportamento), test, docs e chore (tarefas de manutenção). A separação entre tipos ajuda a ler o histórico e, em algumas equipes, a gerar notas de versão automaticamente.

Um hábito que vale ouro: separe refatoração de mudança de comportamento em commits diferentes. Quando um teste quebra, o histórico deve dizer qual das duas mudanças causou o problema.

Exemplo prático · Uma funcionalidade do começo ao pull request

O roteiro abaixo cobre o ciclo completo de uma mudança pequena. Os comandos são os mais usados no dia a dia, e cada linha tem um propósito. 

# 1. Partir de uma main atualizada
git switch main
git pull --ff-only

# 2. Criar uma branch curta, com nome que descreve a mudança
git switch -c feature/filtro-preco

# 3. Fazer commits pequenos; escolher o que entra em cada um
git add -p                      # revisa cada trecho antes de adicionar
git commit -m "feat(catalogo): filtrar por faixa de preço"

# 4. Manter a branch atualizada com a main (rebase para histórico linear)
git fetch origin
git rebase origin/main

# 5. Publicar e abrir o pull request
git push -u origin feature/filtro-preco
gh pr create --fill             # descrição vem dos commits; revise antes de enviar

Dois detalhes fazem diferença. O git add -p obriga a revisar o próprio diff antes de cada commit, e pega muitos erros bobos, como um print de depuração esquecido ou um arquivo de configuração pessoal. E o --ff-only impede que um pull crie um merge acidental na main local.

Antes de qualquer git add, confira se nenhum arquivo sensível entrou no diff: senhas, chaves de API e tokens não devem estar no repositório, nem em commits antigos. Se um segredo foi commitado por engano, considere-o comprometido: troque a chave e só então limpe o histórico.

Teoria · Pull requests e revisão de código

Um pull request é o pedido formal para integrar uma branch. Ele é o lugar onde a revisão acontece, onde os testes automáticos rodam e onde a discussão sobre a mudança fica registrada. Um bom pull request é pequeno, descrito e fácil de revisar. Estudos de revisão de código, como os reunidos por Sadowski et al. (2018) no Google, mostram que as equipes valorizam mudanças pequenas e focadas, que são revisadas mais rápido e com mais proveito. Revisar centenas de linhas de uma vez tende a produzir uma revisão superficial.

Uma descrição útil responde a quatro perguntas:

  • O que muda? Um resumo de duas ou três frases.
  • Por que muda? O problema ou o requisito que motivou a mudança, com link para a issue ou para o requisito.
  • Como testar? Passos concretos que o revisor pode seguir.
  • Onde olhar com atenção? Partes de maior risco ou decisões que você gostaria de discutir.

Do lado do revisor, o objetivo é melhorar o código e ensinar, e não provar que é mais inteligente. Comentários que fazem perguntas (“o que acontece se a lista estiver vazia?”) costumam funcionar melhor do que ordens (“troque isso”). Separe o que é bloqueante do que é sugestão, e use um prefixo como nit: para ajustes de estilo sem importância. Critique o código, nunca a pessoa.

Para quem recebe a revisão, o sinal de maturidade é responder com clareza, aceitar o que faz sentido e explicar, com dados, o que não faz. Discordar é normal; o que importa é que a decisão final seja registrada e que a discussão permaneça técnica.

Boas práticas

  • Pull requests pequenos. Como referência prática, algo que caiba em uma revisão de vinte a trinta minutos. Se for maior, divida em uma sequência de PRs encadeados.
  • Branches de vida curta. Integre ao menos diariamente. Uma branch de três semanas é um projeto paralelo, não uma mudança.
  • A main sempre verde. Os testes passam na main o tempo todo. Quem quebra a main conserta antes de qualquer outra coisa.
  • Revise o próprio PR antes de pedir revisão. Leia o diff como se fosse de outra pessoa. Quase sempre aparece algo para corrigir.
  • Automatize o que não precisa de cabeça humana. Formatação, lint e testes são problema da máquina. A revisão humana deve se concentrar em design e intenção.
  • Proteja a main. Exija revisão e testes verdes para integrar, e nunca faça push --force na branch principal.

Armadilha frequente: tratar o histórico do Git como um rascunho que nunca será lido. Ele é a documentação de como o sistema chegou ao estado atual. Escreva mensagens pensando em quem vai ler daqui a um ano, que pode ser você mesmo.

Dicas de aplicação

No projeto da disciplina, adote o GitHub Flow desde o primeiro commit. Proteja a main, faça ao menos um pull request por funcionalidade e exija que outra pessoa do grupo revise cada um. Essa é a prática que mais aproxima um trabalho acadêmico de um time real, e os colegas de revisão costumam encontrar defeitos que a autora ou o autor nunca veria.

Quando um pull request ficar grande, pergunte se ele pode ser dividido em três: uma refatoração, uma mudança de comportamento e os testes. Cada parte fica mais fácil de revisar, e o histórico conta a história melhor.

Teste seus conhecimentos

O que uma branch representa, no modelo interno do Git?

Correto. Por isso as branches são baratas: criar uma é criar um ponteiro. O custo real está em deixá-las viver muito tempo sem integrar.

Um colega abriu um pull request com 2.000 linhas alteradas. Qual é a ação mais útil como revisor?

Correto. Revisões de mudanças grandes perdem qualidade porque a atenção não acompanha o volume. Dividir o trabalho melhora a revisão e facilita reverter partes da mudança se algo der errado.

O que levar desta página

  • Branch é um ponteiro barato. O custo está em mantê-la separada por tempo demais.
  • Commits devem ser unidades lógicas de mudança, com mensagens que explicam o porquê.
  • Pull requests pequenos, bem descritos e com testes são revisados com qualidade.
  • Revisão de código existe para melhorar o código e ensinar. Critique a mudança, nunca a pessoa.
  • Segredos não entram no repositório. Se entraram, considere-os comprometidos e troque-os.
