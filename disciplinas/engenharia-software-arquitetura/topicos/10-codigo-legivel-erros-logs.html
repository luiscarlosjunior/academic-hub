Visão geral

Código é lido muito mais vezes do que é escrito. Em um time profissional, a proporção costuma ser de muitas leituras para cada alteração: alguém precisa entender o código para corrigi-lo, para estendê-lo, para revisá-lo ou para descobrir por que ele falhou às três da manhã. Escrever código legível não é um luxo estético. É a forma mais barata de reduzir o custo de tudo o que vem depois.

Esta página reúne práticas que um time espera de quem chega do curso: nomes que revelam a intenção, funções que fazem uma coisa, erros que não se escondem, validação no lugar certo, configuração fora do código e logs que ajudam a diagnosticar problemas reais.

Objetivos desta página. Ao final, você deve conseguir:

  • escolher nomes que comunicam intenção e eliminar comentários que apenas repetem o código;
  • decompor funções longas em partes com responsabilidades claras;
  • tratar erros de forma específica, sem engolir exceções nem devolver valores ambíguos;
  • posicionar a validação na borda do sistema e a regra de negócio no núcleo;
  • escrever logs úteis, sem vazar dados sensíveis.

Teoria · Nomes que revelam a intenção

Um nome é uma promessa sobre o que o elemento faz. Nomes bons dispensam comentários, e nomes ruins são comentários mentirosos esperando para acontecer. Martin (2008) resume o critério: um nome deve dizer por que o elemento existe, o que ele faz e como é usado. Se você precisa de um comentário para explicar o nome, o nome ainda não está bom.

  • Evite abreviações obscuras: qtd_dias_atr obriga a decifrar; dias_em_atraso comunica.
  • Evite nomes genéricos: dados, info, manager, processa() não dizem nada.
  • Use o vocabulário do negócio: se o domínio fala de “empréstimo”, o código não deve falar de “transação de registro”.
  • Nomes de booleanos são perguntas: esta_atrasado, pode_renovar. Um booleano chamado status obriga a consultar o contexto.

Comentários devem explicar o porquê, nunca o o que. i += 1 # incrementa i é ruído. Uma linha dizendo que um limite de 30 dias existe por exigência de uma norma interna, e que não deve ser alterado sem consultar a área jurídica, é informação que o código não consegue carregar sozinho.

Teoria · Funções que fazem uma coisa

Uma função deve fazer uma coisa, e fazê-la bem. O critério prático é que o leitor consiga descrever o que ela faz em uma frase sem usar a palavra “e”. Quando a descrição precisa de “e”, há mais de uma responsabilidade, e a função provavelmente deveria ser duas.

Três sinais indicam que uma função merece ser dividida: ela tem muitos níveis de aninhamento, ela tem muitos parâmetros que são usados só em parte do corpo, ou ela mistura os níveis de abstração (como calcular uma regra de negócio e formatar uma string de SQL no mesmo bloco). Extrair uma função com um nome claro é, muitas vezes, a forma mais barata de documentar um trecho complexo.

Cuidado com o excesso. Dividir em funções minúsculas sem nome significativo espalha a lógica em dezenas de lugares e torna a leitura mais difícil, não mais fácil. O objetivo é ter partes que façam sentido isoladamente.

Teoria · Erros que não se escondem

O tratamento de erros é onde muitos sistemas perdem a confiabilidade. Há três posturas comuns, e só uma delas é aceitável:

  • Engolir a exceção: um except: pass faz o erro desaparecer, e o problema reaparece depois, longe da causa. É a pior opção.
  • Capturar tudo e devolver uma mensagem genérica: o sistema continua de pé, mas ninguém sabe o que deu errado, nem o usuário, nem quem opera.
  • Capturar o específico e tratar com intenção: cada erro esperado tem um tipo próprio, que pode ser tratado, traduzido para uma resposta clara ou registrado com contexto. Erros inesperados sobem até um ponto que os registra.

Uma boa prática é a de falhar cedo: quando uma pré-condição não é satisfeita, lance o erro no ponto da violação, com uma mensagem que diga o que estava errado. Assim, o erro aparece perto da causa, não dezenas de linhas depois com um valor None incompreensível.

Também evite devolver valores especiais como -1 ou None para indicar falha, quando o chamador pode esquecer de verificar. Lance uma exceção específica, ou use um tipo que torne a falha explícita, conforme a linguagem e o contexto. O exemplo desta página mostra a diferença.

Teoria · Validar na borda, decidir no núcleo

Entrada de dados é sempre suspeita. Campos vazios, tipos errados, valores fora da faixa, JSON malformado: tudo isso chega. A validação deve acontecer na borda do sistema, onde os dados entram, e deve verificar a forma (tipo, formato, obrigatoriedade). A regra de negócio (a quantidade pode ou não ser maior que o estoque?) pertence ao núcleo, como visto no tópico 6.

A separação importa porque cada tipo de validação responde a uma pergunta diferente. “Quantidade é um inteiro positivo?” é uma pergunta de forma. “Há estoque suficiente?” depende do estado do sistema. Misturar as duas torna a validação lenta, difícil de testar e propensa a inconsistências.

A animação desta página mostra o caminho de uma requisição por uma pipeline de validação, em duas versões: uma que passa e uma que é barrada, com erro claro, e uma que mostra o anti-padrão de devolver um erro genérico.

Animação · Onde a requisição para

Escolha o cenário e avance os passos. Na versão válida, a requisição atravessa todas as etapas. Na inválida, ela para na validação, e a resposta diz exatamente o que corrigir.

Exemplo prático · Refatorando uma função de cobrança

A versão abaixo funciona para o caso feliz, mas esconde erros, usa nomes vagos e mistura validação com regra de negócio e com efeito colateral. 

# antes
def cobra(d):
    try:
        v = d["valor"]
        if v > 0:
            r = gateway.cobra(d["cartao"], v)
            return r
    except:
        pass
    return None

Quem chama essa função recebe None em três situações diferentes: valor inválido, falha do gateway e erro de programação. Não há como distinguir os casos, e o erro de programação (como uma chave ausente no dicionário) é silenciado. A versão abaixo corrige isso: 

# depois
class ValorInvalido(Exception):
    pass

class FalhaNaCobranca(Exception):
    pass

def valida_cobranca(pedido):
    """Validação de forma e de faixa, na borda do sistema."""
    if not isinstance(pedido.get("valor"), (int, float)):
        raise ValorInvalido("valor deve ser numérico")
    if pedido["valor"] <= 0:
        raise ValorInvalido("valor deve ser maior que zero")

def cobra_pedido(pedido, gateway):
    valida_cobranca(pedido)                        # falha cedo, com mensagem clara
    try:
        return gateway.cobra(pedido["cartao"], pedido["valor"])
    except ConnectionError as erro:
        # traduz o erro técnico para o domínio, preservando a causa
        raise FalhaNaCobranca("gateway indisponível, tente novamente") from erro

Agora, cada caso tem um tipo próprio. O chamador pode tratar ValorInvalido como erro do usuário, FalhaNaCobranca como algo a reenviar mais tarde e qualquer outro erro como um bug que precisa aparecer nos logs. Nada é silenciado, e a cláusula from erro preserva a causa original para quem depurar.

Teoria · Configuração fora do código

Um sistema que roda em mais de um ambiente (desenvolvimento, homologação, produção) precisa de valores diferentes para endereços de banco, chaves de API e limites. Esses valores não devem estar no código. A metodologia The Twelve-Factor App, proposta por Wiggins (2011), recomenda guardar a configuração em variáveis de ambiente, e isso continua sendo a abordagem mais simples e portátil.

  • Configuração (endereços, limites, flags) muda por ambiente e pode ficar em variáveis de ambiente ou em arquivos de exemplo versionados.
  • Segredos (senhas, chaves, tokens) nunca são versionados. Usam um cofre de segredos da plataforma ou variáveis de ambiente injetadas em tempo de execução.
  • Valores padrão seguros: se uma variável não existir, o sistema deve falhar com mensagem clara, ou usar um padrão que não cause dano, nunca um valor de produção escondido no código.

Teoria · Logs que ajudam a diagnosticar

Um log é um registro do que o sistema fez e do que aconteceu com ele. Um bom log responde, sem precisar reproduzir o problema, a pergunta “o que aconteceu com esta requisição?”. Três cuidados fazem a diferença:

  • Níveis com significado: DEBUG para detalhes de investigação, INFO para eventos normais relevantes, WARNING para situações anormais que o sistema contornou, ERROR para falhas que exigem atenção.
  • Contexto: identificador da requisição ou do pedido, usuário (de forma não sensível), operação e duração. Sem contexto, a mensagem “erro ao salvar” não serve para nada.
  • Sem dados sensíveis: nunca registre senhas, números de cartão, tokens ou dados pessoais em texto puro. Mascare o que for necessário.

Logs estruturados (pares chave-valor ou JSON) são mais fáceis de pesquisar e agregar do que frases livres. Em vez de “pedido 42 cobrado”, registre evento=cobranca_ok pedido_id=42 valor=80.00. A pergunta “quantas cobranças falharam hoje?” passa a ter resposta em segundos.

Boas práticas

  • Leia o código em voz alta. Se a leitura soa estranha, o nome ou a estrutura provavelmente precisam mudar.
  • Siga o padrão do projeto. Consistência vale mais do que a preferência pessoal. Um formatador automático resolve a maior parte das discussões.
  • Nunca use except sem tipo. Capture a exceção específica que você sabe tratar.
  • Trate o erro no nível que sabe lidar com ele. Se a camada baixa não sabe o que fazer, deixe a exceção subir, traduzida para o vocabulário adequado.
  • Escreva logs como se fossem lidos por um estranho às 3 da manhã. Porque, em algum momento, serão.
  • Revise cada comentário. Comentário desatualizado é pior do que nenhum.

Armadilha frequente: capturar a exceção só para registrá-la e depois relançá-la sem contexto, o que duplica linhas de log. Registre no ponto onde o erro é tratado de fato, uma vez, com contexto suficiente.

Dicas de aplicação

No seu próximo projeto, faça uma leitura de revisão antes de cada entrega com três perguntas: há algum nome que eu precisei explicar? Há algum except genérico? Há algum valor de configuração escrito direto no código? Cada resposta “sim” aponta uma melhoria concreta, de custo baixo.

Teste o log do seu sistema: execute uma operação que falha e tente responder, apenas olhando o log, o que aconteceu, para qual pedido, por qual motivo e o que fazer. Se não conseguir, o log precisa de contexto.

Teste seus conhecimentos

Qual comentário é mais útil em um código?

Correto. O comentário explica o porquê, algo que o código não consegue dizer. Os outros repetem o código ou não dizem nada acionável.

Uma função captura qualquer exceção, registra “erro interno” e devolve None. Qual é o principal problema?

Correto. Registrar uma mensagem genérica não basta: se todos os erros viram o mesmo caso, quem chama não sabe como reagir, e bugs de programação passam despercebidos.

O que levar desta página

  • Código é lido muito mais do que é escrito. Nomes e estrutura são investimento de leitura.
  • Comentários explicam o porquê. O que o código já diz não precisa de comentário.
  • Erros específicos, tratados com intenção. Nada de except genérico nem de falha silenciosa.
  • Valide a forma na borda e a regra no núcleo. Falhe cedo, com mensagem clara.
  • Configuração e segredos ficam fora do código. Logs têm contexto e não expõem dados sensíveis.
