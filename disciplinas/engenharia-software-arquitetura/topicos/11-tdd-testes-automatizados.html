Visão geral

Um teste automatizado é código que verifica outro código, e roda sozinho a cada mudança. Na faculdade, muitos projetos são testados manualmente, uma vez, na hora da apresentação. Na indústria, o teste manual não acompanha o ritmo de mudança: o que não é automático é ignorado, ou feito tarde demais para ser barato.

Esta página trata dos testes automatizados como ferramenta de trabalho no dia a dia. Ela apresenta o TDD (desenvolvimento orientado a testes), um ciclo curto de três passos que muda a forma de projetar o código, e mostra como escrever dublês de teste sem transformar a suíte em uma coleção de simulações frágeis.

Objetivos desta página. Ao final, você deve conseguir:

  • escrever testes automatizados com pytest que documentam o comportamento esperado;
  • executar o ciclo vermelho, verde, refatorar em um exemplo completo;
  • distinguir stub, fake e mock, e escolher o dublê adequado a cada situação;
  • reconhecer os erros típicos de quem começa com testes e corrigi-los.

Teoria · O teste como especificação executável

Um bom teste é a forma mais precisa de documentação que existe, porque ele não pode ficar desatualizado sem que a suíte falhe. Quando um teste se chama test_media_7_ou_mais_e_aprovado, ele diz uma regra de negócio que qualquer pessoa pode ler, e o computador verifica a cada commit.

Por isso, a pergunta para escrever um teste não é “como testar esta função?”, e sim “qual comportamento eu quero garantir?”. A diferença é grande. Testes escritos a partir da implementação repetem o código de forma indireta. Testes escritos a partir do comportamento sobrevivem a refatorações e expressam a intenção do sistema.

Um teste bem escrito segue a estrutura arranjar, agir, verificar (Arrange, Act, Assert): prepara os dados, executa uma ação e confirma um resultado. Três blocos claros tornam o teste legível, mesmo para quem nunca viu o código.

Teoria · O ciclo do TDD

Beck (2002) popularizou o desenvolvimento orientado a testes (TDD) em torno de um ciclo de três passos, repetido em intervalos de minutos:

  • Vermelho: escreva um teste para um comportamento que ainda não existe, e veja-o falhar. A falha prova que o teste de fato verifica algo; um teste que nunca falha não serve para nada.
  • Verde: escreva o código mínimo que faz o teste passar. “Mínimo” é a palavra importante: se a implementação parece óbvia demais, o teste ainda é pequeno demais, e um novo caso deve ser adicionado.
  • Refatorar: melhore o código e os testes mantendo tudo verde. Nomes, duplicação e estrutura são limpos nesse momento, com a segurança de que o comportamento está protegido.

O TDD não é só sobre testes. Ele muda a forma de projetar: como o código precisa ser testável antes de existir, as dependências ficam explícitas, as funções ficam pequenas e as interfaces ficam claras. Por isso o tópico 6 (sobre o núcleo e as portas) e o TDD se complementam.

Nem tudo deve ser feito em TDD. Exploração de uma API desconhecida, protótipos descartáveis e interfaces visuais costumam ser melhor resolvidos de outra forma. O TDD é mais útil nas regras de negócio, que são o coração do sistema e as que mais mudam.

Animação · Vermelho, verde, refatorar

Avance os passos para acompanhar a regra de desconto nascer: o teste falha primeiro, depois o código mínimo passa, depois a refatoração mantém o verde. No fim, uma nova regra começa outro ciclo.

Exemplo prático · TDD na situação do aluno

Vamos construir, em pequenos passos, a regra de situação de um aluno: média igual ou superior a 7,0 é aprovado; de 4,0 a 6,99 vai para recuperação; abaixo de 4,0 é reprovado. A média é ponderada pelos pesos das avaliações.

Passo 1 · Vermelho. Escrevemos primeiro o teste da média ponderada. A função ainda não existe, então o teste falha.

# tests/test_notas.py
import pytest
from notas import media_ponderada

def test_media_ponderada_considera_os_pesos():
    # nota 8 com peso 2 e nota 4 com peso 1: (16 + 4) / 3
    assert media_ponderada([(8, 2), (4, 1)]) == pytest.approx(20 / 3)

Passo 2 · Verde. O código mínimo que passa é a própria fórmula. Nada além disso ainda é exigido pelo teste.

# notas.py
def media_ponderada(notas_e_pesos):
    soma_pesos = sum(peso for _, peso in notas_e_pesos)
    return sum(nota * peso for nota, peso in notas_e_pesos) / soma_pesos

Note que a função ainda não trata peso zero. Esse é um caso que merece um teste próprio, e só depois o código. O TDD não exige prever tudo; exige que cada comportamento novo nasça de um teste que falha.

Passo 3 · Vermelho de novo. A regra de situação ainda não existe. Escrevemos os casos de borda, com valores exatos nos limites:

import pytest
from notas import situacao

@pytest.mark.parametrize("media, esperado", [
    (7.0, "aprovado"),
    (6.99, "recuperação"),
    (4.0, "recuperação"),
    (3.99, "reprovado"),
])
def test_situacao_nos_limites(media, esperado):
    assert situacao(media) == esperado

Passo 4 · Verde. A implementação mínima da regra, passando por todos os casos:

# notas.py (acréscimo)
def situacao(media):
    if media >= 7.0:
        return "aprovado"
    if media >= 4.0:
        return "recuperação"
    return "reprovado"

Passo 5 · Refatorar. Com os testes verdes, podemos dar nomes às constantes e separar a regra. A mudança de forma não altera nenhum resultado, e a suíte garante isso: 

NOTA_APROVACAO = 7.0
NOTA_RECUPERACAO = 4.0

def situacao(media):
    if media >= NOTA_APROVACAO:
        return "aprovado"
    if media >= NOTA_RECUPERACAO:
        return "recuperação"
    return "reprovado"

Ao final dos cinco passos, cada regra tem um teste que a documenta, e o código é mínimo, sem especulação. Se a escola mudar a nota de aprovação para 6,5, a alteração é uma linha no código e uma linha no teste, e a suíte mostra exatamente quais comportamentos mudaram.

Teoria · Dublês de teste: stub, fake e mock

Quando a unidade depende de algo lento, externo ou não determinístico (um e-mail, um relógio, uma API de pagamento), usamos um dublê no lugar da dependência real. Meszaros (2007) organizou os tipos de dublê, e três deles são os mais úteis:

  • Stub: devolve respostas fixas para as chamadas. Serve para controlar a entrada da unidade testada. Ex.: um repositório que sempre devolve uma lista com dois alunos.
  • Fake: tem uma implementação simplificada, mas funcional, como um repositório em memória. Serve quando o teste precisa de comportamento real, como salvar e depois ler.
  • Mock: verifica interações, ou seja, se um método foi chamado com certos argumentos. Serve quando o efeito colateral é o que importa, como “o e-mail de reprovação foi enviado uma vez”.

Um critério simples: prefira verificar estado (o resultado ou o que ficou salvo) a verificar interações (quais métodos foram chamados). Testes baseados em estado sobrevivem a refatorações; testes baseados em interações quebram sempre que a forma interna muda, mesmo sem mudança de comportamento. Mocks são úteis nas fronteiras, como um envio de e-mail, mas não devem simular a própria lógica do sistema.

Exemplo: para testar a notificação de reprovação, um fake de envio de mensagens guarda as mensagens em uma lista, e o teste verifica a lista. Isso verifica o resultado observável, e não a sequência de chamadas internas.

Boas práticas

  • Escreva o teste antes da implementação, e veja-o falhar. Um teste que nunca falhou não provou nada.
  • Cada teste verifica um comportamento. Um teste com cinco asserções diferentes não diz qual regra quebrou.
  • Use parametrize para valores de fronteira. A tabela de casos é a documentação da regra.
  • Mantenha os testes independentes. Nenhum teste deve depender da ordem em que os outros rodam, nem deixar dados para o seguinte.
  • Faça a suíte rodar em segundos. Testes unitários são rápidos por natureza; se a suíte está lenta, algo está acessando recursos externos sem necessidade.
  • Trate teste como código. Revise, refatore e apague os testes que não servem mais.

Problemas comuns

SintomaCausa provávelO que fazer
Teste escrito depois, para “cobrir” o código já prontoTeste como formalidadeEscrever o caso de uso primeiro e ver o teste falhar
Teste passou na primeira execução, sem nunca ter falhadoAsserção que não verifica nada útilQuebrar o código de propósito e confirmar que o teste falha
Refatorar quebra vinte testesTestes verificam interações internasVerificar estado e comportamento público; usar fakes no lugar de mocks
Teste passa sozinho e falha na suíteEstado compartilhado entre testesPreparar o estado dentro de cada teste ou com fixtures de escopo claro
Mock de tudo, sem nada real sendo testadoDublês usados para simular a própria regraTestar a regra com dados reais e usar dublês só nas fronteiras
Equipe desiste dos testes porque demoramTestes de integração no lugar de unitáriosSeparar as suítes e rodar a rápida a cada mudança
Armadilha frequente: escrever o código mínimo que passa e parar ali, sem perguntar se a regra está completa. O verde não significa que o comportamento está certo; significa que os testes escritos passam. Pergunte sempre quais casos ainda não foram especificados.

Dicas de aplicação

Para começar, escolha um exercício pequeno e pure, como cálculo de média, de juros ou de frete, e faça o ciclo completo cinco vezes seguidas, com cronômetro. Quando o ciclo estiver automático, aplique a uma regra real do projeto da disciplina, começando pela mais importante.

Em pares, uma pessoa escreve o teste e a outra faz a implementação mínima. Trocar os papéis a cada ciclo é uma forma excelente de treinar a leitura de código alheio e a disciplina de não adicionar nada além do exigido.

Teste seus conhecimentos

No ciclo do TDD, por que é importante ver o teste falhar antes de escrever a implementação?

Correto. Um teste que passa sem nenhum código novo pode estar verificando algo errado ou nada. A falha inicial é a evidência de que o teste está ligado ao comportamento que se quer.

Um teste precisa verificar que uma notificação de reprovação foi enviada. Qual abordagem tende a ser mais robusta a refatorações?

Correto. O fake verifica o efeito observável, que é a mensagem entregue. O mock acoplado à sequência de chamadas quebra sempre que a forma interna muda, mesmo sem mudar o comportamento.

O que levar desta página

  • Teste automatizado é especificação executável: ele documenta o comportamento e roda a cada mudança.
  • O TDD segue o ciclo vermelho, verde, refatorar. A falha inicial prova que o teste verifica algo.
  • O código mínimo que passa não é o código final: a refatoração vem com a suíte verde.
  • Stub controla entradas, fake simula comportamento real, mock verifica interações. Prefira verificar estado.
  • Use TDD nas regras de negócio, que mudam mais e merecem a maior proteção.
