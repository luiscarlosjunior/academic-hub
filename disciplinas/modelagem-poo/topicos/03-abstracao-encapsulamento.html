Abstração: decidir o que não modelar

Uma pessoa real tem milhares de características. Nenhum sistema precisa de todas. Abstrair é escolher o subconjunto relevante para aquele propósito e descartar o resto com consciência.

Por isso não existe “o modelo correto de Pessoa”: existe o modelo adequado ao contexto. Escolha o sistema abaixo e veja a mesma entidade do mundo real virar três classes diferentes.

Pergunta que guia toda abstração: “o sistema precisa fazer alguma coisa com esse dado?”. Se a resposta for não, ele não entra no modelo — mesmo existindo no mundo real.

Encapsulamento: o objeto defende o próprio estado

Duas contas bancárias com a mesma finalidade e implementações opostas. Execute as operações nas duas e compare — especialmente as que violam a regra de negócio.

Sem encapsulamento

atributo público 
public class ContaAberta {
    public double saldo;   // exposto
}

Com encapsulamento

atributo privado 
public class ContaSegura {
    private double saldo;  // protegido

    public void depositar(double v) {
        if (v <= 0) throw new ValorInvalido();
        saldo += v;
    }
    public void sacar(double v) {
        if (v > saldo) throw new SaldoInsuficiente();
        saldo -= v;
    }
    public double getSaldo() { return saldo; }
}
getSaldo()
R$ 1.000,00
O ponto não é “usar private”. É que a regra de negócio precisa viver em um único lugar. Uma classe com private + getter e setter para tudo continua completamente aberta — só que com mais linhas. Encapsular é não expor o que não precisa ser exposto.

Abstração: o que o modelo decide ignorar

  

    

      Abstração é o processo de destacar o que é essencial para um propósito e suprimir o resto. Booch a
      trata como um dos princípios centrais da orientação a objetos. Ela não é uma propriedade do mundo: é uma escolha
      feita pelo modelador, de acordo com a pergunta que o modelo precisa responder.
    

    

      Por isso a mesma pessoa vira classes diferentes conforme o contexto. Um sistema acadêmico vê Aluno com
      matrícula e coeficiente de rendimento. Um hospital vê Paciente com alergias e tipo sanguíneo. A pessoa é
      a mesma; o recorte muda.
    

  


  

    

      
Tipo de abstraçãoDescriçãoExemplo no Melodia

      
        
Abstração de dadosRepresentar um conceito pelo conjunto de operações que o manipulam“Conta” é definida por depositar, sacar e extrato

        
Abstração de controleEsconder a sequência de passos atrás de uma operação de alto nívelcobrarAssinatura() esconde a consulta, o débito e o registro

        
GeneralizaçãoReunir tipos parecidos sob um tipo comumUsuario abstrai Ouvinte e Artista

      
    

  


  

    
    

      Abstração errada é pior que não abstrair. Uma abstração que esconde o que importa obriga quem usa a
      classe a adivinhar o comportamento. A pergunta de controle é: “o cliente desta classe consegue entender o que ela faz
      sem ler o código dela?”
    

  






  
Encapsulamento e ocultação de informação

  

    

      David Parnas (1972) propôs que um módulo deve esconder decisões de projeto que provavelmente vão mudar.
      Esse é o princípio da ocultação de informação, e o encapsulamento é o mecanismo que o torna possível em
      linguagens orientadas a objetos.
    

    

      Note a diferença entre dois termos que aparecem juntos. Encapsulamento é a técnica de agrupar dados e
      operações e restringir o acesso direto aos dados. Ocultação de informação é o objetivo: proteger o
      cliente de decisões que podem mudar.
    

  


  

    
Exemplo: o saldo pode mudar de formato?

    

      Imagine que o Melodia passe a guardar o saldo em centavos (long) para evitar erros de arredondamento.
      Se o campo for público, todo código que lê conta.saldo quebra. Se for privado e exposto por
      getSaldo(), só a classe muda.
    

  



// Versão 1: saldo em reais (double)
public class ContaBancaria {
    private double saldo;
    public double getSaldo() { return saldo; }
}

// Versão 2: saldo em centavos (long). Quem chama getSaldo() não percebe a mudança.
public class ContaBancaria {
    private long saldoEmCentavos;
    public double getSaldo() { return saldoEmCentavos / 100.0; }
}






  
Invariantes e contratos (Design by Contract)

  

    Bertrand Meyer, criador da linguagem Eiffel, formalizou o encapsulamento como um contrato
    entre a classe e quem a usa. Três tipos de condição definem o contrato.
  

  

    
Pré-condição
O que o cliente precisa garantir antes de chamar. Ex.: valor > 0 em sacar.

    
Pós-condição
O que a operação garante ao terminar. Ex.: saldo@depois = saldo@antes - valor.

    
Invariante
Condição que vale sempre, antes e depois de qualquer operação pública. Ex.: saldo >= 0.

  



public double sacar(double valor) {
    // pré-condição: o cliente deve respeitar
    if (valor <= 0) throw new IllegalArgumentException("pré: valor > 0");
    if (valor > saldo)    throw new IllegalStateException("invariante: saldo >= 0");

    double anterior = saldo;
    saldo -= valor;

    // pós-condição: verificada pela própria classe
    assert saldo == anterior - valor;
    return saldo;
}


  

    
    

      Quem é responsável por quê: se a pré-condição falha, a culpa é do cliente. Se a pós-condição ou o
      invariante falham, a culpa é da classe. Essa separação ajuda a localizar bugs rapidamente.

Exercícios

  

    

      1. Dê um exemplo de abstração que não deveria existir no sistema de uma escola (abstração especulativa).
      
Gabarito: uma hierarquia Pessoa → Aluno/Professor/Funcionario/Terceirizado criada “porque um dia pode haver outro tipo”, quando só existe aluno e professor. Pela regra de bolso (abstrair na terceira repetição), o correto é modelar só o que existe e refatorar quando a variação aparecer.

    

    

      2. Escreva a pré-condição, a pós-condição e um invariante para a operação depositar(valor).
      
Gabarito: pré: valor > 0. Pós: saldo@depois = saldo@antes + valor. Invariante: saldo >= 0 (vale também após o depósito, que só aumenta o saldo).

    

    

      3. Por que tornar o atributo saldo público fere a ocultação de informação, mesmo que o código atual funcione?
      
Gabarito: porque expõe uma decisão de projeto (saldo em double, como armazenado) a todo o sistema. Qualquer mudança futura de representação, ou de regra, passa a exigir alterações em todos os clientes. Além disso, deixa o invariante sem proteção.

Experimente

    
Torne temporariamente o campo saldo de ContaBancaria public e escreva no Principal uma linha que o deixe negativo. Depois, volte o campo para private. O que isso demonstra sobre ocultação de informação?

    

      Ver gabarito
      
Com o campo público, a regra R1 pode ser quebrada de fora da classe sem nenhuma exceção: o compilador não conhece o invariante. Ao ocultar o campo, toda mudança passa por sacar, que valida. A ocultação é o que torna o invariante verdadeiro.
