Associação: objetos que se conhecem

Objetos não vivem sozinhos. Uma associação é um vínculo estrutural entre classes: os objetos se conhecem e trocam mensagens. No Melodia, um Ouvinte tem uma Assinatura, e uma Playlist tem várias Musicas.

Cada associação é descrita por quatro elementos, que a UML desenha e que o Java precisa implementar:

Nome / verbo

O que a ligação significa: possui, contém, publica.

Multiplicidade

Quantos objetos participam de cada lado: 1, 0..1, 0..*, 1..*.

Navegabilidade

De que lado se consegue chegar ao outro (a seta). Define o campo no código.

Papel (role)

O “cargo” de cada ponta na ligação, geralmente o nome do atributo.

classDiagram
    class Ouvinte
    class Assinatura
    class Playlist
    class Musica
    Ouvinte "1" --> "1" Assinatura : possui
    Ouvinte "1" --> "0..*" Playlist : monta
    Playlist "0..*" --> "0..*" Musica : contém

Leia: um ouvinte possui exatamente uma assinatura e monta de zero a muitas playlists. A seta indica que o ouvinte “enxerga” a assinatura, e não o contrário.

Da multiplicidade ao campo Java

A multiplicidade decide o tipo do campo: um objeto, um objeto que pode faltar, ou uma coleção.

UMLSignificaEm Java
1Exatamente um, sempre presenteprivate final Assinatura assinatura;
0..1Pode não existirprivate Assinatura assinatura; (pode ser null ou Optional)
0..*Zero ou muitosprivate final List<Playlist> playlists = new ArrayList<>();
1..*Pelo menos umLista + validação no construtor (não pode vir vazia)
 
public class Ouvinte {
    // 1 --> 1: sempre tem uma assinatura, obrigatória no construtor
    private final Assinatura assinatura;

    // 1 --> 0..*: zero ou muitas playlists, criadas conforme o ouvinte monta
    private final List<Playlist> playlists = new ArrayList<>();

    public Ouvinte(Assinatura assinatura) {
        if (assinatura == null)
            throw new IllegalArgumentException("todo ouvinte tem uma assinatura (multiplicidade 1)");
        this.assinatura = assinatura;
    }

    public Playlist montarPlaylist(String nome) {
        Playlist p = new Playlist(nome, this);
        playlists.add(p);
        return p;
    }
}
Multiplicidade vira regra. O 1 da assinatura se traduz em uma verificação no construtor. Quando o diagrama documenta a regra, o código a reproduz, e quem lê o modelo sabe o que esperar.

Agregação: “tem um”, mas a parte vive sozinha

Na agregação (losango vazio na UML), o todo tem partes, mas as partes existem independentemente. Se a playlist for apagada, as músicas continuam no catálogo.

Em Java, a agregação aparece quando o todo recebe um objeto que já existe, em vez de criá-lo. 

// Playlist (agregação): só APONTA para músicas que já existem no catálogo
public class Playlist {
    private final List<Musica> musicas = new ArrayList<>();

    public void adicionar(Musica m) {   // recebe de fora: a música não nasce aqui
        if (!musicas.contains(m)) musicas.add(m);
    }
}

// Uso: a música é criada pelo catálogo, a playlist só a referencia
Musica cometa = catalogo.buscar("Cometa");
Playlist treino = new Playlist("Treino", ouvinte);
treino.adicionar(cometa);
// apagar "treino" NÃO apaga "cometa" do catálogo

Composição: o todo cria e é dono da parte

Na composição (losango cheio), a parte não faz sentido sem o todo e morre com ele. As faixas de um álbum são criadas dentro do álbum: se ele some, elas somem junto.

Em Java, a composição aparece quando o todo cria a parte internamente, e a parte não é exposta para ser criada por fora. 

// Album (composição): CRIA as faixas. A faixa nasce dentro do álbum.
public class Album {
    private final String titulo;
    private final String artista;
    private final List<Musica> faixas = new ArrayList<>();

    public Musica adicionarFaixa(String tituloFaixa, int duracao) {
        Musica m = new Musica(tituloFaixa, artista, duracao);  // o álbum é o criador
        faixas.add(m);
        return m;
    }

    public List<Musica> getFaixas() {
        return Collections.unmodifiableList(faixas);   // ninguém de fora altera a lista
    }
}

Album album = new Album("Órbita", "Banda Nébula", 2024);
album.adicionarFaixa("Gravidade Zero", 213);
Repare no contraste. Em Album, o método adicionarFaixa cria a música. Em Playlist, o método adicionar recebe uma música pronta. A mesma classe Musica, duas relações diferentes, e isso é o que o diagrama precisa deixar claro.

A tabela de decisão: qual relação usar?

flowchart TD
    A["Ligar a classe X à classe Y"] --> B{"X é um Y?"}
    B -- "Sim" --> C["HERANÇA: extends"]
    B -- "Não" --> D{"X tem um Y?"}
    D -- "Sim, e Y morre com X" --> E["COMPOSIÇÃO: X cria Y"]
    D -- "Sim, mas Y vive sem X" --> F["AGREGAÇÃO: X recebe Y"]
    D -- "Só usa ou conhece" --> G["ASSOCIAÇÃO: Y num método"]

Pergunte nesta ordem: primeiro “é um?” (herança), depois “tem um?”, e então a vida da parte decide entre composição e agregação.

Navegabilidade: uma seta, um campo

Cada seta do diagrama vira um campo no código de quem a origina. Sem seta, não há campo: o objeto não consegue chegar ao outro. 

// Seta de Playlist para Ouvinte: a Playlist guarda o dono; o Ouvinte não precisa guardar a playlist
public class Playlist {
    private final String nome;
    private final Ouvinte dono;   // só existe se houver seta Playlist → Ouvinte
}
Associação bidirecional é cara. Quando os dois lados se conhecem, cada alteração precisa manter os dois em sincronia. Se ouvinte.adicionarPlaylist(p) não atualizar p.setDono(ouvinte), os dois objetos passam a dizer coisas diferentes. Só navegue nos dois sentidos quando o negócio exigir.

O cheiro do acoplamento

Um diagrama com setas para todo lado indica acoplamento alto: mudar uma classe obriga a mexer em muitas outras. Bons modelos têm poucas dependências, bem direcionadas. Menos setas significa sistema mais fácil de mudar.

Erros comuns

ErroConsequênciaComo resolver
Usar herança para tudo (“Playlist é uma Lista”)Hierarquia rígida, difícil de mudarPrefira composição: a playlist tem uma lista

Na indústria

Multiplicidade vira restrição no banco de dados. Uma associação 1 --> 0..* normalmente vira uma chave estrangeira com índice. Modelar a multiplicidade certa evita dados inconsistentes, como uma música sem álbum quando o negócio exige um.

“Composição sobre herança” é um conselho clássico de projeto (do livro Effective Java e do catálogo de padrões GoF). Frameworks modernos preferem montar objetos pequenos a herdar hierarquias profundas.

Em ORMs como JPA/Hibernate, associações bidirecionais são fonte comum de bugs e de problemas de carregamento preguiçoso (lazy loading). Regra prática: só navegue nos dois sentidos se o negócio realmente exigir.

Associação bidirecional: manter os dois lados iguais

Quando a associação é navegável nos dois sentidos, o estado vive em dois lugares. A consistência não é automática: se ouvinte guarda a playlist e playlist guarda o ouvinte, cada operação precisa atualizar os dois. A solução padrão é centralizar a atualização em um único método, que é o único autorizado a alterar o vínculo. 

public class Ouvinte {
    private final List<Playlist> playlists = new ArrayList<>();

    // único ponto que altera os dois lados do vínculo
    public void adicionarPlaylist(Playlist p) {
        if (playlists.contains(p)) return;
        playlists.add(p);
        p.definirDono(this);                 // mantém o outro lado sincronizado
    }
}

public class Playlist {
    private Ouvinte dono;
    // visibilidade de pacote: só Ouvinte deve chamar este método
    void definirDono(Ouvinte o) { this.dono = o; }
}
Visibilidade de pacote resolve a sincronia: o método definirDono é package-private (sem modificador), para que só as classes do mesmo pacote o chamem. Assim, nenhum código externo consegue alterar um lado sem o outro, e a notação ~ do diagrama de classes se torna uma garantia.

Quem é responsável pela vida da parte

Em uma composição, a parte não deve ser criada nem removida por fora do todo. Se o cliente pudesse fazer new Musica(...) e adicionar a um álbum existente, a posse deixaria de ser exclusiva. Por isso, o álbum oferece um método de criação, e a lista de faixas não é exposta para modificação.

Na agregação, o movimento é o oposto: o todo recebe a parte, e nunca a cria. Quem cria a música é o catálogo. A playlist recebe a referência e não a remove do catálogo quando é apagada.

PerguntaComposição (Album)Agregação (Playlist)
Quem cria a parte?O todo, por dentroOutro componente, fora do todo

O que acontece ao apagar o todo?As partes ficam inacessíveisAs partes continuam existindo

Quando a associação vira banco de dados

Em frameworks de persistência como JPA/Hibernate, cada associação do diagrama vira um mapeamento. Uma associação 1 --> 0..* normalmente vira uma chave estrangeira na tabela da parte. A composição costuma ser mapeada com cascade e orphanRemoval, para que a remoção do todo leve as partes. A agregação não usa cascade de remoção, porque a parte sobrevive.

Um detalhe que surpreende iniciantes é o carregamento preguiçoso (lazy loading): a coleção só é buscada no banco quando é acessada. Em uma associação bidirecional mal configurada, isso gera consultas em cascata, e o problema é de modelagem, não de banco: o diagrama mostrou uma navegação que o negócio não precisava.

Exercícios

1. Por que definirDono deve ser package-private, e não public?

Gabarito: se for público, qualquer classe poderia mudar o dono da playlist sem atualizar o ouvinte, e os dois lados ficariam em desacordo. O modificador restringe a alteração ao pacote, onde a regra de sincronia é garantida.

2. Ao remover um álbum do catálogo, suas faixas devem ser removidas do banco? E as playlists que as contêm?

Gabarito: as faixas, por composição, são removidas junto com o álbum (cascade). As playlists que as referenciam, por agregação, não podem perder as músicas em silêncio: é preciso decidir (impedir a remoção, ou removê-las das playlists explicitamente). A decisão é de negócio e deve estar no modelo.

3. Você modela Ouvinte "1" -- "0..*" Playlist como bidirecional. Quais operações precisam ser centralizadas?

Gabarito: adicionar, remover e trocar o dono. Cada uma deve atualizar os dois lados no mesmo método. Se alguma delas for feita diretamente em um lado, a associação deixa de ser consistente.

O que levar deste tópico

  • Associação é o vínculo entre objetos, descrito por multiplicidade, navegabilidade e papel.
  • Multiplicidade define o tipo do campo: objeto único, opcional ou coleção.
  • Composição (o todo cria e é dono) × agregação (o todo recebe e apenas aponta).
  • Prefira composição a herança quando o “é um” não for realmente verdadeiro. Menos setas, menos acoplamento.
