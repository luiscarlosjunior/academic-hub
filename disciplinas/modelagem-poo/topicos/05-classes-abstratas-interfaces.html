Duas formas de dizer “toda classe daqui faz isto”

Às vezes você quer garantir que um conjunto de classes ofereça certas operações, sem se importar com como cada uma as implementa. Existem dois mecanismos para isso, e a diferença entre eles é a pergunta mais frequente em prova.

A interface é um contrato puro: só diz o que precisa existir. A classe abstrata é um esqueleto parcialmente pronto: traz implementação compartilhada e deixa buracos para as subclasses preencherem.

«interface»

Interface

public interface Pagavel {
    double calcularValor();   // sem corpo
    void registrarPagamento();
}

class Fatura implements Pagavel { … }
class Salario implements Pagavel { … }
  • • Uma classe pode implementar quantas quiser
  • • Não tem estado (só constantes)
  • • Define capacidade: “é capaz de ser pago”
  • • Classes sem parentesco algum podem compartilhá-la
ClasseAbstrata

Classe abstrata

public abstract class Conta {
    protected double saldo;        // tem estado

    public void depositar(double v) {  // já pronto
        saldo += v;
    }
    public abstract double taxaMensal();  // buraco
}

class Poupanca extends Conta { … }
  • • Uma classe estende apenas uma
  • • Tem atributos, construtor e código pronto
  • • Define identidade: “é um tipo de conta”
  • • Não pode ser instanciada diretamente
Regra de bolso: se as classes compartilham estado e código e pertencem à mesma família conceitual, classe abstrata. Se compartilham apenas uma habilidade e podem vir de famílias diferentes, interface. Na dúvida, comece pela interface: ela acopla menos.

Por que Java proíbe herança múltipla de classes

  

    

      Se D herdasse de B e C, e ambas tivessem implementações diferentes
      de um mesmo método herdado de A, qual delas D usaria? Essa ambiguidade é o
      problema do diamante — e a razão de Java permitir apenas uma superclasse.
    

  


  

    

      
    

    

      

        
A solução de Java

        
    
          
  • Classes: herança simples. Só existe uma cadeia de implementação, logo não há ambiguidade de estado nem de código.
    • 
          
  • Interfaces: herança múltipla permitida — como eram apenas assinaturas, não havia conflito de implementação.
    • 
          
  • Desde o Java 8: interfaces podem ter métodos default com corpo. O diamante voltou… e a linguagem passou a exigir que você resolva o conflito explicitamente.
    • 
        

      

      

        
Desempate explícito

        
interface B { default String falar() { return "oi"; } }
interface C { default String falar() { return "olá"; } }

class D implements B, C {
    @Override
    public String falar() {
        return B.super.falar();  // você escolhe
    }
}

        
Sem esse override, o código não compila.

Três perguntas sobre contratos e esqueletos.


  

    

      
1. Você precisa que Documento, Pedido e Relatorio — classes sem nenhum parentesco — possam ser exportadas para PDF. O melhor mecanismo é:

      
      
      
      

        As três já pertencem a hierarquias próprias e não têm nada em comum além dessa capacidade.
        Forçar uma superclasse comum criaria uma família artificial e queimaria o único extends
        disponível de cada uma.
      

    


    

      
2. Uma classe abstrata pode ter métodos concretos (com corpo)?

      
      
      
      

        Uma classe abstrata com todos os métodos abstratos e sem atributos é, na prática, uma interface
        mais restritiva — e nesse caso a interface é a escolha melhor. O valor da classe abstrata está no
        código que ela já traz pronto.
      

    


    

      
3. Em UML, a linha tracejada com ponta triangular vazada representa:

      
      
      
      

        Mesma ponta, traço diferente: sólida = generalização (extends);
        tracejada = realização (implements). Tracejada com ponta de seta aberta
        já é outra coisa: dependência.
