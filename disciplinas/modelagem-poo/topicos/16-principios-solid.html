Código que compila × código que sobrevive

Saber a sintaxe de extends não faz ninguém projetar bem. Os cinco princípios SOLID, sistematizados por Robert C. Martin, são heurísticas para que um sistema orientado a objetos continue barato de mudar depois de anos de manutenção.

Eles atacam os quatro sintomas do projeto apodrecido: rigidez (toda mudança respinga em cinco lugares), fragilidade (mexer aqui quebra ali), imobilidade (não dá para reusar nada fora deste sistema) e viscosidade (fazer certo é mais difícil que fazer a gambiarra).

São princípios, não leis. Aplicados sem critério produzem o problema oposto: uma explosão de interfaces e classes minúsculas para um sistema que ninguém vai mudar nunca. Use-os quando houver razão concreta para esperar mudança naquele ponto.

De onde vêm os cinco princípios

  

    

      O acrônimo SOLID foi popularizado por Robert C. Martin (“Uncle Bob”) no início dos anos 2000, reunindo princípios
      formulados por outros autores: Liskov (1987), Meyer (1988, com o open–closed) e o próprio Martin. Eles não são
      leis, e sim heurísticas que descrevem o que torna um projeto fácil de mudar.
    

    

      O objetivo comum é controlar o acoplamento e a coesão. Um módulo coeso faz uma coisa.
      Um módulo pouco acoplado não depende de detalhes de outros. Quando esses dois critérios são atendidos, uma mudança fica
      restrita ao lugar onde ela deve acontecer.
    

  

  

    

      
SiglaPrincípioPergunta de revisão

      
        
SResponsabilidade Única (SRP)Quantas razões diferentes existem para esta classe mudar?

        
OAberto–Fechado (OCP)Adicionar um novo caso exige editar código existente?

        
LSubstituição de Liskov (LSP)O subtipo pode substituir o tipo base sem surpresas?

        
ISegregação de Interfaces (ISP)Algum cliente é obrigado a depender de métodos que não usa?

        
DInversão de Dependência (DIP)A regra de negócio depende de um detalhe concreto (banco, API)?

      
    

  






  
S — Responsabilidade Única

  

    Martin define a responsabilidade como uma razão para mudar, e não como uma tarefa. Uma classe deve ter apenas uma
    razão para mudar, ou seja, um único ator (grupo de pessoas) que a pede.
  


// ❌ Três razões para mudar: regra de cobrança, persistência e formato do recibo
public class Assinatura {
    public void cobrar(double valor) { /* regra */ }
    public void salvarNoBanco() { /* JDBC aqui */ }
    public String gerarReciboHtml() { /* HTML aqui */ }
}

// ✅ Cada responsabilidade tem sua classe
public class Assinatura { public void cobrar(double valor) { /* regra */ } }
public class RepositorioAssinaturas { /* persistência */ }
public class FormatadorRecibo { /* apresentação */ }

  

    
    

      Teste do ator: se o financeiro pede uma mudança na cobrança, a equipe de dados pede outra no banco e o
      marketing pede outra no recibo, a classe tem três atores e precisa ser dividida.
    

  






  
O — Aberto para extensão, fechado para modificação

  

    Bertrand Meyer (1988) propôs que um módulo deveria ser aberto para extensão e fechado para modificação. Na prática, isso
    significa que um novo comportamento entra como uma nova classe, e não como mais um if em código antigo.
  


// ❌ Cada novo meio de pagamento exige editar este método
public void cobrar(String meio, double valor) {
    if (meio.equals("cartao"))     { /* ... */ }
    else if (meio.equals("boleto")) { /* ... */ }
    else if (meio.equals("pix"))    { /* ... */ }
}

// ✅ Um contrato, e cada meio é uma extensão nova
public interface MeioDePagamento { void cobrar(double valor); }
public class Pix implements MeioDePagamento { public void cobrar(double v) { /* ... */ } }

  

    
    

      Aberto e fechado têm custo: o OCP só compensa onde a variação é real e recorrente. Abstrair antes de a
      variação aparecer é o erro de “abstração especulativa” discutido no tópico 03.
    

  






  
L — Substituição de Liskov

  

    O exemplo do retângulo e do quadrado (tópico 04) é o caso clássico. Subtipo que quebra o comportamento esperado do tipo
    base viola o LSP, mesmo que a herança compile sem erros.
  

  

    
    

      Sinal de violação: um if (x instanceof Subtipo) dentro de um método que recebe o tipo base
      é quase sempre um indício de que o subtipo não cumpre o contrato.
    

  






  
I — Segregação de Interfaces

  

    Clientes não devem ser forçados a depender de métodos que não usam. Uma interface “gorda” obriga toda implementação a
    fornecer métodos que podem não fazer sentido para ela.
  


// ❌ Interface gorda: ouvinte e artista não usam tudo
public interface Usuario {
    void ouvir(Musica m);
    void publicarAlbum(Album a);   // ouvinte não publica: seria exceção
}

// ✅ Interfaces por papel
public interface Ouvinte  { void ouvir(Musica m); }
public interface Publicador { void publicarAlbum(Album a); }






  
D — Inversão de Dependência

  

    Módulos de alto nível (regras de negócio) não devem depender de módulos de baixo nível (banco, API). Ambos devem depender
    de abstrações, e as abstrações não devem depender de detalhes.
  

  

    
flowchart LR
    subgraph Antes["Dependência direta"]
        R1["RegraCobranca"] --> B1["BancoPostgres"]
    end
    subgraph Depois["Dependência invertida"]
        R2["RegraCobranca"] --> I["«interface» Repositorio"]
        B2["BancoPostgres"] -.-> I
    end
    

  

  
Depois da inversão, a regra de negócio depende de uma interface que ela mesma define. O banco passa a implementar essa interface, e a seta de dependência aponta para a abstração.


public class RegraCobranca {
    private final Repositorio repositorio;     // abstração, não BancoPostgres
    public RegraCobranca(Repositorio r) { this.repositorio = r; }
}

  

    
    

      Benefício concreto: os testes de RegraCobranca usam um repositório falso em memória. Sem
      DIP, testar a regra exigiria um banco rodando.
    

  






  
SOLID não é uma checklist obrigatória

  

    

      Aplicar SOLID em tudo gera um sistema cheio de interfaces com uma única implementação, classes minúsculas e uma navegação
      cansativa. Os princípios têm custo: cada abstração é uma camada a mais para entender. A decisão correta depende de
      quanto a parte vai mudar.
    

    

      Regra de bolso: aplique o princípio quando a mudança já aconteceu ou é previsível com boa razão. Para código que nunca vai
      mudar, a solução simples é a melhor, e o princípio KISS e o YAGNI pesam mais.
    

  






  
Exercícios

  

    

      1. Uma classe Relatorio calcula totais, gera PDF e envia e-mail. Quais responsabilidades e quais atores?
      
Gabarito: três responsabilidades: cálculo (financeiro), geração do PDF (apresentação) e envio (comunicação). Cada uma muda por um ator diferente. Separe em três classes e uma orquestração simples.

    

    

      2. Por que o DIP ajuda a modelagem, e não só o código?
      
Gabarito: porque o diagrama passa a mostrar as regras de negócio dependendo de interfaces do domínio, e não de tecnologias. O modelo de domínio fica limpo, e a infraestrutura aparece no diagrama de componentes ou de implantação, como uma implementação da interface.

    

    

      3. Um sistema pequeno tem uma única forma de pagamento que não deve mudar. Você aplicaria OCP com uma interface?
      
Gabarito: não, por enquanto. Sem variação, a interface é custo sem benefício (YAGNI). Se a segunda forma de pagamento aparecer, aí se extrai a interface, e a refatoração é pequena com testes em volta.

Teste seu entendimento

  
Cinco perguntas — uma por princípio.


  

    

      
1. Uma classe Relatorio que calcula os dados e gera o PDF e envia por e-mail viola:

      
      
      
      

        Três motivos independentes para a classe mudar: regra de cálculo, layout do PDF e servidor de e-mail.
        Cada um pertence a um “ator” diferente da organização — e é esse o critério do SRP.
      

    


    

      
2. Adicionar uma forma de pagamento exige alterar um switch existente. Isso viola:

      
      
      
      

        Estender o comportamento deveria significar acrescentar uma classe, não editar
        código já testado. A solução é polimorfismo: uma interface e uma implementação por forma de pagamento.
      

    


    

      
3. Quadrado extends Retangulo quebra código que esperava alterar largura e altura de forma independente. Isso viola:

      
      
      
      

        O exemplo clássico: em matemática, quadrado é um retângulo; em código, ele não se comporta
        como um. LSP lembra que herança é sobre comportamento substituível, não sobre semelhança
        conceitual.
      

    


    

      
4. Uma interface Funcionario com 12 métodos obriga Estagiario a implementar aprovarFerias() lançando exceção. Isso viola:

      
      
      
      

        Métodos implementados como throw new UnsupportedOperationException() são o sintoma
        clássico: a interface é grande demais e deveria ser quebrada em contratos menores e coesos.
      

    


    

      
5. Um serviço que faz new MySQLRepositorio() dentro de si mesmo viola:

      
      
      
      

        A regra de negócio passa a depender de um detalhe de infraestrutura — e vira impossível testá-la sem
        um banco de verdade. A correção é receber a abstração Repositorio pelo construtor.
