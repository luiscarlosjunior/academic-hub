Código que compila × código que sobrevive

Saber a sintaxe de extends não faz ninguém projetar bem. Os cinco princípios SOLID, sistematizados por Robert C. Martin, são heurísticas para que um sistema orientado a objetos continue barato de mudar depois de anos de manutenção.

Eles atacam os quatro sintomas do projeto apodrecido: rigidez (toda mudança respinga em cinco lugares), fragilidade (mexer aqui quebra ali), imobilidade (não dá para reusar nada fora deste sistema) e viscosidade (fazer certo é mais difícil que fazer a gambiarra).

São princípios, não leis. Aplicados sem critério produzem o problema oposto: uma explosão de interfaces e classes minúsculas para um sistema que ninguém vai mudar nunca. Use-os quando houver razão concreta para esperar mudança naquele ponto.

Antes e depois, um a um

Escolha um princípio e compare o código problemático com a versão corrigida.

De onde vêm os cinco princípios

  

    

      O acrônimo SOLID foi popularizado por Robert C. Martin (“Uncle Bob”) no início dos anos 2000, reunindo princípios
      formulados por outros autores: Liskov (1987), Meyer (1988, com o open–closed) e o próprio Martin. Eles não são
      leis, e sim heurísticas que descrevem o que torna um projeto fácil de mudar.
    

    

      O objetivo comum é controlar o acoplamento e a coesão. Um módulo coeso faz uma coisa.
      Um módulo pouco acoplado não depende de detalhes de outros. Quando esses dois critérios são atendidos, uma mudança fica
      restrita ao lugar onde ela deve acontecer.

S — Responsabilidade Única

  

    Martin define a responsabilidade como uma razão para mudar, e não como uma tarefa. Uma classe deve ter apenas uma
    razão para mudar, ou seja, um único ator (grupo de pessoas) que a pede.
  


// ❌ Três razões para mudar: regra de cobrança, persistência e formato do recibo
public class Assinatura {
    public void cobrar(double valor) { /* regra */ }
    public void salvarNoBanco() { /* JDBC aqui */ }
    public String gerarReciboHtml() { /* HTML aqui */ }
}

// ✅ Cada responsabilidade tem sua classe
public class Assinatura { public void cobrar(double valor) { /* regra */ } }
public class RepositorioAssinaturas { /* persistência */ }
public class FormatadorRecibo { /* apresentação */ }

  

    
    

      Teste do ator: se o financeiro pede uma mudança na cobrança, a equipe de dados pede outra no banco e o
      marketing pede outra no recibo, a classe tem três atores e precisa ser dividida.
    

  






  
O — Aberto para extensão, fechado para modificação

  

    Bertrand Meyer (1988) propôs que um módulo deveria ser aberto para extensão e fechado para modificação. Na prática, isso
    significa que um novo comportamento entra como uma nova classe, e não como mais um if em código antigo.
  


// ❌ Cada novo meio de pagamento exige editar este método
public void cobrar(String meio, double valor) {
    if (meio.equals("cartao"))     { /* ... */ }
    else if (meio.equals("boleto")) { /* ... */ }
    else if (meio.equals("pix"))    { /* ... */ }
}

// ✅ Um contrato, e cada meio é uma extensão nova
public interface MeioDePagamento { void cobrar(double valor); }
public class Pix implements MeioDePagamento { public void cobrar(double v) { /* ... */ } }

  

    
    

      Aberto e fechado têm custo: o OCP só compensa onde a variação é real e recorrente. Abstrair antes de a
      variação aparecer é o erro de “abstração especulativa” discutido no tópico 03.
    

  






  
L — Substituição de Liskov

  

    O exemplo do retângulo e do quadrado (tópico 04) é o caso clássico. Subtipo que quebra o comportamento esperado do tipo
    base viola o LSP, mesmo que a herança compile sem erros.
  

  

    
    

      Sinal de violação: um if (x instanceof Subtipo) dentro de um método que recebe o tipo base
      é quase sempre um indício de que o subtipo não cumpre o contrato.
    

  






  
I — Segregação de Interfaces

  

    Clientes não devem ser forçados a depender de métodos que não usam. Uma interface “gorda” obriga toda implementação a
    fornecer métodos que podem não fazer sentido para ela.
  


// ❌ Interface gorda: ouvinte e artista não usam tudo
public interface Usuario {
    void ouvir(Musica m);
    void publicarAlbum(Album a);   // ouvinte não publica: seria exceção
}

// ✅ Interfaces por papel
public interface Ouvinte  { void ouvir(Musica m); }
public interface Publicador { void publicarAlbum(Album a); }






  
D — Inversão de Dependência

  

    Módulos de alto nível (regras de negócio) não devem depender de módulos de baixo nível (banco, API). Ambos devem depender
    de abstrações, e as abstrações não devem depender de detalhes.

Depois da inversão, a regra de negócio depende de uma interface que ela mesma define. O banco passa a implementar essa interface, e a seta de dependência aponta para a abstração.


public class RegraCobranca {
    private final Repositorio repositorio;     // abstração, não BancoPostgres
    public RegraCobranca(Repositorio r) { this.repositorio = r; }
}

  

    
    

      Benefício concreto: os testes de RegraCobranca usam um repositório falso em memória. Sem
      DIP, testar a regra exigiria um banco rodando.
    

  






  
SOLID não é uma checklist obrigatória

  

    

      Aplicar SOLID em tudo gera um sistema cheio de interfaces com uma única implementação, classes minúsculas e uma navegação
      cansativa. Os princípios têm custo: cada abstração é uma camada a mais para entender. A decisão correta depende de
      quanto a parte vai mudar.
    

    

      Regra de bolso: aplique o princípio quando a mudança já aconteceu ou é previsível com boa razão. Para código que nunca vai
      mudar, a solução simples é a melhor, e o princípio KISS e o YAGNI pesam mais.
    

  






  
Exercícios

  

    

      1. Uma classe Relatorio calcula totais, gera PDF e envia e-mail. Quais responsabilidades e quais atores?
      
Gabarito: três responsabilidades: cálculo (financeiro), geração do PDF (apresentação) e envio (comunicação). Cada uma muda por um ator diferente. Separe em três classes e uma orquestração simples.

    

    

      2. Por que o DIP ajuda a modelagem, e não só o código?
      
Gabarito: porque o diagrama passa a mostrar as regras de negócio dependendo de interfaces do domínio, e não de tecnologias. O modelo de domínio fica limpo, e a infraestrutura aparece no diagrama de componentes ou de implantação, como uma implementação da interface.

    

    

      3. Um sistema pequeno tem uma única forma de pagamento que não deve mudar. Você aplicaria OCP com uma interface?
      
Gabarito: não, por enquanto. Sem variação, a interface é custo sem benefício (YAGNI). Se a segunda forma de pagamento aparecer, aí se extrai a interface, e a refatoração é pequena com testes em volta.

Exemplo passo a passo: notificações que crescem sem doer

  
Um serviço envia avisos por e-mail e SMS. Depois, o time pediu push e WhatsApp. Vamos aplicar os princípios na ordem em que os problemas aparecem.


  
Passo 1 — a versão inicial que cresce mal

  
public class Notificador {
    public void enviar(String canal, String destino, String texto) {
        if (canal.equals("email")) { /* SMTP */ }
        else if (canal.equals("sms")) { /* operadora */ }
        // push e WhatsApp: mais um else if, mais uma vez mexendo aqui
    }
}

  
Aqui quebram dois princípios: OCP (cada canal novo exige editar o método) e SRP (a classe conhece regras de transporte de cada canal, e também decide o texto).


  
Passo 2 — aberto para extensão

  
public interface Canal {
    void enviar(String destino, String texto);
}

public class Notificador {
    private final Canal canal;                // depende da abstração (DIP)
    public Notificador(Canal canal) { this.canal = canal; }
    public void avisar(String destino, String texto) { canal.enviar(destino, texto); }
}

  
Push vira uma nova classe CanalPush implements Canal. Nenhuma linha de Notificador muda. Um teste pode injetar um Canal falso em memória.


  
Passo 3 — quando parar

  
Se o sistema tem dois canais e nenhuma previsão de terceiro, a interface é custo sem benefício. A regra: abstraia quando a segunda variação aparecer, e não antes. O exemplo vale como ensaio, não como obrigação para todo código.


  
Leitura de SOLID como ferramenta: cada princípio responde a uma dor concreta. Se você não consegue apontar a dor, o princípio ainda não é necessário.






  
Por que o SOLID existe

  



Os princípios não nasceram como lista. Eles surgiram de um problema que se repetia em projetos grandes: uma mudança pequena, como incluir um tipo de desconto, quebrava partes que não tinham nada a ver com ela. O custo de manter o software crescia mais rápido que o software.


A história, em poucas datas:


    

  • 1988. Bertrand Meyer, em Object-Oriented Software Construction, formula a ideia de módulos abertos para extensão e fechados para modificação. É a origem do “O”.
    • 

  • 1987–1994. Barbara Liskov apresenta, em palestra de 1987, a ideia de que um subtipo deve poder substituir o tipo base sem que o programa perceba. Liskov e Wing formalizam isso em 1994. É a origem do “L”.
    • 

  • Final dos anos 1990 a 2003. Robert C. Martin reúne princípios de design orientado a objetos e de desenvolvimento ágil. Em Agile Software Development (2002/2003), define o critério de responsabilidade e a inversão de dependência. Origem de “S” e “D”, e de parte do “I”.
    • 

  • Por volta de 2004. Michael Feathers reúne as cinco iniciais na sigla SOLID, que se espalha pela comunidade.
    • 



Por que isso importa para quem está aprendendo? Porque os cinco princípios descrevem o mesmo problema visto de cinco ângulos: acoplamento. Quanto mais partes de um sistema dependem umas das outras de forma concreta, mais caro fica mudar qualquer uma delas. As animações abaixo mostram esse custo com contas.


  





  
Visão geral: o que é o SOLID, em um parágrafo

  



SOLID é um conjunto de cinco princípios de projeto orientado a objetos. Cada um responde a uma pergunta sobre mudanças: quem deve mudar (S), o que pode ser estendido sem mudar (O), o que pode substituir o quê (L), quem depende do quê (I e D). Eles não são regras absolutas: são critérios para estimar o custo de mudança de um sistema.



Os projetos desta aula seguem o mesmo roteiro para cada princípio: conceito, origem, o problema na versão ruim, a versão boa com a mesma saída e um exercício. Você pode usar os dez programas em sala, na ordem S, O, L, I, D, ou na ordem que for mais útil para a turma.


  





  
Animação: quanto custa a complexidade

  



O argumento a favor dos princípios é quantitativo. Vamos contar: quantas linhas são editadas e quantos testes precisam ser repetidos quando o sistema cresce. Use os botões da animação para ver cada passo.



Cálculo 1: novos descontos (princípio O)


Modelo usado: cada tipo novo de desconto custa 3 linhas. Na versão ruim, ele é um ramo do if/else, então os tipos antigos precisam ser testados de novo. Na versão boa, ele é uma classe nova, e só o novo é testado.



  
Animação: a calculadora de descontos




import java.util.Locale;

/**
 * O ruim: cada novo tipo de desconto obriga a editar o método existente.
 * O if/else cresce, e cada teste antigo precisa ser refeito.
 */
public class Main {

    static final class CalculadoraDesconto {
        double calcular(double total, String tipoCliente) {
            if (tipoCliente.equals("VIP")) {
                return total * 0.80;
            } else if (tipoCliente.equals("FUNCIONARIO")) {
                return total * 0.70;
            } else if (tipoCliente.equals("NORMAL")) {
                return total;
            }
            // para incluir ESTUDANTE, é preciso abrir esta classe e mudar a lógica
            throw new IllegalArgumentException("tipo desconhecido: " + tipoCliente);
        }
    }

    public static void main(String[] args) {
        Locale.setDefault(Locale.ROOT);
        CalculadoraDesconto calc = new CalculadoraDesconto();
        System.out.printf("VIP: %.2f%n", calc.calcular(200, "VIP"));
        System.out.printf("FUNCIONARIO: %.2f%n", calc.calcular(200, "FUNCIONARIO"));
        System.out.printf("NORMAL: %.2f%n", calc.calcular(200, "NORMAL"));
        try {
            calc.calcular(200, "ESTUDANTE");
        } catch (IllegalArgumentException e) {
            System.out.println("erro: " + e.getMessage());
        }
    }
}

Cálculo 2: trocar o banco de dados (princípio D)


Modelo usado: cada serviço que faz new BancoMySql() precisa ser editado para trocar de banco. Na versão boa, a troca acontece em um único ponto de montagem.



  
Animação: a troca de banco




import java.util.ArrayList;
import java.util.List;
import java.util.Locale;

/**
 * D ruim: ServicoPedido cria o banco e o e-mail por conta própria (new).
 * Não dá para testar sem banco real e sem enviar e-mail de verdade.
 */
public class Main {

    static final class BancoMySql {
        private final List<String> tabela = new ArrayList<>();
        void inserir(String pedido) {
            tabela.add(pedido);
            System.out.println("INSERT INTO pedidos (dados) VALUES ('" + pedido + "') -- servidor MySQL");
        }
    }

    static final class ServidorSmtp {
        void enviar(String para, String texto) {
            System.out.println("SMTP -> " + para + ": " + texto);
        }
    }

    static final class ServicoPedido {
        // dependências concretas, criadas aqui dentro
        private final BancoMySql banco = new BancoMySql();
        private final ServidorSmtp smtp = new ServidorSmtp();

        void finalizar(String id, String email) {
            banco.inserir(id);
            smtp.enviar(email, "pedido " + id + " confirmado");
        }
    }

    public static void main(String[] args) {
        Locale.setDefault(Locale.ROOT);
        new ServicoPedido().finalizar("P-1001", "ana@exemplo.com");
    }
}

S — Responsabilidade única

  



Conceito


Uma classe deve ter um, e apenas um, motivo para mudar. Um motivo é um grupo de interessados que pode pedir alterações (Martin, 2003).


Por que existe


O critério nasce da manutenção: quando uma classe tem dois motivos para mudar, cada mudança de um lado arrisca quebrar o outro. Responsabilidade é o motivo, e não a quantidade de métodos.


O problema, na prática


Na versão ruim, ProcessadorPedido valida, calcula o total, aplica desconto, grava em arquivo e envia e-mail. Quando o formato do arquivo muda, o cálculo é retestado; quando a regra de desconto muda, o e-mail também precisa ser verificado.



S — Responsabilidade única: versão ruim


import java.util.ArrayList;
import java.util.List;
import java.util.Locale;

/**
 * S ruim: ProcessadorPedido valida, calcula, grava em arquivo e envia e-mail.
 * Qualquer mudança em uma dessas regras obriga a abrir e testar a mesma classe.
 */
public class Main {

    record Item(String nome, double preco, int quantidade) {}

    static final class Pedido {
        final String id;
        final String emailCliente;
        final List<Item> itens = new ArrayList<>();

        Pedido(String id, String emailCliente) {
            this.id = id;
            this.emailCliente = emailCliente;
        }
    }

    static final class ProcessadorPedido {
        double processar(Pedido pedido) {
            // validação
            if (pedido.itens.isEmpty()) {
                throw new IllegalArgumentException("pedido vazio: " + pedido.id);
            }
            // cálculo do total e regra de desconto
            double total = 0;
            for (Item item : pedido.itens) {
                total += item.preco() * item.quantidade();
            }
            if (total > 500) {
                total *= 0.95;
            }
            // formatação e persistência (arquivo)
            String linha = pedido.id + ";" + String.format("%.2f", total);
            System.out.println("gravando em pedidos.csv: " + linha);
            // notificação por e-mail
            System.out.println("enviando e-mail para " + pedido.emailCliente
                    + ": pedido " + pedido.id + " confirmado, total R$ " + String.format("%.2f", total));
            return total;
        }
    }

    public static void main(String[] args) {
        Locale.setDefault(Locale.ROOT);
        Pedido pedido = new Pedido("P-1001", "ana@exemplo.com");
        pedido.itens.add(new Item("teclado", 150.00, 2));
        pedido.itens.add(new Item("mouse", 80.00, 3));
        new ProcessadorPedido().processar(pedido);
    }
}


Saída real


gravando em pedidos.csv: P-1001;513.00
enviando e-mail para ana@exemplo.com: pedido P-1001 confirmado, total R$ 513.00


S — Responsabilidade única: versão boa


import java.util.ArrayList;
import java.util.List;
import java.util.Locale;

/**
 * S bom: cada classe tem um motivo para mudar.
 * Validação, cálculo, persistência e notificação ficam separados; o orquestrador só chama as partes.
 */
public class Main {

    record Item(String nome, double preco, int quantidade) {}

    static final class Pedido {
        final String id;
        final String emailCliente;
        final List<Item> itens = new ArrayList<>();

        Pedido(String id, String emailCliente) {
            this.id = id;
            this.emailCliente = emailCliente;
        }
    }

    // Motivo para mudar: regras de validação
    static final class ValidadorPedido {
        void validar(Pedido pedido) {
            if (pedido.itens.isEmpty()) {
                throw new IllegalArgumentException("pedido vazio: " + pedido.id);
            }
        }
    }

    // Motivo para mudar: regras de preço e desconto
    static final class CalculadoraTotal {
        double calcular(Pedido pedido) {
            double total = 0;
            for (Item item : pedido.itens) {
                total += item.preco() * item.quantidade();
            }
            return total > 500 ? total * 0.95 : total;
        }
    }

    // Motivo para mudar: formato ou local de gravação
    static final class RepositorioPedidos {
        void salvar(Pedido pedido, double total) {
            System.out.println("gravando em pedidos.csv: " + pedido.id + ";" + String.format("%.2f", total));
        }
    }

    // Motivo para mudar: canal de notificação
    static final class Notificador {
        void confirmar(Pedido pedido, double total) {
            System.out.println("enviando e-mail para " + pedido.emailCliente
                    + ": pedido " + pedido.id + " confirmado, total R$ " + String.format("%.2f", total));
        }
    }

    // Orquestrador: só coordena, não decide regra alguma
    static final class ProcessadorPedido {
        private final ValidadorPedido validador = new ValidadorPedido();
        private final CalculadoraTotal calculadora = new CalculadoraTotal();
        private final RepositorioPedidos repositorio = new RepositorioPedidos();
        private final Notificador notificador = new Notificador();

        double processar(Pedido pedido) {
            validador.validar(pedido);
            double total = calculadora.calcular(pedido);
            repositorio.salvar(pedido, total);
            notificador.confirmar(pedido, total);
            return total;
        }
    }

    public static void main(String[] args) {
        Locale.setDefault(Locale.ROOT);
        Pedido pedido = new Pedido("P-1001", "ana@exemplo.com");
        pedido.itens.add(new Item("teclado", 150.00, 2));
        pedido.itens.add(new Item("mouse", 80.00, 3));
        new ProcessadorPedido().processar(pedido);
    }
}


Saída real


gravando em pedidos.csv: P-1001;513.00
enviando e-mail para ana@exemplo.com: pedido P-1001 confirmado, total R$ 513.00




O que mudou: O orquestrador (ProcessadorPedido) só chama as partes. Cada regra virou uma classe com um motivo para mudar: ValidadorPedido, CalculadoraTotal, RepositorioPedidos, Notificador. O comportamento impresso é o mesmo, e isso é o critério de uma refatoração.


Exercício para a turma

O — Aberto para extensão, fechado para modificação

  



Conceito


Um módulo deve poder ser estendido sem que seu código existente seja alterado (Meyer, 1988).


Por que existe


Meyer propôs a ideia em 1988: código já testado é ativo caro. Se uma nova regra exige editar um método que já funciona, todo o teste anterior volta a valer como dúvida.


O problema, na prática


CalculadoraDesconto tem um if/else por tipo de cliente. Cada tipo novo edita o método, que já tinha testes. A tabela de animação mostra que o número de testes a repetir cresce como uma soma.



O — Aberto para extensão, fechado para modificação: versão ruim


import java.util.Locale;

/**
 * O ruim: cada novo tipo de desconto obriga a editar o método existente.
 * O if/else cresce, e cada teste antigo precisa ser refeito.
 */
public class Main {

    static final class CalculadoraDesconto {
        double calcular(double total, String tipoCliente) {
            if (tipoCliente.equals("VIP")) {
                return total * 0.80;
            } else if (tipoCliente.equals("FUNCIONARIO")) {
                return total * 0.70;
            } else if (tipoCliente.equals("NORMAL")) {
                return total;
            }
            // para incluir ESTUDANTE, é preciso abrir esta classe e mudar a lógica
            throw new IllegalArgumentException("tipo desconhecido: " + tipoCliente);
        }
    }

    public static void main(String[] args) {
        Locale.setDefault(Locale.ROOT);
        CalculadoraDesconto calc = new CalculadoraDesconto();
        System.out.printf("VIP: %.2f%n", calc.calcular(200, "VIP"));
        System.out.printf("FUNCIONARIO: %.2f%n", calc.calcular(200, "FUNCIONARIO"));
        System.out.printf("NORMAL: %.2f%n", calc.calcular(200, "NORMAL"));
        try {
            calc.calcular(200, "ESTUDANTE");
        } catch (IllegalArgumentException e) {
            System.out.println("erro: " + e.getMessage());
        }
    }
}

import java.util.Locale;

/**
 * O bom: a calculadora é fechada para mudança e aberta para extensão.
 * Um novo desconto é uma nova classe que implementa a interface; nenhuma linha antiga muda.
 */
public class Main {

    interface Desconto {
        double aplicar(double total);
    }

    static final class SemDesconto implements Desconto {
        public double aplicar(double total) { return total; }

    static final class DescontoVip implements Desconto {
        public double aplicar(double total) { return total * 0.80; }
    }

    static final class DescontoFuncionario implements Desconto {
        public double aplicar(double total) { return total * 0.70; }
    }

    // Adicionado depois, sem tocar nas classes acima
    static final class DescontoEstudante implements Desconto {
        public double aplicar(double total) { return total * 0.85; }
    }

    static final class CalculadoraDesconto {
        double calcular(double total, Desconto desconto) {
            return desconto.aplicar(total);
        }

        System.out.printf("NORMAL: %.2f%n", calc.calcular(200, new SemDesconto()));

}

NORMAL: 200.00

O que mudou: A calculadora passou a receber um objeto Desconto. Cada regra é uma classe nova que implementa a interface. Adicionar ESTUDANTE é criar uma classe; nenhuma linha antiga muda.

L — Substituição de Liskov

  



Conceito


Objetos de um subtipo devem poder substituir objetos do tipo base sem que o programa deixe de funcionar corretamente (Liskov, 1987; Liskov e Wing, 1994).


Por que existe


Herança é reuso de comportamento, mas herança mal feita quebra o contrato. A regra de Liskov é: o subtipo não pode enfraquecer garantias nem exigir mais do que o tipo base exige.


O problema, na prática


Quadrado herda de Retangulo e sobrescreve setLargura e setAltura para manter os lados iguais. Quem usou Retangulo espera que largura e altura mudem de forma independente. O teste de área com 5 e 4 dá 16, e não 20.



L — Substituição de Liskov: versão ruim


import java.util.Locale;

/**
 * L ruim: Quadrado herda de Retangulo e quebra o contrato de setLargura/setAltura.
 * Código que usa Retangulo espera que largura e altura mudem de forma independente.
 */
public class Main {

    static class Retangulo {
        protected int largura;
        protected int altura;

        void setLargura(int largura) { this.largura = largura; }
        void setAltura(int altura) { this.altura = altura; }
        int area() { return largura * altura; }
    }

    static final class Quadrado extends Retangulo {
        @Override void setLargura(int valor) { largura = valor; altura = valor; }
        @Override void setAltura(int valor) { largura = valor; altura = valor; }
    }

    static void testarArea(Retangulo r) {
        r.setLargura(5);
        r.setAltura(4);
        int esperado = 20;
        System.out.println("esperado " + esperado + ", obtido " + r.area()
                + (r.area() == esperado ? " (ok)" : " (FALHOU)"));
    }

    public static void main(String[] args) {
        Locale.setDefault(Locale.ROOT);
        testarArea(new Retangulo());
        testarArea(new Quadrado());
    }
}


Saída real


esperado 20, obtido 20 (ok)
esperado 20, obtido 16 (FALHOU)


L — Substituição de Liskov: versão boa


import java.util.Locale;

/**
 * L bom: a forma é um contrato comum (área), sem herança que quebre o comportamento.
 * Retangulo e Quadrado são implementações independentes, e o teste de área vale para os dois.
 */
public class Main {

    interface Forma {
        int area();
    }

    // imutável: não há setters, então nenhuma substituição pode quebrar o contrato
    record Retangulo(int largura, int altura) implements Forma {
        public int area() { return largura * altura; }
    }

    record Quadrado(int lado) implements Forma {
        public int area() { return lado * lado; }
    }

    static void testarArea(String nome, Forma forma, int esperado) {
        System.out.println(nome + ": esperado " + esperado + ", obtido " + forma.area()
                + (forma.area() == esperado ? " (ok)" : " (FALHOU)"));
    }

    public static void main(String[] args) {
        Locale.setDefault(Locale.ROOT);
        testarArea("retangulo 5x4", new Retangulo(5, 4), 20);
        testarArea("quadrado 4", new Quadrado(4), 16);
    }
}


Saída real


retangulo 5x4: esperado 20, obtido 20 (ok)
quadrado 4: esperado 16, obtido 16 (ok)




O que mudou: A forma virou um contrato (interface Forma) com área. Retangulo e Quadrado são registros imutáveis e independentes. Não há setter para quebrar, e o teste de área vale para os dois.


Exercício para a turma
Escreva um teste de contrato para Forma que qualquer implementação precisa passar. Depois crie um Triangulo que passe no teste. O que o teste tem de verificar, além da área?


  





  
I — Segregação de interfaces

  



Conceito


Um cliente não deve ser obrigado a depender de métodos que não usa. É melhor várias interfaces pequenas do que uma grande.


Por que existe


Martin descreve o princípio a partir de um projeto de software para impressoras, em que a mesma interface obrigava classes simples a implementar funções de fax e escaneamento.


O problema, na prática


Equipamento obriga toda impressora a ter escanear e enviarFax. ImpressoraSimples lança UnsupportedOperationException. O erro só aparece em tempo de execução, quando alguém chama o método.



I — Segregação de interfaces: versão ruim


import java.util.Locale;

/**
 * I ruim: uma interface gorda obriga a implementação a ter métodos que ela não usa.
 * ImpressoraSimples precisa "implementar" escanear e fax, e lança exceção.
 */
public class Main {

    interface Equipamento {
        void imprimir(String texto);
        void escanear();
        void enviarFax(String numero);
    }

    static final class ImpressoraSimples implements Equipamento {
        public void imprimir(String texto) { System.out.println("imprimindo: " + texto); }
        public void escanear() { throw new UnsupportedOperationException("não escaneia"); }
        public void enviarFax(String numero) { throw new UnsupportedOperationException("não envia fax"); }
    }

    public static void main(String[] args) {
        Locale.setDefault(Locale.ROOT);
        Equipamento eq = new ImpressoraSimples();
        eq.imprimir("relatório de vendas");
        try {
            eq.escanear();
        } catch (UnsupportedOperationException e) {
            System.out.println("erro em tempo de execução: " + e.getMessage());
        }
    }
}


Saída real


imprimindo: relatório de vendas
erro em tempo de execução: não escaneia


I — Segregação de interfaces: versão boa


import java.util.Locale;

/**
 * I bom: interfaces pequenas, uma por capacidade.
 * Cada classe implementa só o que de fato faz; quem precisa de escanear depende só de Escaneavel.
 */
public class Main {

    interface Imprimivel { void imprimir(String texto); }
    interface Escaneavel { void escanear(); }
    interface Fax { void enviarFax(String numero); }

    static final class ImpressoraSimples implements Imprimivel {
        public void imprimir(String texto) { System.out.println("imprimindo: " + texto); }
    }

    static final class MultifuncionalCompleta implements Imprimivel, Escaneavel, Fax {
        public void imprimir(String texto) { System.out.println("imprimindo: " + texto); }
        public void escanear() { System.out.println("escaneando documento"); }
        public void enviarFax(String numero) { System.out.println("enviando fax para " + numero); }
    }

    // depende só do que usa: não precisa saber que existe fax
    static void digitalizar(Escaneavel equipamento) {
        equipamento.escanear();
    }

    public static void main(String[] args) {
        Locale.setDefault(Locale.ROOT);
        new ImpressoraSimples().imprimir("relatório de vendas");
        MultifuncionalCompleta mf = new MultifuncionalCompleta();
        digitalizar(mf);
        mf.enviarFax("1199999-0000");
    }
}


Saída real


imprimindo: relatório de vendas
escaneando documento
enviando fax para 1199999-0000




O que mudou: As capacidades viraram interfaces separadas: Imprimivel, Escaneavel e Fax. A impressora simples implementa só uma. Quem precisa de escanear depende só de Escaneavel, e o compilador acusa qualquer uso errado.

D — Inversão de dependência

  



Conceito


Módulos de alto nível não devem depender de módulos de baixo nível: ambos devem depender de abstrações. Abstrações não devem depender de detalhes (Martin, 2003).


Por que existe


Sem essa regra, a regra de negócio (pedido) fica presa à tecnologia (MySQL, SMTP). Fowler (2004) descreve a injeção de dependência como a forma prática de inverter essa seta: as dependências chegam de fora.


O problema, na prática


ServicoPedido cria BancoMySql e ServidorSmtp com new. Não há como testar o serviço sem banco e sem enviar e-mail de verdade. Trocar o banco exige editar cada serviço que o usa.



D — Inversão de dependência: versão ruim


import java.util.ArrayList;
import java.util.List;
import java.util.Locale;

/**
 * D ruim: ServicoPedido cria o banco e o e-mail por conta própria (new).
 * Não dá para testar sem banco real e sem enviar e-mail de verdade.
 */
public class Main {

    static final class BancoMySql {
        private final List<String> tabela = new ArrayList<>();
        void inserir(String pedido) {
            tabela.add(pedido);
            System.out.println("INSERT INTO pedidos (dados) VALUES ('" + pedido + "') -- servidor MySQL");
        }
    }

    static final class ServidorSmtp {
        void enviar(String para, String texto) {
            System.out.println("SMTP -> " + para + ": " + texto);
        }
    }

    static final class ServicoPedido {
        // dependências concretas, criadas aqui dentro
        private final BancoMySql banco = new BancoMySql();
        private final ServidorSmtp smtp = new ServidorSmtp();

        void finalizar(String id, String email) {
            banco.inserir(id);
            smtp.enviar(email, "pedido " + id + " confirmado");
        }
    }

    public static void main(String[] args) {
        Locale.setDefault(Locale.ROOT);
        new ServicoPedido().finalizar("P-1001", "ana@exemplo.com");
    }
}


Saída real


INSERT INTO pedidos (dados) VALUES ('P-1001') -- servidor MySQL
SMTP -> ana@exemplo.com: pedido P-1001 confirmado


D — Inversão de dependência: versão boa


import java.util.ArrayList;
import java.util.List;
import java.util.Locale;

/**
 * D bom: ServicoPedido depende de abstrações (RepositorioPedidos, Notificador).
 * Quem monta o objeto decide a implementação: produção usa MySQL e SMTP; o teste usa versões falsas.
 */
public class Main {

    // abstrações de alto nível
    interface RepositorioPedidos { void salvar(String id); }
    interface Notificador { void notificar(String destino, String mensagem); }

    // detalhes de baixo nível: produção
    static final class RepositorioMySql implements RepositorioPedidos {
        public void salvar(String id) { System.out.println("MySQL: pedido " + id + " gravado"); }
    }

    static final class NotificadorSmtp implements Notificador {
        public void notificar(String destino, String mensagem) {
            System.out.println("SMTP -> " + destino + ": " + mensagem);
        }
    }

    // detalhe para teste: não toca em rede nem em disco
    static final class RepositorioEmMemoria implements RepositorioPedidos {
        final List<String> gravados = new ArrayList<>();
        public void salvar(String id) { gravados.add(id); }
    }

    static final class NotificadorFalso implements Notificador {
        public void notificar(String destino, String mensagem) {
            System.out.println("(teste) notificação para " + destino + ": " + mensagem);
        }
    }

    static final class ServicoPedido {
        private final RepositorioPedidos repositorio;
        private final Notificador notificador;

        // dependências chegam pelo construtor (injeção de dependência)
        ServicoPedido(RepositorioPedidos repositorio, Notificador notificador) {
            this.repositorio = repositorio;
            this.notificador = notificador;
        }

        void finalizar(String id, String email) {
            repositorio.salvar(id);
            notificador.notificar(email, "pedido " + id + " confirmado");
        }
    }

    public static void main(String[] args) {
        Locale.setDefault(Locale.ROOT);
        System.out.println("== produção");
        new ServicoPedido(new RepositorioMySql(), new NotificadorSmtp()).finalizar("P-1001", "ana@exemplo.com");

        System.out.println("== teste");
        RepositorioEmMemoria memoria = new RepositorioEmMemoria();
        new ServicoPedido(memoria, new NotificadorFalso()).finalizar("P-T1", "teste@exemplo.com");
        System.out.println("gravados em memória: " + memoria.gravados);
    }
}


Saída real


== produção
MySQL: pedido P-1001 gravado
SMTP -> ana@exemplo.com: pedido P-1001 confirmado
== teste
(teste) notificação para teste@exemplo.com: pedido P-T1 confirmado
gravados em memória: [P-T1]




O que mudou: ServicoPedido depende de RepositorioPedidos e Notificador, que são interfaces. O main decide qual implementação usar: MySQL e SMTP em produção, versões em memória no teste. A regra de negócio não sabe qual tecnologia está por trás.

Cinco perguntas — uma por princípio.


  

    

      
1. Uma classe Relatorio que calcula os dados e gera o PDF e envia por e-mail viola:

      
      
      
      

        Três motivos independentes para a classe mudar: regra de cálculo, layout do PDF e servidor de e-mail.
        Cada um pertence a um “ator” diferente da organização — e é esse o critério do SRP.
      

    


    

      
2. Adicionar uma forma de pagamento exige alterar um switch existente. Isso viola:

      
      
      
      

        Estender o comportamento deveria significar acrescentar uma classe, não editar
        código já testado. A solução é polimorfismo: uma interface e uma implementação por forma de pagamento.
      

    


    

      
3. Quadrado extends Retangulo quebra código que esperava alterar largura e altura de forma independente. Isso viola:

      
      
      
      

        O exemplo clássico: em matemática, quadrado é um retângulo; em código, ele não se comporta
        como um. LSP lembra que herança é sobre comportamento substituível, não sobre semelhança
        conceitual.
      

    


    

      
4. Uma interface Funcionario com 12 métodos obriga Estagiario a implementar aprovarFerias() lançando exceção. Isso viola:

      
      
      
      

        Métodos implementados como throw new UnsupportedOperationException() são o sintoma
        clássico: a interface é grande demais e deveria ser quebrada em contratos menores e coesos.
      

    


    

      
5. Um serviço que faz new MySQLRepositorio() dentro de si mesmo viola:

      
      
      
      

        A regra de negócio passa a depender de um detalhe de infraestrutura — e vira impossível testá-la sem
        um banco de verdade. A correção é receber a abstração Repositorio pelo construtor.
