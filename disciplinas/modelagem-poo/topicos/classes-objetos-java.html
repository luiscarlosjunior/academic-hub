Classe é o molde, objeto é o bolo

Esta é a distinção mais importante de toda a orientação a objetos, e o erro mais comum de quem começa. A classe é o molde: existe uma vez, no código, e define quais atributos e operações os objetos terão. O objeto é uma instância feita a partir desse molde: existem muitos, em tempo de execução, cada um com os próprios valores.

Pense em uma fôrma de bolo. A fôrma é uma só, mas dela saem vários bolos. Cada bolo tem o próprio sabor, tamanho e data de validade — mesmo seguindo o mesmo formato.

Na UML, a classe aparece uma vez. Os objetos são as instâncias que o programa cria em memória.

Classe

Existe uma vez, em tempo de projeto. É o arquivo Musica.java.

Objeto

Existe muitas vezes, em tempo de execução. Cada um criado com new.

Estado

Cada objeto guarda seus próprios valores nos atributos.

Declarando uma classe em Java

Uma classe Java tem três partes que você já reconhece do diagrama: o nome, os atributos (o estado) e o construtor, que é a regra de como um objeto nasce. As operações vêm no tópico seguinte. 

// Musica.java — o molde de uma faixa do catálogo Melodia
package com.melodia.catalogo;

public class Musica {

    // atributos: o estado que cada objeto vai guardar
    private final String titulo;
    private final String artista;
    private final int duracaoSegundos;

    // construtor: chamado pelo "new", monta o objeto no estado inicial
    public Musica(String titulo, String artista, int duracaoSegundos) {
        this.titulo = titulo;
        this.artista = artista;
        this.duracaoSegundos = duracaoSegundos;
    }
}
this.titulo = titulo; — o this diferencia o atributo do objeto (lado esquerdo) do parâmetro recebido (lado direito). Quando os nomes são iguais, sem o this o Java atribui o parâmetro a ele mesmo e o atributo fica vazio.

Criando objetos com new

Cada new chama o construtor e produz um objeto distinto, com seus próprios valores. Mesmo que dois objetos tenham o mesmo artista, eles são duas faixas diferentes na memória. 

public class Principal {
    public static void main(String[] args) {
        Musica m1 = new Musica("Gravidade Zero", "Banda Nébula", 213);
        Musica m2 = new Musica("Cometa",          "Banda Nébula", 187);
        Musica m3 = new Musica("Silêncio Sideral", "Banda Nébula", 245);

        // três objetos, um molde: mesmo tipo, estados diferentes
        System.out.println(m1.getTitulo());   // Gravidade Zero
        System.out.println(m2.getTitulo());   // Cometa
    }
}

Três objetos (m1, m2, m3) nascem do mesmo molde Musica. Cada um guarda seu próprio título e duração.

Identidade: o objeto é ele mesmo

Todo objeto tem identidade (é ele, não outro), estado (os valores atuais) e comportamento (o que sabe fazer). Em Java, a variável guarda uma referência para o objeto, não o objeto em si. Por isso a comparação muda de sentido. 

Musica a = new Musica("Cometa", "Banda Nébula", 187);
Musica b = new Musica("Cometa", "Banda Nébula", 187);
Musica c = a;                       // c aponta para o MESMO objeto que a

System.out.println(a == b);           // false: dois objetos diferentes, mesmo conteúdo
System.out.println(a == c);           // true:  é o mesmo objeto (mesma identidade)
c.getTitulo();                        // "Cometa" — alterar por c altera a também
== compara identidade (a mesma referência?), não conteúdo. Para comparar o conteúdo, a classe precisa sobrescrever equals (e hashCode). Na dúvida, pergunte-se: “estou comparando o mesmo objeto ou valores iguais?”

Por que isso importa na modelagem?

Quando o diagrama de classes mostra Playlist apontando para Musica, ele está dizendo que a playlist guarda referências para músicas já existentes. Se duas playlists apontam para a mesma faixa, elas compartilham o mesmo objeto: alterar a música por uma playlist altera a vista pela outra. Isso é exatamente a agregação do tópico de relacionamentos.

O construtor garante um objeto válido

O construtor é a porta de entrada. Se ele aceita qualquer coisa, o objeto nasce inválido e o problema aparece longe da causa. Veja a diferença na classe ContaBancaria do domínio Melodia. 

// ❌ Sem validação: aceita uma conta com saldo negativo logo na criação
public ContaBancaria(String numero, double saldoInicial) {
    this.numero = numero;
    this.saldo  = saldoInicial;           // -500.0 entra sem reclamar
}

// ✅ Com validação: o objeto só existe se estiver em estado válido
public ContaBancaria(String numero, double saldoInicial) {
    if (numero == null || numero.isBlank())
        throw new IllegalArgumentException("número da conta é obrigatório");
    if (saldoInicial < 0)
        throw new IllegalArgumentException("saldo inicial não pode ser negativo (regra R1)");
    this.numero = numero;
    this.saldo  = saldoInicial;
}
Regra prática: a regra de negócio que vale “para sempre” (um invariante) deve ser garantida já no construtor. Assim, nenhum código consegue criar um objeto que a viole.

Na indústria

Em sistemas modernos você verá muitos objetos que só carregam dados, sem regras: os DTOs, que transportam informação entre camadas. Em Java 16+, eles costumam ser escritos como record, que gera construtor, getters, equals e hashCode automaticamente: 

// Um record: molde enxuto para transportar dados de uma música
public record MusicaDTO(String titulo, String artista, int duracaoSegundos) {}

MusicaDTO x = new MusicaDTO("Cometa", "Banda Nébula", 187);
x.titulo();   // "Cometa"

Mesmo assim, a regra de negócio continua precisando morar em alguma classe com comportamento. Um objeto sem regra não é um erro; o erro é espalhar a regra por todo o sistema.

Teste seus conhecimentos

Após Musica a = new Musica(...) e Musica b = a;, o que vale para a == b?

Correto. b = a copia a referência, não o objeto. Os dois nomes apontam para a mesma instância, então a identidade é igual.

Qual trecho impede que uma conta nasça com saldo negativo?

Correto. O construtor é o ponto em que o objeto nasce. Validar ali garante o invariante para toda instância criada.

O que levar deste tópico

  • Classe é o molde (uma vez); objeto é a instância (muitas, criadas com new).
  • Cada objeto tem identidade, estado e comportamento. Em Java, variáveis guardam referências.
  • == compara identidade; equals compara conteúdo.
  • O construtor garante que o objeto nasça válido. Regras que nunca podem ser violadas moram ali.
