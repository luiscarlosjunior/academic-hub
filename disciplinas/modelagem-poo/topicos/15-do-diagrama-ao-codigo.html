Cada símbolo tem um equivalente exato

A maior parte do diagrama de classes traduz-se para código de forma mecânica: caixa vira classe, atributo vira campo, operação vira método, seta vira extends, implements ou atributo. Saber essa tabela de correspondência de cor é o que transforma o diagrama de “desenho bonito” em ferramenta de trabalho.

O que não é mecânico: multiplicidades viram decisões sobre tipo de coleção; composição vira decisão sobre quem cria e destrói; e bidirecionalidade vira código de sincronização que ninguém gosta de manter.

Multiplicidade vira tipo, e o tipo vira regra

  

    

      A multiplicidade é a parte mais informativa do diagrama, e a mais esquecida no código. Ela decide o tipo do campo e as
      validações do construtor. Um 1..* exige uma lista não vazia, e um 0..1 aceita null ou
      Optional.
    

  


// Album "1" *-- "1..*" Musica   (composição, pelo menos uma faixa)
public class Album {
    private final List<Musica> faixas = new ArrayList<>();

    public Album(String titulo, String artista, int primeiraDuracao) {
        // 1..* : o álbum nasce com pelo menos uma faixa
        faixas.add(new Musica(titulo, artista, primeiraDuracao));
    }
}

// Playlist "0..*" o-- "0..*" Musica   (agregação: a música vem de fora)
public class Playlist {
    private final List<Musica> musicas = new ArrayList<>();
    public void adicionar(Musica m) { musicas.add(m); }
}






  
Casos que o mapeamento simples não cobre

  

    

      Alguns elementos não têm uma tradução direta, e exigem uma decisão de projeto explícita:
    

    
    
      
  • Associação qualificada: o qualificador vira a chave de um Map (tópico 06).
    • 
      
  • Classe de associação: vira uma classe própria, com referências aos dois lados, como Assinatura.
    • 
      
  • Classe parametrizada (<<template>>): vira um genérico, como Repositorio<T>.
    • 
      
  • Operações com retorno múltiplo ou sem retorno: use void, um record de resposta ou uma exceção.
    • 
    

  


// Classe parametrizada: um repositório genérico para qualquer entidade
public interface Repositorio<T, ID> {
    void salvar(T entidade);
    Optional<T> buscar(ID id);
}






  
Modelo e código: a sincronização é o problema

  

    
Engenharia direta
Gera código a partir do modelo. Funciona bem para a estrutura (classes, campos, assinaturas). Não gera a lógica, que precisa ser escrita.

    
Engenharia reversa
Gera o diagrama a partir do código. Mostra o que existe, mas não o que deveria existir. Um código ruim gera um diagrama ruim.

  

  

    
    

      O diagrama que mente: depois de algumas semanas, modelo e código divergem. Um diagrama desatualizado é
      pior que nenhum, porque ele inspira confiança. Escolha uma fonte da verdade (normalmente o código, com testes) e
      atualize o diagrama como documentação viva, ou gere-o a partir do código.
    

  






  
Checklist de revisão do código

  
    
    
  • Toda associação do diagrama tem um campo (ou um parâmetro, se for agregação ou dependência)?
    • 
    
  • A multiplicidade 1 é garantida no construtor, e não apenas na documentação?
    • 
    
  • Atributos marcados como privados no diagrama estão privados no código?
    • 
    
  • Toda composição cria a parte dentro do todo, e a parte não é exposta para criação externa?
    • 
    
  • As restrições do diagrama aparecem como validações ou testes?
    • 
    
  • Não há dependência no código que o diagrama não mostra (por exemplo, uma classe de domínio importando um pacote de infraestrutura)?
    • 
  






  
Exercícios

  

    

      1. Traduza para Java: Ouvinte "1" -- "0..*" Playlist, em que a playlist é criada pelo ouvinte.
      
Gabarito: em Ouvinte, private final List<Playlist> playlists e um método montarPlaylist(nome) que cria a playlist com new. Como o ouvinte cria a playlist, a relação é de composição do lado do ouvinte; se a playlist pudesse existir sem ouvinte, seria agregação.

    

    

      2. Um colega gera código de um diagrama com Musica ligada a Album por composição e o código tem public List<Musica> faixas. Qual o problema?
      
Gabarito: a lista pública permite que qualquer código altere as faixas, o que quebra a posse exclusiva do álbum. O correto é private com retorno de lista imutável (Collections.unmodifiableList), e a adição feita pelo próprio álbum.

    

    

      3. Por que a engenharia reversa pura não basta para projetar um sistema?
      
Gabarito: porque ela descreve o que foi feito, com todos os acidentes do código, e não o que deveria ser feito. Projetar exige decidir antes de implementar, e a reversa só documenta essas decisões depois, quando já estão tomadas.

Teste seu entendimento

  
Três perguntas de tradução.


  

    

      
1. Turma "1" —— "3..40" Aluno vira, no código de Turma:

      
      
      
      

        A coleção vem do “muitos”; os limites 3..40 são uma regra de negócio que o compilador
        não garante — precisa virar validação explícita no método que adiciona alunos.
      

    


    

      
2. A diferença no código entre composição e agregação aparece principalmente:

      
      
      
      

        Composição: itens.add(new Item(...)) dentro do todo, coleção final e não
        exposta. Agregação: a parte chega pronta pelo construtor ou por um setter. A sintaxe é
        parecida; a responsabilidade pelo ciclo de vida é o que muda.
      

    


    

      
3. Uma classe associativa entre Aluno e Disciplina, com o atributo nota, vira:

      
      
      
      

        A nota não pertence ao aluno (ele tem várias) nem à disciplina (ela tem várias): pertence ao
        par. Esse é o sinal clássico de que a associação precisa virar classe — e, no banco, a tabela
        de junção com colunas extras.
