O problema: uma matriz de tipos e operações

Imagine uma hierarquia de expressões de preço: Preco, Desconto e Soma. Você quer calcular o valor, e depois imprimir a fórmula, e talvez exportá-la. Cada operação é uma coluna; cada tipo é uma linha.

O expression problem, formulado por Philip Wadler (1998), é a tensão entre duas extensões:

  • Adicionar operação (nova coluna): com métodos nas classes, exige editar todas as classes.
  • Adicionar tipo (nova linha): com um switch central por tipo, exige editar todas as operações.

Nenhuma organização simples torna as duas fáceis ao mesmo tempo. Cada solução escolhe qual extensão favorecer.

Double dispatch: duas escolhas dinâmicas

O despacho simples escolhe um método pelo tipo do receptor. O double dispatch escolhe pelo tipo de dois objetos: o elemento e o visitante. No Visitor, aceitar(v) escolhe a classe do elemento, e dentro dela v.visitar...(this) escolhe a operação. São duas ligações dinâmicas encadeadas.

Esse é o mecanismo que torna possível separar operações dos tipos sem instanceof espalhado pelo código.

Contexto do exemplo

Os tipos são sealed (Java 17), então o compilador conhece todos os casos. Cada operação é um visitante: Avaliador calcula o total e Impressor monta a fórmula, sem alterar as classes de expressão.

/**
 * Double dispatch e o Visitor, com o "expression problem" de Wadler (1998):
 * - Adicionar uma OPERAÇÃO nova é fácil: crie um novo Visitor.
 * - Adicionar um TIPO novo é difícil: todos os visitors precisam mudar.
 */
public class Main {

    // Hierarquia fechada (sealed): o compilador conhece todos os casos.
    sealed interface Valor permits Preco, Desconto, Soma { <R> R aceitar(Visitor<R> v); }

    record Preco(double valor) implements Valor {
        public <R> R aceitar(Visitor<R> v) { return v.visitarPreco(this); }
    }
    record Desconto(Valor base, double percentual) implements Valor {
        public <R> R aceitar(Visitor<R> v) { return v.visitarDesconto(this); }
    }
    record Soma(Valor esquerda, Valor direita) implements Valor {
        public <R> R aceitar(Visitor<R> v) { return v.visitarSoma(this); }
    }

    interface Visitor<R> {
        R visitarPreco(Preco p);
        R visitarDesconto(Desconto d);
        R visitarSoma(Soma s);
    }

    // Operação 1: calcular o valor (um visitor)
    static final class Avaliador implements Visitor<Double> {
        public Double visitarPreco(Preco p) { return p.valor(); }
        public Double visitarDesconto(Desconto d) {
            return d.base().aceitar(this) * (1 - d.percentual() / 100.0);
        }
        public Double visitarSoma(Soma s) {
            return s.esquerda().aceitar(this) + s.direita().aceitar(this);
        }
    }

    // Operação 2: imprimir a fórmula (outro visitor, sem tocar nas classes acima)
    static final class Impressor implements Visitor<String> {
        public String visitarPreco(Preco p) { return String.format("R$%.2f", p.valor()); }
        public String visitarDesconto(Desconto d) {
            return "(" + d.base().aceitar(this) + " - " + d.percentual() + "%)";
        }
        public String visitarSoma(Soma s) {
            return "(" + s.esquerda().aceitar(this) + " + " + s.direita().aceitar(this) + ")";
        }
    }

    public static void main(String[] args) {
        // Assinatura Premium com cupom de 10% + taxa de R$ 2,00
        Valor total = new Soma(new Desconto(new Preco(19.90), 10), new Preco(2.00));

        System.out.println("fórmula: " + total.aceitar(new Impressor()));
        System.out.printf("total:   R$ %.2f%n", total.aceitar(new Avaliador()));

        // Double dispatch: a chamada 'aceitar' escolhe o método pelo tipo do elemento;
        // 'visitar...' escolhe a operação pelo tipo do visitor. Duas escolhas dinâmicas.
        System.out.println("\nSealed: o compilador sabe que os casos são Preco, Desconto e Soma.");
    }
}

Onde isso aparece na prática

O javac expõe a árvore sintática por meio de visitantes (com.sun.source.util.TreeVisitor). Ferramentas de análise estática e formatadores de código percorrem ASTs da mesma forma: a árvore é estável, e as operações variam. É o caso típico em que o expression problem favorece adicionar operações.

Já sistemas com tipos de evento que crescem com o produto favorecem o outro lado. Aí, a escolha costuma ser um tipo selado com switch exaustivo, para que um tipo novo quebre a compilação em todos os pontos que precisam tratá-lo.

Exercícios

1. Adicione um tipo Gratuito ao exemplo. Quantos arquivos e métodos você precisou tocar?

Gabarito: a interface Visitor ganha um método (o compilador aponta todos os visitantes que faltam), e cada visitante implementa esse método. As classes de expressão ganham o aceitar. Esse é o custo do expression problem na forma Visitor: adicionar tipo espalha mudanças.

2. Reescreva Avaliador com switch sobre o tipo selado, sem visitor. Qual extensão ficou mais fácil?

Gabarito: adicionar operação fica fácil (um novo método com switch), e adicionar tipo fica verificado: o switch sobre tipo selado sem o caso novo não compila. Ganhou-se segurança para tipos, e perdeu-se a separação de operações nas classes.
