Programar organizando o mundo

No paradigma estruturado, dados e funções vivem separados: você tem variáveis de um lado e procedimentos que as manipulam do outro. Funciona — até o programa crescer. Aí qualquer função pode alterar qualquer dado, e descobrir “quem mexeu no saldo” vira uma caçada.

A orientação a objetos junta as duas coisas: um objeto guarda seus próprios dados e é o único responsável por alterá-los. O sistema deixa de ser uma lista de rotinas e passa a ser uma sociedade de objetos que trocam mensagens.

Estruturado 
// dados soltos
double saldoJoao = 1000;
double saldoMaria = 500;

// qualquer função mexe em qualquer dado
void sacar(double* saldo, double v) {
    *saldo -= v;   // sem nenhuma validação
}

saldoJoao = -99999;  // ninguém impede

O dado está exposto. A regra de negócio “saldo não fica negativo” precisa ser lembrada em todo lugar que toca o saldo.

Orientado a objetos 
public class Conta {
    private double saldo;   // ninguém alcança

    public void sacar(double v) {
        if (v > saldo)
            throw new SaldoInsuficiente();
        saldo -= v;
    }
}

conta.saldo = -99999;  // erro de compilação

A regra mora junto do dado. É impossível violá-la por fora — o compilador garante.

Modelar é decidir o que ignorar. Um objeto Aluno num sistema acadêmico tem matrícula e notas; num sistema de saúde, tem tipo sanguíneo e alergias. A mesma pessoa, dois modelos — porque modelo não é retrato da realidade, é recorte útil para um propósito.

A classe é a forma; o objeto é o bolo

A classe define quais atributos e métodos existem. O objeto é uma instância concreta, com seus próprios valores. Clique em “new Carro(...)” e veja objetos nascerem da mesma classe, cada um com identidade própria.

A classe existe uma vez, em tempo de compilação. Os objetos existem n vezes, em tempo de execução, cada um em seu endereço de memória.

Onde a UML entra

Modelar não é desenhar bonito: é pensar antes de codificar e ter uma linguagem comum entre analista, programador e cliente. Um diagrama de classes cabe numa folha; o código equivalente, em vinte arquivos.

Modele o suficiente, não tudo. Diagramar cada classe de um sistema grande produz documentação que envelhece em uma semana. Modele o que é difícil de entender lendo o código: arquitetura, fluxos críticos, regras de negócio complexas.

De onde vem a orientação a objetos

A ideia de agrupar dados e os procedimentos que os manipulam não nasceu com a UML. Ela aparece, de forma embrionária, na linguagem Simula 67, criada na Noruega por Ole-Johan Dahl e Kristen Nygaard para simulação de sistemas discretos. Simula introduziu as classes, os objetos e a herança.

A linguagem Smalltalk, desenvolvida no Xerox PARC por Alan Kay e sua equipe nos anos 1970, levou a ideia adiante e definiu o modelo em que tudo é objeto e objetos se comunicam por mensagens. Foi dessa tradição que surgiram C++, Objective-C, Java e C#, e é dela que vem a visão de sistema como uma rede de objetos colaborando.

Duas formas de pensar um sistema

No paradigma estruturado, o sistema é uma sequência de funções que manipulam estruturas de dados globais. No paradigma orientado a objetos, o sistema é uma colaboração entre objetos, cada um responsável pelo próprio estado. A diferença aparece quando o requisito muda. 

// Estruturado: a regra de saldo está espalhada pelas funções que tocam o dado
double saldo = 0;
void sacar(double v)  { saldo -= v; }   // quem garante saldo >= 0?
void relatorio()        { /* lê saldo direto */ }

// Orientado a objetos: o dado e a regra moram juntos
class Conta {
    private double saldo;
    public void sacar(double v) {
        if (v > saldo) throw new IllegalStateException();
        saldo -= v;
    }
}
O que muda na prática: quando a regra de saque mudar (por exemplo, limite diário), no modelo orientado a objetos você altera uma classe. No estruturado, precisa encontrar todas as funções que mexem em saldo. É esse custo de manutenção que a OO busca reduzir.

Definições que caem em prova

Grady Booch, em Object-Oriented Analysis and Design with Applications, define um objeto como algo que tem identidade, estado e comportamento. Essa tríade é a base de todo o curso, e vale decorar, porque ela explica por que dois objetos com os mesmos valores ainda são objetos diferentes.

Identidade

Propriedade que distingue um objeto dos demais, mesmo com estado igual. Duas contas com saldo de R$ 100 são contas diferentes.

Estado

Conjunto dos valores dos atributos em um dado momento. Muda por meio de operações, não por acesso direto.

Comportamento

Conjunto de respostas que o objeto dá às mensagens recebidas. Modelado por operações e máquinas de estado.

Mensagem: é a forma como um objeto pede algo a outro. Na prática, é uma chamada de operação. O diagrama de sequência (tópico 11) mostra a ordem dessas mensagens no tempo.

Exercícios

1. Explique, com suas palavras, a diferença entre classe e objeto usando a analogia de uma fôrma e os bolos.

Gabarito: a classe é a fôrma: existe uma vez e define a estrutura. O objeto é cada bolo: existe em tempo de execução, com identidade própria, mesmo que seja igual a outro. Uma resposta completa menciona que a fôrma não “contém” os bolos, ela só os produz.

2. Dois ouvintes da Melodia têm o mesmo nome e o mesmo plano. Eles são o mesmo objeto?

Gabarito: não. Objetos são distinguidos pela identidade, não pelo conteúdo. Dois cadastros com dados iguais são duas instâncias. Em Java, isso se verifica com ==; a igualdade de conteúdo é equals, e cabe ao modelador decidir se dois ouvintes são “iguais” no sentido de negócio (por exemplo, pelo e-mail).

3. Por que a POO ajuda na manutenção quando a regra de negócio muda?

Gabarito: porque o dado e a regra que o protege ficam na mesma classe. Uma mudança de regra tende a afetar um ponto do código, e não todas as funções que tocam o dado. A resposta forte cita o encapsulamento (tópico 03) como mecanismo.

Teste seu entendimento

Três perguntas de fundamentos.

1. Qual a diferença entre classe e objeto?

Dois objetos da mesma classe têm os mesmos atributos (nomes e tipos), mas valores diferentes — e são distintos mesmo que todos os valores coincidam, porque cada um tem sua identidade.

2. A principal vantagem de juntar dados e comportamento no mesmo objeto é:

Na prática, OO costuma consumir um pouco mais de memória e de tempo. O ganho é de manutenção: quando a regra do saldo muda, há um único lugar para alterar.

3. Modelar em UML antes de codificar serve principalmente para:

Mudar uma seta num diagrama custa segundos; mudar a mesma decisão depois de 5.000 linhas escritas custa semanas. A UML é uma ferramenta de conversa — inclusive com você mesmo daqui a seis meses.
