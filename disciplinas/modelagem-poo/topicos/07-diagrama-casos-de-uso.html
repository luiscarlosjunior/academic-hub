O diagrama que o cliente entende

O diagrama de casos de uso responde a uma pergunta só: quem usa o sistema e para conseguir o quê? Ele não mostra telas, nem banco de dados, nem a ordem dos passos. Justamente por ser pobre em detalhe técnico, é o único diagrama da UML que você consegue discutir com um cliente não técnico.

Cada caso de uso é um objetivo completo do ator, algo que gera valor por si só — “realizar empréstimo”, e não “clicar no botão salvar”.

Legenda

A dupla que todo mundo confunde

«include» — sempre acontece

O caso base sempre executa o incluído. Serve para fatorar um comportamento comum usado por vários casos de uso — como “autenticar usuário”.

Realizar Empréstimo - - «include» - -> Autenticar
a seta aponta do base para o incluído

Análogo: chamar uma sub-rotina obrigatória.

«extend» — às vezes acontece

Comportamento opcional, disparado apenas sob certa condição, em um ponto de extensão do caso base. O caso base funciona perfeitamente sem ele.

Aplicar Multa - - «extend» - -> Devolver Livro
a seta aponta da extensão para o base — sentido invertido!

Condição: “se a devolução estiver atrasada”.

O detalhe que derruba na prova: as setas apontam em sentidos opostos. No include, o base aponta para o incluído (“eu preciso dele”). No extend, a extensão aponta para o base (“eu me encaixo nele”) — o base nem sabe que a extensão existe.

O diagrama é a capa; o texto é o conteúdo

Um caso de uso desenhado é apenas uma elipse com um nome. O valor real está na descrição textual — é ela que vira teste, critério de aceite e tarefa de desenvolvimento.

Cinco erros que aparecem em toda turma

Ator é um papel, caso de uso é um objetivo

Um ator é um papel que alguém ou algo desempenha em relação ao sistema. Não é uma pessoa específica nem um cargo de RH: uma mesma pessoa pode ser, ao mesmo tempo, ouvinte e artista na Melodia. Atores também podem ser sistemas externos (um gateway de pagamento) ou o próprio tempo (um agendador que dispara a cobrança mensal).

Um caso de uso é um objetivo de valor do ator, expresso como uma interação com o sistema que produz algo útil. A regra prática para nomear: use verbo no infinitivo + objeto, como “assinar um plano”. Nomes como “Gerenciar usuários” são grandes demais e escondem vários casos de uso.

Fronteira do sistema: desenhe um retângulo ao redor dos casos de uso. Tudo dentro é responsabilidade do sistema; atores ficam fora. Se você não consegue decidir se algo está dentro ou fora, provavelmente é um sistema externo, e deve ser ator.

«include» e «extend»: a diferença que cai em prova

As duas relações ligam casos de uso e são as mais confundidas do diagrama. A diferença está na obrigatoriedade e na direção da chamada.

«include» — obrigatório

O caso base sempre executa o incluído. Serve para reutilizar um comportamento comum a vários casos.

Ex.: “Assinar plano” inclui “Autenticar ouvinte”. Não existe assinatura sem autenticação.

«extend» — opcional

O caso extensor pode acrescentar comportamento ao caso base, sob uma condição, em um ponto de extensão.

Ex.: “Assinar plano” é estendido por “Aplicar cupom” quando o ouvinte informa um código.

Setas: a ponta aponta para onde o comportamento vai. No «include», a seta vai do caso base para o incluído (o base chama). No «extend», a seta vai do caso extensor para o base (o extensor acrescenta). Essa inversão é a causa mais comum de erro.

Generalização entre atores e entre casos de uso

Atores podem ser especializados: Ouvinte Free e Ouvinte Premium são “tipos de” ouvinte, e herdam suas associações com os casos de uso. Casos de uso também podem ser generalizados: “Pagar” é geral, e “Pagar com cartão” e “Pagar com pix” são especializações. Use generalização quando o comportamento herdado for verdadeiro, da mesma forma que na herança de classes.

O diagrama não basta: a descrição textual

Um diagrama de casos de uso mostra quem e o quê, mas não o como. A descrição textual, em modelo, é o documento que detalha cada caso. Uma forma clássica, usada em cursos de engenharia de requisitos, tem estas partes:

Erros comuns de granularidade

Um caso para cada tela

Telas mudam; objetivos não. Modele o objetivo do ator, e deixe a tela para o protótipo.

Um caso para cada CRUD

“Cadastrar, Consultar, Alterar, Excluir Música” é um sinal de modelagem de banco, não de requisito. Agrupe em objetivos.

Ator que é classe

“Ouvinte” é ator; “Assinatura” é classe do modelo de domínio. Não misture os dois diagramas.

«include» para tudo

Usar include para um passo opcional transforma o opcional em obrigatório. Se pode não acontecer, é extend.

Exercícios

1. Na Melodia, “Reproduzir música” e “Autenticar ouvinte” devem aparecer ligados por include ou extend? Por quê?

Gabarito: include. Reproduzir sempre exige autenticação (quando o ouvinte está logado). A relação é obrigatória e reutilizável por outros casos, como “Criar playlist”. Se a autenticação fosse opcional, seria extend.

2. “Aplicar cupom de desconto” é opcional na assinatura. Qual relação e em que sentido a seta aponta?

Gabarito: «extend». A seta sai de “Aplicar cupom” e aponta para “Assinar plano”, porque o cupom acrescenta comportamento ao caso base sob uma condição (o ouvinte informou um código).

3. Reescreva “Gerenciar assinaturas” em casos de uso bem formados.

Gabarito: “Assinar plano”, “Cancelar assinatura”, “Trocar de plano”, “Consultar cobranças”. Cada um tem valor para o ouvinte, verbo no infinitivo e início e fim claros. A gestão em si não é um objetivo de nenhum ator.

Teste seu entendimento

Quatro perguntas sobre casos de uso.

1. “Informar CPF” é um bom caso de uso?

Um caso de uso precisa entregar valor sozinho. Ninguém entra no sistema para “informar CPF” — entra para “realizar empréstimo”, e informar o CPF é um passo desse fluxo. Decompor demais produz o clássico diagrama-fluxograma.

2. Um ator, em UML, é necessariamente uma pessoa?

Ator é qualquer entidade externa que interage com o sistema. O gateway de pagamento é ator; um relógio que dispara rotina noturna é ator (“ator temporal”). O boneco palito é só a notação.

3. “Aplicar multa” só ocorre quando a devolução está atrasada. A relação com “Devolver livro” é:

Comportamento condicional = extend, e a seta parte da extensão. Se a multa fosse cobrada em toda devolução, aí sim seria include no sentido oposto.

4. Qual elemento delimita o que é responsabilidade do sistema?

Tudo dentro do retângulo é escopo do sistema; os atores ficam de fora por definição. Essa fronteira é a parte mais política do diagrama — é onde se negocia o que entra e o que fica de fora do contrato.
