Classes isoladas não fazem sistema

Um diagrama de classes vale pelas linhas, não pelas caixas. Cada tipo de linha tem significado preciso e vira código diferente. Confundi-los é o erro mais comum em provas — e em projetos.

      Na dúvida, use associação simples. A distinção entre agregação e composição gera

    O número fica na ponta oposta à classe que está “contando”. Leia sempre da classe de
    origem para a de destino: “um Pedido tem 1..* Itens”.

Navegabilidade

        

          A seta aberta no fim da linha indica que apenas um lado conhece o outro. Sem seta, a UML
          deixa em aberto. Associações bidirecionais são mais caras de manter: toda alteração precisa
          atualizar os dois lados.
        

      

    

  








  
O que cada relação afirma sobre o mundo

  

    

      Uma relação no diagrama de classes é uma afirmação sobre o domínio, que pode ser verdadeira ou falsa.
      Desenhar uma seta é dizer “existe este vínculo, com estas regras”. Por isso, a pergunta certa não é “qual símbolo
      eu uso?”, e sim “o que é verdade sobre estes objetos?”.
    

    

      A UML 2.5 define a associação como a relação genérica. Agregação e composição são casos
      especiais de associação, com a semântica de “todo-parte” acrescentada. A dependência é mais fraca: um elemento
      usa outro temporariamente, por exemplo como parâmetro de uma operação.

Navegabilidade, papéis e associação bidirecional

  

    

      A navegabilidade diz em qual sentido é possível percorrer a associação. Uma seta de Ouvinte
      para Assinatura significa que o ouvinte sabe quem é sua assinatura; a assinatura não precisa saber de
      volta. Sem seta, a navegabilidade é indefinida, o que é uma pendência de modelagem, não uma decisão.
    

    

      O papel (role) é o nome da ponta da associação, e geralmente vira o nome do atributo no código.
      Quando a associação é bidirecional, cada lado tem seu papel: Playlist.dono e Ouvinte.playlists.
    

  

  

    
    

      Bidirecional custa caro: cada alteração precisa atualizar os dois lados. Se só um for atualizado, os
      objetos passam a discordar. Use bidirecional apenas quando o negócio exigir navegar nos dois sentidos, e centralize a
      atualização em um método único.
    

  






  
Classe de associação: quando a relação tem dados próprios

  

    

      Às vezes o vínculo entre duas classes tem informação própria. Um Ouvinte e um Plano se
      relacionam por meio de uma assinatura, que tem data de início e status. Esses dados não pertencem
      a nenhum dos dois lados, pertencem ao vínculo. A UML representa isso com uma classe de associação,
      ligada à linha por uma linha pontilhada.
    

  

  

    
classDiagram
    class Ouvinte
    class Plano
    class Assinatura {
        -LocalDate inicio
        -StatusAssinatura status
        +suspender() void
    }
    Ouvinte "*" -- "*" Plano
    Assinatura .. Ouvinte
    Assinatura .. Plano
    

  

  
Um ouvinte pode ter vários planos ao longo do tempo, e um plano tem vários ouvintes. A Assinatura guarda o que pertence ao vínculo: início e status.






  
Associação qualificada: o acesso por chave

  

    

      Em uma associação qualificada, um qualificador (uma chave) seleciona um único objeto do outro lado. Em vez de
      “um ouvinte tem muitas playlists”, a relação passa a ser “um ouvinte tem, para cada nome, uma playlist”. A
      multiplicidade do lado qualificado cai para 0..1.
    

  


// Qualificador "nome": o ouvinte acessa a playlist pela chave
public class Ouvinte {
    private final Map<String, Playlist> playlists = new HashMap<>();

    public Optional<Playlist> playlist(String nome) {
        return Optional.ofNullable(playlists.get(nome));
    }
}






  
Agregação e composição: a regra da multiplicidade

  

    

      Na composição, o todo é o dono exclusivo da parte. Isso impõe uma regra estrutural: a parte pertence
      a no máximo um todo ao mesmo tempo. Por isso, no lado do todo, a multiplicidade de uma composição é
      quase sempre 1 ou 0..1. Um álbum é dono das faixas; uma faixa não pode pertencer a dois álbuns
      como dona.
    

    

      Na agregação, não há exclusividade. A mesma música pode estar em muitas playlists, e a playlist não é dona dela.
    

  


  

    
classDiagram
    class Album {
        -String titulo
    }
    class Musica {
        -String titulo
    }
    class Playlist {
        -String nome
    }
    Album "1" *-- "1..*" Musica : composição
    Playlist "0..*" o-- "0..*" Musica : agregação
    

  

  
Losango cheio do lado do álbum: a faixa não existe sem ele. Losango vazio do lado da playlist: a música existe por conta própria.


  

    
    

      Teste prático: apague o todo mentalmente. Se as partes devem desaparecer junto, é composição. Se
      continuam válidas e úteis, é agregação. Quando não estiver claro, prefira associação simples: é mais fácil de
      tornar mais forte depois do que o contrário.
    

  






  
Dependência: o vínculo mais fraco

  

    

      A dependência indica que uma mudança em um elemento pode afetar outro, geralmente porque o segundo usa o primeiro
      como parâmetro, retorno ou variável local. Não existe campo guardado. Na UML, é uma seta tracejada, muitas vezes
      com o estereótipo «use».
    

  


public class ServicoCobranca {
    // dependência: usa Assinatura só dentro do método, sem guardar referência
    public boolean cobrar(Assinatura a, double valor) {
        return a.debitar(valor);
    }
}

      Leia sempre dos dois lados: em uma associação Ouvinte "1" -- "0..*" Playlist, a
      multiplicidade perto de Playlist responde “quantas playlists um ouvinte tem?”, e a perto de Ouvinte
      responde “quantos ouvintes uma playlist tem?”. Confundir os dois lados é um erro muito comum em prova.
    

  






  
Exercícios

  

    

      1. Um Carro tem quatro Rodas. Se o carro for destruído, as rodas devem ser destruídas? Qual relação?
      
Gabarito: depende do domínio. Em uma oficina que troca rodas, a roda é um item de estoque e sobrevive ao carro: agregação. Em um simulador que modela o veículo como um todo, a roda não existe fora dele: composição. A resposta forte explicita o domínio que decide.

    

    

      2. Por que uma faixa não pode ser composição de dois álbuns ao mesmo tempo?
      
Gabarito: porque a composição implica posse exclusiva: a parte pertence a no máximo um todo. Se a mesma faixa pudesse ser de dois álbuns como dona, a exclusão de um álbum deixaria a questão de quem a apaga indefinida. Se o negócio quer que a faixa esteja em dois álbuns (coletânea), a relação correta é agregação.

    

    

      3. Desenhe a associação entre Ouvinte e Plano com a classe de associação Assinatura, sabendo que um ouvinte tem no máximo um plano ativo por vez.
      
Gabarito: Ouvinte "1" -- "0..*" Plano com Assinatura como classe de associação. A restrição “no máximo um ativo” não cabe na multiplicidade: anote com uma restrição {no máximo uma assinatura com status ATIVA} na classe Ouvinte.

Teste seu entendimento

  
Quatro perguntas sobre relacionamentos.


  

    

      
1. Casa e Comodo: se a casa é demolida, os cômodos deixam de existir. A relação é:

      
      
      
      

        A parte não sobrevive ao todo e pertence a um único todo por vez: composição. O losango preenchido
        fica sempre do lado do todo.
      

    


    

      
2. Um método recebe Relatorio como parâmetro, usa e descarta. Não há atributo. Isso é:

      
      
      
      

        Relação momentânea, que existe só durante a chamada. Se houvesse um atributo guardando a
        referência, aí sim seria associação — a diferença é a permanência do vínculo.
      

    


    

      
3. Pedido —— 1..* —— Item significa que:

      
      
      
      

        1..* = mínimo 1, máximo indefinido. É uma regra de negócio declarada no diagrama:
        salvar um pedido vazio deve ser impedido pelo código.
      

    


    

      
4. A seta aberta no fim de uma associação indica:

      
      
      
      

        No código, isso significa que só um dos lados guarda o atributo. Evitar bidirecionalidade
        desnecessária reduz acoplamento e elimina toda uma classe de bugs de sincronização.
