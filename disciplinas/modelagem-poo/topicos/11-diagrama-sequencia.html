Quem chama quem, e em que ordem

O diagrama de sequência mostra a colaboração entre objetos para realizar um cenário. O tempo corre de cima para baixo; cada objeto tem uma linha de vida vertical; e cada seta é uma mensagem — na prática, uma chamada de método.

É o diagrama que mais ajuda a distribuir responsabilidades: ao desenhá-lo, você é obrigado a decidir qual classe faz cada coisa. Se uma linha de vida concentra todas as setas, é sinal de má distribuição de responsabilidades.

Cenário: realizar um empréstimo

Avance mensagem a mensagem e acompanhe as barras de ativação crescendo e encolhendo — elas mostram quando cada objeto está no controle da execução.

A mesma cena, outro enquadramento

  

    O diagrama de comunicação mostra exatamente a mesma interação, mas organiza os objetos
    no espaço em vez do tempo. A ordem é recuperada pela numeração das mensagens.
    Os dois são ditos isomórficos: dá para converter um no outro sem perder informação.
  


  

    

      
    

    

      

        
Quando preferir cada um

        
    
          
  • Sequência: quando a ordem temporal é o que importa — o caso mais comum. Fica óbvio o que acontece antes e depois.
    • 
          
  • Comunicação: quando interessa quem está ligado a quem. Bom para enxergar acoplamento e objetos centrais demais.

        análises de acoplamento — mas saber ler os dois é exigência da disciplina.

Fragmentos combinados: controle dentro da sequência

  

    Um fragmento combinado é uma moldura com um operador que controla as mensagens dentro dela. Os principais são:
  

  

    

      
OperadorSignificadoQuando usar

      
        
altAlternativas: executa uma das áreas, conforme a guardaSe/senão, caminhos de sucesso e falha

        
optOpcional: executa só se a guarda for verdadeiraUm passo que pode não acontecer

        
loopRepetição, com limites opcionaisCobrança para cada assinatura

        
parParalelo: as áreas podem intercalar suas mensagensEnviar recibo e atualizar histórico

        
breakInterrompe o fluxo quando a guarda valeTratamento de erro que encerra a interação

        
refReferencia outra interação já modeladaReaproveitar um cenário, como a autenticação

        
negInteração inválida: não deve acontecerMostrar uma sequência proibida, como cobrar cancelada

      
    

  

  

    
    

      Cuidado com opt e alt: se o passo é obrigatório, não use opt. Um diagrama
      que tem um opt para tudo esconde regras: o leitor não sabe o que é essencial.
    

  






  
Quando a mensagem é assíncrona

  

    

      Em uma chamada síncrona, o emissor fica bloqueado até a resposta. Em uma assíncrona, ele envia e segue. Essa diferença
      muda a arquitetura: se a cobrança for assíncrona, a plataforma não sabe, naquele instante, se o débito funcionou. A
      sequência precisa então de um passo posterior de confirmação, como um evento “pagamento confirmado”.
    

  






  
Cada mensagem é uma operação


public class PlataformaStreaming {
    public void renovarTodas() {
        for (Assinatura a : assinaturasAtivas()) {       // loop
            if (a.cobrar(a.getConta())) {                   // alt: saldo suficiente
                enviarRecibo(a.getOuvinte());
            } else {                                          // alt: saldo insuficiente
                a.suspender();                                       // R3: suspende, não cancela
            }
        }
    }
}

  

    

      Esse é o ponto da sequência: cada seta vira uma chamada, cada fragmento vira um if, for ou
      while. A sequência é um roteiro do método que está prestes a ser escrito.
    

  






  
Exercícios

  

    

      1. Um ouvinte pede para ver suas playlists. Antes, o sistema precisa autenticá-lo, que é o mesmo cenário em outras telas. Como modelar sem repetir a sequência?
      
Gabarito: criar uma interação “Autenticar” e referenciá-la com um fragmento ref na sequência de “Ver playlists”. Assim o cenário de autenticação existe em um lugar só.

    

    

      2. Na sequência do exemplo, o que aconteceria se o loop fosse substituído por um opt?
      
Gabarito: a cobrança rodaria no máximo uma vez, e só se a guarda fosse verdadeira. Para renovar todas as assinaturas, é preciso repetir: o loop expressa isso, e o opt não.

    

    

      3. Por que uma auto-mensagem em Assinatura pode ser útil no diagrama?
      
Gabarito: ela mostra uma chamada interna de uma operação para outra, por exemplo cobrar() chamando validarStatus(). Revela a lógica privada que não aparece na interface pública, o que ajuda a explicar a regra.

Visão geral: o que é um diagrama de sequência

  



Um diagrama de sequência mostra uma interação: quais participantes trocam mensagens, em que ordem, e quem espera quem. O eixo vertical é o tempo (de cima para baixo) e cada participante tem uma linha de vida. Quando um participante executa uma operação, aparece uma barra de ativação, que é a representação visual da pilha de chamadas.


A notação foi consolidada por Booch, Rumbaugh e Jacobson (1999, The Unified Modeling Language User Guide) e está formalizada na especificação da OMG (UML 2.5.1, 2017, capítulo Interactions). Larman (2004, Utilizando UML e padrões) usa diagramas de sequência do sistema para derivar os contratos das operações, uma das práticas mais difundidas de análise orientada a objetos.


Um ponto que confunde: o diagrama de sequência não mostra o estado interno dos objetos (isso é a máquina de estados) nem o fluxo de decisões de um processo (isso é o diagrama de atividades). Ele mostra mensagens entre participantes, e nada além disso. Por isso é tão útil para revisar um desenho de integração entre sistemas.

Exemplos do dia a dia

  



Sequências são o jeito natural de descrever uma conversa entre sistemas, e aparecem em qualquer integração:


1. Pedir um táxi por aplicativo


O passageiro pede a corrida, o aplicativo procura motoristas próximos (um loop sobre motoristas, até um aceitar), a corrida é confirmada e o passageiro recebe a placa. Se nenhum motorista aceitar em um tempo, um alt leva a “sem motoristas no momento”. A sequência mostra com clareza que a confirmação depende da aceitação do motorista.


2. Fazer uma transferência Pix


O aplicativo do banco envia o pedido ao serviço de pagamentos, que consulta o saldo, verifica limites e antifraude (em sequência), e só depois registra o débito. Se a verificação antifraude recusar, um alt impede o débito. A ordem importa: debitar antes de verificar seria um erro grave, e o diagrama torna essa ordem visível.


3. Uma consulta a um médico por videochamada


Paciente, plataforma de agendamento e prontuário trocam mensagens: agendar, confirmar, abrir a sala, registrar a consulta. Um ref reaproveita o “login do profissional”, que aparece em vários fluxos. Esse tipo de diagrama é usado para explicar a integração a equipes de negócio e de segurança.

Implementação em Java: cada mensagem é uma chamada

  



Cada mensagem da sequência vira uma chamada de método. Cada barra de ativação vira o tempo em que o método está na pilha. Para tornar isso visível, o programa imprime a mensagem com recuo igual à profundidade da pilha: o que você vê na saída é uma barra de ativação em forma de texto.




No diagramaEm Java



mensagem síncronachamada(de, para, texto, () -> { ... }): o corpo roda antes de voltar


mensagem de retornoretorno(de, para, valor)


optif (comCupom) { ... }


loopfor (String item : itens) { ... }


altif (aprovado) { ... } else { ... }


refum rótulo [ref: Autenticação] numa chamada que representa outro cenário




Passo a passo animado sobre o método checkout. Cada passo destaca o fragmento que está sendo executado e mostra quais participantes estão ativos.


  





  
Exemplo executável: a sequência em texto

  



A saída é a sequência real de mensagens, numeradas, com o recuo mostrando quem chamou quem. Confira no cenário A que a validação do cupom aparece antes da reserva, porque é essa a ordem do código; e no cenário B que a recusa do cartão dispara o cancelamento das reservas.




static void checkout(boolean comCupom, boolean aprovado, List2 itens) {
    chamada("Cliente", "Interface", "finalizar compra", () ->
    chamada("Interface", "Checkout", "iniciar(carrinho)", () -> {

        // ref: a autenticação é um cenário reaproveitado (aparece em outros diagramas)
        chamada("Checkout", "Sessao", "autenticar()  [ref: Autenticação]", () ->
                retorno("Sessao", "Checkout", "usuário válido"));

        // opt: o cupom só é validado se o cliente informou um
        if (comCupom) {
            chamada("Checkout", "Cupons", "validar(BEMVINDO10)", () ->
                    retorno("Cupons", "Checkout", "desconto de 10%"));
        }

        // loop: cada item é reservado no estoque
        for (String item : itens.valores) {
            chamada("Checkout", "Estoque", "reservar(" + item + ")", () ->
                    retorno("Estoque", "Checkout", "reservado"));
        }

        // alt: caminho de sucesso ou de recusa do cartão
        chamada("Checkout", "Gateway", "cobrar(total)", () -> {
            if (aprovado) {
                retorno("Gateway", "Checkout", "aprovado");
                chamada("Checkout", "Pedidos", "criar(pedido)", () ->
                        retorno("Pedidos", "Checkout", "pedido P-2001"));
            } else {
                retorno("Gateway", "Checkout", "recusado");
                chamada("Checkout", "Pedidos", "cancelar(reservas)", () ->
                        retorno("Pedidos", "Checkout", "reservas liberadas"));
            }
        });
        retorno("Checkout", "Interface", aprovado ? "pedido concluído" : "pagamento recusado");
    }));
    retorno("Interface", "Cliente", aprovado ? "confirmação na tela" : "tente outro cartão");
}

/**
 * Diagrama de sequência em Java: o checkout de uma loja.
 * Cada chamada vira uma mensagem numerada. O recuo mostra a barra de ativação (a pilha de chamadas).
 * Fragmentos: opt (cupom opcional), alt (aprovado ou recusado), loop (reservar cada item), ref (autenticação).
 */
public class Main {

    static int passo = 0;
    static int profundidade = 0;

    /** Mensagem síncrona: o emissor espera a execução do corpo (barra de ativação). */
    static void chamada(String de, String para, String texto, Runnable corpo) {
        passo++;
        System.out.println("  ".repeat(profundidade) + passo + ": " + de + " -> " + para + ": " + texto);
        profundidade++;
        corpo.run();
        profundidade--;
    }

    /** Mensagem de retorno: linha tracejada no diagrama. */
    static void retorno(String de, String para, String valor) {
        passo++;
        System.out.println("  ".repeat(profundidade) + passo + ": " + de + " --> " + para + ": " + valor);
    }

    static void checkout(boolean comCupom, boolean aprovado, List2 itens) {
        chamada("Cliente", "Interface", "finalizar compra", () ->
        chamada("Interface", "Checkout", "iniciar(carrinho)", () -> {

            // ref: a autenticação é um cenário reaproveitado (aparece em outros diagramas)
            chamada("Checkout", "Sessao", "autenticar()  [ref: Autenticação]", () ->
                    retorno("Sessao", "Checkout", "usuário válido"));

            // opt: o cupom só é validado se o cliente informou um
            if (comCupom) {
                chamada("Checkout", "Cupons", "validar(BEMVINDO10)", () ->
                        retorno("Cupons", "Checkout", "desconto de 10%"));
            }

            // loop: cada item é reservado no estoque
            for (String item : itens.valores) {
                chamada("Checkout", "Estoque", "reservar(" + item + ")", () ->
                        retorno("Estoque", "Checkout", "reservado"));
            }

            // alt: caminho de sucesso ou de recusa do cartão
            chamada("Checkout", "Gateway", "cobrar(total)", () -> {
                if (aprovado) {
                    retorno("Gateway", "Checkout", "aprovado");
                    chamada("Checkout", "Pedidos", "criar(pedido)", () ->
                            retorno("Pedidos", "Checkout", "pedido P-2001"));
                } else {
                    retorno("Gateway", "Checkout", "recusado");
                    chamada("Checkout", "Pedidos", "cancelar(reservas)", () ->
                            retorno("Pedidos", "Checkout", "reservas liberadas"));
                }
            });
            retorno("Checkout", "Interface", aprovado ? "pedido concluído" : "pagamento recusado");
        }));
        retorno("Interface", "Cliente", aprovado ? "confirmação na tela" : "tente outro cartão");
    }

    /** Pequeno invólucro para passar a lista de itens como um valor simples. */
    static final class List2 {
        final java.util.List<String> valores;
        List2(String... v) { valores = java.util.List.of(v); }
    }

    public static void main(String[] args) {
        java.util.Locale.setDefault(java.util.Locale.ROOT);   // saída igual em qualquer máquina
        System.out.println("== Cenário A: com cupom, cartão aprovado");
        passo = 0; profundidade = 0;
        checkout(true, true, new List2("FONE-01", "CAPA-07"));

        System.out.println("\n== Cenário B: sem cupom, cartão recusado");
        passo = 0; profundidade = 0;
        checkout(false, false, new List2("CABO-02"));
    }
}




  





  
No mercado de trabalho

  



Diagramas de sequência estão no centro de duas práticas que as equipes de software usam todos os dias:


    

  • Rastreamento distribuído. Em sistemas com vários serviços, uma requisição passa por muitos componentes. O OpenTelemetry (documentação em opentelemetry.io, seção de traces) registra cada chamada como um span, com início, fim e relação de pai e filho. Um trace visualizado numa ferramenta de observabilidade é, na prática, um diagrama de sequência real, medido em milissegundos.
    • 

  • Contratos de integração. Quando dois times precisam combinar uma API, a sequência esperada (quem chama, o que espera de volta, o que acontece em caso de erro) é uma das formas mais claras de registrar o acordo. Hohpe e Woolf (2003, Enterprise Integration Patterns, Addison-Wesley) catalogam padrões de mensagens que aparecem exatamente nessas sequências.
    • 

  • Revisões de arquitetura. Em design reviews, a sequência do caminho feliz e dos caminhos de erro é desenhada antes do código. Quem revisa procura, principalmente, mensagens sem resposta, chamadas que se repetem sem limite e ordens que causam inconsistência.
    • 

  • Testes de interação. Fowler (2007, Mocks Aren't Stubs) discute testes que verificam a sequência de chamadas e não só o resultado final. É a versão em código do diagrama de sequência.
    • 



Atenção: os usos descritos são práticas comuns da área, e não processos internos de empresas específicas.


  





  
Erros comuns

  



    

  • Mensagem sem retorno quando há resposta. Se o método devolve um valor usado depois, o retorno deve aparecer, ou o leitor não sabe de onde veio o dado.
    • 

  • Ordem invertida entre verificação e ação. Debitar antes de verificar o saldo é o erro mais grave que a sequência pode esconder se for desenhada sem cuidado.
    • 

  • opt para tudo. Fragmento opcional deve ser opcional de verdade.
    • 

  • Diagrama com todos os caminhos misturados. Um alt com cinco ramos costuma indicar que a interação deveria ser dividida em duas, com um ref entre elas.
    • 



  





  
Exercícios com gabarito

  



1. Desenhe a sequência de um login com senha errada seguida de senha certa, com bloqueio após três tentativas.
Gabarito: use um loop com limite de três tentativas; dentro dele, um alt (senha certa: sessão criada; senha errada: contador incrementado). Se o contador chegar a três, um alt externo leva a “conta bloqueada”. Mostre a mensagem de retorno de cada tentativa.


2. No checkout, a reserva de estoque acontece antes da cobrança. Qual o risco se o cartão for recusado, e como a sequência deve tratá-lo?
Gabarito: o estoque fica reservado sem venda. A sequência precisa de um caminho de compensação (cancelar(reservas) no ramo recusado), como o programa mostra no cenário B.


3. Por que o retorno “pedido criado” aparece depois do retorno do gateway, e não antes?
Gabarito: porque a criação do pedido depende da aprovação. A ordem das mensagens é a ordem de dependência: uma mensagem que precisa de um resultado só pode vir depois dele.

Quatro perguntas sobre interação.


  

    

      
1. A barra vertical estreita sobre a linha de vida representa:

      
      
      
      

        A barra corresponde exatamente ao quadro daquele método na pilha de execução. Ela começa quando a
        mensagem chega e termina quando o método retorna — foi o que a animação mostrou.
      

    


    

      
2. Seta com ponta preenchida e linha sólida indica:

      
      
      
      

        Ponta preenchida = síncrona (chamada de método comum). Ponta aberta (meia-seta) = assíncrona,
        o chamador segue sem esperar. Linha tracejada com ponta aberta = retorno.
      

    


    

      
3. Para representar “se o exemplar estiver disponível… senão…”, usa-se:

      
      
      
      

        Losango é do diagrama de
        atividades. Aqui usa-se alt (alternativa), opt (opcional),
        loop (repetição) e par (paralelo).
      

    


    

      
4. Um diagrama em que todas as setas partem de um mesmo objeto sugere:

      
      
      
      

        Esse é um dos maiores valores do diagrama: tornar visível o desequilíbrio. Objetos com comportamento
        próprio colaboram; objetos anêmicos apenas guardam dados enquanto um controlador faz tudo — veja o
        Princípio da Responsabilidade Única.
