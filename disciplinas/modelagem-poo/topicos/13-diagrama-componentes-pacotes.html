Por que subir o nível de abstração

Um sistema de streaming como o Melodia tem centenas de classes: catálogo, reprodução, assinatura, pagamento, recomendação, autenticação. Um diagrama de classes com todas elas não cabe em uma página, e não responde à pergunta que mais importa no dia a dia: quais partes podem mudar sem que as outras percam?

Para isso, a modelagem sobe um nível. Em vez de classes, desenhamos componentes (peças com um contrato) e pacotes (agrupamentos que organizam código e controlam a visibilidade). O diagrama de componentes mostra o que cada peça oferece e o que precisa; o diagrama de pacotes mostra como o código é organizado e quem depende de quem.

De onde vem a ideia

  • Componentes como unidade de reuso. Clemens Szyperski, em Component Software: Beyond Object-Oriented Programming (1998), define componente como uma unidade de composição com interfaces bem definidas, implantada de forma independente.
  • Na UML. Os pacotes já existiam na UML 1.x. Os componentes ganharam forma completa com a UML 2.0, que trouxe portas, interfaces fornecidas e requeridas. A especificação atual está na OMG (UML 2.5.1).
  • Na prática de hoje. O modelo C4, de Simon Brown, usa o diagrama de componentes como o terceiro de quatro níveis: contexto, contêineres, componentes e código.

Por que isso importa para quem programa: o diagrama de componentes é o mapa que decide quem pode importar quem. Quando o mapa está certo, uma mudança no catálogo não obriga a recompilar a reprodução. Quando está errado, qualquer mudança vira uma reação em cadeia.

Como o encaixe aparece no código

Em Java, uma interface fornecida é um tipo público. Uma interface requerida é um parâmetro de construtor. Veja o player: ele não sabe qual catálogo existe, só que existe algo que implementa CatalogoMusica.

catalogo/CatalogoMusica.java (interface fornecida)

package catalogo;

import java.util.Optional;

/** Interface fornecida pelo componente catálogo: quem quiser buscar faixas depende só disto. */
public interface CatalogoMusica {
    Optional<Musica> buscar(String id);
}

reproducao/Player.java (componente que requer as duas interfaces)

package reproducao;

import assinatura.VerificadorAssinatura;
import catalogo.CatalogoMusica;
import catalogo.Musica;

/**
 * Componente reprodução. Requer duas interfaces (catálogo e assinatura) e não conhece
 * nenhuma implementação concreta: quem monta o player decide quais usar.
 */
public class Player {

    private final CatalogoMusica catalogo;
    private final VerificadorAssinatura assinaturas;

    public Player(CatalogoMusica catalogo, VerificadorAssinatura assinaturas) {
        this.catalogo = catalogo;
        this.assinaturas = assinaturas;
    }

    public String tocar(String usuario, String id) {
        if (!assinaturas.podeOuvir(usuario)) {
            return "negado: " + usuario + " sem assinatura ativa";
        }
        return catalogo.buscar(id)
                .map(m -> "tocando " + m.titulo() + " (" + m.segundos() + " s) para " + usuario)
                .orElse("faixa " + id + " não encontrada");
    }
}
Animação
package app;

import assinatura.AssinaturaAtiva;
import catalogo.CatalogoMemoria;
import catalogo.Musica;
import reproducao.Player;

/** Ponto de montagem (composition root): só aqui os componentes são ligados entre si. */
public class Main {

    public static void main(String[] args) {
        CatalogoMemoria catalogo = new CatalogoMemoria(
                new Musica("m1", "Aquarela", 200),
                new Musica("m2", "Garota", 180));
        AssinaturaAtiva assinaturas = new AssinaturaAtiva("ana");
        Player player = new Player(catalogo, assinaturas);

        System.out.println(player.tocar("ana", "m1"));
        System.out.println(player.tocar("bruno", "m2"));
        System.out.println(player.tocar("ana", "m9"));
    }
}
Leitura da animação: repare que a montagem (app.Main) é o único lugar que conhece todas as peças. Os componentes se conhecem apenas pelas interfaces. Esse ponto de montagem é o que a arquitetura chama de composition root.

Pacotes: organização e visibilidade

Um pacote é um espaço de nomes e um limite de visibilidade. No diagrama, é desenhado como uma pasta com o nome do pacote. Uma seta tracejada de pacote para pacote significa que um importa do outro. No código Java, cada import é uma dependência desenhada.

No Melodia, os pacotes são quatro: catalogo (dados e busca), assinatura (quem pode ouvir), reproducao (o player) e app (a montagem). Repare nas dependências: app depende de todos; reproducao depende de catalogo e assinatura; e catalogo e assinatura não dependem de ninguém.

flowchart TD
    app --> reproducao
    app --> catalogo
    app --> assinatura
    reproducao --> catalogo
    reproducao --> assinatura

Visibilidade: o que sai do pacote

  • public: parte da interface do pacote, visível para quem importa.
  • sem modificador (pacote-privado): detalhe interno, invisível fora dele. Em CatalogoMemoria, o HashMap é pacote-privado no sentido prático: ninguém de fora o acessa.
  • public em excesso: cada método público é um contrato que alguém pode usar. Torne público só o que o componente promete.
Erro comum: colocar tudo em um pacote util ou model. Assim o pacote vira um depósito, e todo mundo depende de todo mundo. Pacotes devem ser organizados por responsabilidade, como fizemos com catalogo e assinatura.

Ciclos: o pecado da dependência circular

Robert C. Martin, em Agile Software Development (2003) e no livro Clean Architecture (2017), descreve o princípio das dependências acíclicas: o grafo de dependências entre pacotes e componentes não pode ter ciclos. Se A depende de B, e B depende de A, nenhum dos dois pode ser compilado, testado, implantado ou versionado sozinho.

O ciclo quase sempre nasce de um atalho conveniente. A faixa precisa saber tocar a si mesma, então ganha um método tocarPara. Esse método chama o player, e o player precisa do tipo Musica. Dois pacotes se conhecem, e a conveniência vira um nó.

flowchart LR
    catalogo -- "Musica.tocarPara chama Player" --> reproducao
    reproducao -- "Player.reproduzir recebe Musica" --> catalogo

A animação abaixo segue o ciclo passo a passo, a partir dos dois arquivos da versão ruim. Use os botões para avançar.

Animação
// arquivo: catalogo/Musica.java
package catalogo;

import reproducao.Player;

/** Ruim: a faixa sabe tocar a si mesma. Agora catalogo depende de reproducao... */
public record Musica(String id, String titulo, int segundos) {

    public String tocarPara(String usuario) {
        return new Player().reproduzir(usuario, this);
    }
}

// arquivo: reproducao/Player.java
package reproducao;

import catalogo.Musica;

/** ...e reproducao depende de catalogo (Musica). Ciclo: catalogo -> reproducao -> catalogo. */
public class Player {

    public String reproduzir(String usuario, Musica m) {
        return "tocando " + m.titulo() + " (" + m.segundos() + " s) para " + usuario;
    }
}

Como quebrar o ciclo

  1. Mover o comportamento para quem usa. O método tocarPara não pertence à faixa. Ele pertence ao player, ou à montagem.
  2. Inverter a dependência com uma interface. Se o player precisa de algo do catálogo, o contrato fica no pacote de quem usa (o player), e o catálogo implementa.
  3. Separar o dado do comportamento. Musica como record é só dado, e não conhece reprodução.
Regra prática: se você precisa de um import na direção oposta à do diagrama, pare. Ou o comportamento está no lugar errado, ou falta uma interface.

Exemplo de uso no Melodia: a equipe de reprodução

Imagine que a equipe de reprodução quer trocar o catálogo em memória por um catálogo em banco de dados. Como o player requer apenas CatalogoMusica, a mudança acontece em um arquivo novo (CatalogoBanco) e na linha de montagem. Nenhum arquivo de reproducao é recompilado com outra intenção, e os testes do player continuam usando o CatalogoMemoria.

Agora imagine o contrário: o player importa diretamente CatalogoMemoria. A troca de banco vira uma cirurgia em todo o player, e os testes passam a precisar do banco de verdade. O diagrama de componentes mostra essa diferença antes de qualquer linha de código.

Ferramentas que mostram o grafo real

  • jdeps, que vem com o JDK, lista as dependências entre pacotes de um projeto compilado.
  • Arquitetura como código, com regras executadas nos testes: uma verificação diz quando um pacote importa outro que não deveria.
  • Revisão de código: um import novo entre pacotes é um pedido de atenção, e não um detalhe.

Do diagrama ao Java: os pacotes do Melodia

O projeto completo está em disciplinas/modelagem-poo/exemplos/componentes/, em duas versões: melodia-bom (acíclico) e melodia-ruim (com ciclo). Ambas compilam. A diferença não aparece na saída, e sim no grafo de dependências.

Como compilar e rodar

Entre na pasta da versão e compile todos os arquivos, com o pacote em cada pasta:

cd disciplinas/modelagem-poo/exemplos/componentes/melodia-bom
javac -Xlint:all -d out $(find . -name "*.java")
java -cp out app.Main

Para ver o grafo de dependências entre pacotes (ferramenta do JDK):

jdeps -summary -cp out out

Código da versão boa, arquivo por arquivo

catalogo/Musica.java: dado puro, sem import de outros pacotes

package catalogo;

/** Dado puro: não conhece reprodução nem assinatura. */
public record Musica(String id, String titulo, int segundos) {}

catalogo/CatalogoMemoria.java: implementação trocável

package catalogo;

import java.util.HashMap;
import java.util.Map;
import java.util.Optional;

/** Implementação do catálogo em memória: trocável por um banco sem mudar quem usa a interface. */
public class CatalogoMemoria implements CatalogoMusica {

    private final Map<String, Musica> musicas = new HashMap<>();

    public CatalogoMemoria(Musica... faixas) {
        for (Musica m : faixas) {
            musicas.put(m.id(), m);
        }
    }

    @Override
    public Optional<Musica> buscar(String id) {
        return Optional.ofNullable(musicas.get(id));
    }
}

assinatura/VerificadorAssinatura.java e AssinaturaAtiva.java

package assinatura;

/** Interface fornecida pelo componente assinatura. */
public interface VerificadorAssinatura {
    boolean podeOuvir(String usuario);
}

package assinatura;

import java.util.Set;

/** Implementação simples: uma lista de usuários com assinatura ativa. */
public class AssinaturaAtiva implements VerificadorAssinatura {

    private final Set<String> ativos;

    public AssinaturaAtiva(String... usuarios) {
        this.ativos = Set.of(usuarios);
    }

    @Override
    public boolean podeOuvir(String usuario) {
        return ativos.contains(usuario);
    }
}

Saída real: versão ruim

Saída real
tocando Aquarela (200 s) para ana

A saída é a mesma, e o programa roda. O problema não aparece na execução, e sim na pergunta que o diagrama faz: catalogo importa reproducao, que importa catalogo. O jdeps mostra esse ciclo para quem procura; o javac aceita, porque ciclos entre pacotes são permitidos pela linguagem.

Ponto importante: a linguagem permite o ciclo, e por isso ele é perigoso. Nenhum erro de compilação avisa. O custo aparece depois, quando alguém tenta separar os pacotes em módulos ou em builds independentes.

Ilustração de módulos (não compilada nesta aula)

A partir do Java 9, a mesma regra pode ser declarada em um module-info.java. Para o componente de reprodução, algo como module melodia.reproducao { requires melodia.catalogo; requires melodia.assinatura; exports reproducao; }. Um ciclo entre módulos não é permitido pelo sistema de módulos: o build falha. Vale mostrar essa diferença à turma como exemplo do que o ciclo custa.

Exemplo extra: recomendação sem ciclo

O Melodia ganha uma funcionalidade nova: recomendar músicas com base no histórico de escuta e no catálogo. A tentação é fazer o catálogo consultar o histórico do player, ou o player consultar o catálogo de recomendação, e assim por diante. Vamos desenhar com cuidado.

Três componentes novos ou existentes: reproducao (o player), catalogo (dados) e recomendacao, que requer as duas interfaces: CatalogoMusica e HistoricoEscuta. O player requer um Recomendador, e não a implementação.

flowchart TD
    Player["Player (reproducao)"] -- "requer" --> Rec["«interface» Recomendador (recomendacao)"]
    Rec -. "implementa" .-> RecImpl["RecomendadorPorGenero (recomendacao)"]
    RecImpl -- "requer" --> CI["«interface» CatalogoMusica (catalogo)"]
    RecImpl -- "requer" --> HI["«interface» HistoricoEscuta (historico)"]
    HI -. "implementa" .-> HM["HistoricoMemoria (historico)"]

A versão que gera ciclo

Se o catálogo passar a consultar o player para saber o que está tocando, e o player passar a consultar o catálogo para recomendar, surge o ciclo que já vimos. Repare que ele não aparece no código de uma classe só: aparece na soma das dependências.

flowchart LR
    Catalogo["catalogo"] -- "consulta preferências" --> Player["reproducao"]
    Player -- "pede recomendações" --> Catalogo
Como o desenho certo evita o ciclo: a recomendação recebe o histórico por uma interface (HistoricoEscuta) que vive no pacote da recomendação. O player só vê o Recomendador. Ninguém volta a importar o player.

Exercícios com gabarito

Os exercícios usam o Melodia. Tente antes de abrir o gabarito: o desenho importa mais que a resposta pronta.

1. (Fácil) No Melodia, quais são as interfaces fornecidas e requeridas pelo componente reproducao?

Requeridas: CatalogoMusica e VerificadorAssinatura, passadas pelo construtor do Player. Fornecidas: nenhuma interface nova; o player oferece o método tocar, que é a sua interface de uso. Se você listou Musica, lembre que é um dado, e não uma interface.

2. (Médio) Acrescente o componente pagamento, com a interface Cobrador, implementada por CobradorPix e CobradorCartao. A assinatura precisa cobrar a renovação. Desenhe as dependências e verifique se há ciclo.

A assinatura requer Cobrador, e os cobradores a implementam. Não há ciclo: pagamento não conhece assinatura.

flowchart LR
    Assinatura["assinatura"] -- "requer" --> PI["«interface» Cobrador (pagamento)"]
    PIX["CobradorPix (pagamento-pix)"] -. "implementa" .-> PI
    CART["CobradorCartao (pagamento-cartao)"] -. "implementa" .-> PI

Atenção: se o cobrador precisasse consultar a assinatura para saber o valor, surgiria um ciclo. A correção seria passar o valor como parâmetro.

3. (Médio, streaming) Dado o ciclo da versão ruim, liste duas formas de quebrá-lo sem remover funcionalidades.

Forma 1: remover o método tocarPara de Musica e colocar a chamada no player ou na montagem. Forma 2: definir uma interface no pacote que consome, por exemplo ReproducaoListener no catalogo, implementada pelo player. Em ambas, a seta de catalogo para reproducao desaparece.

4. (Desafio, streaming) Você implementou a recomendação. O histórico é gravado pelo player e lido pela recomendação. Desenhe o grafo que evita ciclo e diga em que pacote fica a interface HistoricoEscuta.

A interface HistoricoEscuta fica no pacote recomendacao, que é quem a requer. O player grava escutas em uma implementação que implementa essa interface (por exemplo, HistoricoMemoria, em outro pacote). Assim, recomendacao não importa reproducao, e o player só depende de Recomendador.

flowchart TD
    Player["Player (reproducao)"] -- "requer" --> Rec["«interface» Recomendador (recomendacao)"]
    Rec -. "implementa" .-> RecImpl["RecomendadorPorGenero (recomendacao)"]
    RecImpl -- "requer" --> CI["«interface» CatalogoMusica (catalogo)"]
    RecImpl -- "requer" --> HI["«interface» HistoricoEscuta (historico)"]
    HI -. "implementa" .-> HM["HistoricoMemoria (historico)"]
5. (Reflexão) Um colega propõe criar um pacote util com todas as classes compartilhadas, para evitar repetição. Quais são os riscos, e o que você faria no lugar?

Um pacote util tende a crescer e a ser importado por todos, o que cria dependências em todas as direções. O que fazer no lugar: colocar cada classe compartilhada no pacote de quem a define, e expor só as interfaces necessárias. Se duas classes realmente dividem um conceito, esse conceito merece um pacote próprio, com um nome que diga o que ele é.

Teste seu entendimento

Três perguntas sobre arquitetura.

1. O semicírculo (soquete) na borda de um componente representa:

Pirulito (círculo cheio na ponta de uma haste) = fornecida. Soquete (semicírculo aberto) = requerida. O encaixe entre os dois é a ligação de montagem (assembly connector).

2. Uma dependência circular entre dois pacotes causa:

Se A precisa de B e B precisa de A, nenhum dos dois pode ser construído antes do outro. O acoplamento vira total: na prática, os dois pacotes viraram um só, com a ilusão de estarem separados.

3. Trocar o componente de pagamento sem alterar quem o usa é possível porque:

É a substituibilidade que define um componente. No código, isso aparece como injeção de dependência: o tipo declarado é a interface, e quem decide a implementação concreta é a configuração.
