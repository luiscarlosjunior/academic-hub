Quando a classe é pequena demais para enxergar o sistema

Um sistema com 300 classes não cabe em um diagrama de classes legível. Para falar de arquitetura, sobe-se o nível de abstração: pacotes agrupam elementos em namespaces; componentes representam partes substituíveis do sistema, definidas pelo que elas fornecem e pelo que exigem.

Pacote

Agrupamento lógico, quase sempre correspondendo a um diretório/namespace. Serve para organizar e controlar visibilidade. Mostra dependências, não interfaces.

Ex.: br.com.loja.dominio

Componente

Unidade substituível com contrato explícito: interfaces fornecidas e requeridas. Se outro componente cumprir o mesmo contrato, pode trocar de lugar.

Ex.: ServicoPagamento, RepositorioPedidos

Fornece e requer: o encaixe

A notação de “pirulito e soquete”: o círculo é uma interface fornecida; o semicírculo é uma interface requerida. Quando se encaixam, os componentes conversam — sem que nenhum conheça a implementação do outro.

Regras de boa vizinhança

        
    
          
  • • Dependências apontam sempre para dentro: UI → aplicação → domínio.
    • 
          
  • • O domínio não deve depender de nada — nem de banco, nem de framework.
    • 
          
  • • Ciclos entre pacotes impedem compilar, testar ou publicar separadamente.
    • 
          
  • • Para quebrar um ciclo, inverta a dependência com uma interface no pacote de baixo.

Componente: uma peça com contrato

  

    

      Um componente é uma parte modular e substituível do sistema, que oferece e consome serviços por meio de
      interfaces. Ele esconde a implementação: quem usa o componente conhece apenas o contrato. Essa é a
      ocultação de informação (tópico 03) aplicada em escala de arquitetura.
    

    

      Na UML, o componente é um retângulo com o estereótipo «component», e suas interfaces aparecem como
      pirulito (interface fornecida, ○) e soquete (interface requerida, ◗).
      A conexão entre um pirulito e um soquete é uma relação de montagem, e mostra quem depende de quem.
    

  

  

    
Interface fornecida
O que o componente oferece. Ex.: IAssinatura, com assinar().

    
Interface requerida
O que o componente precisa de fora. Ex.: IPagamento, com cobrar().

    
Porta
Ponto de interação do componente com o exterior, agrupando interfaces relacionadas.

  

  

    
    

      Substituibilidade: se o gateway de pagamento muda, o componente de cobrança continua válido desde que
      implemente a mesma interface requerida. Esse é o benefício de desenhar pelo contrato.
    

  






  
Pacotes: organização e visibilidade

  

    

      Um pacote agrupa elementos relacionados e cria um espaço de nomes. Dois elementos podem se chamar
      Pagamento desde que estejam em pacotes diferentes. Em Java, o pacote corresponde à declaração
      package no topo do arquivo, e o diagrama de pacotes espelha a estrutura de diretórios do projeto.
    

  

  

    
classDiagram
    namespace catalogo {
        class Musica
        class Album
    }
    namespace assinatura {
        class Assinatura
        class Plano
    }
    namespace cobranca {
        class ContaBancaria
        class Transacao
    }
    Assinatura --> Plano
    Assinatura --> ContaBancaria
    

  

  
Três pacotes. A dependência de assinatura para cobranca é a única que atravessa a fronteira; catalogo não depende de ninguém.






  
O princípio das dependências acíclicas

  

    

      Robert C. Martin propôs, entre os princípios de empacotamento, que o grafo de dependências entre pacotes seja
      acíclico. Um ciclo significa que, para compilar ou testar um pacote, é preciso compilar outro que depende
      dele, e assim por diante. O ciclo cria um bloco que não pode ser separado.
    

  

  

    
flowchart LR
    A["assinatura"] --> B["cobranca"]
    B --> C["relatorios"]
    C --> A
    

  

  
Ciclo: assinatura → cobranca → relatorios → assinatura. Nenhum dos três pode ser testado ou reutilizado isoladamente.

  

    
    

      Como quebrar um ciclo: extraia o elemento compartilhado para um terceiro pacote, ou inverta uma dependência
      com uma interface (DIP, tópico 16). Na maioria dos casos, o ciclo indica uma responsabilidade mal distribuída.
    

  






  
Do diagrama de pacotes ao Java


// src/com/melodia/cobranca/ContaBancaria.java
package com.melodia.cobranca;

public class ContaBancaria { /* ... */ }

// src/com/melodia/assinatura/Assinatura.java  (depende de cobranca)
package com.melodia.assinatura;
import com.melodia.cobranca.ContaBancaria;

// module-info.java: o componente declara o que oferece e o que exige (Java 9+)
module com.melodia.assinatura {
    requires com.melodia.cobranca;   // interface requerida
    exports com.melodia.assinatura;  // interface fornecida
}

  

    

      O module-info.java torna a noção de componente concreta: requires é o soquete, exports
      é o pirulito. Um compilador que aceite requires circular entre módulos não existe; o Java bloqueia o ciclo, que
      é exatamente o que o princípio pede.
    

  






  
Exercícios

  

    

      1. Você precisa trocar o provedor de e-mail do Melodia sem mexer no módulo de assinatura. Quais interfaces desenhar?
      
Gabarito: o módulo de assinatura exige uma interface IEnvioEmail (soquete). Cada provedor fornece uma implementação (pirulito) em seu próprio componente. A troca de provedor é trocar a montagem, sem alterar a assinatura.

    

    

      2. No diagrama de pacotes, relatorios depende de assinatura, e assinatura depende de relatorios para gerar o recibo. Como resolver?
      
Gabarito: extrair a geração do recibo para um pacote próprio que ambos usam, ou inverter a dependência: assinatura define uma interface Recibo e relatorios a implementa. Ambas as soluções eliminam o ciclo.

    

    

      3. Qual a diferença entre a dependência de pacotes e a de componentes?
      
Gabarito: o pacote é uma unidade de organização (nome, arquivos, visibilidade). O componente é uma unidade de implantação e contrato, com interfaces explícitas. Um componente pode conter vários pacotes, e a dependência entre componentes é mais forte, porque envolve um contrato publicado.

Teste seu entendimento

  
Três perguntas sobre arquitetura.


  

    

      
1. O semicírculo (soquete) na borda de um componente representa:

      
      
      
      

        Pirulito (círculo cheio na ponta de uma haste) = fornecida. Soquete (semicírculo aberto) = requerida.
        O encaixe entre os dois é a ligação de montagem (assembly connector).
      

    


    

      
2. Uma dependência circular entre dois pacotes causa:

      
      
      
      

        Se A precisa de B e B precisa de A, nenhum dos dois pode ser construído antes do outro. O acoplamento
        vira total: na prática, os dois pacotes viraram um só, com a ilusão de estarem separados.
      

    


    

      
3. Trocar o componente de pagamento sem alterar quem o usa é possível porque:

      
      
      
      

        É a substituibilidade que define um componente. No código, isso aparece como injeção de dependência:
        o tipo declarado é a interface, e quem decide a implementação concreta é a configuração.
