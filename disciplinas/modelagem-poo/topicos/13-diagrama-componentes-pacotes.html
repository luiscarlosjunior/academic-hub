Quando a classe é pequena demais para enxergar o sistema

Um sistema com 300 classes não cabe em um diagrama de classes legível. Para falar de arquitetura, sobe-se o nível de abstração: pacotes agrupam elementos em namespaces; componentes representam partes substituíveis do sistema, definidas pelo que elas fornecem e pelo que exigem.

Pacote

Agrupamento lógico, quase sempre correspondendo a um diretório/namespace. Serve para organizar e controlar visibilidade. Mostra dependências, não interfaces.

Ex.: br.com.loja.dominio

Componente

Unidade substituível com contrato explícito: interfaces fornecidas e requeridas. Se outro componente cumprir o mesmo contrato, pode trocar de lugar.

Ex.: ServicoPagamento, RepositorioPedidos

Fornece e requer: o encaixe

A notação de “pirulito e soquete”: o círculo é uma interface fornecida; o semicírculo é uma interface requerida. Quando se encaixam, os componentes conversam — sem que nenhum conheça a implementação do outro.

Regras de boa vizinhança

        
    
          
  • • Dependências apontam sempre para dentro: UI → aplicação → domínio.
    • 
          
  • • O domínio não deve depender de nada — nem de banco, nem de framework.
    • 
          
  • • Ciclos entre pacotes impedem compilar, testar ou publicar separadamente.
    • 
          
  • • Para quebrar um ciclo, inverta a dependência com uma interface no pacote de baixo.

Três perguntas sobre arquitetura.


  

    

      
1. O semicírculo (soquete) na borda de um componente representa:

      
      
      
      

        Pirulito (círculo cheio na ponta de uma haste) = fornecida. Soquete (semicírculo aberto) = requerida.
        O encaixe entre os dois é a ligação de montagem (assembly connector).
      

    


    

      
2. Uma dependência circular entre dois pacotes causa:

      
      
      
      

        Se A precisa de B e B precisa de A, nenhum dos dois pode ser construído antes do outro. O acoplamento
        vira total: na prática, os dois pacotes viraram um só, com a ilusão de estarem separados.
      

    


    

      
3. Trocar o componente de pagamento sem alterar quem o usa é possível porque:

      
      
      
      

        É a substituibilidade que define um componente. No código, isso aparece como injeção de dependência:
        o tipo declarado é a interface, e quem decide a implementação concreta é a configuração.
