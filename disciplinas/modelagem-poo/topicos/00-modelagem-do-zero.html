Por que modelar antes de programar?

Imagine construir uma casa sem planta. Os pedreiros começam, descobrem que a cozinha não cabe ao lado da área de serviço, derrubam uma parede e refazem a instalação elétrica. O custo de corrigir uma decisão cresce muito quando a obra já está em andamento.

Com software é igual. Um erro de modelo — uma classe que faltou, uma associação com a multiplicidade errada — custa uma conversa e um rabisco no papel quando está no diagrama. Depois que ele vira código, espalhado em dezenas de arquivos e já usado por clientes, o mesmo erro custa dias.

Modelar é traduzir uma descrição em linguagem natural para uma estrutura que se possa discutir, revisar e transformar em código. Este tópico mostra essa tradução passo a passo, usando um sistema real de exemplo do curso: a plataforma de streaming Melodia.

Ideia central: o diagrama final não é burocracia. Ele é o esqueleto do código: cada classe desenhada vira uma classe Java, cada seta vira um atributo ou uma referência.

Ponto de partida: a frase do cliente

Modelagem começa com um texto, quase sempre vago. Este é o pedido que vamos transformar em modelo:

“A Melodia é uma plataforma de streaming de música. Nela, ouvintes escutam músicas organizadas em álbuns (publicados por artistas) e montam suas próprias playlists. Para ouvir sem anúncios, o ouvinte assina um plano. A assinatura paga é cobrada todo mês de uma conta bancária: se houver saldo, fica ativa; se faltar, é suspensa. Cada reprodução gera um pequeno royalty ao artista.”

Esse parágrafo é a fonte de verdade do sistema. Antes de desenhar qualquer coisa, leia-o mais de uma vez e pergunte: o que o sistema precisa guardar? o que precisa fazer? quais regras não podem ser quebradas?

As regras de negócio (invariantes)

Regras que o sistema sempre deve respeitar. Elas viram validações no código e guardas nos diagramas.

A técnica: sublinhe o texto

A forma mais simples de começar é grifar o texto do cliente com duas cores. Substantivos viram candidatos a classe ou atributo; verbos viram candidatos a operação. Depois você separa o joio do trigo, porque nem todo substantivo é classe.

Substantivos

Coisas do domínio com vida própria.

ouvinte, música, álbum, playlist, plano, conta → classes
título, duração, saldo, status → atributos

Verbos

Ações que o sistema executa ou que alguém pede.

escutar, assinar, cobrar, suspender, publicar, creditar → operações

Trecho do enunciadoViraPor quê
“ouvintes escutam músicas”Classes Ouvinte e MusicaTêm dados e comportamento próprios
“saldo”Atributo de ContaBancariaÉ só um valor, sem vida própria
“reprodução”Classe ou eventoDepende de o sistema precisar guardar histórico
“cobrada todo mês”Operação cobrar() e um ator de tempoÉ uma ação disparada periodicamente
“ativa / suspensa”Estados (ou enum StatusAssinatura)Valores que mudam conforme regras
Pergunta que decide: “isto tem só valor, ou tem valor e comportamento (ou aparece muitas vezes no sistema)?” Se só tem valor, é atributo. Se tem comportamento, é classe. “Saldo” é só número; “conta” tem saldo, sacar, depositar e extrato — por isso é classe.

O modelo cresce em versões

Ninguém acerta o modelo completo de primeira. Um bom modelo começa simples e cresce conforme a necessidade aparece. Acompanhe as quatro primeiras versões do Melodia.

v4

Artista e álbum: composição × agregação

Aqui está o ponto-chave da aula. As duas classes apontam para Musica, mas de formas diferentes. O álbum cria suas faixas; a playlist só aponta para músicas que já existem. 

classDiagram

    class Album
    class Playlist
    class Musica
    Artista "1" --> "0..*" Album : publica
    Album "1" *-- "1..*" Musica : faixas
    Playlist "1" o-- "0..*" Musica : contém

Losango cheio (*--) = composição: a faixa morre com o álbum.  ·  Losango vazio (o--) = agregação: a música continua existindo sem a playlist.

Do modelo ao código Java

Veja como o diagrama v4 se traduz em código. A composição aparece porque o Album cria a Musica dentro de si. A agregação aparece porque a Playlist recebe uma música que já existe. 

public class Album {
    private final String titulo;
    private final String artista;
    private final List<Musica> faixas = new ArrayList<>();

    // Composição: o álbum cria a faixa e é dono dela
    public Musica adicionarFaixa(String tituloFaixa, int duracao) {
        Musica m = new Musica(tituloFaixa, artista, duracao);
        faixas.add(m);
        return m;
    }
}

public class Playlist {
    private final List<Musica> musicas = new ArrayList<>();

    // Agregação: a playlist só recebe uma música que já existe no catálogo
    public void adicionar(Musica m) {
        if (!musicas.contains(m)) musicas.add(m);
    }
}
Repare na correspondência: o losango cheio do diagrama aparece no código como um objeto criado dentro da classe “dona”. O losango vazio aparece como um objeto recebido de fora. Isso é o que o tópico Relacionamentos explica com mais detalhe.

Erros comuns de quem começa

Transformar todo substantivo em classe

“Título” e “saldo” não precisam de classe própria. Uma classe Titulo sem comportamento só polui o modelo.

Desenhar tudo de uma vez

Modelar a versão final antes de entender o básico gera diagramas com 30 classes que ninguém consegue revisar.

Atributos públicos “por preguiça”

Se saldo é público, qualquer código consegue fazer conta.saldo = -999 e quebrar a regra R1.

Associação sem multiplicidade

Uma seta sem 1, 0..* ou 1..* não diz quantos objetos participam. A regra fica escondida.

Na indústria

Ninguém desenha os 13 diagramas da UML para cada projeto. Em uma equipe real, o trabalho típico é uma conversa com o cliente, alguns rabiscos em um quadro, um diagrama de classes para a parte mais difícil e, às vezes, um diagrama de sequência para uma integração. O que muda de empresa para empresa é o tamanho do modelo, não a técnica.

O termo linguagem ubíqua (do Domain-Driven Design) descreve exatamente o glossário do tópico anterior: negócio e desenvolvedores usam as mesmas palavras. Quando o time diz “conta” e o código tem Cliente.saldoDisponivel, a tradução errada começa ali.

O processo de modelagem é iterativo

Muita gente imagina que a modelagem é uma fase única, feita antes de programar, como se o modelo fosse “escrito de uma vez”. Na prática, a modelagem é um ciclo: você entende um pedaço do domínio, desenha, mostra ao cliente, descobre que errou, corrige e avança. Metodologias iterativas, como o Processo Unificado, tratam o modelo como um artefato vivo que acompanha o código.

Um ciclo típico tem quatro movimentos, que se repetem a cada fatia de funcionalidade:

1 · Entender

Conversar com quem conhece o negócio. Ouvir, perguntar, anotar o vocabulário.

2 · Modelar

Traduzir o que foi entendido em classes, relações e casos de uso.

3 · Validar

Mostrar o diagrama ao cliente em linguagem de negócio, sem notação técnica.

4 · Refinar

Corrigir, simplificar e voltar ao passo 1 com as novas perguntas.

Regra de ouro: o diagrama é um meio de comunicação, não um fim. Se ele não ajuda a conversa com o cliente ou com a equipe, ele está mal feito, mesmo que esteja tecnicamente correto.

Modelo de domínio × modelo de projeto

Há dois modelos que se confundem com facilidade. O modelo de domínio representa os conceitos do negócio, sem se preocupar com tecnologia. O modelo de projeto representa as classes de software que vão implementar esses conceitos, com detalhes como banco de dados, interfaces e frameworks.

Um erro clássico é misturar os dois. Quando o analista desenha UsuarioDAO e ConexaoJDBC no modelo de domínio, ele está respondendo a uma pergunta técnica antes de entender o negócio. O cliente do Melodia não sabe o que é um DAO, mas entende “assinatura” e “conta”.

Modelo de domínio: só conceitos do negócio, com nomes que o cliente reconhece. Não há id, DAO ou List<> aqui.

Linguagem ubíqua (Evans, 2003): o termo “assinatura” deve significar a mesma coisa para o cliente, para o analista e para o código. Se o cliente diz “plano” e o código diz “pacote”, cada conversa vira uma tradução com risco de erro. Esse é o motivo de manter um glossário no início do projeto.

Critérios para aceitar ou rejeitar um candidato a classe

Sublinhar substantivos produz uma lista longa e ruidosa. O professor Craig Larman propõe um filtro: cada candidato precisa passar por critérios antes de virar classe. Os mais úteis estão abaixo.

CritérioPerguntaExemplo no MelodiaVeredito
Informação que o sistema precisa guardarPreciso lembrar disso depois?Saldo da contaSim: é atributo
Serviço ou comportamentoIsto faz algo ou só guarda dado?Conta (sacar, depositar)Sim: é classe
RedundânciaJá existe outro nome para a mesma coisa?“Cliente” e “ouvinte” no mesmo sistemaUnifique em um nome
Irrelevante para o problemaO caso de uso precisa disso?Cor favorita do ouvinteNão: fora do modelo
Vago demaisÉ um conceito específico?“Coisa”, “item”, “dado”Não: refine a palavra
Atributo disfarçadoÉ só um valor, sem vida própria?Título da músicaAtributo de Música
Evento ou açãoÉ um acontecimento ou uma operação?“Cobrança” (ação), “Pagamento falhou” (evento)Operação ou evento, não classe comum
Atenção ao “Pagamento”: dependendo do domínio, pagamento é classe (quando guarda histórico e comprovante, como em uma auditoria), ou apenas uma operação (quando só dispara um débito). Não existe resposta única: a decisão depende do que o sistema precisa fazer. Justifique sempre.

Exemplo resolvido: do texto ao modelo

Um domínio pequeno, para você acompanhar a técnica do começo ao fim.

Enunciado

“Uma biblioteca empresta livros a leitores cadastrados. Cada empréstimo tem uma data de devolução prevista. Um leitor pode ter até três empréstimos simultâneos. Se o livro for devolvido com atraso, o leitor fica bloqueado por dez dias.”

  1. Sublinhe os substantivos: biblioteca, livros, leitores, empréstimo, data de devolução, atraso, bloqueio.
  2. Aplique os critérios: “biblioteca” é o próprio sistema, não uma classe do domínio. “Data de devolução” é atributo do empréstimo. “Atraso” é uma condição calculada, não precisa ser classe. “Bloqueio” tem duração e estado, então merece ser classe ou estado.
  3. Escolha as classes: Livro, Leitor, Emprestimo. O empréstimo é uma classe porque tem dados (datas) e comportamento (devolver, verificar atraso).
  4. Identifique as relações: um leitor tem zero ou mais empréstimos (0..*); um empréstimo se refere a exatamente um livro e um leitor.
  5. Extraia as regras: “até três empréstimos” é um limite de multiplicidade e uma regra de negócio, que deve estar no construtor ou em uma operação de Leitor.
classDiagram
    class Leitor {
        -String nome
        -boolean bloqueado
        +podeEmprestar() boolean
    }
    class Livro {
        -String titulo
        -boolean disponivel
    }
    class Emprestimo {
        -Date dataEmprestimo
        -Date dataPrevista
        +estaAtrasado() boolean
    }
    Leitor "1" --> "0..*" Emprestimo : realiza
    Emprestimo "*" --> "1" Livro : refere-se a

Note que a regra “máximo de três empréstimos” não aparece no diagrama como texto solto: ela pertence ao comportamento de Leitor.podeEmprestar().

Exercícios

Tente antes de abrir o gabarito. Justifique cada decisão, porque a justificativa é o que a banca avalia.

1. Um restaurante recebe pedidos de clientes. Cada pedido tem vários itens de cardápio. O garçom é quem atende a mesa. Liste as classes e justifique o que ficou de fora.

Gabarito: classes candidatas: Pedido, ItemPedido, ItemCardapio, Garcom, Mesa. Ficam de fora: “restaurante” (é o próprio sistema), “cliente” (se o sistema não guarda dados do cliente, não é classe), e “fome” (fora do escopo). ItemPedido é necessário porque o pedido guarda quantidade e observação de cada item: uma associação simples entre Pedido e ItemCardapio não basta.

2. Na Melodia, o plano Família permite até seis contas vinculadas. Como isso aparece no diagrama?

Gabarito: uma associação entre Plano (ou Assinatura) e Ouvinte com multiplicidade 1 de um lado e 1..6 do outro. O limite de seis é uma regra de negócio: pode aparecer como restrição {tamanho <= 6} na associação, e deve ser verificado no código antes de adicionar um novo ouvinte.

3. Um colega desenhou UsuarioMySQL no diagrama de domínio. O que você diz a ele?

Gabarito: o diagrama de domínio deve conter conceitos do negócio. MySQL é detalhe de implementação, que pertence ao modelo de projeto ou à infraestrutura. Sugira o conceito de negócio (Ouvinte) e, se for preciso representar persistência, faça isso em outro diagrama.

Teste seus conhecimentos

Na frase “a conta tem saldo e pode sacar”, o que “saldo” deve virar no modelo?

Correto. “Saldo” é só um valor, sem comportamento próprio: vira atributo. O verbo “sacar” é que vira operação.

Qual relacionamento melhor representa o vínculo entre Album e Musica, sabendo que a faixa só existe dentro do álbum?

Correto. Quando a parte não faz sentido sem o todo e morre com ele, é composição. A playlist, ao contrário, só aponta para músicas que já existem: isso é agregação.

O que levar deste tópico

  • Modelar antes de codar é mais barato: erro no papel custa uma conversa; erro em produção custa dias.
  • Substantivo com comportamento vira classe; substantivo só com valor vira atributo; verbo vira operação.
  • Um bom modelo começa simples e cresce, versão a versão.
  • Composição (o todo cria e é dono) e agregação (o todo apenas aponta) se distinguem pela vida da parte.
