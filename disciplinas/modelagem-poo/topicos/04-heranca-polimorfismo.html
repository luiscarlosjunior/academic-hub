Herança: especializar sem repetir

Quando várias classes compartilham estrutura e comportamento, a parte comum sobe para uma superclasse e cada subclasse acrescenta o que tem de particular. Em UML a relação é desenhada com uma seta de ponta triangular vazada apontando da subclasse para a superclasse.

O teste para saber se a herança cabe é a frase “é um tipo de”: um Gerente é um Funcionário. Se a frase soar estranha, provavelmente o caso é de composição, não de herança.

Generalização ↑

Do específico para o geral: extrair o que Gerente e Analista têm em comum e criar Funcionário.

Especialização ↓

Do geral para o específico: criar Estagiário a partir de Funcionário, ajustando o que muda.

Herança de que exatamente?

A subclasse herda atributos e métodos (inclusive os private, que existem mas não são acessíveis), e não herda construtores.

Polimorfismo: a mesma chamada, respostas diferentes

O código abaixo trata todo mundo como Funcionario e chama calcularBonus(). Qual implementação roda em cada volta? Quem decide é o tipo real do objeto, em tempo de execução — não o tipo da variável. Execute passo a passo.

Ligação tardia (late binding): o compilador só garante que calcularBonus()
        existe em Funcionario. Qual código executa é resolvido pela JVM no instante da
        chamada, olhando o objeto real.

Duas coisas diferentes com nomes parecidos


  

    

      
Sobrecarga (overloading)

      

        Vários métodos com o mesmo nome e assinaturas diferentes,
        na mesma classe. Quem escolhe é o compilador, pelos tipos dos argumentos.
        É polimorfismo estático.
      

      
class Calculadora {
    int somar(int a, int b) { … }
    double somar(double a, double b) { … }
    int somar(int a, int b, int c) { … }
}

      
Não exige herança nenhuma.

    

    

      
Sobrescrita (overriding)

      

        A subclasse substitui um método herdado, mantendo a mesma assinatura.
        Quem escolhe é a JVM, em tempo de execução, pelo tipo real do objeto.
        É polimorfismo dinâmico.
      

      
class Funcionario {
    double calcularBonus() { return salario * 0.10; }
}
class Gerente extends Funcionario {
    @Override
    double calcularBonus() { return salario * 0.25; }
}

      
Só existe com herança (ou implementação de interface).

Anotação típica—@Override

      
    

  


  

    
    

      Use sempre @Override. Se você errar a assinatura, sem a anotação o Java
      cria silenciosamente um método novo — e a sobrescrita que você acha que fez simplesmente não
      acontece. Com a anotação, vira erro de compilação na hora.
    

  







  
Herança é tentadora — e frequentemente errada

  

    

      Herdar para “reaproveitar código” é o erro mais comum de quem está aprendendo. Herança cria o
      acoplamento mais forte que existe: a subclasse depende de detalhes internos do pai, e
      qualquer mudança na superclasse pode quebrar todas as subclasses de uma vez.
    

  


  

    

      herança forçada
      
class Pilha extends ArrayList {
    public void empilhar(Object o) { add(o); }
    public Object desempilhar() { … }
}

// e agora isto compila:
pilha.add(0, item);   // insere no meio!
pilha.remove(3);      // fura a pilha

      

        A pilha herdou toda a interface pública da lista — inclusive os métodos que destroem sua regra
        (só se insere e remove pelo topo). Uma pilha não é uma lista.
      

    

    

      composição
      
class Pilha {
    private ArrayList itens = new ArrayList();

    public void empilhar(Object o) { itens.add(o); }
    public Object desempilhar() { … }
}

// pilha.add(...) nem existe:
// só o que a Pilha decidiu expor

      

        A pilha tem uma lista e escolhe o que delegar. A regra de negócio fica protegida, e trocar
        ArrayList por LinkedList não afeta ninguém.
      

    

  


  

    
    

      Regra prática: use herança quando a subclasse puder substituir a superclasse em
      qualquer situação sem surpresas (isso é o
      Princípio de Substituição de
      Liskov). Caso contrário, prefira composição — “tem um” é quase sempre mais flexível que “é um”.
    

  







  
Teste seu entendimento

  
Quatro perguntas sobre herança e polimorfismo.


  

    

      
1. Funcionario f = new Gerente(); — ao chamar f.calcularBonus(), executa:

      
      
      
      

        O tipo da variável decide quais métodos podem ser chamados (o que o compilador aceita);
        o tipo do objeto decide qual implementação roda. É exatamente isso que o simulador acima mostra.
      

    


    

      
2. Dois métodos imprimir(int) e imprimir(String) na mesma classe são um caso de:

      
      
      
      

        Mesmo nome, assinaturas diferentes, mesma classe: sobrecarga. O compilador escolhe pelo tipo do
        argumento — não há objeto nem herança envolvidos.
      

    


    

      
3. Em UML, a seta com ponta triangular vazada apontando de B para A significa:

      
      
      
      

        A seta sempre aponta da subclasse para a superclasse — da especialização para a generalização.
        Com linha tracejada e a mesma ponta vazada, ela indica realização de interface.
      

    


    

      
4. Você quer reaproveitar o código de ArrayList numa classe Pilha. O melhor caminho é:

      
      
      
      

        Herdar exporia add(índice, elemento) e remove(índice), que violam a própria
        definição de pilha. Herança não é ferramenta de reúso de código: é declaração de subtipo.
