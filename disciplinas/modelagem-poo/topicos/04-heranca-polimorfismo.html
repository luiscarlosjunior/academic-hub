Herança: especializar sem repetir

Quando várias classes compartilham estrutura e comportamento, a parte comum sobe para uma superclasse e cada subclasse acrescenta o que tem de particular. Em UML a relação é desenhada com uma seta de ponta triangular vazada apontando da subclasse para a superclasse.

O teste para saber se a herança cabe é a frase “é um tipo de”: um Gerente é um Funcionário. Se a frase soar estranha, provavelmente o caso é de composição, não de herança.

Generalização ↑

Do específico para o geral: extrair o que Gerente e Analista têm em comum e criar Funcionário.

Especialização ↓

Do geral para o específico: criar Estagiário a partir de Funcionário, ajustando o que muda.

Herança de que exatamente?

A subclasse herda atributos e métodos (inclusive os private, que existem mas não são acessíveis), e não herda construtores.

Polimorfismo: a mesma chamada, respostas diferentes

O código abaixo trata todo mundo como Funcionario e chama calcularBonus(). Qual implementação roda em cada volta? Quem decide é o tipo real do objeto, em tempo de execução — não o tipo da variável. Execute passo a passo.

Duas coisas diferentes com nomes parecidos


  

    

      
Sobrecarga (overloading)

      

        Vários métodos com o mesmo nome e assinaturas diferentes,
        na mesma classe. Quem escolhe é o compilador, pelos tipos dos argumentos.
        É polimorfismo estático.
      

      
class Calculadora {
    int somar(int a, int b) { … }
    double somar(double a, double b) { … }
    int somar(int a, int b, int c) { … }
}

      
Não exige herança nenhuma.

    

    

      
Sobrescrita (overriding)

      

        A subclasse substitui um método herdado, mantendo a mesma assinatura.
        Quem escolhe é a JVM, em tempo de execução, pelo tipo real do objeto.
        É polimorfismo dinâmico.
      

      
class Funcionario {
    double calcularBonus() { return salario * 0.10; }
}
class Gerente extends Funcionario {
    @Override
    double calcularBonus() { return salario * 0.25; }
}

      
Só existe com herança (ou implementação de interface).

    

  


  

    

      
CritérioSobrecargaSobrescrita

Anotação típica—@Override

      
    

  


  

    
    

      Use sempre @Override. Se você errar a assinatura, sem a anotação o Java
      cria silenciosamente um método novo — e a sobrescrita que você acha que fez simplesmente não
      acontece. Com a anotação, vira erro de compilação na hora.
    

  







  
Herança é tentadora — e frequentemente errada

  

    

      Herdar para “reaproveitar código” é o erro mais comum de quem está aprendendo. Herança cria o
      acoplamento mais forte que existe: a subclasse depende de detalhes internos do pai, e
      qualquer mudança na superclasse pode quebrar todas as subclasses de uma vez.
    

  


  

    

      herança forçada
      
class Pilha extends ArrayList {
    public void empilhar(Object o) { add(o); }
    public Object desempilhar() { … }
}

// e agora isto compila:
pilha.add(0, item);   // insere no meio!
pilha.remove(3);      // fura a pilha

      

        A pilha herdou toda a interface pública da lista — inclusive os métodos que destroem sua regra
        (só se insere e remove pelo topo). Uma pilha não é uma lista.
      

    

    

      composição
      
class Pilha {
    private ArrayList itens = new ArrayList();

    public void empilhar(Object o) { itens.add(o); }
    public Object desempilhar() { … }
}

// pilha.add(...) nem existe:
// só o que a Pilha decidiu expor

      

        A pilha tem uma lista e escolhe o que delegar. A regra de negócio fica protegida, e trocar
        ArrayList por LinkedList não afeta ninguém.
      

    

  


  

    
    

      Regra prática: use herança quando a subclasse puder substituir a superclasse em
      qualquer situação sem surpresas (isso é o
      Princípio de Substituição de
      Liskov). Caso contrário, prefira composição — “tem um” é quase sempre mais flexível que “é um”.
    

  








  
Generalização e especialização na UML

  

    

      A relação de generalização expressa o “é um”: um Ouvinte é um Usuario. A
      superclasse (mais geral) define o que é comum; a subclasse (mais específica) acrescenta ou redefine. Na UML, a seta é
      uma linha com triângulo vazio apontando para a superclasse.
    

    

      A herança é a implementação dessa relação em código. Quando o modelo não tem um “é um” verdadeiro, a herança é
      errada, mesmo que seja tecnicamente possível. A verificação mais simples é o teste da substituição, que
      veremos adiante com o princípio de Liskov.

Polimorfismo: quatro formas que o termo cobre

  

    A palavra “polimorfismo” (do grego, “muitas formas”) aparece em contextos diferentes. Na prova, convém distinguir os quatro tipos.
  

  

    

      
TipoQuando é resolvidoExemplo

      
        
Inclusão (subtipo)Em tempo de execução (ligação dinâmica)Usuario u = new Ouvinte(); u.tipoDePerfil();

        
Paramétrico (genéricos)Em compilação, uma implementação para vários tiposList<Musica>, Repositorio<T>

        
Sobrecarga (ad hoc)Em compilação, pela assinaturasomar(int, int) e somar(double, double)

        
CoerçãoEm compilação, conversão implícitadouble d = 3;

      
    

  

  

    
    

      Quando o termo é usado sem qualificação, em POO, quase sempre se refere ao polimorfismo de inclusão
      (subtipo), que é o que a herança permite. É o que este tópico trata.
    

  






  
Ligação dinâmica: quem decide o método é o objeto

  

    

      Na chamada u.tipoDePerfil(), o compilador só sabe que u é um Usuario. O método
      que roda é escolhido em execução, pelo tipo real do objeto. Essa escolha chama-se ligação
      dinâmica (ou despacho dinâmico).
    

  


public static void main(String[] args) {
    Usuario[] usuarios = { new Ouvinte(), new Artista() };
    for (Usuario u : usuarios) {
        System.out.println(u.tipoDePerfil());   // Ouvinte, depois Artista: o objeto escolhe
    }
}

  

    
    

      Por que isso importa na modelagem: um diagrama de sequência que chama tipoDePerfil() em um
      Usuario é válido para qualquer subtipo. Você não precisa desenhar uma interação por tipo concreto.
    

  






  
Quando a herança mente: o princípio de Liskov

  

    Barbara Liskov (1987) propôs: objetos de um subtipo devem poder substituir objetos do tipo base sem alterar o
    comportamento correto do programa. O exemplo clássico mostra a violação.
  



public class Retangulo {
    protected int largura, altura;
    public void setLargura(int l) { largura = l; }
    public void setAltura(int a)  { altura = a; }
    public int area() { return largura * altura; }
}

// "Quadrado é um Retângulo"? Geometricamente, sim. Como classe, quebra o contrato:
public class Quadrado extends Retangulo {
    @Override public void setLargura(int l) { largura = altura = l; }   // altera o outro lado!
    @Override public void setAltura(int a)  { largura = altura = a; }
}

// Cliente que funciona com Retangulo e quebra com Quadrado:
Retangulo r = new Quadrado();
r.setLargura(4);
r.setAltura(5);
System.out.println(r.area());   // esperado: 20. Obtido: 25


  

    
    

      Lição de modelagem: o “é um” precisa valer para comportamento, e não só para o vocabulário.
      Um quadrado é um retângulo na geometria, mas um objeto mutável Quadrado não substitui Retangulo.
      A solução típica é não herdar, e sim compartilhar uma interface ou composição.
    

  






  
Herança ou composição?

  

    

      Herança é uma relação forte e fixa: a subclasse fica presa às decisões da superclasse, e mudanças na
      base quebram os filhos (o problema da fragilidade da classe base). A composição é uma relação fraca e
      flexível: um objeto usa outro, e a troca de comportamento é feita em tempo de execução.
    

    

      O conselho do Gang of Four (Gamma et al., 1994) é “prefira composição a herança”. Não é uma proibição, e sim uma
      ordem de preferência: use herança quando o “é um” for verdadeiro e estável.
    

  

  

    

      
CritérioHerançaComposição

      
        
Relaçãoé umtem um / usa um

        
AcoplamentoAlto: a subclasse conhece detalhes da baseBaixo: depende só da interface

        
Troca de comportamentoEstática (na criação da classe)Dinâmica (troca de objeto em execução)

        
ReusoPor especializaçãoPor delegação

      
    

  






  
Exercícios

  

    

      1. Na Melodia, um “Podcast” deveria herdar de “Musica”? Justifique pelo princípio de Liskov.
      
Gabarito: depende do comportamento que o cliente espera. Se a Playlist trata qualquer item como música (duração, faixa, álbum), um podcast pode não ter álbum nem faixa, e a substituição quebra. A resposta forte propõe uma interface FonteDeAudio com o contrato comum (duração, título, reproduzir) e deixa música e podcast implementá-la.

    

    

      2. Qual será a saída do código do exemplo Retângulo/Quadrado se o setter de altura for chamado antes do de largura?
      
Gabarito: setAltura(5) define os dois lados como 5; setLargura(4) define os dois como 4; a área é 16. Qualquer ordem resulta no último valor para os dois lados, o que mostra que o quadrado não preserva a independência esperada dos lados de um retângulo.

    

    

      3. Um sistema tem Pagamento com subclasses por forma de pagamento (cartão, boleto, pix). Você modelaria com herança ou composição?
      
Gabarito: a forma de pagamento muda com frequência e pode ser trocada em execução; isso favorece uma interface MeioDePagamento injetada em Pagamento (composição). Herança aqui cria uma hierarquia rígida que cresce a cada novo meio.

1. Funcionario f = new Gerente(); — ao chamar f.calcularBonus(), executa:

      
      
      
      

        O tipo da variável decide quais métodos podem ser chamados (o que o compilador aceita);
        o tipo do objeto decide qual implementação roda. É exatamente isso que o simulador acima mostra.
      

    


    

      
2. Dois métodos imprimir(int) e imprimir(String) na mesma classe são um caso de:

      
      
      
      

        Mesmo nome, assinaturas diferentes, mesma classe: sobrecarga. O compilador escolhe pelo tipo do
        argumento — não há objeto nem herança envolvidos.
      

    


    

      
3. Em UML, a seta com ponta triangular vazada apontando de B para A significa:

      
      
      
      

        A seta sempre aponta da subclasse para a superclasse — da especialização para a generalização.
        Com linha tracejada e a mesma ponta vazada, ela indica realização de interface.
      

    


    

      
4. Você quer reaproveitar o código de ArrayList numa classe Pilha. O melhor caminho é:

      
      
      
      

        Herdar exporia add(índice, elemento) e remove(índice), que violam a própria
        definição de pilha. Herança não é ferramenta de reúso de código: é declaração de subtipo.
