Dados em vários lugares, verdades diferentes

Imagine a loja virtual guardando o endereço da cliente Ana em três lugares: a planilha de pedidos, o cadastro do setor de entregas e um arquivo de boletos. Quando Ana se muda, alguém atualiza duas planilhas e esquece a terceira. Agora a nota fiscal sai para o endereço antigo.

Esse é o problema que os bancos de dados resolvem. Os dados ficam em um lugar organizado, com regras, e todos os programas consultam essa mesma fonte.

Animação · o endereço de Ana em arquivos separados
Dado não é informação. Dado é o registro bruto, como “Ana, Curitiba, 2024-01-15”. Informação é o que você extrai dele para decidir algo, como “a cidade com mais clientes ativos”. Um banco de dados guarda dados de forma que a informação possa ser extraída com segurança.

SGBD: o software que guarda e protege os dados

Banco de dados é a coleção organizada de dados. SGBD (Sistema de Gerenciamento de Banco de Dados) é o software que cria, consulta, protege e recupera essa coleção. PostgreSQL, MySQL, Oracle, SQL Server e SQLite são SGBDs; os dados em si ficam no banco.

Um SGBD oferece, em geral, seis funções:

  • Definição: descrever a estrutura dos dados (tabelas, tipos, restrições).
  • Manipulação: consultar, inserir, alterar e remover registros.
  • Integridade: impedir dados inválidos, como um preço negativo.
  • Concorrência: deixar muitas pessoas usarem o banco ao mesmo tempo sem se atropelar.
  • Recuperação: voltar a um estado consistente depois de uma queda de energia.
  • Segurança: controlar quem pode ler ou escrever o quê.

Modelos de dados: como a estrutura é pensada

Um modelo de dados é o conjunto de conceitos que você usa para descrever dados. O modelo determina o que pode ser representado e como se navega pelos dados. A história dos SGBDs é a história de três modelos.

Hierárquico (anos 60)

Os dados formam uma árvore. Cada registro tem um único pai. Para chegar a um dado, você segue o caminho a partir da raiz.

Empresa
 └─ Departamento Vendas
     ├─ Ana
     └─ Bruno
Em rede (anos 70)

Um registro pode ter vários pais. Ganha flexibilidade, mas o programador passa a navegar por ponteiros, o que torna o código frágil.

Ana ──► Pedido 1
 │         ▲
 └──► Pedido 3 ◄── Bruno
Relacional (Codd, 1970)

Tudo são tabelas. Relações entre tabelas são expressas por valores (chaves), não por ponteiros. A consulta descreve o que quer, e o banco decide como buscar.

SELECT nome
FROM clientes
WHERE cidade = 'Recife';
Por que o relacional venceu? Porque separa a lógica da física. Você muda o índice ou a forma de armazenar sem reescrever suas consultas. Codd chamou isso de independência de dados. Outros modelos aparecem depois, como documentos (NoSQL) e grafos, mas o relacional continua sendo a base da maioria dos sistemas de informação.

Transações e as propriedades ACID

Uma transação é um conjunto de operações tratado como uma unidade só: ou tudo acontece, ou nada. Transferir R$ 100 da conta A para a conta B são dois UPDATEs. Se a energia cair entre eles, o dinheiro some. As propriedades ACID existem para evitar isso.

A
Atomicidade

Tudo ou nada. Se uma parte falha, as demais são desfeitas.

C
Consistência

Leva o banco de um estado válido a outro estado válido, respeitando as restrições.

I
Isolamento

Transações simultâneas não enxergam o trabalho uma da outra pela metade.

D
Durabilidade

Depois do COMMIT, o dado sobrevive a uma queda do sistema.

Animação · transferência com falha no meio

Como funciona de verdade

Quando você executa um SELECT, o texto percorre um pipeline de componentes. Entender esse caminho explica por que algumas consultas são rápidas e outras, lentas.

1. Analisador
valida a sintaxe
2. Otimizador
escolhe o plano
3. Executor
lê e combina linhas
4. Buffer
páginas em memória
5. Disco
páginas de 4 a 8 KB
  • Os dados não ficam como texto. São guardados em páginas de tamanho fixo (em SQLite, 4 KB por padrão). Ler uma linha significa ler a página que a contém.
  • Antes de qualquer escrita, o SGBD registra a intenção num log (no SQLite, o arquivo WAL ou o journal). Se a energia cair, o log permite refazer ou desfazer o trabalho. É isso que dá a durabilidade.
  • O otimizador não executa a consulta como você escreveu. Ele estima quantas linhas cada passo produz e escolhe a ordem mais barata. Você descreve o resultado; o banco escolhe o caminho.
  • SQLite é uma biblioteca embutida: o banco inteiro é um único arquivo, sem servidor. PostgreSQL e MySQL rodam como servidores separados, atendendo muitos clientes pela rede. Os conceitos são os mesmos.

Exemplo: a loja em um comando

Todos os tópicos desta disciplina usam o mesmo banco: uma loja com clientes, produtos, pedidos, itens e funcionários. A consulta abaixo pergunta ao banco quantos clientes existem. O resultado é calculado agora, pelo SQLite rodando no seu navegador. 

SELECT COUNT(*) AS total_clientes
FROM clientes;

Repare que você não disse onde os dados estão nem como percorrê-los. Só disse o resultado desejado. Essa é a essência da linguagem declarativa SQL, que vamos explorar a partir do tópico 06.

Problemas para resolver

Tente responder antes de abrir a solução.

Problema 1 · Redundância na prática

Uma planilha de pedidos tem as colunas: pedido, cliente, cidade_cliente, produto, preco. Ana fez 3 pedidos. Quantas vezes o nome e a cidade dela aparecem? O que acontece se Ana mudar de cidade?

Ver solução

O nome e a cidade aparecem três vezes (uma por pedido). Se Ana mudar de cidade e a planilha for atualizada em apenas algumas linhas, o mesmo cliente ficará com duas cidades diferentes. Isso é uma anomalia de atualização. O tópico 05 mostra como eliminá-la.

Problema 2 · Consulta contra o modelo

Escreva, em linguagem natural, o que a consulta a seguir pergunta ao banco:

SELECT nome, cidade FROM clientes WHERE cidade = 'Curitiba';
Ver solução

“Liste o nome e a cidade de todos os clientes que moram em Curitiba.” O resultado tem duas linhas (Elisa e Helena). Note que o SQL não diz como procurar: o SGBD decide se faz uma varredura ou usa índice.

Problema 3 · ACID na vida real

Um cliente paga um pedido. O sistema debita o cartão, mas cai antes de marcar o pedido como “pago”. Qual propriedade ACID foi violada e o que a transação deveria ter feito?

Ver solução

A atomicidade. Débito e atualização do pedido deveriam estar na mesma transação. Sem o COMMIT, o ROLLBACK desfaz o débito. Com o COMMIT, ambos ficam gravados de forma durável.

Aprofundamento e prática

Um pouco de história

Em 1970, Edgar F. Codd publicou o artigo “A Relational Model of Data for Large Shared Data Banks”, que propôs tabelas, chaves e uma álgebra para consultar dados. Na IBM, o projeto System R criou a linguagem SEQUEL, que virou SQL. Na Universidade de Berkeley, o Ingres seguiu um caminho paralelo com a linguagem QUEL, que não prosperou.

O SQL foi padronizado pelo ANSI em 1986 e pela ISO em 1987. O padrão cresceu desde então, com a versão de 2023 incluindo recursos como consultas em JSON. Na prática, cada banco implementa um dialeto: o núcleo é o mesmo, mas funções, tipos e recursos avançados mudam. Por isso a disciplina usa SQLite e aponta as diferenças quando elas importam.

Quando um banco relacional não é a resposta

O modelo relacional é a escolha padrão quando os dados têm relações, precisam de consistência e são consultados de formas variadas. Há casos em que outra ferramenta é mais adequada:

  • Documentos com estrutura variável, como catálogos em que cada produto tem atributos diferentes. Bancos de documentos (MongoDB, por exemplo) armazenam isso naturalmente, embora relacionar documentos seja mais trabalhoso.
  • Travessias profundas em grafos, como “caminhos de amizade de até seis graus”. Bancos de grafos (Neo4j) fazem isso com um custo que a recursão em SQL pode não acompanhar (o tópico 13 mostra o limite).
  • Séries temporais de alta frequência, como leituras de sensores a cada segundo. Bancos especializados comprimem e agregam esses dados com muito mais eficiência.
  • Cache de chave e valor, em que a latência de microssegundos importa mais que a consulta. Redis e similares resolvem isso.

Muitas arquiteturas reais combinam ferramentas: o relacional como fonte da verdade e os outros como complemento.

Como uma aplicação conversa com o banco

Uma aplicação não abre uma conexão nova a cada requisição, porque o custo de autenticação e de criação de sessão seria alto. Ela usa um pool de conexões: um conjunto de conexões abertas e reutilizadas. A mudança do esquema é feita por migrações versionadas, arquivos SQL que rodam em ordem e registram o que já foi aplicado. Backups e réplicas de leitura completam o quadro operacional.

Prática 1 · inventário do banco

Antes de consultar qualquer dado, um bom profissional confere o tamanho e a forma do banco. Esta consulta conta as linhas de cada tabela numa única resposta, usando UNION ALL para empilhar os resultados. 

SELECT 'clientes' AS tabela, COUNT(*) AS linhas FROM clientes
UNION ALL SELECT 'produtos', COUNT(*) FROM produtos
UNION ALL SELECT 'pedidos', COUNT(*) FROM pedidos
UNION ALL SELECT 'itens_pedido', COUNT(*) FROM itens_pedido
UNION ALL SELECT 'funcionarios', COUNT(*) FROM funcionarios;

Prática 2 · catálogo de tabelas

O próprio banco guarda a lista das tabelas que criou. No SQLite, essa informação está na tabela de sistema sqlite_master. 

SELECT name AS tabela
FROM sqlite_master
WHERE type = 'table'
ORDER BY name;
Dica de carreira. Nas empresas, perguntas como “quantas linhas tem esta tabela?” e “de onde vêm estes dados?” são o começo de qualquer análise. Acostume-se a verificar o banco antes de confiar em um relatório.

Teste seu entendimento

Três perguntas de fundamentos.

1. Qual é a principal vantagem do modelo relacional sobre o hierárquico?

No relacional, relações são valores (chaves), não ponteiros. Por isso a consulta é declarativa e o SGBD pode otimizar o caminho sem que o programa precise mudar.

2. Num SGBD, qual componente garante que um pedido não fique pela metade após uma queda?

O log registra as operações antes de aplicá-las. Na recuperação, transações não confirmadas são desfeitas e as confirmadas são garantidas. Isso sustenta a atomicidade e a durabilidade.

3. Uma transação transfere R$ 100 entre duas contas, mas o sistema cai após o primeiro UPDATE. Qual resultado o ACID garante?

Sem COMMIT, a transação é desfeita na recuperação. É a atomicidade em ação: o estado parcial nunca fica visível.
