Uma tabela “gorda” que mente

Imagine um único arquivo com tudo: pedido, cliente, cidade do cliente, produto, preço e quantidade. Parece prático. Na prática, o mesmo fato aparece várias vezes, e cada cópia é uma oportunidade de contradição. A normalização é o processo sistemático de reorganizar as tabelas para eliminar essa redundância.

O critério não é estético. Cada forma normal proíbe um tipo específico de dependência entre colunas, justamente a que causa anomalias.

Animação · as três anomalias

Dependência funcional: o conceito central

Dizemos que X → Y (X determina Y) quando dois registros com o mesmo valor em X obrigatoriamente têm o mesmo valor em Y. Por exemplo, id_cliente → nome: um código de cliente tem exatamente um nome. Essa é uma regra do negócio, não uma coincidência dos dados de hoje.

Chave é um caso especial

Uma superchave determina todos os atributos da tabela. Uma chave candidata é uma superchave minimal: não dá para tirar nenhum atributo dela sem perder a propriedade. A chave primária é uma das chaves candidatas.

Como descobrir

Dependências vêm do domínio, não dos dados. Pergunte: “se eu soubesse X, conseguiria dizer Y?”. Se a resposta for sim, X → Y. Dados de exemplo podem sugerir uma dependência que não existe, então valide com quem conhece o negócio. 

-- Relação não normalizada, com chave (id_pedido, id_produto)
pedido_detalhe(id_pedido, id_cliente, nome_cliente, cidade_cliente,
                 id_produto, nome_produto, quantidade, preco_unitario)

Dependências identificadas:
  id_pedido             → id_cliente
  id_cliente            → nome_cliente, cidade_cliente
  id_produto            → nome_produto
  (id_pedido, id_produto) → quantidade, preco_unitario

Decomposição: 1FN → 2FN → 3FN

Cada passo remove um tipo de dependência indesejada, dividindo a tabela em duas. Acompanhe a animação: observe que as colunas migram para tabelas cuja chave realmente as determina.

As formas normais, uma a uma

1FN · valores atômicos

Cada célula guarda um único valor, e não há grupos repetidos (colunas produto1, produto2…). Toda tabela relacional já deve estar na 1FN; é o mínimo.

2FN · sem dependência parcial

Se a chave é composta, nenhum atributo não chave pode depender de só parte dela. Em (id_pedido, id_produto) → nome_produto, o nome depende apenas de id_produto: deve ir para a tabela de produtos.

3FN · sem dependência transitiva

Nenhum atributo não chave pode depender de outro atributo não chave. Em id_pedido → id_cliente → nome_cliente, o nome depende do cliente, não do pedido: a cadeia é transitiva e o nome vai para a tabela de clientes.

FNBC · todo determinante é chave

Para toda dependência X → Y não trivial, X deve ser superchave. É mais rígida que a 3FN: a 3FN permite que o lado direito seja um atributo primo (parte de alguma chave candidata). Veja o exemplo na animação abaixo.

Exemplo de FNBC: o professor e a disciplina

Num curso, cada professor leciona uma única disciplina, mas várias turmas podem ser da mesma disciplina. Uma relação (aluno, disciplina, professor) tem as dependências: (aluno, disciplina) → professor e professor → disciplina.

O problema

professor não é chave, mas determina disciplina. Está na 3FN, porque disciplina é primo (faz parte da chave (aluno, disciplina)). Mesmo assim, o professor é repetido, e trocar a disciplina dele exige alterar várias linhas.

A decomposição

Separe em (professor, disciplina) e (aluno, professor). Agora o determinante professor é chave da primeira tabela. Trade-off: a dependência (aluno, disciplina) → professor deixa de ser verificável numa única tabela, e a decomposição pode perder dependências.

Por isso a prática é 3FN. A FNBC elimina toda redundância baseada em dependências, mas nem sempre preserva todas as dependências. A 3FN sempre pode ser alcançada preservando dependências. Projetistas escolhem caso a caso, e às vezes desnormalizam de propósito para ganhar desempenho.

Exemplo: a loja já está normalizada

O banco da loja está na 3FN: cada fato mora na tabela cuja chave o determina. Nenhum nome de cliente é repetido em pedidos. A junção abaixo reconstrói a tabela “gorda” original sem perda de informação, o que chamamos de decomposição sem perda. 

SELECT p.id_pedido, c.nome AS cliente, c.cidade,
       pr.nome AS produto, i.quantidade, i.preco_unitario
FROM pedidos p
JOIN clientes c     ON c.id_cliente  = p.id_cliente
JOIN itens_pedido i ON i.id_pedido   = p.id_pedido
JOIN produtos pr    ON pr.id_produto = i.id_produto
WHERE p.id_pedido IN (1, 2);

Como funciona de verdade

Como o projetista sabe se uma decomposição está correta? Dois testes formais, que os algoritmos de normalização garantem:

  • Junção sem perda: juntar as tabelas decompostas devolve exatamente a tabela original. Sem isso, a decomposição inventa linhas.
  • Preservação de dependências: cada dependência original pode ser verificada numa única tabela decomposta, sem juntar nada. Sem isso, o banco não consegue impor a regra de negócio de forma barata.

Para descobrir se uma chave é candidata, o SGBD (e a teoria) usa o fecho de atributos: a partir de um conjunto X, aplique repetidamente as dependências, acrescentando o que for determinado, até nada mais mudar. Se o fecho de X contém todos os atributos, X é superchave. Esse algoritmo é o que os livros-texto ensinam para checar a normalização.

Na prática, a normalização é um equilíbrio. Consultas que juntam muitas tabelas custam mais, e sistemas de leitura intensa (como relatórios) às vezes guardam cópias de propósito, em tabelas de resumo ou visões materializadas. A regra é: normalize para escrever com segurança; desnormalize com consciência, e só quando a medição mostrar necessidade.

Erros comuns

Normalizar sem o negócio

Deduzir dependências de uma amostra de dados. Se, por acaso, dois clientes têm a mesma cidade hoje, não existe a dependência cidade → nome.

Achar que 3FN é o fim

Uma tabela pode estar na 3FN e ainda ter anomalias (o caso professor/disciplina). Verifique a FNBC quando houver chaves candidatas sobrepostas.

Esquecer o preço histórico

Normalizar preco_unitario para a tabela de produtos parece correto, mas apaga o fato histórico. Ver o tópico 03.

Desnormalizar por hábito

Copiar dados “para facilitar” cria anomalias que o banco não consegue detectar. Desnormalize só com uma medição que justifique.

Problemas para resolver

Resolva no papel, identificando as dependências antes da solução.

Problema 1 · Anomalias na prática

Tabela alocacao(id_funcionario, nome_funcionario, id_projeto, nome_projeto, horas). Descreva uma anomalia de inserção, uma de atualização e uma de remoção.

Ver solução

Inserção: não é possível cadastrar um projeto novo sem alocar alguém a ele, porque a chave exige funcionário. Atualização: mudar o nome do projeto exige alterar várias linhas; se uma for esquecida, há dois nomes para o mesmo projeto. Remoção: excluir a última alocação de um funcionário também apaga os dados dele, mesmo que ele continue na empresa. A correção: separar em funcionários, projetos e alocações.

Problema 2 · Em qual forma está?

A tabela item(id_pedido, id_produto, nome_produto, quantidade), com chave composta (id_pedido, id_produto), está em qual forma normal?

Ver solução

Está na 1FN (valores atômicos), mas não na 2FN: id_produto → nome_produto é uma dependência parcial, porque id_produto é só parte da chave. A correção é levar nome_produto para a tabela de produtos.

Problema 3 · Verifique a junção

Reconstrua, com JOIN, a lista de produtos do pedido 9 com nome do cliente, nome do produto e quantidade. Qual é o resultado?

Ver solução 
SELECT c.nome AS cliente, pr.nome AS produto, i.quantidade
FROM pedidos p
JOIN clientes c     ON c.id_cliente  = p.id_cliente
JOIN itens_pedido i ON i.id_pedido   = p.id_pedido
JOIN produtos pr    ON pr.id_produto = i.id_produto
WHERE p.id_pedido = 9;

Uma linha: Gabriel Tavares, Fone Bluetooth, 1. O cliente sem e-mail não impede a junção, porque o e-mail não participa dela.

Aprofundamento e prática

Calculando o fecho de atributos, passo a passo

Para decidir se um conjunto de atributos X é chave, calcula-se o fecho de X sob as dependências F: o conjunto de todos os atributos que X determina. Se o fecho contém a relação inteira, X é superchave.

Exemplo: a relação R(A, B, C, D) com dependências F = {A → B, B → C}.

  1. Comece com o fecho de {A} igual a {A}.
  2. Aplique A → B: o fecho passa a {A, B}.
  3. Aplique B → C: o fecho passa a {A, B, C}.
  4. Nenhuma dependência acrescenta mais nada. D nunca aparece.

Conclusão: {A} não é superchave, porque não determina D. Qualquer chave precisa incluir D, e como ninguém determina D, D deve estar em todas as chaves candidatas. Esse raciocínio mecânico é o que os algoritmos de normalização executam automaticamente.

Prática · dependências são regras, não coincidências

A cidade de um cliente é uma dependência de negócio? Não: duas pessoas podem morar na mesma cidade sem que a cidade determine o nome. Veja se a cidade pode servir de chave: ela se repete nos dados. 

-- cidades que aparecem mais de uma vez: cidade não identifica o cliente
SELECT cidade, COUNT(*) AS clientes
FROM clientes
GROUP BY cidade
HAVING COUNT(*) > 1;

Agora a dependência que é de negócio: cada cliente tem uma cidade. A consulta abaixo procura violações dessa dependência nos dados que cruzam pedidos e clientes. Resultado vazio é o esperado. 

WITH pedido_cliente AS (
  SELECT p.id_pedido, p.id_cliente, c.cidade
  FROM pedidos p
  JOIN clientes c ON c.id_cliente = p.id_cliente
)
SELECT id_cliente, COUNT(DISTINCT cidade) AS cidades
FROM pedido_cliente
GROUP BY id_cliente
HAVING COUNT(DISTINCT cidade) > 1;
Os dados podem satisfazer uma dependência por acaso, e a consulta só detecta violações. Quem decide se uma dependência é válida é o negócio. Em uma tabela desnormalizada, a mesma consulta é a forma de encontrar as contradições que a anomalia de atualização produz.

Checklist de normalização

1. Liste as entidades e as dependências do negócio, não as dos dados de hoje.
2. Calcule as chaves candidatas com o fecho de atributos.
3. Verifique 2FN: nenhum atributo depende de parte de uma chave composta.
4. Verifique 3FN: nenhum atributo depende de outro atributo que não é chave.
5. Teste a decomposição: a junção reconstrói a tabela original?
6. Desnormalize apenas por medição, documentando o motivo e a origem da cópia.

Problemas do mundo real para discutir

Casos típicos, descritos de forma genérica. Discuta em grupo antes de olhar as pistas.

Caso 1 · Três endereços para a mesma cliente

O cadastro de clientes de um e-commerce guarda o endereço junto de cada pedido, por comodidade. Um cliente que mudou de cidade aparece com dois endereços nos relatórios de entrega, e a rota de uma transportadora é calculada para o endereço antigo.

Para discutir:

  • Qual é a dependência funcional que está sendo violada? Ela é uma regra de negócio ou apenas um padrão dos dados de hoje?
  • Um pedido deve manter o endereço do dia da compra? Isso muda a resposta sobre normalização?
-- detecção: uma mesma cliente com mais de uma cidade na tabela desnormalizada
WITH pedidos_com_endereco AS (
  SELECT 1 AS id_cliente, 'Ana' AS nome, 'São Paulo' AS cidade
  UNION ALL SELECT 1, 'Ana', 'Recife'
  UNION ALL SELECT 2, 'Bruno', 'Rio de Janeiro'
)
SELECT id_cliente, COUNT(DISTINCT cidade) AS cidades
FROM pedidos_com_endereco
GROUP BY id_cliente
HAVING COUNT(DISTINCT cidade) > 1;

Pista: a consulta encontra a contradição, mas não decide qual endereço é o certo. Distinguir o “endereço atual do cliente” do “endereço de entrega de um pedido” é a solução: são dois fatos diferentes, e cada um pertence a uma tabela diferente.

Caso 2 · O painel de BI que é propositalmente desnormalizado

Uma equipe de análise de dados cria uma tabela larga, com todas as colunas juntas, para que os dashboards rodem sem junções. Em pouco tempo, alguém corrige o nome de um produto na tabela de origem, e o painel continua mostrando o nome antigo, porque a cópia não foi atualizada.

Para discutir:

  • A desnormalização era um erro ou uma decisão? Como documentar essa decisão para quem vem depois?
  • Qual processo garante que a cópia seja reconstruída quando a origem muda?

Pista: em data warehouses, a desnormalização é intencional e controlada (modelo estrela, cargas periódicas). O erro está em esquecer a cópia e não ter processo de atualização.

Teste seu entendimento

Três perguntas de fundamentos.

1. Em (id_pedido, id_produto) → nome_produto, qual é o problema?

Ela viola a 2FN. A chave é composta, e o nome depende apenas de id_produto, que é parte dela. A correção é mover o nome para a tabela de produtos.

2. Qual das afirmações sobre a 3FN e a FNBC é verdadeira?

A FNBC é mais rígida e, por isso, pode exigir decomposições que perdem dependências. Por isso a 3FN é o alvo mais comum na prática.

3. O que significa uma decomposição “sem perda”?

É o teste de junção sem perda: a decomposição não inventa linhas nem perde informação. Espaço em disco não é critério da normalização.
