Mudar dados é a parte perigosa

Consultar não altera nada. Já INSERT, UPDATE e DELETE mudam o estado do banco, e um erro aqui não se desfaz sozinho. A regra que evita a maioria dos desastres é simples: toda alteração deve ser precisa e, quando envolve mais de um passo, deve estar numa transação.

INSERT: criando linhas

Informe sempre as colunas por nome. Assim, a inserção continua correta mesmo que a ordem das colunas mude no futuro, e colunas com DEFAULT ou chave automática ficam de fora. 

INSERT INTO categorias (id_categoria, nome)
VALUES (6, 'Papelaria'), (7, 'Brinquedos');
SELECT * FROM categorias;

Também é possível inserir o resultado de uma consulta. Esse é o INSERT ... SELECT, muito usado para copiar ou resumir dados: 

CREATE TABLE pedidos_arquivados (id_pedido INTEGER, status TEXT);
INSERT INTO pedidos_arquivados
SELECT id_pedido, status FROM pedidos WHERE status = 'cancelado';
SELECT * FROM pedidos_arquivados;

UPDATE e DELETE: a cláusula WHERE é tudo

UPDATE e DELETE afetam todas as linhas que satisfazem o WHERE. Sem WHERE, afetam a tabela inteira, sem aviso. Antes de executar, rode o mesmo WHERE num SELECT e confira a quantidade de linhas.

Seguro: escopo explícito
UPDATE produtos SET preco = preco * 1.10 WHERE id_categoria = 2;
Perigoso: sem WHERE
UPDATE produtos SET preco = preco * 1.10; -- aumenta TODOS os produtos
-- reajuste de 10% nos livros
UPDATE produtos SET preco = ROUND(preco * 1.10, 2)
WHERE id_categoria = 2;
SELECT id_produto, nome, preco FROM produtos WHERE id_categoria = 2;
-- remove itens de um pedido cancelado
DELETE FROM itens_pedido
WHERE id_pedido IN (SELECT id_pedido FROM pedidos WHERE status = 'cancelado');
SELECT COUNT(*) AS itens_restantes FROM itens_pedido;

Transações: tudo ou nada

Uma transação agrupa comandos. BEGIN inicia; COMMIT confirma tudo; ROLLBACK desfaz tudo. Até o COMMIT, as alterações são provisórias para quem está na mesma conexão.

Animação · compra com estoque insuficiente

BEGIN;
UPDATE produtos SET estoque = estoque - 2 WHERE id_produto = 1;
SELECT id_produto, nome, estoque FROM produtos WHERE id_produto = 1;
ROLLBACK;
SELECT id_produto, nome, estoque FROM produtos WHERE id_produto = 1;

Você verá duas tabelas. Dentro da transação, o estoque do notebook caiu para 6. Depois do ROLLBACK, voltou a 8. Nenhum outro usuário veria a queda antes do COMMIT.

Como funciona de verdade

  • Autocommit. Na maioria dos clientes, cada comando sem BEGIN é uma transação própria, confirmada logo após executar. Um UPDATE sem WHERE, nesse modo, já está gravado quando você percebe o erro.
  • Como o ROLLBACK desfaz. Antes de modificar uma página, o SGBD grava a versão antiga no log (undo). ROLLBACK aplica esse registro de volta. No SQLite, isso é o journal ou o WAL.
  • Por que o COMMIT é durável. O COMMIT só retorna depois que o log está escrito no disco (fsync). Se a energia cair um instante depois, o sistema reexecuta o log e o dado está lá.
  • Escrita e bloqueio. Um UPDATE trava as linhas que modifica até o fim da transação. Transações longas que modificam muita coisa atrapalham outras. Mantenha-as curtas.

Exemplo clássico: o checkout

Um pedido novo exige pelo menos três escritas: registrar o pedido, registrar o item e baixar o estoque. Se qualquer uma falhar, as outras não podem ficar gravadas. O UPDATE abaixo só baixa o estoque se houver unidades suficientes, e informa quantas linhas foram afetadas. 

BEGIN;
INSERT INTO pedidos VALUES (10, 7, '2024-10-01', 'pendente');
INSERT INTO itens_pedido VALUES (10, 5, 1, 120.00);
UPDATE produtos SET estoque = estoque - 1 WHERE id_produto = 5 AND estoque >= 1;
SELECT id_produto, nome, estoque FROM produtos WHERE id_produto = 5;
ROLLBACK;

O “Livro Algoritmos” tem estoque 0, então o UPDATE não atinge nenhuma linha. A aplicação deve checar isso e fazer ROLLBACK. Nesta execução, o banco desfaz também o pedido e o item inseridos antes. Só faria sentido confirmar (COMMIT) se o UPDATE tivesse afetado exatamente uma linha. Confirmar com zero linhas gravaria um pedido sem baixa de estoque, que é justamente a inconsistência que a transação existe para evitar.

Experimente

Altere o exemplo e execute. Cada execução parte de um banco novo, então você pode quebrar à vontade.

UPDATE produtos SET estoque = estoque + 10 WHERE id_categoria = 4; SELECT nome, estoque FROM produtos WHERE id_categoria = 4;

Problemas para resolver

Cada problema roda em um banco novo: experimente sem medo.

Problema 1 · Cancelamento seguro

Cancele o pedido 9 e confirme que o status mudou. Use uma transação, para que você possa desfazer caso algo dê errado.

Ver solução 
BEGIN;
UPDATE pedidos SET status = 'cancelado' WHERE id_pedido = 9;
SELECT id_pedido, status FROM pedidos WHERE id_pedido = 9;
COMMIT;

O resultado mostra o pedido cancelado. Em um sistema real, o COMMIT só viria depois de checar a regra de negócio.

Problema 2 · Reajuste dos eletrônicos com 5%

Aumente em 5% o preço dos produtos da categoria Eletrônicos, arredondando para 2 casas, e mostre o resultado. Quantas linhas foram afetadas?

Ver solução 
UPDATE produtos SET preco = ROUND(preco * 1.05, 2)
WHERE id_categoria = (SELECT id_categoria FROM categorias WHERE nome = 'Eletrônicos');
SELECT nome, preco FROM produtos WHERE id_categoria = 1;

Três produtos são afetados (Notebook, Smartphone e Fone). A subconsulta descobre o id da categoria pelo nome. O tópico 11 explica esse padrão.

Problema 3 · Arquivar e apagar com segurança

Copie os pedidos com status “cancelado” para pedidos_arquivados e, na mesma transação, apague-os da tabela pedidos. Atenção à ordem: os itens dependem dos pedidos.

Ver solução 
CREATE TABLE pedidos_arquivados (id_pedido INTEGER, status TEXT);
BEGIN;
INSERT INTO pedidos_arquivados
  SELECT id_pedido, status FROM pedidos WHERE status = 'cancelado';
DELETE FROM itens_pedido
  WHERE id_pedido IN (SELECT id_pedido FROM pedidos WHERE status = 'cancelado');
DELETE FROM pedidos WHERE status = 'cancelado';
COMMIT;
SELECT COUNT(*) AS arquivados FROM pedidos_arquivados;

A ordem importa. Se apagássemos os pedidos primeiro, a subconsulta dos itens não encontraria nada, e os itens órfãos violariam a chave estrangeira (com a verificação ligada). Tudo dentro de uma transação para não haver meio-termo.

Aprofundamento e prática

Upsert: inserir ou atualizar em um comando

Muitas vezes a aplicação não sabe se a linha já existe. Fazer um SELECT antes e depois decidir entre INSERT e UPDATE é perigoso: entre a checagem e a escrita, outra transação pode ter inserido a mesma linha. O upsert resolve isso em uma instrução: se houver conflito na chave, executa a atualização. 

INSERT INTO categorias (id_categoria, nome)
VALUES (1, 'Eletrônicos e Informática')
ON CONFLICT (id_categoria) DO UPDATE SET nome = excluded.nome;
SELECT * FROM categorias WHERE id_categoria = 1;

Dentro do DO UPDATE, excluded é a linha que tentou ser inserida. PostgreSQL, SQLite e MySQL usam sintaxes parecidas (MySQL usa ON DUPLICATE KEY UPDATE). Upsert é ótimo para cargas e sincronizações repetíveis.

Savepoints: desfazer só uma parte

Um savepoint marca um ponto dentro da transação. ROLLBACK TO desfaz só o que veio depois dele, e a transação continua. É útil quando uma etapa opcional falha e o restante deve ser preservado. 

BEGIN;
UPDATE produtos SET estoque = estoque - 1 WHERE id_produto = 2;
SAVEPOINT antes_brinde;
UPDATE produtos SET estoque = estoque - 1 WHERE id_produto = 6;
ROLLBACK TO antes_brinde;
COMMIT;
SELECT id_produto, estoque FROM produtos WHERE id_produto IN (2, 6) ORDER BY id_produto;

O smartphone perdeu uma unidade e a camiseta não. A baixa do “brinde” foi desfeita, e a venda principal foi confirmada.

Exclusão lógica: apagar sem perder

Em sistemas com histórico, DELETE destrói informação que pode ser necessária para auditoria, relatórios e reclamações. A alternativa é a exclusão lógica: uma coluna indica que a linha está inativa, e as consultas do dia a dia filtram por ela. O preço é a disciplina de lembrar o filtro em toda consulta, e uma chave UNIQUE que deve considerar linhas inativas. 

ALTER TABLE clientes ADD COLUMN ativo INTEGER NOT NULL DEFAULT 1;
UPDATE clientes SET ativo = 0 WHERE id_cliente = 3;
SELECT nome, ativo FROM clientes ORDER BY id_cliente;

Boas práticas de escrita

Ensaie com SELECT

Troque UPDATE ... SET por SELECT * FROM ... com o mesmo WHERE, confira as linhas e só depois execute a escrita.

Use lotes pequenos

Apagar milhões de linhas em uma transação segura travas por muito tempo. Divida em lotes com LIMIT e confirme cada um.

Confira as linhas afetadas

A aplicação deve checar o número de linhas que a escrita afetou. Zero onde se esperava uma é sinal de conflito ou de erro de lógica.

Tenha backup antes

Nenhuma transação desfaz um COMMIT já feito. Para mudanças em massa, faça uma cópia ou um snapshot antes.

Teste seu entendimento

Três perguntas de fundamentos.

1. O que acontece com DELETE FROM clientes; sem WHERE?

Sem WHERE, a condição é verdadeira para todas as linhas. Por isso o hábito de conferir o escopo com um SELECT antes.

2. Quando as alterações de uma transação ficam definitivas?

Ver o dado dentro da transação não o torna definitivo. O COMMIT é o ponto de durabilidade, e o log garante isso mesmo com queda de energia.

3. Por que o UPDATE do checkout usa AND estoque >= 1?

A condição protege o invariante de estoque. Se nenhuma linha casar, o número de linhas afetadas é zero, e a aplicação sabe que deve desfazer a transação. Veja o tópico 15 para o caso em que duas compras competem pela mesma unidade.
