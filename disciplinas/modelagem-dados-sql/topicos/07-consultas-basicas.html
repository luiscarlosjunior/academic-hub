Perguntar ao banco

Um SELECT faz duas coisas: seleciona linhas (quais registros interessam) e projeta colunas (quais campos mostrar). Em álgebra relacional, são os operadores σ (seleção) e π (projeção). Quase toda consulta SQL é uma combinação dos dois, com ordenação e limite.

A forma mais simples é SELECT colunas FROM tabela. Acrescente WHERE para filtrar linhas, ORDER BY para ordenar e LIMIT para parar cedo.

Animação · σ filtra linhas, π escolhe colunas

Filtros: WHERE e seus operadores

A condição do WHERE é uma expressão lógica. Só as linhas em que ela vale verdadeiro são mantidas.

Comparação

= <> (ou !=) < <= > >=. Texto é comparado em ordem alfabética.

Combinação

AND, OR, NOT. AND tem precedência sobre OR: use parênteses para deixar a intenção explícita.

Intervalo e lista

BETWEEN a AND b inclui os extremos. IN (…) testa pertinência em uma lista.

Padrão de texto

LIKE usa % (qualquer sequência) e _ (um caractere). Ex.: 'Notebook%'.

SELECT nome, preco
FROM produtos
WHERE preco BETWEEN 100 AND 500
  AND estoque > 0
ORDER BY preco DESC;

NULL: o valor que não é valor

NULL significa “valor desconhecido ou ausente”. Ele não é zero, não é texto vazio e não é igual a nada, nem a outro NULL. Por isso, a lógica do SQL tem três valores de verdade: verdadeiro, falso e desconhecido. O WHERE só mantém a linha quando a condição é verdadeira.

-- armadilha: a comparação com NULL nunca é verdadeira
SELECT nome FROM clientes WHERE email = NULL;

-- forma correta
SELECT nome FROM clientes WHERE email IS NULL;

A primeira consulta devolve zero linhas, sem erro. Esse é um dos bugs mais silenciosos do SQL: a consulta roda, responde “nada encontrado”, e ninguém percebe que deveria ter achado o cliente Gabriel.

Ordenação, duplicatas e paginação

  • ORDER BY coluna DESC, outra ASC: ordena por mais de um critério. Sem ORDER BY, a ordem é indefinida.
  • DISTINCT remove linhas repetidas do resultado, comparando todas as colunas selecionadas.
  • LIMIT n OFFSET k devolve n linhas a partir da posição k: a base da paginação de telas.
SELECT DISTINCT cidade
FROM clientes
ORDER BY cidade;
-- página 2 com 3 produtos por página
SELECT id_produto, nome
FROM produtos
ORDER BY id_produto
LIMIT 3 OFFSET 3;
Paginação com OFFSET fica lenta. O banco ainda precisa percorrer as linhas puladas. Em tabelas grandes, paginar por “keyset” (WHERE id > último_visto LIMIT n) é muito mais rápido. O tópico 14 mostra o motivo.

Como funciona de verdade

Escreva o SELECT na ordem em que ele aparece, mas entenda-o na ordem em que é avaliado:

1. FROM
2. WHERE
3. SELECT
4. ORDER BY
5. LIMIT
  • Por isso, um alias criado no SELECT não existe no WHERE, porque o WHERE é avaliado antes. O SQLite aceita por tolerância, mas o padrão não. Já no ORDER BY, o alias funciona.
  • O WHERE é avaliado linha a linha. Se houver um índice sobre a coluna filtrada, o banco nem lê as linhas descartadas. O tópico 14 mostra isso.
  • O LIMIT pode parar a execução cedo, mas só quando o ORDER BY não obriga a ler tudo antes (o banco precisa conhecer as primeiras n linhas da ordem final).

Exemplo: perguntas clássicas sobre a loja

Cada consulta responde uma pergunta de negócio. Os resultados abaixo são calculados ao vivo.

Quais clientes moram em Curitiba ou Recife, em ordem alfabética?

SELECT nome, cidade
FROM clientes
WHERE cidade IN ('Curitiba', 'Recife')
ORDER BY nome;

Quais produtos têm “Livro” no nome?

SELECT nome, preco
FROM produtos
WHERE nome LIKE 'Livro%';

Quais clientes não informaram e-mail?

SELECT nome
FROM clientes
WHERE email IS NULL;

Experimente

Altere o exemplo e execute. Cada execução parte de um banco novo, então você pode quebrar à vontade.

SELECT nome, cidade FROM clientes WHERE email IS NULL OR cidade = 'Curitiba' ORDER BY nome;

Problemas para resolver

Tente escrever a consulta antes de abrir a solução.

Problema 1 · Faixa de preço com estoque

Liste nome e preço dos produtos com preço entre 50 e 300 (inclusive) e estoque maior que zero, do mais barato para o mais caro.

Ver solução 
SELECT nome, preco
FROM produtos
WHERE preco BETWEEN 50 AND 300
  AND estoque > 0
ORDER BY preco;

BETWEEN inclui os extremos. O livro “Algoritmos” tem preço 120, mas estoque zero, e por isso não aparece.

Problema 2 · Parênteses fazem diferença

Quais produtos são de “Casa” (categoria 4) ou de “Roupas” (categoria 3) e custam menos de 100? Escreva a consulta com parênteses e explique por que sem eles o resultado muda.

Ver solução 
SELECT nome, preco, id_categoria
FROM produtos
WHERE (id_categoria = 4 OR id_categoria = 3)
  AND preco < 100;

Sem parênteses, AND é avaliado antes de OR, e a condição vira id_categoria = 4 OR (id_categoria = 3 AND preco < 100): Casa aparece mesmo com preço alto. Os parênteses deixam a intenção explícita.

Problema 3 · Contar o que é desconhecido

Quantos clientes têm e-mail diferente de 'ana@loja.com'? Antes de rodar, preveja o resultado. Ele inclui quem não tem e-mail?

Ver solução 
SELECT COUNT(*) AS com_outro_email
FROM clientes
WHERE email <> 'ana@loja.com';

O resultado é 5, e não 6. Os sete clientes menos a Ana (que tem exatamente esse e-mail) dariam 6, mas a comparação NULL <> 'ana@loja.com' é desconhecida, e o WHERE descarta a linha do Gabriel, que não tem e-mail. Para incluí-lo: WHERE email IS NULL OR email <> 'ana@loja.com', que devolve 6.

Aprofundamento e prática

CASE: classificar linhas sem criar tabelas

CASE é o “se–senão” do SQL. Ele avalia condições em ordem e devolve o valor do primeiro caso verdadeiro. Sem ELSE, a resposta para os demais casos é NULL. Ele aparece em qualquer lugar onde uma expressão é aceita: SELECT, WHERE, ORDER BY e até dentro de funções de agregação (tópico 09). 

SELECT nome, preco,
       CASE WHEN preco < 100  THEN 'barato'
            WHEN preco < 1000 THEN 'intermediário'
            ELSE 'premium'
       END AS faixa
FROM produtos
ORDER BY preco;

A ordem das condições importa: como “preço < 1000” é avaliado depois de “preço < 100”, um produto de 50 não chega a ser testado contra a faixa intermediária. Se a faixa for definida por intervalos que se sobrepõem, o primeiro caso vence, e isso precisa estar documentado.

Buscas por texto e por vários termos

LIKE aceita % (zero ou mais caracteres) e _ (exatamente um). Em SQLite, LIKE ignora maiúsculas e minúsculas para letras ASCII; em PostgreSQL, LIKE diferencia, e ILIKE não. Para combinar termos, use OR entre os padrões. Padrões que começam com % percorrem toda a tabela, como o tópico 14 explica. 

SELECT nome, preco
FROM produtos
WHERE nome LIKE '%livro%'
   OR nome LIKE '%camiseta%'
ORDER BY nome;

Apresentar dados faltantes com COALESCE

NULL é correto para o banco, mas feio na tela. COALESCE(a, b, …) devolve o primeiro argumento não nulo. Use-o na consulta de exibição, e nunca para “consertar” um NULL que deveria ser tratado como regra de negócio. 

SELECT nome, COALESCE(email, '(sem e-mail cadastrado)') AS contato
FROM clientes
ORDER BY nome;

Por que evitar SELECT * em código de produção

  • Custo: o banco lê e transporta colunas que ninguém usa, inclusive colunas grandes como textos e binários.
  • Fragilidade: se uma coluna for adicionada ou reordenada, o código que lê o resultado por posição quebra sem aviso.
  • Índices: um índice de cobertura (tópico 14) só funciona se a consulta pede apenas as colunas indexadas.

Para exploração no terminal, SELECT * é ótimo. Em código, liste as colunas.

Problemas do mundo real para discutir

Casos típicos, descritos de forma genérica. Discuta em grupo antes de olhar as pistas.

Caso 1 · A campanha que esqueceu alguns clientes

O marketing quer enviar uma campanha para “todos os clientes que não são da loja”, ou seja, com e-mail de outro domínio. A consulta filtra por NOT LIKE, e o relatório mostra zero destinatários. Um cliente sem e-mail cadastrado, que deveria ser contatado por telefone, simplesmente não aparece em nenhuma lista.

Para discutir:

  • Por que a condição email NOT LIKE '%@loja.com' nunca é verdadeira para um e-mail NULL?
  • Como escrever a lista de forma que o NULL seja tratado como um caso próprio, e não descartado?
-- o NULL precisa ser incluído explicitamente
SELECT nome, email
FROM clientes
WHERE email NOT LIKE '%@loja.com'
   OR email IS NULL
ORDER BY nome;

Pista: sempre que uma coluna pode ser NULL, pergunte o que o NULL significa no negócio (“não informado”, “não se aplica”, “desconhecido”) e escreva a condição para cada caso.

Caso 2 · A API que quebrou com uma coluna nova

Um aplicativo móvel lê a resposta de uma API que faz SELECT * na tabela de clientes. Um dia, o banco ganha a coluna cpf_criptografado, e o app antigo passa a receber dados que não deveria ver. Em outro dia, uma coluna é reordenada e o app mostra o telefone no lugar do nome.

Para discutir:

  • Quais são os dois riscos: vazamento de dados e quebra por posição? Qual deles é mais grave?
  • Como uma lista explícita de colunas e um contrato de API protegem o sistema contra mudanças no esquema?

Pista: ao escrever uma consulta que alimenta outro sistema, a lista de colunas é parte do contrato. Mudar o esquema deve ser uma decisão visível, não um efeito colateral.

Teste seu entendimento

Três perguntas de fundamentos.

1. Qual condição encontra as linhas com e-mail ausente?

NULL não é igual a nada, nem a NULL. Só IS NULL testa ausência. = '' testa texto vazio, que é outro valor.

2. Em WHERE a = 1 OR b = 2 AND c = 3, qual é avaliado primeiro?

A precedência é AND antes de OR. Para evitar dúvidas, use parênteses.

3. Qual é o resultado de SELECT 5 BETWEEN 5 AND 10?

a BETWEEN x AND y equivale a a >= x AND a <= y, então os extremos entram.
