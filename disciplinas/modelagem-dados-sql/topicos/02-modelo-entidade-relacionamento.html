Antes das tabelas, o conceito

Se você sair programando tabelas a partir da frase “o cliente faz pedidos”, vai errar com frequência. O Modelo Entidade-Relacionamento, proposto por Peter Chen em 1976, é uma linguagem para pensar o domínio antes de decidir o esquema. Ele responde três perguntas: que coisas existem, que propriedades elas têm e como se relacionam.

O MER não depende de nenhum SGBD. Ele é um mapa conceitual. Depois, no tópico 04, o diagrama é traduzido para tabelas.

Regra prática. Substantivos viram entidades, adjetivos viram atributos e verbos viram relacionamentos. “Cliente faz pedido” gera duas entidades e um relacionamento.

Entidades, atributos e chaves

Uma entidade é um conjunto de objetos do mundo real com as mesmas propriedades, como “Cliente”. Cada objeto é uma ocorrência (Ana, Bruno…). Um atributo descreve uma propriedade de cada ocorrência, como nome ou cidade.

Tipos de atributo

  • Simples: indivisível, como cidade.
  • Composto: formado por partes, como endereco = rua + número + cidade.
  • Monovalorado ou multivalorado: um valor, ou vários, como telefones.
  • Derivado: calculado a partir de outros, como idade a partir de data_nascimento. Em geral não se guarda.
  • Opcional: pode não ter valor (NULL), como email do cliente Gabriel.

Chave: identifica uma ocorrência

A chave é um atributo (ou conjunto) cujo valor é único para cada ocorrência. Uma entidade pode ter várias chaves candidatas; uma é escolhida como chave primária. 

Cliente
  # id_cliente     ← chave primária
    email          ← candidata: única, mas pode ser trocada
    nome
    cidade

Um bom critério: chaves naturais (CPF, e-mail) mudam ou são sensíveis. Chaves artificiais (um número sequencial) são estáveis. Por isso, a loja usa id_cliente.

Relacionamentos e cardinalidade

Um relacionamento associa ocorrências de duas ou mais entidades. A cardinalidade diz quantas ocorrências de cada lado podem (máximo) e devem (mínimo) participar. Ela é a parte do modelo que mais gera discussão, e a que mais produz bugs no banco.

1 : 1

Um cliente tem um cadastro fiscal, e cada cadastro pertence a um cliente.

1 : N

Um cliente faz muitos pedidos, mas cada pedido pertence a um cliente. É o caso mais comum.

N : N

Um pedido tem muitos produtos, e um produto aparece em muitos pedidos.

Notação de pé de galinha (crow's foot)

Ao lado de cada entidade, o símbolo na linha diz a cardinalidade máxima (um traço = 1, pé de galinha = N) e a mínima (um círculo = zero, traço = um). É a notação usada pela maioria das ferramentas, incluindo o dbdiagram.io.

Cliente ||──o< Pedido · um cliente faz zero ou muitos pedidos
Pedido ||──|< Nota fiscal · exatamente um, para cada

Animação · montando o diagrama da loja

Como funciona de verdade

O MER não entra no banco. Ele é uma etapa de projeto, e a cardinalidade é o que decide onde a informação de relacionamento é guardada no esquema físico:

  • 1:N: a chave do lado “um” é copiada para a tabela do lado “muitos”, como chave estrangeira. Ex.: pedidos.id_cliente.
  • 1:1: a chave pode ir para qualquer lado, mas convém um deles ser UNIQUE para garantir o “um”.
  • N:N: não cabe em nenhuma tabela, então cria-se uma tabela intermediária (entidade associativa). Ex.: itens_pedido.

Além disso, a cardinalidade mínima vira restrição: se o mínimo é 1, a coluna da chave estrangeira é NOT NULL. Se é 0, ela aceita NULL. Ou seja, o diagrama já especifica parte das regras do banco.

Exemplo: o que o diagrama da loja afirma

Cada pedido pertence a exatamente um cliente, e um cliente pode não ter pedido nenhum. Essa frase é uma cardinalidade (pedido: mínimo 1 e máximo 1 de cliente; cliente: mínimo 0 e máximo N de pedidos). Verifique-a nos dados: a cliente Helena (id 7) não tem pedidos, e nenhum pedido está sem cliente. 

SELECT c.nome, COUNT(p.id_pedido) AS pedidos
FROM clientes c
LEFT JOIN pedidos p ON p.id_cliente = c.id_cliente
GROUP BY c.id_cliente, c.nome
ORDER BY pedidos DESC, c.nome;

A consulta usa LEFT JOIN para manter quem não tem pedido (Helena aparece com zero). Os tópicos 09 e 10 explicam cada parte. Por enquanto, perceba que a cardinalidade 0..N do cliente é o que obriga o uso da junção externa.

Erros comuns de modelagem

Atributo que deveria ser entidade

“Cidade” como atributo do cliente esconde regras (estado, CEP, população). Se a cidade tem dados próprios ou é compartilhada por muitos clientes, vire entidade.

Relacionamento N:N sem tabela intermediária

“Produto” com uma lista de pedidos, ou “pedido” com uma lista de produtos, não funciona com colunas. A solução é a entidade associativa do tópico 03.

Chave que muda

Usar o e-mail como chave primária parece natural, mas quando o cliente troca de e-mail, todas as chaves estrangeiras precisam mudar.

Ignorar a cardinalidade mínima

Dizer “pedido tem cliente” sem o “obrigatório” deixa o banco aceitar pedidos órfãos. A cardinalidade mínima é uma regra de negócio.

Problemas para resolver

Desenhe no papel antes de abrir a solução.

Problema 1 · Biblioteca

Um livro pode ser escrito por vários autores, e um autor pode escrever vários livros. Cada livro tem um único exemplar físico cadastrado? Identifique entidades, atributos, chave e as cardinalidades.

Ver solução

Entidades: Livro (chave isbn) e Autor (chave id_autor). Relacionamento escreve: N:N. Como um livro tem “vários autores” e um autor tem “vários livros”, o MER usa cardinalidade 1..N dos dois lados, e a associação recebe um atributo de ordem (quem é o primeiro autor). Exemplares: entidade Exemplar ligada ao livro com 1:N, porque cada exemplar é de um único título.

Problema 2 · Quantas chaves estrangeiras?

Um funcionário é supervisionado por no máximo um outro funcionário. Qual é o relacionamento e a cardinalidade?

Ver solução

É um auto-relacionamento 1:N: um supervisor tem muitos supervisionados, e cada funcionário tem no máximo um supervisor. O supervisor é opcional (mínimo 0), porque a diretora não tem supervisor. Por isso funcionarios.id_supervisor é uma chave estrangeira que aceita NULL. O tópico 13 usa essa mesma tabela.

Problema 3 · Atributo derivado

Num cadastro de pedidos, o valor total do pedido é um atributo a ser guardado?

Ver solução

Em geral, não. O total é derivado de quantidade × preco_unitario dos itens. Guardá-lo cria redundância: se um item mudar, o total precisa mudar também. Calcule na consulta. Se for preciso guardar, faça-o conscientemente, sabendo que é uma cópia que pode ficar desatualizada.

Aprofundamento e prática

Convenções de nomes que evitam confusão

Nomes são documentação. Um bom nome diz o que a coluna guarda sem precisar de comentário. Algumas convenções simples poupam horas de leitura de código e de esquema:

  • Tabelas no plural (clientes, pedidos), porque cada linha é um dos itens. Há quem prefira o singular; o importante é escolher um e manter.
  • Chaves com o nome da tabela (id_cliente), para que a chave estrangeira se reconheça sozinha em pedidos.id_cliente.
  • snake_case e sem acentos (data_pedido, não DataPedido ou Data do Pedido), porque espaços e maiúsculas exigem aspas em muitos bancos.
  • Evitar nomes genéricos como valor, tipo ou data. Se o conceito é “valor da compra”, a coluna se chama valor_compra.

Exercício guiado: do requisito ao modelo

Considere este requisito, escrito por um cliente que não fala a língua dos bancos:

“Um cliente faz pedidos. Cada pedido tem vários produtos, cada um com uma quantidade. Todo produto pertence a uma categoria. Cada pedido é atendido por um vendedor, e um vendedor atende muitos pedidos.”

Os passos de extração são sempre os mesmos:

  1. Substantivos → entidades: cliente, pedido, produto, categoria, vendedor.
  2. Verbos → relacionamentos: “faz” (cliente–pedido), “tem” (pedido–produto), “pertence” (produto–categoria), “atende” (vendedor–pedido).
  3. Cardinalidades: cliente–pedido é 1:N; produto–categoria é N:1; pedido–produto é N:N (exige associativa com quantidade); vendedor–pedido é 1:N.
  4. Obrigatoriedade: um pedido precisa de cliente e vendedor (mínimo 1); um produto precisa de categoria (mínimo 1). Um cliente pode não ter pedido (mínimo 0).

Ao final, confira o modelo voltando ao requisito: cada frase deve estar representada, e nenhuma informação deve ter ficado sem lugar. Esta revisão, feita em papel, custa minutos e evita refazer o esquema depois.

Prática · validando uma regra de negócio nos dados

Uma regra como “todo pedido tem pelo menos um item” pode ser testada procurando exceções. A consulta devolve as linhas que violam a regra; resultado vazio significa que nenhuma violação existe agora. 

SELECT p.id_pedido
FROM pedidos p
LEFT JOIN itens_pedido i ON i.id_pedido = p.id_pedido
WHERE i.id_pedido IS NULL;

Atenção: um resultado vazio prova que os dados atuais respeitam a regra, não que a regra está garantida. Para garanti-la para sempre, seria preciso um mecanismo do banco (uma trigger ou uma restrição), como o tópico 06 mostra.

Problemas do mundo real para discutir

Casos típicos, descritos de forma genérica. Discuta em grupo antes de olhar as pistas.

Caso 1 · Ingresso, assento e sessão

Um sistema de ingressos de cinema precisa responder: um assento pode ser vendido várias vezes? Um ingresso pertence a um assento, a uma sessão ou aos dois? Dois analistas desenham o modelo e chegam a respostas diferentes, e a diferença só aparece quando o sistema vende o mesmo assento para duas sessões no mesmo dia.

Para discutir:

  • Qual é a entidade fraca nesse modelo? O assento depende da sala, e a sala do cinema?
  • Escreva as cardinalidades entre assento, sessão e ingresso. Cada par tem mínimo 0 ou 1?
  • Como o modelo muda se o mesmo cinema tiver salas diferentes com números de assentos distintos?
-- caso de gestão: quantos subordinados cada gerente tem na equipe
SELECT s.nome AS supervisor,
       COUNT(f.id_funcionario) AS subordinados
FROM funcionarios s
JOIN funcionarios f ON f.id_supervisor = s.id_funcionario
GROUP BY s.id_funcionario, s.nome
ORDER BY subordinados DESC, s.nome;

Pista: a resposta do sistema de ingressos depende da regra de negócio, não de uma “verdade” do modelo. O MER existe para tornar a regra explícita antes de virar código.

Caso 2 · O cadastro antigo sem CPF

A loja decide que todo cliente precisa ter CPF, para emitir nota fiscal. Ao migrar a base, descobre-se que 40% dos clientes antigos não têm o campo. Bloquear o cadastro de todos é inviável, e aceitar NULL viola a regra.

Para discutir:

  • A cardinalidade mínima “1” deve valer para todos os registros, ou apenas para os novos? Como representar essa transição?
  • Quem decide se um cliente sem CPF pode comprar? Essa decisão é do modelo ou do processo de negócio?

Pista: migrações costumam separar “dado obrigatório para o futuro” de “dado legado incompleto”, com uma data de corte e uma fila de regularização.

Teste seu entendimento

Três perguntas de fundamentos.

1. Num relacionamento 1:N entre Cliente e Pedido, onde fica a chave estrangeira?

Do lado “muitos” cabe apenas uma referência ao lado “um”. Um pedido tem um cliente, então a chave vai no pedido. Colocar uma lista de pedidos no cliente exigiria uma coluna com vários valores, o que o modelo relacional não permite.

2. Qual atributo é o melhor candidato a chave primária de Cliente?

Chave deve ser única e estável. Nomes se repetem e mudam; cidades se repetem. Um identificador sem significado de negócio não muda, por isso é a escolha mais segura.

3. Um pedido precisa obrigatoriamente ter um cliente. Qual é o efeito no esquema?

A cardinalidade mínima 1 se traduz em NOT NULL na chave estrangeira. Assim, o banco recusa pedidos sem cliente.
