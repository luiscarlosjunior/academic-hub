SQL: uma linguagem em três partes

SQL (Structured Query Language) é a linguagem padrão para bancos relacionais. Ela se divide em partes conforme o que faz com o banco:

  • DDL (Data Definition Language): cria e altera a estrutura. CREATE, ALTER, DROP.
  • DML (Data Manipulation Language): trabalha com os dados. INSERT, UPDATE, DELETE, e também a consulta SELECT.
  • DCL/TCL: controla permissões (GRANT, REVOKE) e transações (COMMIT, ROLLBACK, tópico 08).

Este tópico é sobre DDL: como o esquema da loja foi criado e como as restrições protegem os dados.

CREATE TABLE: definindo a estrutura

Cada coluna tem nome, tipo e, opcionalmente, restrições. A ordem das definições não importa para o banco, mas uma boa leitura começa pela chave primária.

Animação · da linha de código à tabela

CREATE TABLE avaliacoes (
  id_avaliacao INTEGER PRIMARY KEY,
  id_produto   INTEGER NOT NULL REFERENCES produtos(id_produto),
  nota         INTEGER NOT NULL CHECK (nota BETWEEN 1 AND 5),
  comentario   TEXT,
  criada_em    TEXT    NOT NULL DEFAULT (date('now'))
);
INSERT INTO avaliacoes (id_produto, nota, comentario)
VALUES (1, 5, 'Excelente'), (4, 3, NULL);
SELECT * FROM avaliacoes;

Veja o que aconteceu: id_avaliacao não foi informado e recebeu um valor automaticamente, porque é INTEGER PRIMARY KEY (no SQLite, um apelido para o identificador da linha). criada_em usou o DEFAULT. O comentário ausente virou NULL.

Tipos de dados

O tipo define que valores a coluna aceita, quanto espaço ocupa e quais operações são possíveis. Escolher o tipo certo é a primeira restrição do esquema.

Tipo SQL padrãoUso típicoCuidado
INTEGERIdentificadores, quantidadesEstoque não deveria aceitar negativo: use CHECK
DECIMAL(p, s)DinheiroNunca use ponto flutuante para dinheiro (REAL/FLOAT)
VARCHAR(n) / CHAR(n)Textos com limiteCHAR preenche com espaços
DATE / TIMESTAMPDatas e instantesFuso horário: guarde em UTC
BOOLEANSim/nãoNem todo SGBD tem; SQLite usa 0/1
Dinheiro em REAL é um erro clássico. Números de ponto flutuante são binários e não representam 0,1 exatamente. Some 0,1 dez vezes e o total não é 1. A loja guarda os preços como REAL por simplicidade didática; em produção use DECIMAL ou inteiros em centavos.

O SQLite segue outra filosofia: usa afinidade de tipo. Uma coluna INTEGER tenta converter o valor para inteiro, mas uma célula pode guardar texto se a conversão não for possível. Por isso o SQLite aceita VARCHAR(80) e DECIMAL(10,2) sem reclamar, mas o tamanho e a escala não são impostos. Bancos como PostgreSQL são mais rígidos. Escreva o esquema pensando no padrão.

Restrições: o banco recusa o que é inválido

Uma restrição é uma regra que o SGBD verifica em cada inserção e alteração. Se a regra falha, a operação inteira é recusada. Não depende do programa que escreveu os dados: vale para qualquer cliente de banco.

NOT NULL

A coluna precisa de valor. Ex.: todo cliente tem nome.

UNIQUE

Não repete valores (NULLs contam como distintos na maioria dos bancos). Ex.: e-mail.

CHECK (condição)

Expressão que precisa ser verdadeira. Ex.: preço não negativo.

DEFAULT valor

Valor usado quando a coluna não é informada. Ex.: estoque começa em 0.

PRIMARY KEY

Identifica a linha: única e não nula.

REFERENCES

Chave estrangeira: o valor precisa existir na tabela referenciada.

ALTER e DROP: evoluindo o esquema

Esquemas mudam. ALTER TABLE altera uma tabela existente, e DROP TABLE a remove, com todos os seus dados. Remover é irreversível: faça backup antes. 

ALTER TABLE clientes ADD COLUMN telefone TEXT;
UPDATE clientes SET telefone = '41 99999-0007' WHERE id_cliente = 7;
SELECT id_cliente, nome, telefone FROM clientes WHERE id_cliente IN (1, 7);
Limitações do ALTER no SQLite. O SQLite aceita ADD COLUMN, RENAME e DROP COLUMN, mas não altera o tipo nem acrescenta restrições a uma coluna existente. Nesses casos, o procedimento padrão é criar uma tabela nova, copiar os dados e renomear. Em PostgreSQL e MySQL, a maioria das alterações é direta. 
-- DROP TABLE IF EXISTS evita erro quando a tabela não existe
DROP TABLE IF EXISTS avaliacoes;
SELECT name FROM sqlite_master WHERE type = 'table' AND name = 'avaliacoes';

Como funciona de verdade

  • Restrições custam trabalho. Cada INSERT precisa testar UNIQUE e consultar a tabela referenciada. Por isso o SGBD cria um índice automático para PRIMARY KEY e UNIQUE: a verificação vira uma busca rápida, não uma varredura.
  • CHECK é avaliado linha a linha, sem olhar outras linhas. Uma regra que compara com outras linhas (“não pode haver dois pedidos no mesmo dia para o mesmo cliente”) precisa de UNIQUE sobre colunas, ou de um gatilho.
  • Transações e DDL. Em PostgreSQL, DDL também é transacional: um CREATE TABLE pode ser desfeito com ROLLBACK. Em MySQL, DDL causa COMMIT implícito. Essa diferença aparece em migrações de esquema.
  • O esquema é dado. O SQLite guarda o texto de cada CREATE TABLE em sqlite_master. Ferramentas de migração leem esse catálogo para comparar o banco real com o modelo.

Exemplo: quatro inserções inválidas

Cada instrução abaixo viola uma restrição do banco da loja. Cada bloco roda em um banco próprio, então uma falha não interfere nas outras. Veja a mensagem que o SGBD devolve em cada caso. 

INSERT INTO clientes VALUES (8, 'Igor', 'Porto Alegre', 'ana@loja.com', '2024-10-01');
INSERT INTO clientes VALUES (8, NULL, 'Porto Alegre', 'igor@loja.com', '2024-10-01');
INSERT INTO produtos VALUES (10, 'Teclado', 1, -50.00, 3);
INSERT INTO pedidos VALUES (10, 1, '2024-10-02', 'entregue');

As quatro mensagens são: e-mail duplicado (UNIQUE), nome ausente (NOT NULL), preço negativo (CHECK) e status fora da lista (CHECK). Note que, nos dois últimos casos, a mensagem menciona a expressão exata que falhou: isso ajuda a depurar.

Experimente

Altere o exemplo e execute. Cada execução parte de um banco novo, então você pode quebrar à vontade.

CREATE TABLE teste (id INTEGER PRIMARY KEY, valor INTEGER CHECK (valor > 0)); INSERT INTO teste VALUES (1, 10); INSERT INTO teste VALUES (2, -1); SELECT * FROM teste;

Problemas para resolver

Escreva o comando antes de abrir a solução.

Problema 1 · Tabela de cupons

Crie a tabela cupons com: código único e obrigatório (texto), percentual de desconto entre 1 e 50 (inteiro, obrigatório) e uma data de validade obrigatória. Insira um cupom e consulte-o.

Ver solução 
CREATE TABLE cupons (
  codigo     TEXT    PRIMARY KEY,
  percentual INTEGER NOT NULL CHECK (percentual BETWEEN 1 AND 50),
  validade   TEXT    NOT NULL
);
INSERT INTO cupons VALUES ('BEMVINDO10', 10, '2025-12-31');
SELECT * FROM cupons;

Usar o código como PRIMARY KEY já garante unicidade e não nulidade. O CHECK limita o intervalo.

Problema 2 · Só o CHECK segura?

Tente inserir um produto de preço zero e outro com estoque negativo. Alguma das duas é recusada?

Ver solução 
INSERT INTO produtos VALUES (11, 'Brinde', 5, 0.00, 10);
INSERT INTO produtos VALUES (12, 'Brinde 2', 5, 1.00, -3);
SELECT id_produto, nome, preco, estoque FROM produtos WHERE id_produto IN (11, 12);

Nenhuma é recusada. Preço zero satisfaz preco >= 0. Estoque negativo passa porque a coluna estoque não tem CHECK. Se, no negócio, estoque negativo é impossível, o banco precisa dizer isso, com CHECK (estoque >= 0). Regra que não está no esquema não é garantida por ninguém.

Problema 3 · Chave estrangeira sem regra de exclusão

Explique o que acontece com os pedidos de um cliente quando o cliente é excluído, usando a declaração padrão de pedidos.id_cliente (sem ON DELETE).

Ver solução

Com o comportamento padrão (NO ACTION), a exclusão do cliente é recusada enquanto houver pedidos referenciando-o (com a verificação ligada). Para apagar em cascata, é preciso declarar REFERENCES clientes(id_cliente) ON DELETE CASCADE. Escolher entre as duas é uma decisão de negócio: apagar pedidos junto com o cliente pode ser perigoso para a contabilidade.

Aprofundamento e prática

Chaves geradas automaticamente

Em quase todo sistema, a chave primária é gerada pelo banco, e não pela aplicação. Cada SGBD tem sua forma:

SGBDSintaxe típica
SQLiteINTEGER PRIMARY KEY (vira apelido do rowid)
PostgreSQLid INTEGER GENERATED ALWAYS AS IDENTITY (ou o antigo SERIAL)
MySQLid INT AUTO_INCREMENT PRIMARY KEY
SQL Serverid INT IDENTITY(1,1) PRIMARY KEY

Um detalhe que surpreende: a sequência não volta atrás quando uma transação sofre ROLLBACK. Se o pedido 10 foi revertido, o próximo pedido será o 11, e o 10 nunca será reutilizado. Isso é correto (identificadores não precisam ser contínuos), mas não serve como contagem de pedidos. Para contar, use COUNT.

Colunas calculadas pelo próprio banco

Uma coluna gerada recebe o valor de uma expressão sobre outras colunas da mesma linha. O banco recalcula sempre que a linha muda, então a cópia nunca fica desatualizada. É a forma segura de guardar um valor derivado quando ele precisa estar disponível para índices ou relatórios (o tópico 02 discutiu esse trade-off). 

CREATE TABLE itens_calc (
  id INTEGER PRIMARY KEY,
  quantidade INTEGER NOT NULL,
  preco REAL NOT NULL,
  total REAL GENERATED ALWAYS AS (quantidade * preco) STORED
);
INSERT INTO itens_calc (quantidade, preco) VALUES (2, 49.90), (3, 250);
SELECT * FROM itens_calc;

Quando CHECK não basta: triggers

CHECK só enxerga a própria linha. Uma regra que depende de outro valor, como “o estoque não pode ficar negativo após uma atualização”, pode ser garantida por uma trigger: um bloco executado automaticamente antes ou depois de uma operação. O exemplo abaixo recusa qualquer UPDATE que deixe o estoque negativo. 

CREATE TRIGGER impede_estoque_negativo
BEFORE UPDATE OF estoque ON produtos
WHEN NEW.estoque < 0
BEGIN
  SELECT RAISE(ABORT, 'estoque não pode ser negativo');
END;
UPDATE produtos SET estoque = estoque - 100 WHERE id_produto = 1;
Trigger é lógica escondida. Quem lê o UPDATE não vê a regra, e uma migração pode desabilitá-la sem aviso. Use triggers para invariantes que o banco precisa proteger de qualquer cliente, e documente-as junto com o esquema.

Boas práticas de DDL

  • Escreva o esquema em migrações versionadas, nunca alterando o banco à mão. Quem vier depois precisa reproduzir exatamente o mesmo estado.
  • Use IF NOT EXISTS e IF EXISTS apenas quando a migração for idempotente de propósito. Esconder erros de DDL costuma atrasar a descoberta de problemas.
  • Em tabelas grandes, uma alteração de coluna pode reescrever a tabela inteira e travá-la. Planeje essas mudanças em janelas de manutenção, ou em etapas (nova coluna, cópia, troca).
  • Nomeie as restrições (CONSTRAINT chk_preco CHECK (preco >= 0)). Quando a mensagem de erro aparecer em produção, o nome aponta direto para a regra violada.

Problemas do mundo real para discutir

Casos típicos, descritos de forma genérica. Discuta em grupo antes de olhar as pistas.

Caso 1 · Centavos que desaparecem

Um sistema de cobrança guarda valores em REAL. Em um fechamento mensal com milhares de lançamentos, o total calculado não bate com o extrato do banco por alguns centavos. A soma individual parece correta, mas a conferência falha.

Para discutir:

  • Por que a representação binária de frações como 0,1 causa esse erro? Ele aparece sempre ou só em algumas somas?
  • Quais são as opções: DECIMAL, inteiros em centavos, ou arredondar a cada operação? Quais os custos de cada uma?
-- com ponto flutuante, 0,1 + 0,2 não é exatamente 0,3
SELECT 0.1 + 0.2 = 0.3 AS igual,
       ROUND(0.1 + 0.2, 2) = 0.3 AS igual_arredondado;

Pista: bancos de pagamento e contábeis costumam guardar dinheiro como inteiro de centavos ou como DECIMAL com escala fixa. O erro é pequeno em cada linha e grande no acumulado.

Caso 2 · A migração que trava a produção

Um time quer adicionar uma coluna obrigatória à tabela de pedidos, com milhões de linhas. A alteração bloqueia a tabela por vários minutos, e o site para de aceitar compras no horário de pico. Em outro sistema, o mesmo comando foi executado sem problemas porque a tabela era pequena.

Para discutir:

  • Por que adicionar uma coluna NOT NULL sem valor padrão falha, mesmo com a tabela vazia de valores novos?
  • Como dividir a mudança em etapas (coluna opcional, preenchimento em lotes, restrição no fim) para não travar o sistema?
-- falha: a coluna não pode ser NOT NULL sem um valor padrão para as linhas existentes
ALTER TABLE clientes ADD COLUMN telefone TEXT NOT NULL;
-- caminho seguro: primeiro com DEFAULT, depois o preenchimento real em lotes
ALTER TABLE clientes ADD COLUMN telefone TEXT NOT NULL DEFAULT '';
SELECT COUNT(*) AS sem_telefone FROM clientes WHERE telefone = '';

Pista: o primeiro bloco ilustra a regra do SQLite; em PostgreSQL, a mesma mudança pode reescrever a tabela inteira. Cada banco tem seu custo de DDL, e vale conferir antes de rodar em produção.

Teste seu entendimento

Três perguntas de fundamentos.

1. Qual comando faz parte da DDL?

DDL define estrutura: CREATE, ALTER, DROP. UPDATE e SELECT trabalham com dados (DML).

2. Por que não se deve guardar dinheiro em tipo de ponto flutuante?

0,1 não tem representação binária exata. Somas repetidas acumulam erro. DECIMAL ou centavos em inteiro evitam isso.

3. Qual restrição garante que estoque nunca fique negativo?

CHECK avalia uma condição em cada linha. NOT NULL só trata nulos, e UNIQUE impediria dois produtos com o mesmo estoque.
