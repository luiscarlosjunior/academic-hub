Quando duas transações se encontram

No tópico 08 vimos que uma transação é “tudo ou nada”. Mas uma loja tem centenas de transações simultâneas, e elas leem e escrevem os mesmos dados. Se o banco executasse uma de cada vez, seria lento. Se executasse todas sem controle, daria resultados errados. A concorrência é o equilíbrio entre velocidade e correção.

A propriedade I do ACID (isolamento) diz o que uma transação pode ver das outras. Os níveis de isolamento são o contrato: quanto mais isolamento, menos anomalias, e mais espera ou conflito.

Animação · a atualização perdida

As anomalias clássicas

Cada anomalia é um resultado que nenhuma execução sequencial produziria. Os nomes vêm da teoria de transações.

Leitura suja (dirty read)

A transação B lê um valor que A escreveu, mas ainda não confirmou. Se A der ROLLBACK, B agiu com um dado que nunca existiu.

Leitura não repetível

B lê uma linha duas vezes na mesma transação e obtém valores diferentes, porque A confirmou uma alteração entre as duas leituras.

Fantasma (phantom)

B executa a mesma consulta com filtro duas vezes e vê um conjunto diferente de linhas, porque A inseriu ou removeu linhas que casam com o filtro.

Atualização perdida (lost update)

Duas transações leem o mesmo valor, calculam um novo com base nele e gravam. A segunda gravação sobrescreve a primeira, e a alteração de uma some.

Os quatro níveis de isolamento

O padrão SQL define quatro níveis, cada um proibindo um subconjunto de anomalias. Escolha pelo menor nível que garanta a correção do seu caso, porque cada nível mais alto custa mais em concorrência.

O padrão é um piso, não o comportamento de cada banco. PostgreSQL implementa READ UNCOMMITTED como READ COMMITTED (nunca lê dado não confirmado). Seu REPEATABLE READ também impede fantasmas, por usar snapshots. MySQL InnoDB usa gap locks no REPEATABLE READ. Leia a documentação do seu SGBD: o nome do nível é igual, a garantia nem sempre.

Como o banco controla a concorrência

Travas (locks)

Uma transação que escreve trava a linha. Outra que tenta escrever nela espera. Leituras podem ou não esperar, conforme o nível. Travas garantem a correção, mas causam espera e, no pior caso, deadlock: A espera B e B espera A. O banco detecta o ciclo e aborta uma das transações.

Versões (MVCC)

O banco guarda versões da linha. Cada transação lê a versão que era confirmada no seu snapshot, sem esperar quem escreve. Leitores e escritores não se bloqueiam. Quem escreve sobre a mesma linha ainda pode conflitar, e então uma é abortada. PostgreSQL e InnoDB usam essa abordagem.

E o SQLite? Ele é mais simples: uma escrita por vez no arquivo inteiro. Em modo WAL, leitores não esperam o escritor, mas só há um escritor de cada vez. Para uma aplicação de um usuário, isso basta. Para centenas de usuários escrevendo, use um servidor como PostgreSQL.

Três formas de corrigir

O erro está em ler, calcular na aplicação e gravar o resultado. Há três saídas, com trade-offs diferentes.

1. Cálculo no banco

Faça a conta dentro do UPDATE, em uma só instrução atômica. Simples e eficiente.

2. Trava pessimista

SELECT … FOR UPDATE trava a linha durante a leitura. Quem vem depois espera.

3. Versão otimista

Uma coluna versao é conferida no UPDATE. Se mudou, a aplicação relê e tenta de novo. Não trava nada.

-- 1. cálculo no banco: nenhuma leitura intermediária na aplicação
UPDATE produtos SET estoque = estoque - 1 WHERE id_produto = 1 AND estoque >= 1;
SELECT id_produto, estoque FROM produtos WHERE id_produto = 1;
-- 3. versão otimista: só grava se ninguém mudou a linha desde a leitura
ALTER TABLE produtos ADD COLUMN versao INTEGER NOT NULL DEFAULT 1;
UPDATE produtos SET estoque = estoque - 1, versao = versao + 1
WHERE id_produto = 1 AND versao = 1;
SELECT id_produto, estoque, versao FROM produtos WHERE id_produto = 1;

Na versão otimista, a aplicação lê a versão 1, calcula e grava “se a versão ainda for 1”. Se duas aplicações fizeram isso ao mesmo tempo, só a primeira casa a condição: a segunda afeta zero linhas e repete a leitura.

Como funciona de verdade

  • Serializabilidade é o padrão-ouro. Um conjunto de transações concorrentes é serializável se o resultado é igual ao de alguma execução sequencial delas. SERIALIZABLE garante isso; os outros níveis aceitam resultados que não correspondem a nenhuma ordem sequencial.
  • Write skew. Duas transações leem um conjunto, cada uma verifica uma regra sobre ele e grava em linhas diferentes. Nenhuma atualização colide, mas juntas violam a regra. Exemplo: “pelo menos um médico de plantão”, com dois médicos saindo ao mesmo tempo. Nem REPEATABLE READ impede isso; só SERIALIZABLE, ou uma trava explícita.
  • Deadlock é normal. Aplicações devem repetir a transação abortada, e acessar as tabelas sempre na mesma ordem reduz a chance de deadlock.
  • Transações longas são o inimigo. Uma transação aberta por minutos segura travas ou versões antigas por todo esse tempo. Mantenha-as curtas e sem esperar entrada do usuário no meio.

Exemplo clássico: a corrida pelo último item

O produto 8 (Cafeteira) tem estoque 5. Dois clientes compram ao mesmo tempo. Sem controle, os dois leem “5”, cada um calcula “4”, e o estoque final é 4, quando deveria ser 3. A versão correta usa uma única instrução atômica, como no tópico 08. 

-- cliente A e cliente B executam, quase ao mesmo tempo, o mesmo comando:
UPDATE produtos SET estoque = estoque - 1 WHERE id_produto = 8 AND estoque >= 1;
UPDATE produtos SET estoque = estoque - 1 WHERE id_produto = 8 AND estoque >= 1;
SELECT id_produto, nome, estoque FROM produtos WHERE id_produto = 8;

Aqui os comandos rodam em sequência, num só banco, e o resultado é 3: cada UPDATE vê o efeito do anterior. Em concorrência real, o banco garante o mesmo resultado: a segunda transação espera a primeira ou lê a nova versão antes de gravar. A leitura separada e o cálculo na aplicação é que provocariam a perda.

Problemas para resolver

Os cenários de concorrência são conceituais: o editor roda um único banco. Use o raciocínio.

Problema 1 · Identifique a anomalia

A transação T1 lê o saldo de uma conta (100). T2 atualiza o saldo para 50 e confirma. T1 lê o saldo de novo e obtém 50. Qual anomalia ocorreu, e em qual nível ela é proibida?

Ver solução

É uma leitura não repetível. T1 leu o mesmo dado duas vezes e obteve valores diferentes porque T2 confirmou uma alteração entre as leituras. Ela é proibida a partir de REPEATABLE READ.

Problema 2 · Escolha a correção

Um sistema de reservas verifica se um assento está livre e, em seguida, marca como ocupado. Duas pessoas escolhem o mesmo assento ao mesmo tempo. Qual correção você escolheria, e por quê?

Ver solução

A verificação e a marcação formam um par “ler, decidir, gravar”, e a correção é fazer tudo numa só instrução condicional: UPDATE assentos SET ocupado = 1 WHERE id = ? AND ocupado = 0. Se afetar uma linha, a reserva é sua; se afetar zero, o assento já foi tomado. Essa é a correção mais simples e mais segura, porque não há janela entre a checagem e a gravação.

Problema 3 · Write skew

A regra é “pelo menos um dos plantonistas deve estar de plantão”. Dois plantonistas, Ana e Bruno, estão de plantão. Cada um pede para sair, verificando antes que o outro continua. Por que a regra pode ser violada mesmo com atualizações em linhas diferentes?

Ver solução

Cada transação lê as duas linhas, vê que “o outro está de plantão”, e atualiza só a sua. As escritas não colidem, então nenhuma trava de linha é disputada. Juntas, porém, deixam o plantão vazio. É um write skew. Soluções: SERIALIZABLE, ou travar explicitamente uma linha compartilhada (um registro de plantão do dia) antes de decidir.

Aprofundamento e prática

Reproduzindo a anomalia com duas sessões

Para ver uma anomalia de verdade, é preciso duas conexões ao mesmo tempo. Como o editor desta página roda um único banco, o exemplo abaixo mostra os comandos de cada sessão em PostgreSQL. Rode-os em dois terminais psql na ordem indicada, e observe o resultado de cada passo.

Sessão A (leitor)
BEGIN ISOLATION LEVEL READ COMMITTED;
-- passo 1
SELECT estoque FROM produtos WHERE id_produto = 8;   -- 5
-- passo 4 (depois que B confirmar)
SELECT estoque FROM produtos WHERE id_produto = 8;   -- 4 ou 3?
COMMIT;
Sessão B (escritor)
BEGIN;
-- passo 2
UPDATE produtos SET estoque = estoque - 1 WHERE id_produto = 8;
-- passo 3
COMMIT;

Em READ COMMITTED, a segunda leitura de A vê a alteração de B, porque ela já foi confirmada: é a leitura não repetível. Troque o nível de A para REPEATABLE READ e repita: a segunda leitura continuará vendo 5, porque a transação mantém o snapshot do início. Esse experimento de dois terminais vale mais que muitos parágrafos.

Deadlock: quando dois esperam um pelo outro

Deadlock acontece quando a transação T1 trava a linha X e quer a Y, enquanto T2 trava Y e quer a X. Nenhuma pode avançar. O banco detecta o ciclo de espera e aborta uma delas com um erro, e a aplicação deve repetir a transação.

T1: UPDATE produtos SET estoque = estoque - 1 WHERE id_produto = 1; -- trava produto 1 T2: UPDATE produtos SET estoque = estoque - 1 WHERE id_produto = 2; -- trava produto 2 T1: UPDATE produtos SET estoque = estoque - 1 WHERE id_produto = 2; -- espera T2 T2: UPDATE produtos SET estoque = estoque - 1 WHERE id_produto = 1; -- espera T1 => deadlock

A regra de prevenção é simples: todas as transações que tocam as mesmas linhas devem travá-las na mesma ordem (por exemplo, por id crescente). Com a ordem fixa, o ciclo de espera não se forma.

Fila de trabalho sem disputa

Um padrão muito comum é um conjunto de tarefas que vários workers consomem. Se todos fizerem a mesma consulta, disputam a mesma linha. A cláusula FOR UPDATE SKIP LOCKED (PostgreSQL e MySQL 8) pega a primeira tarefa livre e ignora as já travadas por outros workers.

BEGIN; SELECT id, payload FROM fila_tarefas WHERE status = 'pendente' ORDER BY id LIMIT 1 FOR UPDATE SKIP LOCKED; -- processa a tarefa e depois: UPDATE fila_tarefas SET status = 'feita' WHERE id = ?; COMMIT;

Qual nível usar? Um guia por caso

CasoAbordagem razoávelMotivo

Comece pelo problema, não pelo nível. Antes de subir o isolamento, tente tornar a operação atômica. Isolamento mais alto custa espera e falhas de serialização. Uma instrução bem escrita costuma resolver o caso com custo zero.

Teste seu entendimento

Três perguntas de fundamentos.

1. Qual anomalia permite ler um valor que outra transação ainda não confirmou?

A leitura suja expõe dados não confirmados. READ COMMITTED e níveis acima a proíbem.

2. Qual nível de isolamento garante que o resultado seja equivalente a alguma execução sequencial?

SERIALIZABLE é o único nível do padrão que elimina todas as anomalias, incluindo o write skew, e garante serializabilidade.

3. Por que UPDATE … SET estoque = estoque - 1 WHERE … AND estoque >= 1 é mais seguro do que ler, calcular e gravar?

A atomicidade da instrução única elimina a atualização perdida. Ela não evita travas: o banco ainda pode travar a linha durante a execução, o que é desejável.
