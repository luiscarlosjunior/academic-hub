Do diagrama ao esquema

Codd definiu o modelo relacional sobre a matemática de conjuntos. Uma relação é um conjunto de tuplas (linhas) que têm os mesmos atributos (colunas), cada um com um domínio (o conjunto de valores válidos, como “inteiros” ou “textos de até 80 caracteres”).

Em SQL, a relação vira tabela, a tupla vira linha e o atributo vira coluna. A diferença sutil é importante: uma relação matemática não tem linhas repetidas nem ordem. Uma tabela SQL, por padrão, permite duplicatas e tem ordem indefinida, a menos que você crie chaves e use ORDER BY.

Animação · uma relação pela lente da teoria

Chaves: como as tabelas se conectam

A chave primária identifica cada linha. A chave estrangeira é uma coluna que referencia a chave primária de outra tabela (ou da mesma). É ela que materializa os relacionamentos do diagrama.

Integridade de entidade

Nenhuma parte da chave primária pode ser NULL. Toda linha precisa ser identificável. Por isso, PRIMARY KEY já implica NOT NULL e unicidade.

Integridade referencial

Toda chave estrangeira não nula deve apontar para uma linha existente. Não é possível ter um pedido de um cliente que não existe. Essa é a regra mais importante que o modelo relacional garante.

Animação · a chave estrangeira aponta para a chave primária

Regras de mapeamento: do MER ao esquema

Traduzir o diagrama é quase mecânico. Cada elemento do MER tem uma regra. Aplicá-las com disciplina evita a maioria dos erros de esquema.

Exemplo: o esquema da loja, rule por rule

Cada tabela da loja segue as regras acima. Observe a tabela itens_pedido: é a associativa do N:N, com chave composta. E funcionarios.id_supervisor é o auto-relacionamento 1:N com coluna opcional. O comando abaixo mostra o esquema do banco, lido direto do catálogo do SQLite. 

SELECT name AS tabela, sql
FROM sqlite_master
WHERE type = 'table' AND name = 'itens_pedido';

O SQLite guarda o próprio esquema numa tabela de sistema, sqlite_master. Outros SGBDs têm o information_schema, padronizado pelo SQL. Ler o catálogo é uma forma de inspecionar o que o banco de fato aplicou.

Como funciona de verdade

Por padrão, o SQLite não verifica chaves estrangeiras. Isso é herança de compatibilidade: a verificação precisa ser ligada por conexão com PRAGMA foreign_keys = ON. PostgreSQL e MySQL (InnoDB) verificam sempre. Esse detalhe causa surpresas em sistemas que migram de banco. Abaixo, o mesmo INSERT sem e com a verificação ligada.

Sem PRAGMA: aceita o pedido órfão
INSERT INTO pedidos VALUES (10, 99, '2024-10-01', 'pago');
Com PRAGMA: recusa
PRAGMA foreign_keys = ON; INSERT INTO pedidos VALUES (10, 99, '2024-10-01', 'pago'); -- FOREIGN KEY constraint failed

Ao declarar a chave estrangeira com ON DELETE CASCADE, apagar o cliente apaga os pedidos dele. Com ON DELETE RESTRICT (ou o padrão, NO ACTION), a exclusão é recusada enquanto houver pedidos. A escolha é uma regra de negócio disfarçada de detalhe técnico, e por isso precisa ser decidida no modelo.

Problemas para resolver

Os problemas com SQL usam o banco da loja. Experimente as soluções.

Problema 1 · Traduzir o multivalorado

Um cliente pode ter vários telefones. Como o atributo telefones é traduzido para o esquema? Escreva o CREATE TABLE da tabela nova.

Ver solução 
CREATE TABLE telefones (
  id_cliente INTEGER NOT NULL REFERENCES clientes(id_cliente),
  numero     TEXT    NOT NULL,
  PRIMARY KEY (id_cliente, numero)
);
INSERT INTO telefones VALUES (1, '11 99999-0001'), (1, '11 3333-0002');
SELECT * FROM telefones;

Um atributo com vários valores vira tabela própria. A chave composta impede o mesmo número duas vezes para o cliente.

Problema 2 · Reconstruir a linha do pedido

Usando as chaves estrangeiras, escreva uma consulta que mostre, para o pedido 1, o nome do cliente, o nome do produto e a quantidade. Use apenas as tabelas do banco.

Ver solução 
SELECT p.id_pedido, c.nome AS cliente, pr.nome AS produto, i.quantidade
FROM pedidos p
JOIN clientes c       ON c.id_cliente = p.id_cliente
JOIN itens_pedido i   ON i.id_pedido  = p.id_pedido
JOIN produtos pr      ON pr.id_produto = i.id_produto
WHERE p.id_pedido = 1;

Cada chave estrangeira vira uma condição de junção. Os tópicos 10 e 11 detalham essa técnica.

Problema 3 · Ligar a verificação

Ligue a verificação de chaves estrangeiras e tente inserir um item de um pedido que não existe (pedido 42). O que o banco responde?

Ver solução 
PRAGMA foreign_keys = ON;
INSERT INTO itens_pedido VALUES (42, 1, 1, 3500.00);

A resposta é FOREIGN KEY constraint failed. A inserção é recusada e nada muda no banco.

Aprofundamento e prática

Chave natural ou chave substituta?

Uma chave natural já existe no mundo real: CPF, CNPJ, ISBN, código de barras. Uma chave substituta é um número criado só para identificar a linha, como id_cliente. A escolha tem consequências práticas:

  • Natural: dispensa um campo extra e facilita a leitura. Mas o valor pode mudar (um CPF corrigido, um código reutilizado) e, quando muda, precisa ser propagado a todas as chaves estrangeiras.
  • Substituta: é estável e pequena, o que favorece índices e junções. Não diz nada sobre a linha, então exige uma restrição UNIQUE sobre o dado natural quando ele é único de verdade.

A prática mais comum é usar substitutas como chave primária e manter o natural como UNIQUE. Isso une estabilidade e a garantia de unicidade, como na tabela de clientes da loja, com email UNIQUE.

Ações referenciais: o que acontece ao apagar a dona

CláusulaAo apagar a linha referenciadaUso típico
NO ACTION / RESTRICTRecusa a exclusão enquanto houver referênciasPedidos: não apague o cliente com histórico
CASCADEApaga as linhas dependentesItens de um pedido, arquivos de uma pasta
SET NULLZera a chave estrangeiraAutor de um post que saiu da empresa
SET DEFAULTAplica um valor padrãoAtribuir a um “responsável geral”

Os dois exemplos abaixo mostram SET NULL e CASCADE. Eles usam tabelas próprias, para não alterar os dados da loja. 

PRAGMA foreign_keys = ON;
CREATE TABLE autor (id INTEGER PRIMARY KEY, nome TEXT);
CREATE TABLE post (
  id INTEGER PRIMARY KEY,
  titulo TEXT,
  id_autor INTEGER REFERENCES autor(id) ON DELETE SET NULL
);
INSERT INTO autor VALUES (1, 'Ana'), (2, 'Bruno');
INSERT INTO post VALUES (10, 'Intro', 1), (11, 'SQL', 1), (12, 'Índices', 2);
DELETE FROM autor WHERE id = 1;
SELECT * FROM post;

Os posts de Ana continuam existindo, mas sem autor. A escolha entre SET NULL e CASCADE é de negócio: o conteúdo deve sumir com o autor, ou apenas perder a atribuição? 

PRAGMA foreign_keys = ON;
CREATE TABLE pasta (id INTEGER PRIMARY KEY, nome TEXT);
CREATE TABLE arquivo (
  id INTEGER PRIMARY KEY,
  nome TEXT,
  id_pasta INTEGER REFERENCES pasta(id) ON DELETE CASCADE
);
INSERT INTO pasta VALUES (1, 'Projetos'), (2, 'Fotos');
INSERT INTO arquivo VALUES (1, 'a.sql', 1), (2, 'b.sql', 1), (3, 'c.jpg', 2);
DELETE FROM pasta WHERE id = 1;
SELECT * FROM arquivo;
CASCADE é perigoso em cadeias longas. Apagar uma linha pode disparar outra cascata, e outra, sem que ninguém veja o total. Em sistemas com dados financeiros, a convenção mais segura é não apagar: marcar a linha como inativa (tópico 08, “exclusão lógica”).

Custos escondidos do esquema físico

Cada chave primária e cada UNIQUE cria um índice automaticamente. Já a chave estrangeira não cria índice em muitos bancos, o que causa um problema clássico: apagar ou alterar a chave da tabela pai obriga o banco a varrer a tabela filha inteira para conferir as referências. Por isso, a boa prática é criar índice em toda coluna de chave estrangeira usada em junções.

Teste seu entendimento

Três perguntas de fundamentos.

1. Qual propriedade a integridade referencial garante?

É a regra que impede referências pendentes (órfãs). As outras opções são a integridade de entidade e a de domínio.

2. Por que o SQLite aceitou o pedido 10 para o cliente 99, que não existe?

No SQLite, a verificação depende de cada conexão. A declaração REFERENCES existe, mas só é aplicada com o PRAGMA ligado.

3. Um atributo multivalorado, como vários telefones por cliente, deve ser traduzido como:

Colunas numeradas limitam a quantidade e espalham NULL. Lista separada por vírgulas quebra a atomicidade do valor, e é impossível consultar um telefone específico com segurança. Tabela própria é a solução relacional.
