De muitas linhas para um número

“Quanto vendemos por mês?”, “Qual o ticket médio?”, “Quantos pedidos cada status tem?”. Essas perguntas não querem linhas: querem resumos. As funções de agregação recebem um conjunto de valores e devolvem um só: COUNT, SUM, AVG, MIN e MAX.

Com GROUP BY, o conjunto é dividido em grupos e a agregação roda em cada um.

Animação · GROUP BY separa linhas em baldes

As funções e o tratamento de NULL

FunçãoResultadoAtenção com NULL
COUNT(*)Número de linhasConta todas, inclusive com NULL
COUNT(coluna)Número de valores não nulosIgnora NULL
COUNT(DISTINCT coluna)Valores distintos não nulosIgnora NULL
SUM(coluna)SomaIgnora NULL; sem linhas, devolve NULL
AVG(coluna)MédiaIgnora NULL: a média é sobre os valores presentes
MIN / MAXMenor e maiorIgnoram NULL
 
SELECT COUNT(*)          AS clientes,
       COUNT(email)     AS com_email,
       COUNT(DISTINCT cidade) AS cidades,
       ROUND(AVG(preco), 2) AS preco_medio
FROM clientes, produtos;

Este exemplo mistura duas tabelas sem condição, de propósito, só para mostrar as funções. Repare que ele não é a forma certa de combinar tabelas: isso é tema do tópico 10. Aqui, o importante é ver que COUNT(email) é menor que o total de clientes, porque um deles não tem e-mail.

GROUP BY: uma linha por grupo

Tudo que aparece no SELECT, fora das funções de agregação, precisa estar no GROUP BY. Cada valor distinto das colunas de agrupamento vira uma linha do resultado. 

SELECT status, COUNT(*) AS quantidade
FROM pedidos
GROUP BY status
ORDER BY quantidade DESC, status;
Erro comum: SELECT nome, COUNT(*) FROM clientes; não tem GROUP BY. O padrão exige que nome seja agrupado ou agregado. O SQLite aceita e devolve um valor arbitrário de nome, o que mascara o erro. Não confie nessa tolerância.

WHERE filtra linhas; HAVING filtra grupos

WHERE decide quais linhas entram no agrupamento. HAVING decide quais grupos saem no resultado, depois que as agregações já foram calculadas. Por isso, só o HAVING pode usar SUM, COUNT etc. como condição. 

-- clientes cujo total gasto (sem cancelados) passa de 500
SELECT p.id_cliente,
       SUM(i.quantidade * i.preco_unitario) AS total
FROM pedidos p
JOIN itens_pedido i ON i.id_pedido = p.id_pedido
WHERE p.status <> 'cancelado'
GROUP BY p.id_cliente
HAVING SUM(i.quantidade * i.preco_unitario) > 500
ORDER BY total DESC;

O WHERE remove os pedidos cancelados antes de somar. O HAVING remove clientes com total de 500 ou menos depois de somar. Trocar um pelo outro produz resultados errados ou erros de sintaxe.

A ordem lógica de execução

Uma consulta é escrita em uma ordem e avaliada em outra. Conhecer a ordem explica quase todos os erros de “coluna não existe”.

FROM / JOIN
WHERE
GROUP BY
HAVING
SELECT
ORDER BY
LIMIT

Consequências: o SELECT ainda não criou os aliases quando o WHERE roda, então o WHERE não pode usá-los (o SQLite tolera; o padrão não). O HAVING vê as agregações, mas não as colunas que não foram agrupadas. O ORDER BY é o último a ver os aliases do SELECT.

Como funciona de verdade

Para agrupar, o banco precisa juntar as linhas de mesmo valor. Há duas estratégias clássicas:

  • Agregação por hash. Uma tabela em memória mapeia cada valor de grupo ao acumulador (soma, contagem). Uma passada pela entrada basta. É rápida quando os grupos cabem na memória.
  • Agregação por ordenação. Ordena as linhas pelo GROUP BY e acumula enquanto o valor não muda. Mais lenta, mas não depende de memória para os grupos, e o resultado já sai ordenado.

O SQLite usa principalmente a segunda, e por isso um índice sobre a coluna do GROUP BY pode eliminar a ordenação. Em PostgreSQL, o planejador escolhe entre as duas conforme as estimativas. Você verá o plano escolhido no tópico 14.

Um detalhe: para o GROUP BY, todos os NULLs formam um único grupo, mesmo que a comparação NULL = NULL seja desconhecida. É o único lugar em que o SQL trata NULLs como iguais.

Exemplo: produtos e preço médio por categoria

Uma pergunta clássica de relatório. Usamos LEFT JOIN para manter a categoria Esportes, que não tem produtos: ela aparece com zero, em vez de sumir. Essa escolha de junção é o tema do tópico 10. 

SELECT c.nome AS categoria,
       COUNT(p.id_produto)       AS produtos,
       ROUND(AVG(p.preco), 2)    AS preco_medio
FROM categorias c
LEFT JOIN produtos p ON p.id_categoria = c.id_categoria
GROUP BY c.id_categoria, c.nome
ORDER BY preco_medio DESC;

Experimente

Altere o exemplo e execute. Cada execução parte de um banco novo, então você pode quebrar à vontade.

SELECT cidade, COUNT(*) AS clientes FROM clientes GROUP BY cidade HAVING COUNT(*) >= 1 ORDER BY clientes DESC, cidade;

Problemas para resolver

Escreva antes de olhar a solução. Os resultados são calculados ao vivo.

Problema 1 · Pedidos por status

Quantos pedidos existem em cada status? Mostre apenas os status com mais de um pedido.

Ver solução 
SELECT status, COUNT(*) AS quantidade
FROM pedidos
GROUP BY status
HAVING COUNT(*) > 1
ORDER BY quantidade DESC, status;

Três status têm mais de um pedido: “enviado”, “pago” e “pendente”. O filtro de grupos é HAVING, porque depende de COUNT.

Problema 2 · Ticket médio por cliente

Para cada cliente com pelo menos um pedido não cancelado, calcule o valor médio por pedido. Use o total de cada pedido como base (quantidade × preço unitário, somado por pedido), depois a média por cliente.

Ver solução 
SELECT t.id_cliente,
       ROUND(AVG(t.total_pedido), 2) AS ticket_medio
FROM (
  SELECT p.id_pedido, p.id_cliente,
         SUM(i.quantidade * i.preco_unitario) AS total_pedido
  FROM pedidos p
  JOIN itens_pedido i ON i.id_pedido = p.id_pedido
  WHERE p.status <> 'cancelado'
  GROUP BY p.id_pedido, p.id_cliente
) t
GROUP BY t.id_cliente
ORDER BY ticket_medio DESC;

São duas agregações em níveis diferentes: primeiro soma por pedido (dentro da subconsulta), depois tira a média por cliente. Fazer AVG direto sobre os itens daria a média por item, não por pedido. Subconsultas são tema do tópico 11.

Problema 3 · O erro do GROUP BY

A consulta a seguir está errada segundo o padrão SQL, mesmo rodando no SQLite. Por quê? Corrija-a.

SELECT cidade, nome, COUNT(*) FROM clientes GROUP BY cidade;
Ver solução 
SELECT cidade, COUNT(*) AS clientes
FROM clientes
GROUP BY cidade
ORDER BY clientes DESC, cidade;

A coluna nome não é agregada nem agrupada: dentro de uma cidade há vários nomes, e o padrão não sabe qual mostrar. Ou se remove nome, ou se agrega (GROUP_CONCAT(nome), por exemplo).

Aprofundamento e prática

Tabela dinâmica com CASE

Relatórios costumam pedir um pivô: uma linha por cidade e uma coluna por status. SQL não tem um comando PIVOT universal, mas a combinação de agregação com CASE faz o mesmo. Cada coluna soma apenas as linhas que atendem à sua condição. 

SELECT c.cidade,
       SUM(CASE WHEN p.status = 'pago'     THEN 1 ELSE 0 END) AS pagos,
       SUM(CASE WHEN p.status = 'enviado'  THEN 1 ELSE 0 END) AS enviados,
       SUM(CASE WHEN p.status = 'pendente' THEN 1 ELSE 0 END) AS pendentes,
       COUNT(*) AS total
FROM pedidos p
JOIN clientes c ON c.id_cliente = p.id_cliente
GROUP BY c.cidade
ORDER BY total DESC, c.cidade;

Por que SUM e não COUNT dentro do CASE? Porque COUNT conta valores não nulos, e um CASE sem ELSE devolveria NULL para as linhas de outros status, contando-as indevidamente. Com ELSE 0 e SUM, o cálculo fica exato.

Juntar valores de um grupo em um texto

GROUP_CONCAT (SQLite e MySQL) e STRING_AGG (PostgreSQL) concatenam valores de um grupo. Útil para listar, por pedido, os produtos envolvidos. A ordem dos valores dentro do grupo não é garantida pelo padrão: se importar, o ideal é ordenar numa subconsulta ou usar a sintaxe com ORDER BY do banco. 

SELECT id_pedido, GROUP_CONCAT(id_produto, ', ') AS produtos
FROM itens_pedido
GROUP BY id_pedido
ORDER BY id_pedido;

LEFT JOIN e COUNT: o cuidado com o que se conta

Ao agregar depois de um LEFT JOIN, COUNT(*) conta a linha de todo cliente, mesmo sem pedido, porque a linha existe (com NULLs). Para contar apenas pedidos reais, conte a coluna da tabela da direita: COUNT(p.id_pedido) ignora os NULLs. A diferença aparece na própria saída abaixo. 

SELECT c.nome,
       COUNT(*)          AS linhas,
       COUNT(p.id_pedido) AS pedidos
FROM clientes c
LEFT JOIN pedidos p ON p.id_cliente = c.id_cliente
GROUP BY c.id_cliente, c.nome
ORDER BY c.nome
LIMIT 3;

Roteiro para escrever um relatório

  1. Defina a granularidade: uma linha por pedido? por cliente? por mês? Tudo que vem depois depende disso.
  2. Escreva o FROM e os JOINs sem agregar, e confira se a quantidade de linhas faz sentido.
  3. Aplique os filtros de linha (WHERE), como período e status válidos.
  4. Agregue com GROUP BY na granularidade do passo 1.
  5. Filtre grupos com HAVING, se for o caso, e ordene a saída.
  6. Compare o total com uma consulta independente. Diferenças quase sempre vêm de um JOIN que duplica linhas.

Problemas do mundo real para discutir

Casos típicos, descritos de forma genérica. Discuta em grupo antes de olhar as pistas.

Caso 1 · O painel que conta pedidos em dobro

Um dashboard de vendas mostra “pedidos do mês” e o número parece alto demais. A consulta junta pedidos com itens e conta as linhas do resultado. Um pedido com três produtos vira três pedidos no painel. A diretoria toma uma decisão de estoque com base nesse número.

Para discutir:

  • Em qual granularidade a métrica “pedidos” deve ser contada? O que muda ao juntar com itens?
  • Como você testaria, com uma consulta independente, se o número do painel está certo?
-- a contagem errada, depois da junção com os itens
SELECT COUNT(*) AS pedidos_contados_errado
FROM pedidos p
JOIN itens_pedido i ON i.id_pedido = p.id_pedido;

-- a contagem certa, na granularidade do pedido
SELECT COUNT(*) AS pedidos_reais FROM pedidos;

Pista: a diferença entre as duas consultas é exatamente o número de itens extras. Conferir uma métrica com uma consulta de outra granularidade é uma das verificações mais úteis em análise de dados.

Caso 2 · A média que esconde o problema

Um relatório mostra o “tempo médio de entrega” de 3 dias, e a diretoria considera o serviço bom. Ao abrir os dados, descobre-se que 5% dos pedidos levam mais de 30 dias e puxam a média para cima, enquanto a maioria chega no prazo. Nenhum cliente típico vive a média.

Para discutir:

  • Que outras medidas (mediana, percentis, contagem de atrasos) revelam o que a média esconde?
  • Quais decisões mudariam se o relatório mostrasse a distribuição, e não apenas o centro?

Pista: a média é sensível a valores extremos. Em análise de negócios, combine-a com contagens por faixa (usando CASE, como na seção de pivô) e com a parcela de casos fora do padrão.

Teste seu entendimento

Três perguntas de fundamentos.

1. Qual é a diferença entre COUNT(*) e COUNT(email)?

Funções de agregação ignoram NULL, exceto COUNT(*), que conta linhas. Por isso, em clientes, COUNT(email) é 6 e COUNT(*) é 7.

2. Para mostrar só os grupos com soma acima de 500, onde a condição vai?

Na ordem lógica, o HAVING roda depois do GROUP BY, quando a soma já existe. O WHERE roda antes, quando ela ainda não foi calculada.

3. Quantos grupos o GROUP BY cria para as linhas em que cidade é NULL?

Para agrupamento, NULLs são tratados como iguais e formam um único grupo. Este é um caso em que NULL se comporta diferente do WHERE.
