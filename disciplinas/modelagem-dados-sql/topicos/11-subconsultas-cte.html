Perguntas que dependem de outras respostas

“Quais produtos custam mais que a média?” exige duas respostas: primeiro a média, depois os produtos. Uma subconsulta é um SELECT dentro de outro SELECT, que resolve a parte interna e a usa como valor, lista ou conjunto. Uma CTE (cláusula WITH) dá nome a uma etapa intermediária, para que a consulta possa ser lida de cima para baixo.

Animação · a subconsulta resolve primeiro

Os quatro formatos

Escalar (um valor)

Devolve uma linha e uma coluna. Pode ficar em WHERE, SELECT ou HAVING. Se devolver mais de uma linha, dá erro.

Lista (IN)

Devolve uma coluna. x IN (SELECT …) testa pertinência.

Existência (EXISTS)

Verdadeiro se a subconsulta devolve pelo menos uma linha. Não importa o conteúdo.

Tabela derivada (FROM)

Uma subconsulta no FROM, tratada como tabela. Precisa de um alias.

-- escalar: produtos mais caros que a média
SELECT nome, preco
FROM produtos
WHERE preco > (SELECT AVG(preco) FROM produtos);
-- lista: clientes que já compraram alguma coisa
SELECT nome
FROM clientes
WHERE id_cliente IN (SELECT id_cliente FROM pedidos);

Correlacionada: a subconsulta olha para a linha de fora

Numa subconsulta correlacionada, a parte interna referencia uma coluna da consulta de fora. Ela é avaliada para cada linha externa. Isso é poderoso, e também custa caro se a tabela for grande. 

-- clientes com ao menos um pedido, usando EXISTS
SELECT c.nome
FROM clientes c
WHERE EXISTS (
  SELECT 1
  FROM pedidos p
  WHERE p.id_cliente = c.id_cliente
);

O c.id_cliente dentro da subconsulta vem da linha de clientes que está sendo testada. EXISTS para ao achar a primeira linha, então não precisa contar tudo. O SELECT 1 é só convenção: o conteúdo não importa.

NOT EXISTS é o anti-join. “Clientes sem pedidos” também pode ser escrito com NOT EXISTS. Ele é mais seguro que NOT IN quando a subconsulta pode devolver NULL, como você verá na seção “Como funciona de verdade”.

CTE: dar nome às etapas

A cláusula WITH define uma ou mais expressões de tabela comuns. Cada uma é uma tabela temporária que existe só durante a consulta. O resultado é o mesmo de uma subconsulta aninhada, mas a leitura flui de cima para baixo. 

WITH total_por_pedido AS (
  SELECT id_pedido, SUM(quantidade * preco_unitario) AS total
  FROM itens_pedido
  GROUP BY id_pedido
),
pedidos_grandes AS (
  SELECT t.id_pedido, t.total, p.id_cliente
  FROM total_por_pedido t
  JOIN pedidos p ON p.id_pedido = t.id_pedido
  WHERE t.total > 500
)
SELECT c.nome, g.id_pedido, g.total
FROM pedidos_grandes g
JOIN clientes c ON c.id_cliente = g.id_cliente
ORDER BY g.total DESC;

Cada CTE é uma etapa que se explica sozinha. Ler a consulta é seguir o raciocínio. Em muitos bancos, uma CTE pode ser usada mais de uma vez no mesmo SELECT; sem a cláusula, a mesma lógica precisaria ser repetida.

Como funciona de verdade

  • Subconsulta não correlacionada é calculada uma vez. O banco executa a média, obtém um valor e o usa na consulta externa. O custo é o de uma consulta a mais.
  • Correlacionada é reavaliada por linha (na teoria). O otimizador costuma transformá-la em um JOIN ou um semi-join, então o custo real depende do plano. Por isso o tópico 14 manda verificar com EXPLAIN.
  • CTE nem sempre é materializada. Em PostgreSQL 12+, uma CTE simples pode ser incorporada à consulta principal, como uma subconsulta. Em outros casos, o banco calcula o resultado uma vez e guarda. Não conte com um comportamento: confira o plano.
  • A armadilha do NOT IN com NULL. x NOT IN (lista) é verdadeiro somente se x for diferente de todos os valores da lista. Se a lista tiver um NULL, a comparação com ele é desconhecida, e nenhuma linha passa. NOT EXISTS não tem esse problema.
-- deveria listar quem não tem pedido, mas devolve vazio:
SELECT nome FROM clientes
WHERE id_cliente NOT IN (SELECT id_cliente FROM pedidos WHERE id_cliente IS NOT NULL
                         UNION ALL SELECT NULL);

O bloco acima injeta um NULL na lista de propósito para mostrar o efeito: nenhum cliente é devolvido. Com NOT EXISTS, o resultado seria Helena, como esperado.

Exemplo clássico: quem gasta mais que a média

A pergunta combina agregação, junção e subconsulta. Calcula-se o total por cliente, depois a média desses totais, e só então se filtra. Cada etapa vira uma CTE. 

WITH gasto AS (
  SELECT p.id_cliente, SUM(i.quantidade * i.preco_unitario) AS total
  FROM pedidos p
  JOIN itens_pedido i ON i.id_pedido = p.id_pedido
  WHERE p.status <> 'cancelado'
  GROUP BY p.id_cliente
)
SELECT c.nome, ROUND(g.total, 2) AS total
FROM gasto g
JOIN clientes c ON c.id_cliente = g.id_cliente
WHERE g.total > (SELECT AVG(total) FROM gasto)
ORDER BY total DESC;

Experimente

Clientes sem nenhum pedido pago. Troque 'pago' por outro status e veja a lista mudar.

SELECT c.nome FROM clientes c WHERE NOT EXISTS ( SELECT 1 FROM pedidos p WHERE p.id_cliente = c.id_cliente AND p.status = 'pago' );

Problemas para resolver

Escreva com subconsulta ou CTE antes de olhar a solução.

Problema 1 · Produtos nunca vendidos, sem JOIN

Liste os produtos que nunca aparecem em um item de pedido, usando NOT EXISTS.

Ver solução 
SELECT pr.nome
FROM produtos pr
WHERE NOT EXISTS (
  SELECT 1 FROM itens_pedido i WHERE i.id_produto = pr.id_produto
);

Equivalente à anti-junção do tópico 10, mas expresso como “não existe item deste produto”. Ambas são corretas aqui; NOT EXISTS é mais seguro quando colunas podem ser NULL.

Problema 2 · Pedido com mais itens

Encontre o pedido com a maior quantidade total de unidades (somando as quantidades dos itens). Mostre o id e a quantidade. Se houver empate, mostre todos.

Ver solução 
WITH unidades AS (
  SELECT id_pedido, SUM(quantidade) AS total
  FROM itens_pedido
  GROUP BY id_pedido
)
SELECT id_pedido, total
FROM unidades
WHERE total = (SELECT MAX(total) FROM unidades);

A CTE calcula as unidades por pedido; a subconsulta escalar encontra o máximo; o WHERE mantém todos os pedidos que o atingem, então empates aparecem juntos.

Problema 3 · Cidades com mais de um cliente comprador

Liste as cidades que têm mais de um cliente que já fez algum pedido. Use EXISTS dentro de uma consulta agrupada, ou uma CTE com os clientes que compraram.

Ver solução 
WITH compradores AS (
  SELECT c.id_cliente, c.cidade
  FROM clientes c
  WHERE EXISTS (SELECT 1 FROM pedidos p WHERE p.id_cliente = c.id_cliente)
)
SELECT cidade, COUNT(*) AS compradores
FROM compradores
GROUP BY cidade
HAVING COUNT(*) > 1;

Em São Paulo há dois compradores (Ana e Diego), e em Curitiba só Elisa, porque Helena não comprou. Por isso só São Paulo aparece.

Aprofundamento e prática

Divisão relacional: “comprou todos os livros”

Uma das perguntas mais difíceis de escrever em SQL é a divisão: “quais clientes compraram todos os produtos de uma categoria?”. A palavra “todos” pede uma dupla negação. Lê-se assim: não existe um produto da categoria que o cliente não tenha comprado.

Traduzindo para o SQL, usamos dois NOT EXISTS aninhados. O externo percorre os clientes; o do meio percorre os livros; o interno pergunta se o cliente comprou aquele livro. Se alguma dessas perguntas falhar, o cliente é descartado. 

SELECT c.nome
FROM clientes c
WHERE NOT EXISTS (
  SELECT 1
  FROM produtos pr
  WHERE pr.id_categoria = 2                      -- categoria Livros
    AND NOT EXISTS (
      SELECT 1
      FROM pedidos p
      JOIN itens_pedido i ON i.id_pedido = p.id_pedido
      WHERE p.id_cliente = c.id_cliente
        AND i.id_produto = pr.id_produto
    )
);

Só Bruno comprou os dois livros (“SQL Essencial” e “Algoritmos”). Se você tiver dificuldade em ler a consulta, teste cada nível isoladamente: primeiro a lista dos livros, depois o que cada cliente comprou. A divisão é sempre mais clara quando montada em etapas, com CTEs.

Subconsulta no SELECT: um valor por linha

Uma subconsulta escalar também pode aparecer na lista de colunas, produzindo um valor para cada linha da consulta de fora. É cômodo, mas cada uma é executada (ou planejada como junção) para cada linha, então use com moderação em tabelas grandes. 

SELECT c.nome,
       (SELECT COUNT(*) FROM pedidos p WHERE p.id_cliente = c.id_cliente) AS qtd_pedidos
FROM clientes c
ORDER BY qtd_pedidos DESC, c.nome;

CTE ou subconsulta? Um critério prático

Prefira CTE quando
  • A mesma etapa é usada mais de uma vez.
  • A consulta tem três ou mais níveis de aninhamento.
  • Você quer depurar cada etapa isoladamente (basta rodar o SELECT do WITH).
  • Há uma recursão (só CTE faz isso).
Prefira subconsulta quando
  • É um teste simples de pertinência ou existência (IN, EXISTS).
  • Um valor único precisa ser comparado (um escalar).
  • A consulta é curta e a leitura é imediata.
  • Você precisa de uma garantia de otimização que só o planejador do seu banco dá (confira o plano).

Problemas do mundo real para discutir

Casos típicos, descritos de forma genérica. Discuta em grupo antes de olhar as pistas.

Caso 1 · A lista de exclusão que zerou o envio

Uma equipe monta a lista de clientes que não devem receber e-mail usando NOT IN sobre uma subconsulta. Um registro da lista veio com valor NULL por erro de importação. Resultado: a campanha tem zero destinatários, e ninguém percebe até o fim do dia, porque a consulta não dá erro.

Para discutir:

  • Por que um único NULL na subconsulta esvazia todo o resultado? Explique com a lógica de três valores.
  • Como você escreveria a regra para não depender de a lista estar limpa? Qual forma é mais segura?
-- com o NULL na lista: nenhum cliente passa
SELECT COUNT(*) AS destinatarios_com_null
FROM clientes
WHERE id_cliente NOT IN (
  SELECT id_cliente FROM pedidos WHERE status = 'cancelado'
  UNION ALL SELECT NULL
);

-- a forma segura: NOT EXISTS não é afetado pelo NULL
SELECT COUNT(*) AS destinatarios_seguros
FROM clientes c
WHERE NOT EXISTS (
  SELECT 1 FROM pedidos p
  WHERE p.id_cliente = c.id_cliente AND p.status = 'cancelado'
);

Pista: o resultado silencioso é o pior tipo de bug. Testes com dados reais (que costumam ter NULL) e checagens de contagem antes do envio pegariam o problema.

Caso 2 · A consulta que ninguém consegue manter

Um relatório financeiro tem seis subconsultas aninhadas, escritas em épocas diferentes por pessoas diferentes. Quando um número diverge, ninguém consegue isolar qual parte está errada, porque nenhuma etapa tem nome nem pode ser executada sozinha.

Para discutir:

  • Como reescrever o relatório com CTEs para que cada etapa seja testável?
  • Qual é o custo de manutenção de uma consulta que ninguém entende, comparado ao custo de algumas linhas a mais de código?

Pista: escreva cada CTE e rode-a isolada, conferindo o total de linhas e uma soma de controle antes de seguir para a próxima etapa.

Teste seu entendimento

Três perguntas de fundamentos.

1. Uma subconsulta escalar que devolve mais de uma linha causa o quê?

Um valor escalar não pode ser ambíguo. Se a subconsulta devolver mais de uma linha, o banco recusa a consulta. Para listas, use IN.

2. Por que NOT IN pode devolver vazio quando a lista tem NULL?

Para o NOT IN ser verdadeiro, x precisa ser diferente de todos os valores, inclusive do NULL. Essa comparação é desconhecida, e nenhuma linha passa. NOT EXISTS evita isso.

3. Qual é a principal vantagem de uma CTE sobre uma subconsulta aninhada?

CTE não garante desempenho: depende do plano. Seu valor principal é organizar o raciocínio. E ela é temporária, existindo só durante a consulta.
