Quantos níveis tem o organograma?

Para listar todos os subordinados de Marta, de qualquer nível, você precisaria de um JOIN para cada nível da hierarquia. Com três níveis, dá para escrever. Com profundidade desconhecida, não dá. Quem garante isso é a consulta recursiva: uma CTE que se referencia a si mesma até não encontrar mais nada.

Animação · a iteração até o ponto fixo

Âncora e recursão: duas partes obrigatórias

Toda CTE recursiva tem duas partes unidas por UNION ALL (ou UNION):

Âncora

A parte que não se referencia a si mesma. Define o conjunto inicial: o presidente, a raiz da árvore.

Recursão

A parte que referencia o nome da própria CTE. Cada rodada encontra os “filhos” das linhas da rodada anterior.

-- a árvore inteira, a partir de Marta (id 1), com o nível de cada pessoa
WITH RECURSIVE equipe(id_funcionario, nome, nivel) AS (
  SELECT id_funcionario, nome, 0
  FROM funcionarios
  WHERE id_funcionario = 1                         -- âncora
  UNION ALL
  SELECT f.id_funcionario, f.nome, e.nivel + 1
  FROM funcionarios f
  JOIN equipe e ON f.id_supervisor = e.id_funcionario  -- recursão
)
SELECT nivel, nome FROM equipe ORDER BY nivel, nome;

Carregando o caminho e gerando sequências

Como a recursão carrega colunas de uma rodada para a seguinte, é possível acumular informação: por exemplo, o caminho completo da raiz até cada funcionário. 

WITH RECURSIVE caminho(id_funcionario, nome, trilha) AS (
  SELECT id_funcionario, nome, nome
  FROM funcionarios WHERE id_supervisor IS NULL
  UNION ALL
  SELECT f.id_funcionario, f.nome, c.trilha || ' > ' || f.nome
  FROM funcionarios f
  JOIN caminho c ON f.id_supervisor = c.id_funcionario
)
SELECT trilha FROM caminho ORDER BY trilha;

Recursão também gera dados. Uma sequência de 1 a 5 é útil para preencher lacunas num relatório (por exemplo, meses sem vendas): 

WITH RECURSIVE n(x) AS (
  SELECT 1
  UNION ALL
  SELECT x + 1 FROM n WHERE x < 5
)
SELECT x FROM n;

Quando a recursão não termina

Numa árvore, a recursão sempre termina: cada passo desce um nível, e as folhas não têm filhos. Num grafo com ciclos (A indica B, B indica A), a recursão pode girar para sempre. Toda consulta recursiva precisa de uma condição de parada garantida.

UNION ALL × UNION

UNION ALL mantém duplicatas e é mais rápido. UNION remove linhas repetidas a cada rodada, e isso faz a recursão terminar em grafos com ciclos, porque nenhuma linha nova aparece. Em árvores, use UNION ALL.

Limite explícito

Uma condição como WHERE nivel < 10 é a rede de segurança mais simples. Em produção, combine-a com uma coluna de caminho para detectar ciclos (“este id já está na trilha?”).

Recursão sem parada é um laço infinito disfarçado. Um UNION ALL sobre um ciclo nunca produz uma linha vazia. O banco pode consumir memória até falhar, ou o SQLite pode parar por limite de profundidade. Nunca execute uma consulta recursiva em dados de origem desconhecida sem limite.

Como funciona de verdade

O SGBD avalia a consulta recursiva por iteração de ponto fixo, com duas tabelas de trabalho:

  1. Executa a âncora e guarda o resultado num conjunto de trabalho (working table). Esse conjunto também é o resultado parcial.
  2. Executa a parte recursiva, substituindo a referência ao nome da CTE pelo conjunto de trabalho atual. As linhas novas formam o próximo conjunto de trabalho e são acrescentadas ao resultado.
  3. Repete o passo 2 até que a parte recursiva não produza nenhuma linha nova.

Cada iteração corresponde a um nível da árvore. A animação acima mostra exatamente isso. Por ser uma iteração de conjuntos, a recursão é mais previsível que um laço programado, mas não é gratuita: cada rodada é um passo do plano de execução.

Em PostgreSQL, a mesma lógica existe, com a diferença de que o banco pode usar um índice sobre a coluna de supervisor em cada rodada. Sem esse índice, cada iteração varre a tabela inteira. O tópico 14 mostra como verificar isso.

Exemplo clássico: subordinados diretos e indiretos

Para cada gerente, quantas pessoas estão abaixo dele em toda a cadeia? A recursão gera os pares (gerente, subordinado) e a agregação conta. 

WITH RECURSIVE abaixo(gerente, subordinado) AS (
  SELECT id_supervisor, id_funcionario
  FROM funcionarios
  WHERE id_supervisor IS NOT NULL
  UNION
  SELECT a.gerente, f.id_funcionario
  FROM abaixo a
  JOIN funcionarios f ON f.id_supervisor = a.subordinado
)
SELECT f.nome, COUNT(a.subordinado) AS total_abaixo
FROM funcionarios f
JOIN abaixo a ON a.gerente = f.id_funcionario
GROUP BY f.id_funcionario, f.nome
ORDER BY total_abaixo DESC, f.nome;

Este exemplo usa UNION (não ALL) para remover pares repetidos: um mesmo par aparece por mais de um caminho apenas se a estrutura tiver ciclos ou múltiplos caminhos. Repare que a diretora, Marta, aparece com o total de toda a equipe.

Experimente

Uma progressão geométrica gerada por recursão. Troque a condição de parada ou a multiplicação e execute.

WITH RECURSIVE potencias(x) AS ( SELECT 1 UNION ALL SELECT x * 2 FROM potencias WHERE x < 64 ) SELECT x FROM potencias;

Problemas para resolver

Desenhe a árvore no papel antes de rodar.

Problema 1 · Equipe de Roberto

Liste todas as pessoas que estão abaixo de Roberto Alves (id 2), em qualquer nível, com o nível relativo a ele.

Ver solução 
WITH RECURSIVE equipe(id_funcionario, nome, nivel) AS (
  SELECT id_funcionario, nome, 0 FROM funcionarios WHERE id_funcionario = 2
  UNION ALL
  SELECT f.id_funcionario, f.nome, e.nivel + 1
  FROM funcionarios f
  JOIN equipe e ON f.id_supervisor = e.id_funcionario
)
SELECT nivel, nome FROM equipe ORDER BY nivel, nome;

O resultado mostra Roberto no nível 0, Tiago e Juliana no nível 1 e nenhuma outra pessoa. Lúcia e Paulo estão na outra ramificação, sob Marta, e não aparecem.

Problema 2 · Ancestrais de um funcionário

Para a Renata Lopes (id 7), liste todos os seus superiores, até a diretora.

Ver solução 
WITH RECURSIVE acima(id_funcionario, nome, id_supervisor) AS (
  SELECT id_funcionario, nome, id_supervisor FROM funcionarios WHERE id_funcionario = 7
  UNION ALL
  SELECT f.id_funcionario, f.nome, f.id_supervisor
  FROM funcionarios f
  JOIN acima a ON f.id_funcionario = a.id_supervisor
)
SELECT nome FROM acima;

A recursão sobe pela coluna de supervisor. A parada é natural: a diretora tem id_supervisor NULL, então o JOIN não encontra mais nada. Renata aparece com Paulo, Lúcia, Marta.

Problema 3 · Calendário de datas

Gere as datas de 1 a 7 de outubro de 2024, usando recursão e a função date().

Ver solução 
WITH RECURSIVE dias(dia) AS (
  SELECT date('2024-10-01')
  UNION ALL
  SELECT date(dia, '+1 day') FROM dias WHERE dia < date('2024-10-07')
)
SELECT dia FROM dias;

Esse calendário é útil para mostrar dias sem vendas: basta um LEFT JOIN da sequência com a tabela de pedidos.

Aprofundamento e prática

Grafos: alcance e fecho transitivo

Hierarquias são árvores, mas muitas estruturas reais são grafos: rotas de transporte, rede de indicações, dependências entre pacotes. Nelas, a pergunta típica é “a partir deste ponto, o que consigo alcançar?”. Isso se chama fecho transitivo, e a recursão responde a ele.

Num grafo com ciclos, o UNION (sem ALL) é essencial: ele descarta cidades já encontradas, e a recursão termina quando nada novo aparece. A consulta abaixo parte de São Paulo e descobre todas as cidades alcançáveis, mesmo as que só são alcançadas pelo caminho de volta. 

CREATE TABLE rota (origem TEXT, destino TEXT);
INSERT INTO rota VALUES ('SP','RJ'), ('RJ','BH'), ('BH','SP'), ('SP','CWB');

WITH RECURSIVE alcance(cidade) AS (
  SELECT 'SP'
  UNION
  SELECT r.destino
  FROM rota r
  JOIN alcance a ON r.origem = a.cidade
)
SELECT cidade FROM alcance ORDER BY cidade;

O ciclo SP → RJ → BH → SP não gera linhas infinitas. Com UNION ALL, a mesma consulta nunca terminaria.

Guardar o caminho e cortar ciclos

Às vezes importa como chegar a um lugar, não só se ele é alcançável. Acumulamos o caminho numa coluna de texto e impedimos que a recursão revisite uma cidade já presente nele. Também limitamos a profundidade, como rede de segurança. A função instr procura um texto dentro de outro; em produção, use separadores delimitados para não confundir “SP” com “SPO”. 

CREATE TABLE rota (origem TEXT, destino TEXT);
INSERT INTO rota VALUES ('SP','RJ'), ('RJ','BH'), ('BH','SP'), ('SP','CWB');

WITH RECURSIVE caminho(atual, trilha, profundidade) AS (
  SELECT 'SP', 'SP', 0
  UNION ALL
  SELECT r.destino,
         c.trilha || ' > ' || r.destino,
         c.profundidade + 1
  FROM rota r
  JOIN caminho c ON r.origem = c.atual
  WHERE c.profundidade < 4
    AND instr(c.trilha, r.destino) = 0
)
SELECT trilha FROM caminho WHERE atual = 'CWB' ORDER BY trilha;

Só o caminho direto SP → CWB aparece. O caminho SP → RJ → BH → SP foi cortado, porque SP já estava na trilha.

Quando a recursão em SQL deixa de ser a ferramenta certa

  • Grafos muito grandes e buscas de caminho mínimo: algoritmos como Dijkstra (tópico de estrutura de dados) são mais eficientes que a iteração de conjuntos do SQL.
  • Profundidade sem limite conhecido: cada nível é uma rodada completa, e o custo cresce com o número de caminhos, não só de nós.
  • Consultas repetidas em alta frequência: considere materializar o fecho (uma tabela de ancestrais, atualizada na escrita) em vez de recalcular a cada leitura.

Problemas do mundo real para discutir

Casos típicos, descritos de forma genérica. Discuta em grupo antes de olhar as pistas.

Caso 1 · O organograma com um ciclo

Um erro de cadastro faz a diretora aparecer como subordinada de uma analista que, por sua vez, reporta a ela, por meio de outros níveis. A consulta recursiva de “todos os subordinados” com UNION ALL nunca termina: o banco continua gerando linhas e o servidor esgota a memória. Com UNION, a mesma consulta termina, porque nenhuma linha nova aparece.

Para discutir:

  • Por que um ciclo em dados de cadastro é mais comum do que parece? Quais validações impediriam esse erro?
  • Se a consulta for executada num sistema que não permite UNION (apenas UNION ALL), qual proteção adicional é necessária?
-- cadastro errado: a diretora (1) passa a reportar a Renata (7), que reporta a ela por outro caminho
UPDATE funcionarios SET id_supervisor = 7 WHERE id_funcionario = 1;

-- com UNION, a recursão termina mesmo com o ciclo
WITH RECURSIVE sub(id) AS (
  SELECT 1
  UNION
  SELECT f.id_funcionario
  FROM funcionarios f
  JOIN sub s ON f.id_supervisor = s.id
)
SELECT COUNT(*) AS alcancados FROM sub;

Pista: a validação deve ser feita na escrita (uma verificação de ciclo antes de gravar o supervisor) e a consulta deve ter um limite de profundidade ou UNION, como rede de segurança.

Caso 2 · A rede de indicações que virou fraude

Um programa de indicação paga um bônus a quem indica novos clientes, e o bônus cresce a cada nível da rede. Um grupo de contas cria indicações em círculo (A indica B, B indica C, C indica A) e passa a receber bônus repetidamente. Uma análise com recursão, que conta quantas pessoas estão “abaixo” de cada conta, revela o anel.

Para discutir:

  • Como uma consulta recursiva ajudaria a detectar o padrão de círculos? Que atributo do caminho precisaria ser guardado?
  • Quais limites operacionais (profundidade, frequência de bônus, verificação humana) devem existir num programa desses?

Pista: a consulta do tópico, que guarda a trilha e corta quando o destino já aparece nela, é exatamente o padrão de detecção de ciclo.

Teste seu entendimento

Três perguntas de fundamentos.

1. Qual é o papel da parte âncora numa CTE recursiva?

A âncora é o ponto de partida da iteração. Sem ela, a recursão não teria por onde começar.

2. Por que usar UNION em vez de UNION ALL num grafo com ciclos?

Num ciclo, UNION ALL acrescenta sempre as mesmas linhas e nunca para. UNION impede repetição, e a iteração termina quando nada novo aparece.

3. Na avaliação de uma CTE recursiva, o que cada iteração representa?

Cada rodada da recursão expande o conjunto de trabalho em um nível. A execução é uma sequência de rodadas até o ponto fixo.
