Sem índice, o banco lê tudo

Imagine procurar um cliente numa lista de um milhão de nomes sem ordem alguma. Você precisa ler todos. Se a lista estiver ordenada, pode ir direto ao meio, descartar metade e repetir. Um índice é exatamente essa organização extra, mantida pelo banco ao lado da tabela.

Sem índice, uma consulta com filtro faz uma varredura completa (full scan). Com índice adequado, faz uma busca que lê umas poucas páginas. A diferença entre as duas é, muitas vezes, a diferença entre milissegundos e minutos.

A B-tree: a estrutura por trás do índice

A maioria dos índices é uma B-tree: uma árvore balanceada em que cada nó guarda várias chaves ordenadas e muitos filhos (o fan-out). Como o fan-out é grande, a árvore é rasa: poucos níveis bastam para milhões de linhas.

Animação · buscando o id 6

Num banco real, cada nó é uma página de disco (4 a 16 KB). Com 300 chaves por página, três níveis cobrem cerca de 27 milhões de chaves: três leituras de página para achar uma linha, em vez de ler milhões. Por isso o custo de busca cresce com o logaritmo do número de linhas.

Quando um índice ajuda, e quando não

Um índice acelera filtros seletivos (que retornam poucas linhas), junções pela chave e ordenações. Não ajuda quando a consulta precisa de quase todas as linhas: nesse caso, a varredura sequencial é mais barata.

Primeiro: veja o plano

EXPLAIN QUERY PLAN mostra como o banco executará a consulta. Os dois termos que importam são SCAN (lê a tabela inteira) e SEARCH … USING INDEX (busca pelo índice). 

EXPLAIN QUERY PLAN
SELECT * FROM pedidos WHERE status = 'pago';

Sem índice em status, o resultado é SCAN pedidos. A próxima seção cria o índice e compara. 

CREATE INDEX idx_pedidos_status ON pedidos(status);
EXPLAIN QUERY PLAN
SELECT * FROM pedidos WHERE status = 'pago';

Agora o plano é SEARCH pedidos USING INDEX idx_pedidos_status (status=?). O ? é o valor procurado, passado como parâmetro. Em aplicações, consultas com parâmetros também reutilizam o plano.

Seletividade. Um índice em status ajuda pouco quando há só quatro valores, porque cada um cobre uma fatia grande da tabela. Em colunas de baixa seletividade (sexo, sim/não), o otimizador frequentemente ignora o índice. Índices em colunas de alta cardinalidade, como e-mail ou CPF, são os mais úteis.

Índices compostos: a ordem importa

Um índice em (a, b) está ordenado por a e, dentro de cada valor de a, por b. Ele serve a consultas que filtram por a, ou por a e b, mas não serve bem a consultas que filtram só por b. É como uma lista telefônica ordenada por sobrenome e depois por nome. 

CREATE INDEX idx_ped_cli_status ON pedidos(id_cliente, status);
EXPLAIN QUERY PLAN
SELECT * FROM pedidos WHERE id_cliente = 1 AND status = 'pago';
-- só status: o índice composto não ajuda, pois id_cliente é o primeiro da ordem
CREATE INDEX idx_ped_cli_status ON pedidos(id_cliente, status);
EXPLAIN QUERY PLAN
SELECT * FROM pedidos WHERE status = 'pago';

A primeira consulta usa o índice composto; a segunda cai em SCAN. Regra prática: coloque primeiro as colunas usadas com igualdade e, em seguida, as de intervalo ou ordenação.

Índice de cobertura

Se o índice contém todas as colunas que a consulta precisa, o banco nem lê a tabela: responde só pelo índice. O plano mostra COVERING INDEX. Um exemplo com a chave primária composta da tabela de itens: 

EXPLAIN QUERY PLAN
SELECT id_pedido, id_produto FROM itens_pedido;

O que anula um índice

O índice está ordenado pelo valor da coluna nua. Qualquer operação sobre a coluna dentro do WHERE esconde essa ordem do otimizador, que então faz varredura. 

CREATE INDEX idx_prod_preco ON produtos(preco);
-- função sobre a coluna: não usa o índice
EXPLAIN QUERY PLAN SELECT nome FROM produtos WHERE preco * 1.1 > 100;
-- condição isolada na coluna: usa
EXPLAIN QUERY PLAN SELECT nome FROM produtos WHERE preco > 100 / 1.1;

Lista de vilões

Função na coluna
WHERE UPPER(nome) = 'ANA'. Reescreva o valor, não a coluna, ou crie um índice sobre a expressão.
Curinga à esquerda
LIKE '%costa' não tem ponto de partida na ordem. Já LIKE 'Ana%' pode usar índice, mas o SQLite só faz isso com collation NOCASE ou a opção case_sensitive_like desligada.
OR com colunas sem índice
WHERE id_categoria = 1 OR preco > 100 exige que ambas sejam indexadas.
Tipos incompatíveis
Comparar texto com número força conversão em cada linha, e o índice não entra.

Ordenação, paginação e o custo do OFFSET

Um índice pode também evitar uma ordenação. Se a consulta filtra por uma coluna e ordena por outra, o índice composto certo entrega as linhas já na ordem pedida. 

CREATE INDEX idx_item_prod ON itens_pedido(id_produto);
EXPLAIN QUERY PLAN
SELECT id_pedido FROM itens_pedido WHERE id_produto = 3 ORDER BY id_pedido;

Aparece USE TEMP B-TREE FOR ORDER BY: o banco ainda precisa ordenar, porque o índice está por id_produto e não por id_pedido. Um índice (id_produto, id_pedido) eliminaria essa etapa.

OFFSET cresce o custo. LIMIT 20 OFFSET 100000 lê e descarta 100 mil linhas antes de devolver 20. Para paginar com desempenho, guarde o último valor visto e use um filtro sobre o índice: WHERE id_pedido > 42 ORDER BY id_pedido LIMIT 20.

Índices não são de graça

  • Escrita mais lenta. Cada INSERT, UPDATE ou DELETE precisa atualizar todos os índices da tabela. Tabela com dez índices sofre dez vezes a manutenção.
  • Espaço. Um índice é uma cópia ordenada (parcial) da coluna, com ponteiros. Em tabelas grandes, pode ocupar tanto quanto os dados.
  • Estatísticas. O otimizador depende de estatísticas atualizadas. O SQLite as mantém com ANALYZE; sem elas, pode escolher um plano ruim.

Por isso a regra é: crie índices para as consultas que existem e são lentas, medidas no plano, e não para cada coluna “que pode ser pesquisada um dia”. Chaves primárias e UNIQUE já criam índices automaticamente; o restante é decisão de projeto.

Como funciona de verdade

  • Otimizador baseado em custo. Para cada plano possível, o banco estima o número de páginas lidas e o número de linhas produzidas, com base em estatísticas, e escolhe o de menor custo. Não existe “a melhor forma” universal: depende dos dados.
  • Plano não é sempre o mesmo. Mudanças de dados ou de estatísticas podem mudar o plano. Consultas que eram rápidas ontem podem ficar lentas depois de um ANALYZE ou de muitas inserções. Por isso, monitore e não confie em memória.
  • Sargable. Um predicado é “sargable” (search-argument-able) quando pode ser usado como ponto de busca no índice. coluna > valor é sargable; função(coluna) > valor geralmente não. Reescrever para sargable é o ajuste mais comum.
  • Leitura de página. Mesmo com índice, a busca precisa buscar a linha na tabela (lookup), a menos que o índice seja de cobertura. Uma busca com muitos lookups aleatórios pode ser mais lenta que uma varredura sequencial, e o otimizador sabe disso.

Exemplo clássico: diagnosticar e corrigir

Uma tela de busca de clientes por cidade está lenta. O procedimento é sempre o mesmo: ver o plano, criar o índice certo, verificar o plano de novo. 

-- 1. o plano antes
EXPLAIN QUERY PLAN
SELECT nome, email FROM clientes WHERE cidade = 'Curitiba';

-- 2. criar o índice e ver o plano depois
CREATE INDEX idx_clientes_cidade ON clientes(cidade);
EXPLAIN QUERY PLAN
SELECT nome, email FROM clientes WHERE cidade = 'Curitiba';

Em um banco de milhões de clientes, a primeira saída seria SCAN e a segunda, SEARCH. Aqui, com sete linhas, o resultado é o mesmo, mas o plano mostra a mudança, e é isso que importa para aprender a ler o diagnóstico.

Experimente

Crie um índice e veja o plano mudar. Depois troque a data do filtro por uma faixa mais estreita e observe se o plano se mantém.

CREATE INDEX idx_pedidos_data ON pedidos(data_pedido); EXPLAIN QUERY PLAN SELECT * FROM pedidos WHERE data_pedido >= '2024-08-01';

Problemas para resolver

Antes de rodar, preveja se haverá SCAN ou SEARCH.

Problema 1 · Índice para a tela de pedidos de um cliente

A tela “meus pedidos” filtra por id_cliente e ordena por data_pedido. Qual índice você criaria? Mostre o plano.

Ver solução 
CREATE INDEX idx_ped_cliente_data ON pedidos(id_cliente, data_pedido);
EXPLAIN QUERY PLAN
SELECT id_pedido, data_pedido, status
FROM pedidos
WHERE id_cliente = 1
ORDER BY data_pedido;

A coluna de igualdade vem primeiro (id_cliente), e a de ordenação depois (data_pedido). Com isso, as linhas do cliente já saem ordenadas, e a consulta não precisa de sort temporário.

Problema 2 · Tornar sargable

A consulta SELECT nome FROM produtos WHERE preco * 1.1 > 100 não usa o índice em preco. Reescreva-a para que use, mantendo o mesmo resultado.

Ver solução 
CREATE INDEX idx_prod_preco ON produtos(preco);
EXPLAIN QUERY PLAN
SELECT nome FROM produtos WHERE preco > 100 / 1.1;
SELECT nome FROM produtos WHERE preco * 1.1 > 100;
SELECT nome FROM produtos WHERE preco > 100 / 1.1;

Passar a operação para o outro lado da desigualdade isola a coluna. A saída mostra SEARCH … USING INDEX. Os dois SELECT finais devolvem os mesmos produtos, então a reescrita é segura nesse caso.

Problema 3 · Quando o índice não adianta

Crie um índice em pedidos(status) e mostre o plano de SELECT * FROM pedidos WHERE status <> 'cancelado'. Ele usa o índice? Por quê?

Ver solução 
CREATE INDEX idx_pedidos_status ON pedidos(status);
EXPLAIN QUERY PLAN
SELECT * FROM pedidos WHERE status <> 'cancelado';

O plano é um SCAN pedidos, sem usar o índice. A condição “diferente de” cobre oito das nove linhas. Ler o índice e depois buscar cada linha custaria mais que varrer a tabela de uma vez. Esse é o critério da seletividade.

Aprofundamento e prática

Índice parcial: indexar só o que importa

Muitas consultas só se interessam por uma fração da tabela. Na loja, a fila de pedidos pendentes é lida o tempo todo, mas a grande maioria dos pedidos já está enviada ou cancelada. Um índice parcial guarda apenas as linhas que satisfazem uma condição, deixando o índice pequeno e rápido de manter. 

CREATE INDEX idx_pendentes ON pedidos(data_pedido) WHERE status = 'pendente';
EXPLAIN QUERY PLAN
SELECT id_pedido FROM pedidos WHERE status = 'pendente' AND data_pedido > '2024-09-01';

O plano usa o índice parcial. Note também a palavra COVERING: como o índice já contém a chave da tabela e a data, a consulta é respondida sem ler a tabela. A condição da consulta precisa implicar a condição do índice (aqui, o status literal), ou o banco não pode usá-lo.

Paginação eficiente com keyset

Em vez de OFFSET, guarde o último identificador visto e peça as linhas seguintes. O índice da chave primária leva direto ao ponto certo, sem descartar linhas antes. É a técnica usada por feeds e listas infinitas. 

-- “próxima página”, sabendo que a última linha vista tinha id 3
SELECT id_pedido, data_pedido
FROM pedidos
WHERE id_pedido > 3
ORDER BY id_pedido
LIMIT 3;
Keyset não permite pular para a página 50. Essa é a troca: ele é rápido e estável, mas sequencial. Para telas com números de página, o OFFSET continua valendo em tabelas pequenas ou médias.

Estatísticas: o otimizador só é tão bom quanto os números que recebe

O otimizador estima quantas linhas cada filtro produz. Essas estimativas vêm de estatísticas, como a quantidade de linhas e a distribuição de valores de um índice. O comando ANALYZE recalcula essas estatísticas, e o SQLite as guarda na tabela sqlite_stat1. Depois de cargas grandes, um ANALYZE é uma das ações mais baratas e eficazes para corrigir um plano ruim. 

ANALYZE;
SELECT tbl, idx, stat FROM sqlite_stat1 ORDER BY tbl, idx;

Roteiro de diagnóstico de uma consulta lenta

  1. Meça antes de mudar: quanto tempo leva, com que dados, em qual ambiente.
  2. Leia o plano (EXPLAIN): procure SCAN em tabelas grandes e ordenações temporárias.
  3. Verifique a sargabilidade dos filtros: há função ou conversão sobre a coluna indexada?
  4. Crie o índice certo (igualdade primeiro, depois faixa e ordenação) e meça de novo.
  5. Revise a consulta: colunas desnecessárias, junções que não precisa, OFFSET grande.
  6. Confirme as estatísticas com ANALYZE e repita o plano. Anote o ganho para justificar o índice no futuro.

Teste seu entendimento

Três perguntas de fundamentos.

1. Num índice composto (a, b), qual consulta tende a usar o índice?

O índice está ordenado primeiro por a. Filtros que começam em a (ou em a e b) conseguem usar essa ordem. Só b não tem ponto de partida.

2. Por que WHERE preco * 1.1 > 100 não usa o índice em preco?

Para usar a ordem do índice, o banco precisa comparar a coluna com um valor. Aplicar uma operação sobre a coluna impede isso. Mova a operação para o outro lado.

3. Qual é o principal custo de criar muitos índices?

Índices aceleram leituras à custa de escritas e espaço. Um SELECT bem indexado não fica mais lento por causa de índices extras.
