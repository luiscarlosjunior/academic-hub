Tópico 9 · Padrões paralelos

Muitos algoritmos paralelos úteis são combinações de um pequeno conjunto de padrões: mapa (aplicar a mesma função a cada elemento, como o kernel do tópico 7), redução (combinar todos os elementos em um só valor), scan (todos os prefixos de uma operação associativa) e histograma (contagem por categoria, com colisões). Reconhecer o padrão é o primeiro passo para escrever um kernel bom.

Redução: somar sem perder a ordem

Somar n elementos sequencialmente leva n − 1 passos. Em paralelo, a redução em árvore faz pares de elementos se somarem: em cada passo, a metade das threads soma seu par à distância s, e s é dividido por dois. Após log₂(n) passos, o resultado está no elemento 0.

Dentro de um bloco, a soma usa a memória compartilhada, e cada passo termina com __syncthreads(). Sem essa barreira, uma thread poderia ler um valor que outra ainda não escreveu: uma condição de corrida. Cada bloco produz uma soma parcial, e a soma final é feita com um segundo passo (no exemplo, na CPU, porque são poucos valores). 

__shared__ float cache[BLOCO];
cache[tid] = (i < n) ? x[i] : 0.0f;
__syncthreads();
for (int s = blockDim.x / 2; s > 0; s >>= 1) {
    if (tid < s)
        cache[tid] += cache[tid + s];
    __syncthreads();
}
if (tid == 0) parcial[blockIdx.x] = cache[0];

Arquivo: 09-reducao-scan.cu

Uma redução em CUDA com atomicAdd em cada thread também funciona, mas serializa as escritas no mesmo endereço e costuma ser mais lenta. A árvore na memória compartilhada evita essa contenção. Este é um bom exemplo de que a forma do algoritmo importa tanto quanto o número de threads.

Scan: todos os prefixos

O scan inclusivo produz saída[i] = x[0] + x[1] + ... + x[i]. Ele é a base de muitos algoritmos: compactação de dados (saber onde cada elemento válido vai parar), ordenação por raiz, cálculo de índices em estruturas esparsas. A versão de Hillis-Steele usado aqui faz log₂(B) passos, em que cada thread soma o valor de quem está deslocamento posições antes dela.

Esta versão é a mais simples e faz mais trabalho do que o necessário (O(n log n) no total, contra O(n) da versão de Blelloch). Para produção, use a biblioteca CUB ou o Thrust, que implementam o scan eficiente. Entender a versão simples ajuda a ler as outras. 

for (int d = 1; d < blockDim.x; d <<= 1) {
    int v = (tid >= d) ? temp[tid - d] : 0;
    __syncthreads();      /* todos leram antes de qualquer escrita */
    temp[tid] += v;
    __syncthreads();
}

Histograma: colisões e operações atômicas

Um histograma conta quantos elementos caem em cada categoria. Em paralelo, duas threads podem querer incrementar o mesmo bin ao mesmo tempo. Sem proteção, uma das contagens se perde. atomicAdd faz a leitura, a soma e a escrita como uma operação indivisível.

O custo é a serialização das colisões: se todos os elementos caem no mesmo bin, o kernel vira quase sequencial. Duas técnicas reduzem isso: histogramas parciais na memória compartilhada (um por bloco, somados no final) e a distribuição dos dados para que as colisões sejam raras. O laço de passo (grid-stride loop) deixa o kernel funcionar com qualquer tamanho de grade. 

__global__ void histograma(const unsigned char *x, unsigned int *bins, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    int passo = blockDim.x * gridDim.x;
    for (; i < n; i += passo)
        atomicAdd(&bins[x[i]], 1u);
}

Quando cada padrão vale a pena: redução e scan são ótimos quando a operação é associativa e o custo por elemento é baixo; o limite passa a ser a largura de banda. O histograma é bom quando as categorias são muitas ou os dados são espalhados. Quando há poucas categorias muito disputadas, a versão com histogramas parciais por bloco tende a ser bem mais rápida.

Teste seus conhecimentos

Por que o __syncthreads() aparece dentro do laço da redução em árvore?

Correto. Sem a barreira, uma thread poderia ler um valor que outra ainda não escreveu, o que é uma condição de corrida.

Muitas threads incrementam o mesmo bin de um histograma. O que acontece sem atomicAdd?

Correto. A condição de corrida é clássica: duas threads leem o mesmo valor e escrevem o mesmo resultado, perdendo um incremento.
