Tópico 10 · Multiplicação de matrizes em CUDA

A multiplicação de matrizes (GEMM) é o kernel mais importante da computação científica e do aprendizado de máquina: quase todo o custo de uma rede neural ou de uma simulação linear passa por ela. Se você entender por que a versão ingênua é lenta e a versão com tiling é rápida, entende o essencial da otimização de GPU.

Versão ingênua: uma thread por elemento de C

Para calcular C = A × B com N × N, cada thread calcula um elemento de C e faz N multiplicações e somas, lendo uma linha de A e uma coluna de B direto da memória global. O problema: cada elemento de A é lido N vezes, por N threads diferentes, e cada elemento de B também. O mesmo dado trafega pela memória muitas vezes. 

__global__ void matmul_ingenua(const float *A, const float *B, float *C, int N) {
    int col = blockIdx.x * blockDim.x + threadIdx.x;
    int row = blockIdx.y * blockDim.y + threadIdx.y;
    if (row < N && col < N) {
        float acc = 0.0f;
        for (int k = 0; k < N; k++)
            acc += A[row * N + k] * B[k * N + col];
        C[row * N + col] = acc;
    }
}

A intensidade aritmética desse kernel é baixa (cerca de 2 flops para cada 8 bytes lidos, sem reuso no cache), então ele fica limitado pela memória, como previsto no roofline do tópico 6.

Tiling: reusar o que já está perto

A ideia é dividir A e B em tiles de TILE × TILE. O bloco de threads carrega um tile de A e um de B para a memória compartilhada, cada thread lê uma posição de cada tile, e então o bloco inteiro calcula o produto parcial com esses dados. Em seguida carrega o próximo par de tiles. Cada elemento da memória global é lido N / TILE vezes, e não N vezes: o reuso aumenta por um fator de TILE.

Dois __syncthreads() por fase têm papéis diferentes: o primeiro garante que o tile está completo antes do uso; o segundo garante que nenhuma thread sobrescreve o tile que outra ainda está lendo. 

for (int t = 0; t < fases; t++) {
    As[threadIdx.y][threadIdx.x] = A[row * N + (t * TILE + threadIdx.x)];
    Bs[threadIdx.y][threadIdx.x] = B[(t * TILE + threadIdx.y) * N + col];
    __syncthreads();                       /* tiles completos */
    for (int k = 0; k < TILE; k++)
        acc += As[threadIdx.y][k] * Bs[k][threadIdx.x];
    __syncthreads();                       /* ninguém sobrescreve ainda */
}

Arquivo: 10-matmul-tiling.cu. Ele verifica as duas versões contra a CPU em N = 256 e mede as duas em N = 4096.

Medindo: o que esperar

O exemplo verifica a correção de ambas as versões antes de medir, o que é a ordem certa: um kernel rápido e errado não serve. A diferença de desempenho entre elas costuma ser grande, na faixa de algumas vezes a dezenas de vezes, dependendo da GPU e do tamanho. Os números não estão neste material porque não há GPU disponível onde ele foi preparado: execute no seu ambiente e compare com o teto de GFLOP/s da sua placa, no estilo do roofline do tópico 6.

Para ir além do tiling, as próximas otimizações são: carregar tiles com acessos vetorizados, usar registradores para acumular mais de um elemento por thread, e tirar proveito de instruções de matriz (Tensor Cores), que a biblioteca cuBLAS já usa. Em código de produção, prefira o cuBLAS, e use o kernel escrito à mão para entender o que ele faz por dentro.

Teste seus conhecimentos

Com TILE = 16, quantas vezes cada elemento de A é lido da memória global no tiling, contra N vezes na versão ingênua, para N = 4096?

Correto. 4096 / 16 = 256 leituras por elemento, contra 4096 na versão ingênua: o reuso cresce com o tamanho do tile.

Por que existe o segundo __syncthreads() dentro do laço de fases do tiling?

Correto. Sem ele, uma thread mais rápida poderia carregar o próximo tile por cima do atual antes que as outras terminassem de usá-lo.
