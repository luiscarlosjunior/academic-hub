Tópico 8 · Hierarquia de memória da GPU

Na GPU, a regra do tópico 2 vale com ainda mais força: o gargalo é quase sempre a memória. Uma GPU moderna pode executar dezenas de teraflops, mas sua memória global entrega uma fração disso em largura de banda. Um kernel que lê a memória de forma desorganizada desperdiça a largura de banda, e o núcleo fica parado esperando dados, mesmo com milhares de threads prontas.

Este tópico mostra os níveis de memória, como o acesso de um warp é agrupado em transações e como usar a memória compartilhada para reorganizar dados.

Os níveis de memória

MemóriaEscopoCaracterística
Registradoresuma threado mais rápido; limitados e divididos entre as threads do multiprocessador
Compartilhada (__shared__)um blocoon-chip, muito rápida; programada pelo usuário; dividida em bancos

Um padrão recorrente nas aulas de GPU é: leia da memória global de forma organizada, trabalhe na memória compartilhada e escreva de forma organizada. Os tópicos 9 e 10 usam esse padrão em redução e multiplicação de matrizes.

Coalescência: o acesso de um warp

Quando as 32 threads de um warp leem a memória global, o hardware tenta juntar esses acessos em poucas transações de tamanho fixo (32, 64 ou 128 bytes). Se as threads leem endereços consecutivos, o warp inteiro cabe em uma ou duas transações. Esse é o caso coalescido. Se os endereços são espalhados, o hardware faz uma transação por endereço, e a largura de banda efetiva cai na mesma proporção.

A consequência prática: o índice threadIdx.x deve variar no endereço que varia mais devagar, ou seja, o último índice de um array 2D em C. Trocar essa relação é a causa mais comum de kernels lentos. 

/* coalescido: thread i lê o elemento i */
out[i] = in[i];

/* passo 32: thread i lê o elemento 32 * i; o warp espalha os acessos */
out[i] = in[(i * 32) % n];

Arquivo: 08-coalescencia.cu. Ele mede a cópia para passos 1, 2, 4, 8 e 32, e a transposição de uma matriz 4096 × 4096.

Transposição: o problema e a solução

Transpor uma matriz é um caso em que não há como ser coalescido nos dois sentidos ao mesmo tempo: se a leitura segue as linhas da entrada, a escrita segue as colunas da saída, e vice-versa. A transposição ingênua escolhe um dos dois e paga no outro.

A solução usa a memória compartilhada como área de reorganização. Cada bloco lê um tile de linhas (coalescido), guarda o tile na memória compartilhada, sincroniza com __syncthreads() e escreve o tile transposto em linhas (coalescido de novo). A leitura por colunas acontece agora na memória compartilhada, que é rápida.

Repare no tile[TILE][TILE + 1], com uma coluna extra. A memória compartilhada é dividida em bancos (32 em GPUs atuais), e acessos de threads diferentes ao mesmo banco são serializados (bank conflict). Quando o tile tem 32 colunas, a leitura por colunas cai toda no mesmo banco. A coluna extra desloca cada linha em um banco e elimina o conflito, com custo mínimo de memória. 

__shared__ float tile[TILE][TILE + 1];     /* +1 evita bank conflicts */
tile[threadIdx.y][threadIdx.x] = in[y * n + x];   /* leitura coalescida */
__syncthreads();                           /* o tile inteiro está pronto */
out[y2 * n + x2] = tile[threadIdx.x][threadIdx.y]; /* escrita coalescida */

O exemplo verifica que a transposta da transposta devolve a matriz original, para as duas versões. Os tempos dependem da GPU e não foram medidos neste material: a diferença entre as versões costuma ser significativa, mas compare você mesmo com nvprof ou com o Nsight, como no tópico 14.

Teste seus conhecimentos

Em um array 2D armazenado por linhas, qual atribuição de índices de thread tende a ser coalescida?

Correto. O último índice do array deve variar com threadIdx.x, para que o warp leia endereços consecutivos.

Por que o tile de memória compartilhada é declarado como [TILE][TILE + 1]?

Correto. Sem a coluna extra, as threads de uma coluna acessam o mesmo banco e os acessos são serializados.
