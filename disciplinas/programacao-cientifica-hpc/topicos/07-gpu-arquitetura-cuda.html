Tópico 7 · GPUs e CUDA

Uma CPU é projetada para executar poucas threads muito rápido, com caches grandes e lógica de controle sofisticada. Uma GPU faz o oposto: tem milhares de unidades de execução simples, pensadas para aplicar a mesma operação a muitos dados ao mesmo tempo. Para simulações científicas, que são em grande parte laços sobre malhas, vetores e matrizes, isso é uma combinação poderosa.

CUDA é a plataforma da NVIDIA para programar essas GPUs. Ela estende C e C++ com um modelo de execução, uma hierarquia de threads e uma API para gerenciar memória e lançar trabalho. Este tópico apresenta o modelo; os tópicos 8 a 12 tratam de memória, padrões e casos reais.

Host e device: dois mundos com memórias separadas

Em CUDA, a CPU é o host e a GPU é o device. Cada um tem sua própria memória. Um ponteiro obtido com malloc aponta para a memória do host; um ponteiro obtido com cudaMalloc aponta para a memória da GPU, e o host não pode desreferenciá-lo diretamente. Por isso o fluxo típico de um programa CUDA é sempre o mesmo:

  1. Alocar memória na GPU com cudaMalloc.
  2. Copiar os dados de entrada do host para a GPU com cudaMemcpy.
  3. Lançar um kernel, a função que roda na GPU.
  4. Copiar o resultado de volta e liberar a memória.

Cópias entre host e device atravessam o barramento PCIe (ou NVLink, em servidores), que é muito mais lento que a memória da GPU. Um erro comum de iniciantes é copiar dados a cada operação pequena: o custo da cópia passa a dominar o ganho da GPU.

Kernel, grade, bloco e thread

Um kernel é declarado com __global__ e lançado com a sintaxe <<<blocos, threads>>>. Esse lançamento cria uma grade de blocos, e cada bloco tem várias threads. Todas executam o mesmo código; cada uma descobre sua posição com as variáveis threadIdx (posição dentro do bloco), blockIdx (posição do bloco na grade) e blockDim (tamanho do bloco).

O índice global de cada thread, que é o que se usa para escolher o elemento a processar, é:

i = blockIdx.x × blockDim.x + threadIdx.x

Como o número de threads costuma não ser múltiplo exato do tamanho do vetor, o último bloco tem threads além do fim. A guarda if (i < n) é obrigatória. 

__global__ void soma_vetores(const float *a, const float *b, float *c, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n)
        c[i] = a[i] + b[i];
}

int blocos = (n + threads - 1) / threads;          /* arredonda para cima */
soma_vetores<<<blocos, threads>>>(da, db, dc, n);

Warps: a unidade real de execução

O hardware não executa threads uma a uma. Threads de um bloco são agrupadas em warps de 32, que executam a mesma instrução em lockstep (modelo SIMT, single instruction, multiple threads). Por isso, dentro de um warp, um if com caminhos diferentes para threads diferentes faz as duas partes serem executadas em sequência: é a divergência de warp, tratada no tópico 11.

Por isso, o tamanho do bloco é um múltiplo de 32 (128, 256 ou 512 são escolhas comuns). Um bloco de 100 threads ocuparia quatro warps, com 28 threads inativas no último.

Exemplo completo: soma de vetores com medição

O programa a seguir soma dois vetores de 16 milhões de floats, mede o tempo do kernel com eventos CUDA, calcula a largura de banda efetiva e verifica o resultado contra a CPU. Observe a checagem de erro em cada chamada da API e depois do lançamento do kernel.

Arquivo: 07-vetor-add.cu

// Macro de checagem: sem isso, um erro passa em silêncio
#define CHECK(chamada)                                  \
    do {                                                \
        cudaError_t e_ = (chamada);                     \
        if (e_ != cudaSuccess) {                        \
            fprintf(stderr, "erro CUDA %s em %s:%d\n",  \
                    cudaGetErrorString(e_), __FILE__, __LINE__); \
            exit(EXIT_FAILURE);                         \
        }                                               \
    } while (0)

CHECK(cudaMalloc(&da, bytes));
CHECK(cudaMemcpy(da, ha, bytes, cudaMemcpyHostToDevice));
soma_vetores<<<blocos, threads>>>(da, db, dc, n);
CHECK(cudaGetLastError());          /* erro de configuração do lançamento */
CHECK(cudaMemcpy(hc, dc, bytes, cudaMemcpyDeviceToHost));

Dois detalhes importantes. cudaGetLastError() captura erros do lançamento (por exemplo, um número de threads inválido), que não são retornados pelo próprio lançamento. E a medição com cudaEvent mede o tempo na GPU, sem contar o tempo de cópia; por isso é preciso separar as duas medidas ao analisar o desempenho.

Nota sobre a execução: este material foi preparado em um Mac sem GPU NVIDIA e sem nvcc, e não foi executado em GPU. O código foi verificado apenas com checagem de sintaxe e tipos por um cabeçalho de substituição. Execute em uma máquina com CUDA para obter os tempos.

Teste seus conhecimentos

Um vetor tem 1000 elementos e o bloco tem 256 threads. Quantos blocos são necessários?

Correto. (1000 + 255) / 256 = 4 blocos, com 1024 threads ao todo. As 24 threads excedentes são barradas pela guarda i < n.

Por que um ponteiro de cudaMalloc não pode ser lido diretamente na CPU?

Correto. Os dois espaços de memória são separados; a cópia com cudaMemcpy é o caminho entre eles.
