Tópico 4 · Memória compartilhada com OpenMP

Em um servidor com dezenas de núcleos, todos enxergam a mesma memória. A forma mais direta de paralelizar um laço nesse cenário é com OpenMP: você escreve o código serial e acrescenta diretivas (#pragma omp) que dizem ao compilador como dividir o trabalho entre threads. O programa continua o mesmo; o que muda é quem executa cada parte.

O ganho é fácil de obter e fácil de perder. Quase todo o trabalho deste tópico está em evitar as três armadilhas clássicas: condição de corrida, false sharing e desbalanceamento de carga.

Modelo fork-join

O programa começa com uma thread. Ao entrar em uma região parallel, ela se divide em um time de threads (fork). Ao sair da região, as threads esperam umas pelas outras e apenas a thread principal continua (join). Cada thread roda o mesmo código, mas pode descobrir quem é com omp_get_thread_num(). 

#include <omp.h>
#pragma omp parallel num_threads(4)
{
    int id = omp_get_thread_num();   /* 0, 1, 2 ou 3 */
    printf("olá da thread %d\n", id);
}   /* join: só a thread principal segue daqui */

Compile com -fopenmp. Sem essa opção, as diretivas são ignoradas e o programa roda serial, o que é útil para testar a lógica antes.

Redução: somar sem corromper

Somar um vetor em paralelo é o exemplo típico de condição de corrida: várias threads leem e escrevem a mesma variável soma ao mesmo tempo, e algumas atualizações se perdem. A cláusula reduction(+:soma) resolve isso: cada thread recebe uma cópia privada de soma, zerada, e ao final o OpenMP combina as cópias. 

double soma = 0.0;
#pragma omp parallel for reduction(+:soma) schedule(static)
for (long i = 0; i < N; i++)
    soma += x[i];

Sem a cláusula, o resultado muda de execução para execução. Veja no exemplo: incrementar um contador compartilhado sem proteção produz um número menor que o esperado, e a versão com #pragma omp atomic produz o correto. atomic é mais simples, mas serializa as atualizações, então é mais lenta. Para somas, prefira reduction.

False sharing: o custo invisível

Cada thread escreve no próprio contador, então por que haveria disputa? Porque a coerência de cache trabalha com linhas de 64 bytes. Se oito contadores de 8 bytes estão juntos em um vetor, uma única linha de cache contém todos. Cada escrita de uma thread invalida a cópia que as outras têm, e a linha vai e volta entre núcleos. O programa fica lento sem que nenhum dado seja compartilhado de fato.

A correção é separar os dados por linha de cache, por exemplo com um preenchimento até 64 bytes (como no exemplo). Essa é a mesma ideia de layout do tópico 3, agora aplicada entre núcleos. 

typedef struct {
    long valor;
    char preenchimento[64 - sizeof(long)];   /* um contador por linha de cache */
} ContadorAlinhado;

Escalonamento: quem faz qual iteração

  • static: as iterações são divididas em blocos iguais, de antemão. Ótimo quando todas custam o mesmo, com custo de agendamento nulo.
  • dynamic, c: blocos de c iterações são entregues às threads que ficam livres. Boa escolha quando o custo varia muito.
  • guided: começa com blocos grandes e diminui. Um meio-termo entre os dois.

Regra prática: comece com static. Mude para dynamic apenas se o perfilamento mostrar que as threads terminam em tempos muito diferentes.

O que este exemplo não mostrou (e por quê)

O código de 04-openmp.c não foi executado com OpenMP real neste material: o compilador disponível no ambiente de preparação (Apple clang) não traz a biblioteca. O arquivo foi verificado com cabeçalhos de substituição que executam em uma única thread, o que confirma sintaxe e lógica serial, mas não os ganhos de desempenho nem a ausência de corridas em paralelo. Para ver os números, compile com gcc -O2 -fopenmp em um Linux ou com clang e libomp instalada, e meça.

Teste seus conhecimentos

Por que a soma paralela de um vetor deve usar reduction(+:soma) em vez de um soma += x[i] simples dentro de parallel for?

Correto. Sem redução, a leitura e a escrita de soma por threads diferentes se misturam e o resultado varia.

Dois contadores de threads diferentes ficam na mesma linha de cache. O que acontece e como se corrige?

Correto. A coerência de cache trabalha por linha, então escritas independentes ainda disputam a mesma linha.
