Tópico 11 · Ocupação, divergência e streams

Os tópicos anteriores mostraram como escrever kernels corretos e com bom acesso à memória. Este tópico trata de três fatores que decidem se a GPU de fato fica ocupada: quantas threads estão prontas para executar (ocupação), se as threads de um warp seguem o mesmo caminho (divergência) e se as cópias de dados se sobrepõem à computação (streams).

Ocupação: por que muitas threads ajudam

Quando um warp espera por uma leitura da memória (centenas de ciclos), o multiprocessador troca para outro warp pronto, sem custo. Esse é o mecanismo de esconder latência da GPU: ela depende de ter warps suficientes para trocar. A ocupação é a razão entre os warps ativos e o máximo que o multiprocessador suporta.

A ocupação é limitada pelo que cada bloco usa: registradores por thread, memória compartilhada por bloco e o número de threads por bloco. Um kernel que usa muitos registradores ocupa menos warps, e um que usa muita memória compartilhada pode impedir que dois blocos caibam no mesmo multiprocessador.

Um equívoco comum é achar que ocupação 100% é sempre o objetivo. Um kernel de tiling com alta reutilização pode ir bem com ocupação moderada, desde que o trabalho por thread seja grande. Meça o tempo, não só a ocupação.

Divergência: quando um warp se separa

Como um warp executa uma instrução por vez para todas as suas threads (SIMT), um if cujo resultado difere entre as threads faz o warp executar os dois caminhos em sequência. Threads que não tomam um caminho ficam mascaradas (inativas) durante ele. Se o caminho cai em cada thread de forma alternada, o custo pode ser quase o dobro. 

/* divergente: threads pares e ímpares tomam caminhos diferentes no mesmo warp */
if (threadIdx.x % 2 == 0) a = f(x); else a = g(x);

/* sem divergência: a condição é a mesma para todas as threads do warp */
if (blockIdx.x % 2 == 0) a = f(x); else a = g(x);

A correção quase sempre é reorganizar o trabalho: fazer a condição depender do bloco (ou do warp, pois o warp é de 32 threads consecutivas), ou separar os elementos de cada caminho em grupos antes do kernel. Divergência não é um erro, mas em laços pesados é um custo que merece ser medido.

Streams: cópia e computação em paralelo

Por padrão, todas as operações na GPU entram em um mesmo stream (fila de execução) e rodam em ordem. Um stream adicional permite que operações independentes se sobreponham: enquanto uma fatia de dados é copiada para a GPU, outra fatia já está sendo processada, e uma terceira volta para o host. Para isso acontecer, dois requisitos precisam ser atendidos:

  • Memória pinned (fixa): alocada com cudaMallocHost. Cópias assíncronas (cudaMemcpyAsync) só são realmente assíncronas com ela; com memória paginável, a cópia passa por um buffer intermediário e bloqueia.
  • Trabalho dividido em fatias independentes: cada fatia usa seu stream e não depende das outras.

O ganho máximo é limitado pela operação mais lenta: se a cópia é 10 vezes mais demorada que o kernel, sobrepor não reduz o tempo abaixo do tempo da cópia. 

cudaStream_t fluxo[2];
cudaStreamCreate(&fluxo[0]); cudaStreamCreate(&fluxo[1]);
for (int f = 0; f < fatias; f++) {
    cudaStream_t s = fluxo[f % 2];
    size_t off = (size_t)f * m;
    cudaMemcpyAsync(din + off, hin + off, bf, cudaMemcpyHostToDevice, s);
    transforma<<<(m + 255) / 256, 256, 0, s>>>(din + off, dout + off, m);
    cudaMemcpyAsync(hout_str + off, dout + off, bf, cudaMemcpyDeviceToHost, s);
}

Como saber se a sobreposição funcionou

Um tempo total menor não basta: é preciso ver as operações no tempo. Ferramentas como o Nsight Systems mostram a linha do tempo de cada stream, com as cópias e os kernels. Se as barras das cópias de uma fatia e do kernel de outra estão lado a lado, a sobreposição está acontecendo. Se estão em sequência, algo impede o paralelismo, quase sempre memória paginável ou uma sincronização implícita no meio do laço.

Nota sobre a execução: o exemplo não foi executado em GPU neste material. Os tempos e a diferença entre as versões dependem da placa e da interconexão, e devem ser medidos no seu ambiente.

Teste seus conhecimentos

Por que cudaMemcpyAsync com memória paginável não se sobrepõe de verdade à computação?

Correto. Com memória paginável, a cópia assíncrona não tem o caminho direto que a memória pinned oferece, e o resultado é um bloqueio.

Dentro de um warp, a condição de um if é verdadeira para metade das threads e falsa para a outra metade. O que acontece?

Correto. Esse é o custo da divergência: o warp executa os dois caminhos, e cada thread só participa do seu.
