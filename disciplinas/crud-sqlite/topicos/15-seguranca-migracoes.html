Injeção de SQL

A injeção acontece quando dados de fora do programa são tratados como parte do comando SQL. É uma das falhas de segurança mais antigas e ainda comuns. O exemplo mostra o efeito: a consulta montada por concatenação devolve todos os títulos, porque ' OR '1'='1 torna a condição sempre verdadeira. A consulta com parâmetro trata a mesma string como texto literal, e não encontra nada.

A defesa é uma regra só: parâmetros para todos os valores, sempre. Para nomes de tabela ou coluna, que não podem ser parâmetros, use uma lista permitida no código.

Migrações versionadas

O esquema muda com o tempo. Em vez de cada desenvolvedor alterar o banco à mão, cada mudança é um passo numerado, e o banco guarda até qual passo já foi aplicado. O SQLite oferece essa guarda no próprio arquivo: a pragma user_version, um inteiro livre que o programa lê e escreve.

MIGRACOES = [
    (1, "CREATE TABLE livro (id INTEGER PRIMARY KEY, titulo TEXT NOT NULL)"),
    (2, "ALTER TABLE livro ADD COLUMN ano INTEGER"),
]
versao = con.execute("PRAGMA user_version").fetchone()[0]
for numero, sql in MIGRACOES:
    if numero > versao:
        with con:
            con.execute(sql)
            con.execute(f"PRAGMA user_version = {numero}")

Cada migração roda uma única vez, e rodar o programa de novo não faz nada. Uma migração que precisa mudar uma coluna existente segue o procedimento do tópico 3: criar a tabela nova, copiar, remover a antiga e renomear. Migrações devem ser testadas em uma cópia do banco de produção antes de rodar no original.

Modo WAL

Por padrão, o SQLite usa um diário de desfazer. No modo WAL (Write-Ahead Logging), as escritas vão para um arquivo de log separado, e leitores não bloqueiam o escritor. Em aplicações com muitas leituras e algumas escritas, a diferença é grande. O modo é persistente: uma vez ligado no arquivo, continua ligado. O exemplo mostra PRAGMA journal_mode = WAL devolvendo wal.

Backup consistente

Copiar o arquivo .db com o programa em uso pode gerar uma cópia inconsistente, sobretudo no modo WAL, porque parte das alterações está no log. O comando VACUUM INTO 'arquivo.bak' gera uma cópia íntegra e compactada, mesmo com o banco aberto. O exemplo confere a cópia com PRAGMA integrity_check, que deve devolver ok.

Exemplo executável: migrações, WAL, backup e injeção

O script aplica as migrações duas vezes (na segunda, nada muda), ativa o WAL, gera e verifica um backup, e compara a consulta vulnerável com a parametrizada usando a mesma entrada maliciosa.

import sqlite3, os, tempfile

# Migrações versionadas com PRAGMA user_version: cada passo roda uma única vez.
MIGRACOES = [
    (1, "CREATE TABLE livro (id INTEGER PRIMARY KEY, titulo TEXT NOT NULL)"),
    (2, "ALTER TABLE livro ADD COLUMN ano INTEGER"),
    (3, "CREATE INDEX idx_livro_titulo ON livro (titulo)"),
]

def migrar(con):
    versao = con.execute("PRAGMA user_version").fetchone()[0]
    for numero, sql in MIGRACOES:
        if numero > versao:
            with con:
                con.execute(sql)
                con.execute(f"PRAGMA user_version = {numero}")   # número vem do código, não do usuário
            print(f"  aplicada migração {numero}")
    return con.execute("PRAGMA user_version").fetchone()[0]

caminho = os.path.join(tempfile.mkdtemp(), "biblioteca.db")
con = sqlite3.connect(caminho)
# WAL: escritas vão para um arquivo de log separado, leitores não bloqueiam o escritor
print("modo de journal:", con.execute("PRAGMA journal_mode = WAL").fetchone()[0])
print("primeira execução:")
print("  versão final:", migrar(con))
con.close()

con = sqlite3.connect(caminho)
print("segunda execução (nada a fazer):")
print("  versão final:", migrar(con))

# Backup consistente com o banco em uso: VACUUM INTO gera uma cópia íntegra
destino = caminho + ".bak"
con.execute(f"VACUUM INTO '{destino}'")
copia = sqlite3.connect(destino)
print("backup íntegro:", copia.execute("PRAGMA integrity_check").fetchone()[0], "| versão:", copia.execute("PRAGMA user_version").fetchone()[0])

# Injeção de SQL: a versão vulnerável x a segura
con.execute("INSERT INTO livro (titulo) VALUES ('Dom Casmurro'), ('Vidas Secas')")
entrada = "' OR '1'='1"
vulneravel = f"SELECT titulo FROM livro WHERE titulo = '{entrada}'"
print("\nconsulta vulnerável devolve:", con.execute(vulneravel).fetchall())
print("consulta parametrizada devolve:", con.execute("SELECT titulo FROM livro WHERE titulo = ?", (entrada,)).fetchall())

Erros comuns

  • Migração que muda o código antes do banco: a aplicação nova roda contra um esquema antigo e falha. Migre primeiro, depois publique o código.
  • Backup nunca testado: um backup que não foi restaurado é uma hipótese. Restaure periodicamente em outro lugar.
  • Permissão do arquivo: no SQLite, quem consegue ler o arquivo lê todos os dados. Proteja o arquivo com permissões do sistema operacional.

Exercícios

1. Adicione a migração 4 que cria a tabela cliente com id e nome, e confirme que ela é aplicada uma única vez.

Gabarito: acrescente (4, "CREATE TABLE cliente (id INTEGER PRIMARY KEY, nome TEXT NOT NULL)") à lista. A primeira execução aplica a 4; a segunda confirma versão 4 e nada faz.

2. Um colega sugere “escapar” a entrada removendo apóstrofos em vez de usar parâmetros. Qual o problema?

Gabarito: a lista de caracteres perigosos sempre fica incompleta, e cada banco tem sintaxe própria de escape. Parâmetros separam o valor do comando por construção, sem depender de lista. É uma correção por design, não por remendo.
