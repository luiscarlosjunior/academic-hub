VIEW: uma consulta com nome

CREATE VIEW vw_emprestimos_abertos AS
SELECT e.id, l.titulo, c.nome AS cliente, e.data_saida
FROM emprestimo e
JOIN livro l   ON l.id = e.livro_id
JOIN cliente c ON c.id = e.cliente_id
WHERE e.devolvido = 0;

SELECT * FROM vw_emprestimos_abertos;

Uma VIEW não guarda dados: é a consulta armazenada, executada a cada uso. Ela serve para esconder joins complicados, expor só as colunas certas e dar um nome estável para uma regra de leitura, como “empréstimos em aberto”. Uma VIEW no SQLite é somente leitura.

TRIGGER: código que roda sozinho

CREATE TRIGGER trg_log_emprestimo AFTER INSERT ON emprestimo
BEGIN
  INSERT INTO log_emprestimo VALUES (NEW.id, 'registrado');
END;

Um trigger dispara automaticamente antes (BEFORE) ou depois (AFTER) de INSERT, UPDATE ou DELETE. Dentro dele, NEW é a linha nova e OLD é a linha antiga. Triggers são úteis para auditoria e para regras que precisam valer independentemente de quem grava.

Triggers que impedem: RAISE

Um trigger BEFORE pode recusar a operação com RAISE(ABORT, 'mensagem'). No exemplo, uma devolução repetida é bloqueada no próprio banco, e a aplicação recebe um erro de integridade com a mensagem definida.

Quando views e triggers ajudam e quando atrapalham

  • Ajudam: auditoria consistente, regras que não podem ser contornadas, leituras padronizadas.
  • Atrapalham: lógica escondida. Um INSERT que parece simples pode gerar cascatas de triggers difíceis de depurar, e o código da aplicação não mostra nada disso.
  • Limite do SQLite: não há procedimentos armazenados. Regras complexas ficam na aplicação, e o banco só guarda as regras simples como triggers.

Exemplo executável: view, log automático e bloqueio

O script cria a view e mostra só os empréstimos abertos, cria um trigger que registra cada novo empréstimo, e outro que recusa uma segunda devolução.

Este programa roda de ponta a ponta. A saída abaixo é a execução real, feita com Python 3.13 e SQLite 3.45.

import sqlite3

con = sqlite3.connect(":memory:")
con.executescript(open("biblioteca_schema.sql", encoding="utf-8").read())
con.execute("INSERT INTO cliente (id, nome, email) VALUES (1, 'Ana', 'ana@x.com')")
con.executemany("INSERT INTO livro (id, titulo, ano) VALUES (?,?,?)", [(1, "Dom Casmurro", 1899), (2, "Vidas Secas", 1938)])

# VIEW: uma consulta salva, tratada como tabela só de leitura
con.execute("""CREATE VIEW vw_emprestimos_abertos AS
               SELECT e.id, l.titulo, c.nome AS cliente, e.data_saida
               FROM emprestimo e
               JOIN livro l   ON l.id = e.livro_id
               JOIN cliente c ON c.id = e.cliente_id
               WHERE e.devolvido = 0""")
con.execute("INSERT INTO emprestimo (livro_id, cliente_id, data_saida) VALUES (1, 1, '2026-10-01')")
con.execute("INSERT INTO emprestimo (livro_id, cliente_id, data_saida, devolvido) VALUES (2, 1, '2026-09-01', 1)")
print("VIEW mostra só os abertos:", con.execute("SELECT titulo, cliente FROM vw_emprestimos_abertos").fetchall())

# TRIGGER: regra que roda sozinha depois de uma inserção
con.execute("CREATE TABLE log_emprestimo (emprestimo_id INTEGER, mensagem TEXT)")
con.execute("""CREATE TRIGGER trg_log_emprestimo AFTER INSERT ON emprestimo
               BEGIN
                 INSERT INTO log_emprestimo VALUES (NEW.id, 'empréstimo registrado para livro ' || NEW.livro_id);
               END""")
con.execute("INSERT INTO emprestimo (livro_id, cliente_id, data_saida) VALUES (2, 1, '2026-10-03')")
print("log gerado pelo trigger:", con.execute("SELECT * FROM log_emprestimo").fetchall())

# TRIGGER de validação: impede devolver um livro duas vezes
con.execute("""CREATE TRIGGER trg_nao_devolver_duas_vezes BEFORE UPDATE OF devolvido ON emprestimo
               WHEN OLD.devolvido = 1 AND NEW.devolvido = 1
               BEGIN SELECT RAISE(ABORT, 'empréstimo já devolvido'); END""")
try:
    con.execute("UPDATE emprestimo SET devolvido = 1 WHERE id = 2")
except sqlite3.IntegrityError as e:
    print("segunda devolução:", "RECUSADA -", e)

Erros comuns

  • Esquecer a condição da view ao usar: a view é uma consulta, e ela precisa de filtros explícitos se a aplicação não os fornecer.
  • Trigger que chama a si mesmo: um trigger de UPDATE que atualiza a mesma tabela pode entrar em laço. O SQLite limita a recursão, mas o erro deve ser evitado no desenho.
  • Trigger de auditoria sem o usuário: o SQLite não sabe quem fez a alteração. Se precisar, a aplicação deve passar essa informação.

Exercícios

1. Crie uma view com os livros e o número de empréstimos de cada um.

Gabarito: CREATE VIEW vw_popularidade AS SELECT l.id, l.titulo, COUNT(e.id) AS emprestimos FROM livro l LEFT JOIN emprestimo e ON e.livro_id = l.id GROUP BY l.id. O LEFT JOIN garante que livros sem empréstimo aparecem com zero.

2. Escreva um trigger que impede emprestar um livro com ano maior que o ano atual.

Gabarito: um BEFORE INSERT ON emprestimo que consulta o livro e aborta com RAISE(ABORT, ...) se o ano for maior que o atual. A regra fica no banco, então nenhum caminho de gravação a contorna.
